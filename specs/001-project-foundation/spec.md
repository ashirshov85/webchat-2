# Feature Specification: Каркас проекта, CI/CD и базовая инфраструктура

**Feature Branch**: `001-project-foundation`

**Created**: 2026-09-06

**Status**: Approved

**Input**: User description: "Создать каркас проекта веб-чата: монорепозиторий с backend-сервисом (Kotlin 2.x + Spring Boot 3.x) и frontend-приложением (React + TypeScript, strict), Docker-образы и базовые манифесты Kubernetes, CI/CD-пайплайн (сборка, линт, тесты, деплой) с первой фичи. Настроить пайплайн публичного OpenAPI-контракта с генерацией TypeScript-типов для фронтенда и базовую observability (структурированные логи, распределённый трейсинг, метрики latency/throughput/errors). Все сервисы stateless. Бизнес-функций в этой фиче нет."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Единый каркас монорепозитория (Priority: P1)

Разработчик клонирует репозиторий и одной командой для backend и для frontend запускает сборку, линт и тесты. Оба приложения стартуют локально и сообщают о готовности (health-check). Скелет backend-сервиса и frontend-приложения содержит минимальный smoke-тест и настроенные линт/форматирование, чтобы конвейер качества был проверяем с первого дня.

**Why this priority**: Без собирающегося и тестируемого скелета невозможна ни одна последующая фича; это фундамент всего проекта (фаза 0 дорожной карты).

**Independent Test**: Полностью проверяется клонированием репозитория на чистой машине: команды сборки/линта/тестов для backend и frontend завершаются успешно, оба приложения запускаются и отвечают на health-check.

**Acceptance Scenarios**:

1. **Given** свежий клон репозитория на машине с предустановленным тулчейном, **When** разработчик запускает сборку backend и frontend, **Then** обе сборки завершаются успешно без ручного редактирования файлов.
2. **Given** собранные приложения, **When** разработчик запускает их локально, **Then** каждое приложение сообщает о готовности через health-check в течение 60 секунд.
3. **Given** код с нарушением правил линтера, **When** запускается линт, **Then** проверка завершается ошибкой с указанием файла и строки.
4. **Given** скелеты приложений, **When** запускаются тесты, **Then** smoke-тесты проходят, и тестовый раннер интегрирован в общий сценарий запуска.

### User Story 2 - Конвейер качества для каждого изменения (Priority: P1)

Каждое изменение (pull request) автоматически проходит конвейер: сборка, линт, unit-тесты backend и frontend. Если любая стадия падает — слияние (merge) в основную ветку заблокировано, а автор изменения видит причину отказа.

**Why this priority**: Конституция требует CI/CD с первой фичи; защита качества должна существовать до появления любой бизнес-логики.

**Independent Test**: Открывается PR с заведомо падающим тестом — пайплайн становится красным, merge заблокирован; PR с зелёными проверками — merge разрешён.

**Acceptance Scenarios**:

1. **Given** открытый pull request, **When** автоматический конвейер (сборка, линт, тесты) завершается с ошибкой, **Then** слияние в основную ветку заблокировано, а причина указана в результатах проверки.
2. **Given** открытый pull request, **When** все проверки конвейера зелёные, **Then** слияние разрешено без ручных дополнительных действий.
3. **Given** несколько открытых pull request, **When** каждый из них изменяет код, **Then** конвейер запускается независимо для каждого.

---

### User Story 3 - Автоматический деплой в dev-окружение (Priority: P2)

После слияния в основную ветку система автоматически собирает контейнерные образы backend и frontend, публикует их в registry и разворачивает в dev-окружении Kubernetes по декларативным манифестам (deployments, services, ingress) с health-пробами. Развернутые сервисы stateless: перезапуск экземпляра не требует ручных действий и не ломает обслуживание.

**Why this priority**: Автоматический путь «коммит → dev-окружение» обязателен с первой фичи по конституции; при этом конвейер качества (US2) ценен и без деплоя, поэтому деплой — P2.

**Independent Test**: Слияние зелёного изменения в основную ветку — через несколько минут новая версия обоих приложений доступна в dev-окружении по своему адресу; перезапуск подов не требует ручного вмешательства.

**Acceptance Scenarios**:

1. **Given** изменение слито в основную ветку, **When** пайплайн завершён, **Then** новые контейнерные образы собраны, опубликованы и развёрнуты в dev-окружении без ручных действий.
2. **Given** развёрнутые сервисы, **When** Kubernetes-манифесты применяются к кластеру, **Then** создаются deployments, services и ingress с настроенными health-пробами.
3. **Given** работающий экземпляр сервиса, **When** он перезапускается (падение/обновление), **Then** обслуживание автоматически восстанавливается без ручных действий и без потери конфигурации.
4. **Given** новая версия не проходит health-пробы после деплоя, **When** система это обнаруживает, **Then** новая версия не считается успешной и предыдущее состояние остаётся доступным/восстановимым.

### User Story 4 - Пайплайн публичного OpenAPI-контракта (Priority: P2)

Публичный API-контракт хранится в репозитории и является источником истины. TypeScript-типы фронтенда генерируются из контракта автоматически. Изменение контракта в pull request видно ревьюерам; если типы не перегенерированы — конвейер падает. Обратно несовместимые (breaking) изменения контракта обнаруживаются и требуют явного решения (версионирование) до слияния.

**Why this priority**: API-First — принцип конституции; каркас контракта нужен к моменту появления первого публичного endpoint, но сам по себе не блокирует US1–US3.

**Independent Test**: В PR изменяется контракт — конвейер регенерирует типы и/или детектирует расхождение; забытая регенерация фейлит проверку.

**Acceptance Scenarios**:

1. **Given** контракт в репозитории, **When** изменяется его содержимое в pull request, **Then** сгенерированные TypeScript-типы пересоздаются автоматически, и diff типов виден в ревью.
2. **Given** контракт изменён, а сгенерированные типы не обновлены, **When** выполняется проверка, **Then** конвейер завершается ошибкой (детекция расхождения).
3. **Given** pull request вводит обратно несовместимое изменение контракта, **When** выполняется проверка совместимости, **Then** изменение явно помечено как breaking и требует явного решения (версионирование) до слияния.
4. **Given** контракт не менялся, **When** типы генерируются повторно, **Then** результат детерминирован (нет ложных расхождений).

### User Story 5 - Observability-базлайн (Priority: P3)

Дежурный инженер для каждого сервиса видит: структурированные логи (каждая запись содержит идентификатор трейса), распределённые трейсы, проходящие через frontend и backend, и метрики latency/throughput/errors. Ошибка обработки запроса наблюдаема во всех трёх сигналах.

**Why this priority**: Observability обязательна по конституции, но это надстройка над каркасом: каркас должен сначала существовать и деплоиться.

**Independent Test**: Выполняется тестовый запрос через frontend в backend — во всех логах обоих сервисов виден один и тот же trace id, запрос виден в трейсе, метрики latency/throughput/errors обновляются.

**Acceptance Scenarios**:

1. **Given** запрос проходит из frontend в backend, **When** запрос обработан, **Then** записи логов всех затронутых сервисов содержат один и тот же идентификатор трейса.
2. **Given** сервис обрабатывает запросы, **When** инженер запрашивает метрики сервиса, **Then** доступны latency, throughput и error rate.
3. **Given** при обработке запроса произошла ошибка, **When** инженер исследует инцидент, **Then** ошибка видна в структурированных логах, в трейсе и в метриках ошибок.
4. **Given** записи логов сервисов, **When** они просматриваются, **Then** 100% записей имеют машиночитаемую структурированную форму.

---

### Edge Cases

- Что происходит, когда любая стадия конвейера (сборка, линт, тесты, сборка образа) падает? — Слияние блокируется; причина однозначно указана в результатах проверки.
- Что происходит, когда registry или dev-кластер недоступны на стадии деплоя? — Пайплайн завершается ошибкой, частично развёрнутое состояние не считается успешным деплоем, повторный запуск безопасен.
- Что происходит, когда деплой прошёл, но новая версия не отвечает на health-пробы? — Новая версия не получает статус успешной; откат/сохранение работоспособности восстанавливаемо.
- Что происходит, когда OpenAPI-контракт изменён, а сгенерированные типы — нет? — Конвейер падает (drift-детекция), слияние заблокировано.
- Что происходит при одновременном слиянии нескольких изменений в основную ветку? — Каждый деплой идентифицируется своей версией образа; итоговое состояние кластера соответствует последнему успешному деплою.
- Что происходит при перезапуске экземпляра под нагрузкой? — Обслуживание восстанавливается автоматически (stateless, health-пробы, рестарт пода), без ручных действий.
- Что происходит, когда секрет (credential) случайно добавлен в код? — Проверка не пропускает его в репозиторий/образы; секреты передаются только через защищённое хранилище/переменные окружения.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система репозитория MUST предоставлять единый монорепозиторий, содержащий исходники backend-сервиса и frontend-приложения, каждый из которых собирается, линтится и тестируется одной командой.
- **FR-002**: Backend-скелет MUST предоставлять health-check (готовность/живость) и точку экспорта метрик; frontend-скелет MUST собираться в артефакт, пригодный для раздачи пользователю.
- **FR-003**: CI-конвейер MUST запускаться на каждое изменение (pull request) и включать стадии: сборка, линт, unit-тесты для backend и frontend; падение любой стадии MUST блокировать слияние.
- **FR-004**: CI-конвейер MUST собирать контейнерный образ для каждого приложения; каждый образ MUST идентифицироваться версией (тегом), однозначно связанной с изменением (коммитом).
- **FR-005**: После слияния в основную ветку система MUST автоматически разворачивать новые версии в dev-окружении без ручных действий.
- **FR-006**: Разворачиваемые сервисы MUST декларироваться манифестами оркестрации, включающими deployments, services, ingress и health-пробы.
- **FR-007**: Все сервисы MUST быть stateless: состояние между запросами в памяти процесса не хранится; перезапуск любого экземпляра MUST восстанавливать обслуживание автоматически.
- **FR-008**: Публичный API-контракт MUST храниться в репозитории как единственный источник истины публичного API.
- **FR-009**: TypeScript-типы фронтенда MUST генерироваться из публичного контракта автоматически; расхождение между контрактом и типами MUST приводить к ошибке конвейера.
- **FR-010**: Конвейер MUST обнаруживать обратно несовместимые изменения публичного контракта и MUST требовать явного решения (версионирование) до слияния.
- **FR-011**: Все сервисы MUST вести логи в структурированном машиночитаемом виде; каждая запись лога, относящаяся к обработке запроса, MUST содержать идентификатор трейса.
- **FR-012**: Система MUST распространять контекст трейсинга сквозь вызовы от frontend к backend (распределённый трейсинг).
- **FR-013**: Каждый сервис MUST экспонировать метрики latency, throughput и error rate.
- **FR-014**: Секреты (учётные данные registry, кластера и пр.) MUST храниться только в защищённом хранилище секретов/переменных окружения и MUST NOT попадать в репозиторий, образы или логи.
- **FR-015**: Фича MUST NOT вводить бизнес-функциональность: допускаются только технические интерфейсы (health, метрики, контракт).

### Key Entities *(include if feature involves data)*

- **Публичный API-контракт**: машиночитаемое описание публичного API; версионируется в репозитории; единственный источник истины для клиентов.
- **Сгенерированные клиентские типы**: производный артефакт контракта; создаётся автоматически при изменении контракта; изменяется вручную только через контракт.
- **Контейнерный образ**: неизменяемый артефакт сборки приложения; идентифицируется версией (тегом), однозначно связанной с коммитом.
- **Телеметрия**: структурированная запись лога (содержит trace id), трейс/span (распределённый контекст вызова), метрики (latency, throughput, errors) — по каждому сервису.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Новый инженер с чистого клона репозитория собирает и запускает оба приложения локально без ручного редактирования файлов за время ≤ 30 минут.
- **SC-002**: 100% изменений основной ветки проходят автоматический конвейер «сборка → линт → тесты»; ни одно изменение не попадает в основную ветку без успешного прохождения конвейера.
- **SC-003**: После слияния изменения в основную ветку новая версия обоих приложений доступна в dev-окружении автоматически за ≤ 15 минут.
- **SC-004**: Перезапуск любого экземпляра сервиса восстанавливает обслуживание автоматически, без ручных действий и без изменения конфигурации.
- **SC-005**: 100% записей логов сервисов структурированы; каждый обработанный запрос имеет идентификатор трейса, присутствующий в записях всех затронутых сервисов.
- **SC-006**: Метрики latency/throughput/errors запрашиваемы для каждого сервиса в любой момент времени его работы.
- **SC-007**: Изменение публичного контракта отражается в сгенерированных TypeScript-типах автоматически за одну итерацию конвейера; расхождение блокирует слияние.
- **SC-008**: Конвейер содержит ноль стадий, требующих ручного подтверждения на пути от слияния до dev-окружения.

## Assumptions

- Технологический стек зафиксирован конституцией проекта: backend — Kotlin 2.x + Spring Boot 3.x, frontend — React + TypeScript (strict mode); он приводится здесь как ограничение, а не как проектное решение данной фичи.
- Конкретные инструменты (система сборки backend Maven/Gradle, CI-платформа, container registry, инструменты codegen, tracing/metrics-стек, логгирование) не заданы и выбираются на этапе `plan.md` с обоснованием (конституция, принцип VII); пайплайн-синтаксис в спеке не фиксируется.
- Целевое окружение деплоя этой фичи — только dev; staging/production вводятся в последующих фичах.
- Внешние хранилища (СУБД, брокер сообщений, кэш) в этой фиче не вводятся (YAGNI); поэтому требование stateless сводится к отсутствию состояния в памяти процесса.
- Tracing-бэкенд (сбор/хранение трейсов и метрик) считается внешней доступной зависимостью dev-окружения; его выбор фиксируется в `plan.md`.
- Команда имеет доступ к container registry и dev-кластеру Kubernetes (предоставляются инфраструктурой организации); создание самой инфраструктуры кластера вне scope.
- Unit-тесты в скелетах минимальны (smoke-уровень) — достаточно для проверки работоспособности конвейера; содержательные интеграционные тесты появятся в бизнес-фичах.
- Контракт на этом этапе — каркасный (минимальный) без бизнес-endpoints; генерация типов и детекция breaking changes должны работать на нём же.
- Работа ведётся по trunk-based-модели: изменения попадают в основную ветку только через pull request с обязательными проверками.
