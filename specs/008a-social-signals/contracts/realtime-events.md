# Realtime-события: 008a-social-signals (канал №18)

**Дата**: 2026-10-08 | Расширение контракта №18 (`GET /api/v1/users/me/events`, SSE) — строго аддитивно.

Общие конвенции канала №18 (004/007) сохраняются: framing `event:{name}\ndata:{одна строка JSON}\n\n`, opening-кадры `retry: 3000` + `connected {connectionId}`, heartbeat-комментарий `:ka` каждые 15 с, **at-most-once**, реконнект-рефетч клиентом, **неизвестные `event:` игнорируются** — механизм аддитивности 008a.

---

## 1. Новые события

### 1.1 `typing.started`

```json
event: typing.started
data: {"chatId":"7f2c…","userId":"9ab1…"}
```

- **Схема** `TypingStartedEvent`: `chatId` (uuid), `userId` (uuid); `additionalProperties: false`.
- **Аудитория**: активные участники чата, **кроме отправителя сигнала** (own-устройства свой набор не отображают — AC9 решается адресацией).
- **Когда публикуется**: при каждом валидном `start`-сигнале №41 (включая продления — окно повтора 3 с; AC4 «индикатор не отвисает»). Дребезг исключён клиентским дебаунсом + флуд-лимитом 60/мин (AC8).
- **Подавление**: DIRECT-блок-пара — не публикуется ни в одну сторону (AC7); отправитель не участник — операция отклонена раньше (гейт №41).
- **Эфемерность**: не сохраняется, не попадает в историю/sync (005), не реплеится при (ре)подключении (AC5, FR-007).

### 1.2 `typing.stopped`

```json
event: typing.stopped
data: {"chatId":"7f2c…","userId":"9ab1…"}
```

- **Схема** `TypingStoppedEvent`: идентична `TypingStartedEvent`.
- **Когда публикуется** (та же аудитория, что started):
  1. валидный `stop`-сигнал №41 при активном состоянии (очистка поля, явное завершение; повторный stop без активного состояния — без публикации, идемпотентность; в т.ч. клиентский stop при отклонённой валидацией пустой отправке — edge-кейс: попытка отправки = завершение, ui-behavior.md §2.1);
  2. **успешная отправка сообщения** №16 печатающим (сервер гасит состояние при INSERT сообщения — data-model.md §2.1);
  3. **серверное истечение состояния** по таймауту 8 с (poller; обрыв сети/падение клиента — AC6, метрика `webchat_typing_state_expired_total`).
- **Клиентская страховка**: наблюдатель скрывает индикатор также по `message.created` от печатающего и по локальному таймауту **10 с** без продления (at-most-once потери).

### 1.3 `chat.sound.updated`

```json
event: chat.sound.updated
data: {"chatId":"7f2c…","soundEnabled":false}
```

- **Схема** `ChatSoundUpdatedEvent`: `chatId` (uuid), `soundEnabled` (boolean); `additionalProperties: false`.
- **Аудитория**: **только сам пользователь** (собственный канал `rt:user:{me}`) — синхронизация мультидевайс (FR-015); другие участники чата событие не получают никогда (приватность FR-012).
- **Когда публикуется**: успешная **смена** значения №42 (повтор того же значения — без события, идемпотентность).
- Подключающиеся/переподключающиеся клиенты получают актуальное состояние из №12/№13 (`soundEnabled`), событие — только для живых подключений.

## 2. Изменение существующего события

### 2.1 `presence.updated` — + опциональное `lastSeenAt`

```json
event: presence.updated
data: {"userId":"9ab1…","status":"offline","rev":42,"lastSeenAt":"2026-10-08T16:20:03Z"}
```

- **Схема** `PresenceUpdatedEvent`: добавлено `lastSeenAt?: string (date-time)`.
- **Правила присутствия поля** (FR-010, SC-002):
  - только при `status=offline` (при `online` поля нет);
  - только в рамках аудитории видимости 007 (событие уже адресуется аудитории);
  - субъект не в инкогнито (freeze публикует `offline` **без** `lastSeenAt` — целиком скрыт, edge-кейс «не время включения инкогнито»);
  - данные есть (ключ `presence:lastseen:{userId}` существует);
  - **отсутствие поля нейтрально** — «нет данных» ≡ «инкогнито» ≡ «блок-пара» ≡ «вне аудитории» (неотличимо, US3 AC2–AC4).
- Точность значения — в пределах TTL-модели 007 (≤ ~136 с = 90 + 45 + 1 при обрыве; штатное закрытие — точное, SC-005).
- Клиенты 007, не знающие поля, игнорируют его без изменений поведения.
