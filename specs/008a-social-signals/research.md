## A. Typing-индикатор: транспорт, параметры, самоистечение

### A1. Транспорт сигналов: REST-операция + события канала №18

- **Decision**: Один REST-endpoint `POST /api/v1/chats/{chatId}/typing` (№41, тело `{action: "start"|"stop"}`, ответ 204, идемпотентно) + доставка наблюдателям событиями `typing.started {chatId, userId}` / `typing.stopped {chatId, userId}` через существующий SSE-канал №18 (`rt:user:{observerId}` Redis Pub/Sub).
- **Rationale**: Канал №18 уже мультиплексирует все события пользователя и обязывает клиентов игнорировать неизвестные `event:` (контракт 004, `realtime-channel.md`) — аддитивное расширение без нового соединения; REST-управление проходит стандартные гейты (membership-авторизация, флуд-лимит 429 `flood_limit` + Retry-After, конвенция `UserRateLimiter`). Пара start/stop в одной операции (а не два endpoint'а) — один флуд-бакет и одна семантика идемпотентности.
- **Alternatives**: WebSocket-канал чата (отвергну: в проекте его нет, violates YAGNI и конвенцию единого канала №18); публикация сигналов без REST-гейтов напрямую из SSE-пинга (отвергну: обходит авторизацию membership и флуд-защиту, конституция V).

### A2. Параметры дебаунса и таймауты (фиксируются в контракте)

- **Decision**:
  - Клиент: сигнал `start` — после первого введённого символа и далее **не чаще одного раза в 3 с** (окно повтора) пока ввод продолжается; сигнал `stop` — при отправке сообщения (включая отклонённую валидацией пустую отправку), очистке поля; после **5 с молчания** клиент шлёт `stop` (окно молчания клиента ≤ серверного TTL).
  - Сервер: состояние `{chatId, userId}` живёт **TTL 8 с** (≈ 2.5× окна повтора — переживает одну потерю повтора), каждый `start` продлевает; истечение → poller публикует `typing.stopped` участникам (серверный таймаут состояния, FR-007/AC6).
  - Наблюдатель: скрывает индикатор по `typing.stopped`, приходу `message.created` от печатающего и по **клиентскому страхующему таймауту 10 с** без продления (компенсирует at-most-once потерю события — конвенция канала №18).
- **Rationale**: Соотношения соответствуют практике зрелых мессенджеров (Telegram/Slack: повтор каждые ~5 с, серверное истечение ~6–10 с) и допущению at-most-once: 8-с TTL переживает пропуск одного 3-с повтора; страхующий клиентский таймаут > TTL гарантирует исчезновение «вечного печатает» даже при полной потере `typing.stopped`. SC-001 (2 с) обеспечено: событие публикуется синхронно с POST-ом start, задержка доставки — SSE-путь ≈ десятки мс.
- **Alternatives**: TTL = окну повтора (хрупко к одной потере); polling-модель «кто печатает» в №36-подобном снапшоте (отвергну: нарушает эфемерность FR-007 — состояние не должно читаться «задним числом» подключившимся); keyspace-notifications Redis для истечения (см. A4).

### A3. Адресация, приватность, self-exclusion

- **Decision**: Сервер публикует `typing.*` **всем активным участникам чата, кроме отправителя** (его собственный канал не получает событие — AC9 «свои устройства не показывают свой набор» решается адресацией, а не клиентским фильтром). Для DIRECT-чатов обе стороны блок-пары не доставляют и не получают сигналы (обе проверки `BlockRepository.exists`, образец — `publishToPeerUnlessBlocked` в `ReadService`); GROUP-чаты блоками не фильтруются (паритет `chat.read`/`message.created`, 006). Отправитель обязан быть активным участником чата (404/403 по существующим кодам №16). Состояние живёт только в Redis (`typing:active:{chatId}` ZSET userId→expiresAtMs + глобальный `typing:watch` ZSET для poller'а), ключи самоистекают; 0 записей в PG/истории/sync (SC-003).
- **Rationale**: Семантика блок-пар 004 FR-020 распространена на новые события буквально по спеке (FR-008); группы в проекте никогда не фильтруются блоками — сохраняем консистентность. Self-exclusion адресацией проще и надёжнее клиентской фильтрации (не зависит от актуальности meUserId на устройстве).
- **Alternatives**: Отправка себе + фильтр на клиенте (лишний трафик, риск бага отображения); отдельная проверка блокировок в группах (отвергну — противоречит поведению 006).

### A4. Механизм самоистечения: poller по образцу offq-модели 007

- **Decision**: `TypingTransitionScheduler` — `@Scheduled(fixedDelay = 1 с)` bean, gated `chats.typing.poller-enabled` (в тестах выключен, включается в `TypingTestSupport`), батч ≤1000: `ZRANGEBYSCORE typing:watch -inf..now` → для истёкших пар ZREM из `typing:active` + публикация `typing.stopped`. Дополнительно все ключи несут Redis-TTL как страховку мусора.
- **Rationale**: Точная копия проверенного паттерна `PresenceTransitionScheduler.drainDueOfflinePublishes` (007): детерминированное событие-«стоп» наблюдателям, конфигурируемые окна в тестах (`application-test.yml`), batch-cap от шторма. Гарантирует AC6/SC-003 наблюдаемо (метрика `webchat_typing_state_expired_total`).
- **Alternatives**: Redis keyspace notifications (`__keyevent@0__:expired`) — отвергну: ненадёжно (fire-and-forget, requires notify-keyspace-events, события теряются при рестарте подписчика) и вне дом-паттерна; чисто клиентский таймаут без серверного стопа — отвергну: FR-007 требует серверное самоистечение состояния.

### A5. Флуд-лимит

- **Decision**: Бакет `rl:user:typing:{userId}`, **60 сигналов/мин** (permits 60, окно 60 с, `UserRateLimiter`); превышение — 429 `flood_limit` + Retry-After (стандартный ответ), избыточные сигналы не публикуются. Заблокированный композер (008 FR-022) сигналы не отправляет (FR-006) — сервер дополнительно подавляет по блок-паре (A3).
- **Rationale**: Честный клиент шлёт ≤ 20 start/мин на чат (окно 3 с) + стопы; 60/мин покрывает несколько чатов и дребезг stop/start без дребезга индикатора у наблюдателей (AC8). Дом-конвенция msgsend 30/мин и presence 30–60/мин.
- **Alternatives**: 30/мин (мешает длительному набору в двух чатах); per-(user,chat) бакеты (усложняет ключи без необходимости — спам-атака идёт от пользователя).

## B. lastSeen: хранение, API, приватность, формат

### B1. Источник и запись времени

- **Decision**: Redis-ключ `presence:lastseen:{userId}` (string, epoch ms из Redis `TIME`), TTL **30 дней** (старше — фолбэк «давно»). Запись в существующих Lua-ногах `RedisPresenceStore`: `REGISTER_SCRIPT` (открытие соединения), `RENEW_SCRIPT` (heartbeat №37), `UNREGISTER_SCRIPT` (штатное закрытие), `CLEAR_SESSION_SCRIPT` (logout №7). Чтение — в `SNAPSHOT_SCRIPT` (пакетно). При TTL-истечении регистрации (reap) отдельной записи нет — остаётся stamp последнего heartbeat: погрешность ≤ TTL 90 c + гистерезис 45 c + poller 1 c ≈ **137 с** (допуск спеки — единая оценка ≤ ~137 с, SC-005).
- **Rationale**: «Последняя активность presence-канала» буквально = heartbeat/открытие/закрытие; запись в тех же атомарных Lua-скриптах не добавляет кругов и гонок; Redis — уже установленное внешнее хранилище presence (конституция II). Мультидевайс: ключ один на пользователя, пишется любым живым подключением (edge-кейс спеки).
- **Alternatives**: Колонка в PG (отвергну: presence целиком в Redis с 007, писать в PG на каждый heartbeat — лишняя нагрузка); фиксация только на закрытии (хуже точность при падении инстанса).

### B2. Раскрытие через API: №36-снапшот + presence.updated

- **Decision**: `PresenceStatusItem` (№36) и `PresenceUpdatedEvent` (№18) получают **опциональное** поле `lastSeenAt` (RFC 3339 date-time). Поле присутствует только когда: `status = offline` И наблюдатель в аудитории видимости 007 И субъект не в инкогнито И ключ существует. Иначе поле отсутствует — «скрыто» неотличимо от «нет данных» (продолжение унификации `unknown` из 007, SC-002). Инкогнито-фильтр: пакетное чтение `presence_hidden` (`JdbcPresenceSettingsStore`, один SELECT … WHERE id IN (…)) в `PresenceService.snapshot` перед формированием ответа; событие offline при freeze (`FREEZE`-нога) идёт без `lastSeenAt`.
- **Rationale**: Поверхности US3 (заголовок чата, «Контакты») уже питаются от №36/`presence.updated` через `presenceStore` — поле «доезжает» до UI без новых запросов; offline-событие с `lastSeenAt` даёт мгновенное обновление заголовка без рефетча (SC-005 «в 100% приёмочных прогонов»). Отсутствие поля вместо `null`/sentinel — единственный способ сделать причины неотличимыми на уровне контракта.
- **Alternatives**: Отдельный endpoint `GET /users/{id}/lastSeen` (отвергну: новая поверхность утечки, дублирует приватность №36); `lastSeenAt: null` для скрытых (отвергну: различимо клиентом по наличию поля — против AC3/AC4).

### B3. Формат отображения (фиксация по прототипу)

- **Decision**: `В сети` — без изменений (007). Офлайн: `Был в сети — {время}`, где время: сегодня (по локальному времени наблюдателя) → `HH:MM`; иначе → `D месяца, HH:MM` (`24 сентября, 16:20` — точный формат демо-данных прототипа, `chats.html:585`); при отличии года → `D месяца YYYY, HH:MM`. Нет/скрыто → `Был в сети — давно` (прототип `chats.html:796`). Локаль `ru-RU`, часовой пояс наблюдателя (решение 008 — без i18n). Реализация — композиция существующих `formatTime`/`formatDate` (`frontend/src/ui/time.ts`), новая функция `lastSeenFormat`.
- **Rationale**: Прототип не содержит логики «сегодня/вчера» (статичные демо-даты полного формата) — вводим минимальное правило из FR-011 («сегодня — только время»), «вчера» не вводим (нет прототипа и потребности — YAGNI; полное «D месяца, HH:MM» однозначно и не противоречит). Граница суток сходится к локали/поясу наблюдателя (edge-кейс спеки).
- **Alternatives**: Всегда полная дата (прототип так и делает, но FR-011 явно требует «сегодня — только время»); спец-кейс «вчера, HH:MM» (отвергнут — YAGNI, нет в прототипе).

## C. Отображаемые имена: хранение, операции, распространение

### C1. Хранение

- **Decision**: миграция `V16__social_signals.sql`: `ALTER TABLE users ADD COLUMN display_name VARCHAR(64)` (NULL = не задано); `ALTER TABLE user_contacts ADD COLUMN alias VARCHAR(64)` (NULL = нет) с CHECK `alias IS NULL OR (length(btrim(alias)) BETWEEN 1 AND 64)`; значения пишутся после серверного trim. Валидация сервиса: отклонение пустых/пробельных и >64 символов (400, коды `invalid_display_name` / `invalid_alias`).
- **Rationale**: NULL-семантика = «не задано» даёт обратную совместимость без миграции данных (все существующие пользователи — username, edge-кейс «первое включение фичи»); VARCHAR(64) — дефолт из FR-001; конвенция аддитивных колонок V12/V14/V15.
- **Alternatives**: Отдельные таблицы profile_names/contact_aliases (отвергну: 1:1 к users/user_contacts, лишний join — YAGNI).

### C2. Операции

- **Decision**:
  - **№39** `PUT /api/v1/users/me/profile` `{displayName?: string | null}` → 200 `PublicUser` (обновлённый); отсутствующее/null — сброс. Флуд `rl:user:profile:` 30/мин.
  - **№40** `PUT /api/v1/contacts/{userId}/alias` `{alias?: string | null}` → 200 `ContactView`; отсутствующее/null — сброс alias; 404 `contact_not_found` если пользователь не контакт. Флуд `rl:user:alias:` 30/мин. Alias удаляется вместе с контактом (№22, каскад по строке), переживает удаление чата (живёт на `user_contacts`, edge-кейсы спеки).
  - Обе идемпотентны (последний write wins, повтор того же значения — 200 без события).
- **Rationale**: PUT со сбросом через null — один endpoint на сущность (DELETE-сброс отвергнут: вторая операция ради того же эффекта); флуд 30/мин — паритет с settings №38 (редкие ручные операции). Существующие GET-операции не меняются.
- **Alternatives**: PATCH-семантика частичных апдейтов (не нужна — поле одно); realtime-событие смены имени (отвергну: YAGNI, спека фиксирует рефетч-семантику — «другие видят при следующем обновлении данных»).

### C3. Распространение по представлениям (аддитивно, FR-016)

- **Decision**: Схема `PublicUser` получает опциональное `displayName`; `ContactView` — опциональное `alias` (персональный alias запросчика). Серверные проекции: `ChatPeerView` (№11/№12/№13) — `displayName` + `alias` запросчика к peer; `GroupMember.user` (№28 и members-tip) — `displayName` + `alias` запросчика к участнику; №19 поиск — `displayName` (+`alias`, если найденный — контакт запросчика). Единый helper `aliasesOf(ownerId, userIds): Map<UUID, String>` в `ContactRepository` (один SELECT по `user_contacts`). Серверная сортировка/семантика поиска НЕ меняются (FR-005); клиент сортирует/фильтрует по цепочке.
- **Rationale**: Добавление alias к каждой пользователь-проекции на сервере — единственный способ дать «alias на всех поверхностях» (FR-003) без второй сетки запросов клиента; фронтенд разрешает имя одной функцией `resolveDisplayName(alias, displayName, username)`. Существующие клиенты игнорируют неизвестные поля (обратная совместимость, FR-002).
- **Alternatives**: Клиент сам джойнит contacts-alias к чатам/группам (отвергну: поиск №19 не знает контактов; рассинхрон поверхностей); сервер возвращает только «resolved» имя без исходных полей (отвергну: теряется различие для отладки/UI-подсказок, ломает аддитивность — замена семантики существующих полей).

### C4. Инициалы, цвет, цепочка

- **Decision**: `Avatar` получает отдельный источник инициалов (вызов sites передают `initialsOf(resolveDisplayName(...))`), цвет остаётся `colorOf(username)` / названия группы (FR-004: переименование не перекрашивает). Цепочка — единственная функция `resolveDisplayName` в `frontend/src/ui/names.ts`.
- **Rationale**: Сегодня `Avatar` выводит оба производных из одного `source` (avatar.ts:41-52) — при разноимённых источниках нужен отдельный проп; цвет от стабильного идентификатора — требование FR-004 и прецедент прототипа (`initialsOf(c.displayName)` при сохранённом цвете, `chats.html:1304`).
- **Alternatives**: Менять `colorOf` на displayName (отвергнуто — прямое нарушение FR-004).

## D. Per-chat звук: хранение, операция, синхронизация

### D1. Хранение

- **Decision**: `ALTER TABLE chat_participants ADD COLUMN sound_enabled BOOLEAN NOT NULL DEFAULT TRUE` (та же V16). Умолчание TRUE = паритет 008 «всегда включено» (edge-кейс спеки). Настройка читается в `ChatView`/`ChatListItem` (новое опциональное поле `soundEnabled: boolean`, сервер выставляет всегда) и переживает удаление чата (строка участника сохраняется, 008 FR-013).
- **Rationale**: PK `chat_participants (chat_id, user_id)` — в точности per-user-per-chat; аддитивные NOT NULL DEFAULT колонки на этой таблице — установленная конвенция (V12 `delivered_up_to_seq`, V14 `role/state`). Отдельная таблица настроек — избыточна (YAGNI).
- **Alternatives**: Таблица `chat_sound_settings` (отвергнута — дублирует PK участников); хранение только в Redis (отвергнуто — требование FR-012 «хранится на сервере» durable, переживает рестарты/миграции).

### D2. Операция и синхронизация

- **Decision**:
  - **№42** `PUT /api/v1/chats/{chatId}/sound` `{enabled: boolean}` → 200 `{soundEnabled: boolean}`; membership-гейт (403/404 по кодам чата), идемпотентна (повтор того же значения — 200 без события), флуд `rl:user:chat-sound:` 30/мин. Без сети операция падает ошибкой — локального опережающего переключения нет (edge-кейс спеки).
  - Событие `chat.sound.updated {chatId, soundEnabled}` — только в **собственный** канал пользователя (другие участники о настройке не узнают, FR-012 «персональна»). Подключающиеся/переподключающиеся клиенты получают состояние из №12/№13 (поле `soundEnabled`).
- **Rationale**: Событие в собственный канал — единственный механизм мультидевайс-синхронизации в проекте (№18 per-user); приватность настройки — отсутствие каких-либо полей/событий у других участников. 30/мин — консервативный паритет settings №38 (ручная кнопка).
- **Alternatives**: Оптимистичный UI-переключ с откатом (отвергнуто — спека фиксирует серверную операцию); событие в канал чата с фильтром (отвергнуто — рассекрет факта настройки трафиком).

### D3. Клиентское поведение звука

- **Decision**: `chimeOnRealtimeIncoming(event, meUserId)` (в сигнатуре уже есть `chatId`) гейтится per-chat mute-состоянием; sync-батчи 005: `MessengerPage` ведёт per-chat счётчик входящих (сегодня `syncIncomingRef` — глобальный) — звонок батча звучит только если среди пришедших есть неприглушённые чаты. Bell-кнопка: `.ch-btn` с SVG прототипа, состояние `.off {opacity:.45}`, `aria-pressed`, тосты `Звуковые оповещения включены/отключены — {имя}`, звук выключения — «глухой щелчок» `bellTone(300 Hz)` из прототипа (`chats.html:779`). Визуальные уведомления не фильтруются (FR-014).
- **Rationale**: Минимальные изменения готового sound.ts; per-chat подсчёт батчей — необходимая точность FR-014 («пакеты массовой доставки»), строки/облик — прототип.
- **Alternatives**: Глобальный mute (отвергнут — per-chat по спеке); фильтрация на уровне AudioContext (отвергнуто — меняет семантику для неприглушённых).

## E. Нагрузочный расчёт typing-событий (конституция II, SC-008)

- **Decision**: Пиковый сценарий: 1M CCU (бюджет II), одновременно печатают 5% = 50k; средняя аудитория чата 4 (3 получателя). Частота start: 1/3 с → **16.7k POST/с**, публикаций: 16.7k × 3 ≈ **50k событий/с** в Redis Pub/Sub + SSE-запись. Оценка объёма: кадр `event:typing.started\ndata:{…}\n\n` ≈ 60–80 байт → ~4 МБ/с Pub/Sub — на 2–3 порядка ниже килобайтных сообщений; Redis Pub/Sub одиночного инстанса ~100k+ msg/с, при росте — шардирование `rt:user:*` по инстансам (каналы уже изолированы per-user). CPU: publishing-нога — сериализация ~100 байт JSON + LPUBLISH, ≈ единицы μs; poller при 50k активных состояниях — ZRANGEBYSCORE батчами ≤1000/с-тик, амортизировано ~50 операций/тик. Вывод: в пределах бюджетов II при том же порядке, что presence-события 007 (там публикация offline/online на ту же аудиторию).
- **Верификация**: `load/k6/social-signals.smoke.js` — базовый прогон (мессенджинг) vs прогон с активным набором (VU печатает: start каждые 3 с, stop на отправке): критерий Δp99 push ≤ 10% (шаблон 007 SC-007, `presence.smoke.js`); метрики FR-017 включены.
- **Alternatives**: Снижение окна повтора до 5 с (экономия ×1.7 ценой «зависания» индикатора при потере одного повтора — принято 3 с по практике мессенджеров); отказ от повторов вообще (нарушает AC4 «не отвисает»).
