# Research: Присутствие пользователей (007)

**Date**: 2026-10-01 | **Status: Complete** — все вопросы plan-раунда закрыты; источники: код 002–006 (`backend/src/main/kotlin/webchat/backend/{realtime,chats,contacts,groups}`, `frontend/src/{api,chats}`), планы 004–006, `contracts/openapi.yaml` 0.6.0.

## A. Хранение и самоистечение регистраций

### A1. Носитель состояния присутствия

- **Decision**: Redis 7 (существующий Lettuce-стек) — registrations-as-data: per-user ZSET `presence:alive:{userId}` (member=connectionId, score=expiry-timestamp) + глобальные очереди-триггеры (§3 data-model). PG — только durable-настройка «невидимки» и чтение аудитории.
- **Rationale**: Присутствие — эфемерное состояние с TTL-семантикой: конвенция 004 «Redis — ephemeral, PG — source of truth for durable». Redis уже несёт RL-бакеты, SSO-flow, Pub/Sub;新增 типов ключей дешевле нового хранилища (VII). Инстансы не держат статус (II): SSE-коннекты одного пользователя живут на разных подах — статус обязан быть внешним.
- **Alternatives considered**: (1) Память инстанса (`SseConnectionRegistry` уже знает локальные коннекты) — отвергнуто: рестарт/перекидка теряет и расщепляет статус (нарушение II, US3); (2) PG-таблица регистраций с крон-чисткой — отвергнуто: нет нативного TTL, нужен джоб-компакт, 43k heartbeat-RPS пишут в durable-СУБД без ценности истории (FR-001 запрещает историю); (3) отдельное хранилище (Aerospike/Scylla) — YAGNI, бюджеты покрывает Redis.

### A2. Механика самоистечения (тихая смерть без явного disconnect)

- **Decision**: Deadline-watcher: глобальный ZSET `presence:watch` (member=userId, score=max(expiry) регистраций пользователя). Обновляется при каждой регистрации/продлении/удалении. Фоновый поллер (fixed-delay 1 c, батчево ZRANGEBYSCORE `−inf..now`) находит кандидатов на истечение, вычищает истёкшие members из `presence:alive:{userId}` и запускает пересчёт статуса (при пустоте — гистерезис-очередь `presence:offq`).
- **Rationale**: Надёжный, тестируемый (время управляется конфигом) триггер пересчёта для регистраций, истёкших молча (зависшая вкладка, kill −9 инстанса, метро без FIN). Поллеры всех инстансов конкурируют идемпотентно: переход статуса публикует только атомарный CAS по `presence:pub:{userId}` (Lua), повторная обработка того же кандидата — no-op. SC-003: «офлайн» гарантирован ≤ TTL (90 c) + гистерезис (45 c).
- **Alternatives considered**: (1) Redis keyspace notifications (`__keyevent@*__:expired` на per-connection String-ключах) — отвергнуто: fire-and-forget (потеря при рестарте подписчика), выключены на managed-Redis, в кластере слушание всех шард; (2) перечисление per-connection String-ключей с нативным TTL как источника истины — требует KEYS/SCAN по кластеру для мультидевайс-подсчёта (O(N), недопустимо); нативный TTL заменён score-expiry + watcher'ом, что эквивалентно по гарантии сходимости; (3) серверное продление по живости SSE (`:ka` каждые 15 c) — отвергнуто: keep-alive-кадры не детектируют half-open TCP (вкладка зависла, буфер прокси не переполнен) и не оставляют наблюдаемого deadline'а для пересчёта.

### A3. Heartbeat клиента

- **Decision**: REST `POST /api/v1/users/me/presence/heartbeat {connectionId}` (№37). `connectionId` выдаётся сервером в новом opening-фрейме `connected` SSE №18 сразу после `retry: 3000`. Параметры контракта: TTL регистрации **90 c**, рекомендованный интервал heartbeat **30 c** (3× запаса); heartbeat атомарно (Lua) продлевает score в `presence:alive` + `presence:watch`. Rate-limit — существующий `flood_limit` (429) поверх per-user бакета.
- **Rationale**: FR-002 требует продленияheartbeat'ом **клиента**: только клиент доказывает свою жизнь при half-open TCP/зависшей вкладке. REST-запрос обрабатывается любым stateless-инстансом (II) — не привязан к поду SSE-канала. `connected`-фрейм — аддитивное расширение канала; клиенты 004/006 игнорируют неизвестные `event:` (контракт №18), обратная совместимость сохранена (IV).
- **Alternatives considered**: (1) безымянный heartbeat (без connectionId), продлевающий «все регистрации пользователя» — отвергнуто: зависшее устройство оставалось бы вечно-онлайн, пока живо второе (нарушение FR-002, edge «зависшая вкладка»); (2) WebSocket-канал upstream — отвергнуто 004 (SSE+REST выбраны, новый транспорт не вводим); (3) продление «бесплатно» любым REST-запросом клиента (piggyback) — отвергнуто: неявный контракт, ломается фоновым режимом без сообщений, сложнее тестировать.

## B. Анти-флап: дебаунс и гистерезис

### B1. Механика подавления переключений

- **Decision**: `presence:offq` — глобальный ZSET отложенных публикаций (member=userId, score=publishAt=потеря-последней-регистрации + 45 c). Потеря последней регистрации (явное закрытие SSE или watcher-истечение) никогда не публикует сразу — только ставит в offq. Поллер offq по наступлении publishAt пересчитывает: есть живая регистрация → **отмена** (ZREM, счётчик `hysteresis_suppressed_total`), нет → атомарный CAS `pub: online→offline` + публикация. Появление первой регистрации: немедленная отмена offq + CAS-публикация `online` (дебаунс-online ≈ 0; «защита от событий-эхо» — сам CAS: повторная публикация того же значения невозможна, дубль кадра безвреден — FR-006 идемпотентность). Окно гистерезиса **45 c** — параметр контракта (FR-004), конфигурируемо (`presence.hysteresis`) для тестов.
- **Rationale**: Один механизм закрывает US2 (метро-серия → 0 наблюдаемых переключений; долгий разрыв → ровно одно), edge «разрыв на границе окна» (допустимы 0 или 1 переключение — CAS исключает ≥2) и US3-шторм (массовые реконнекты гасятся окном; публикации ≈ числу невозвратившихся). Отдельный debounce-таймер для online не нужен: CAS `pub≠online` сам подавляет эхо/дубли (VII — не вводим сущность без потребности).
- **Alternatives considered**: (1) клиентский дебаунс индикатора — отвергнут: наблюдатели на N клиентах дребезжали бы независимо, а событие уже заняло канал; подавлять надо у источника; (2) отложенная публикация через Redis `SET ... PX` + keyspace — см. A2; (3) Spring `@Scheduled` per-user задачи в памяти — stateless-нарушение (рестарт теряет отложенные публикации).

### B2. Logout vs закрытие устройства

- **Decision**: Явное закрытие SSE (FIN/complete/error → колбэк реестра) удаляет регистрацию немедленно (FR-002), но публикацию «офлайн» ставит в offq на общих основаниях (гистерезис). Исключение — **logout** (REST 002): logout-флоу вызывает очистку всех регистраций пользователя и **немедленную** CAS-публикацию «офлайн» (обход offq) — edge «logout на последнем устройстве — без ожидания окна»: сессия отозвана, реконнект невозможен, ждать нечего.
- **Rationale**: Сервер не отличает закрытие вкладки от метро в моменте — различие делает семантика команды: logout гарантирует невозврат (токены отозваны), значит гистерезис бессмыслен; закрытие вкладки/обрыв — реконнект возможен → окно. Ровно та же асимметрия, что зафиксирована в edge cases спеки.
- **Alternatives considered**: публиковать «офлайн» сразу на любой FIN — отвергнуто: мобильные браузеры рвут SSE в свёрнутом состоянии и восстанавливают за секунды (то самое «метро»), US2 требует 0 переключений.

## C. Доставка: адресация и формат

### C1. Аудитория видимости

- **Decision**: Вычисляется на сервере SQL по PG в момент публикации перехода: активные сосparticipants чатов пользователя (direct+group, `chat_participants.state='active'`) ∪ владельцы контактов (`user_contacts.contact_user_id=X`) − обе стороны блок-пар (`user_blocks` в обе стороны) − сам X. Кэширование аудитории в v1 не вводится; запрос идёт по существующим индексам V10/V11/V14.
- **Rationale**: Аудитория обязана следовать текущему состоянию чатов/контактов («добавил в контакты — статус стал виден», edge) — живой SQL без инвалидации кэша даёт сходимость «бесплатно». Частота — только на переходы статуса (редкие относительно сообщений, §Load Estimate plan.md): ~1 SQL + ~50–2000 PUBLISH на переключение — на два порядка ниже фанаута групповых сообщений 006.
- **Alternatives considered**: (1) кэш аудитории в Redis TTL 30–60 c — отвергнут (VII): экономия на редком запросе ценой рассинхрона видимости при добавлении контакта/исключении из группы; (2) подписки-топики per-observer (`ps:sub:{observer}` SET) с инкрементальным ведением — отвергнуто: сложная инвалидация при каждом изменении чатов/контактов/блокировок во всех фичах 004/006 — риск рассинхрона политики приватности (V); (3) широковещательная публикация с клиентской фильтрацией — прямо запрещена FR-003 (шум) и V (утечка факта статуса посторонним).

### C2. Событие и сходимость «событие/снапшот»

- **Decision**: Один новый тип кадра №18: `event: presence.updated`, `data: {"userId","status":"online|offline","rev"}` — публикуется в `rt:user:{observerId}` каждого адресата аудитории через существующий конверт `{"event","data"}` (RedisRealtimePublisher). `rev` — монотонная ревизия статуса пользователя (INCR при каждом фактическом переходе и при переключении «невидимки»), хранится в Redis, возвращается и в событии, и в снапшоте №36. Клиентское правило слияния: применять только строгое возрастание `rev` per-user; остальное (дубль кадра, событие до снапшота, устаревший снапшот) — no-op.
- **Rationale**: Канал №18 at-most-once (004 §2): событие может потеряться (сходимость — снапшот на (re)connect) или задублироваться (безвредно). Гонка «кадр до применения снапшота» (edge спеки) без ревизии неразрешима: снапшот, взятый позже события, затёр бы свежий статус; `rev` даёт детерминированное сведение к последнему серверному значению — буквальное выполнение FR-006 идемпотентности.
- **Alternatives considered**: (1) слияние по client-clock timestamp — отвергнуто: несравнимые часы, jitter доставки; (2) «снапшот всегда прав» — отвергнуто: затирает более свежие события, пришедшие в окне запроса; (3) серверный снапшот-фрейм при открытии SSE — отвергнут: сервер не знает отображаемые поверхности клиента (clarify 2026-10-01: снапшок только видимых поверхностей), кадр пришлось бы делать «на всю аудиторию» — нарушение FR-003/budgets.

### C3. Снимок отображаемых поверхностей

- **Decision**: REST №36 `GET /users/me/presence?userIds=` (batch ≤ 200, дедуп): для каждого запрошенного — политика (общий чат ∪ «у меня в контактах» − блок-пара) → нет доступа: `unknown`; иначе фактический статус по `presence:alive` (с учётом «невидимки» цели → `offline`, неотличимо). Ответ `{items:[{userId,status,rev}]}`. Вызов — из клиентского цикла (re)connect 005 (после sync/чатов/контактов) и при открытии новой поверхности; никакого «полного снапшота аудитории» при подключении (clarify).
- **Rationale**: Отображаемые поверхности (открытые чаты, видимый список «Контакты») знает только клиент; batch-запрос — точный механизм «по запросу API» из FR-003/FR-006. `unknown` для посторонних/блок-пары — единая семантика «нет доступа» без различения «офлайн»/«скрыто» (FR-007.4); «невидимка» в аудитории отвечает `offline` — неотличимость обязательна (FR-007.2).
- **Alternatives considered**: (1) отдельный endpoint per-user (`GET /users/{id}/presence`) — отвергнут: N+1 на список чатов/контактов; (2) включать статусы в ответы №15/№20 (chats/contacts) — отвергнуто: ломает single-responsibility контрактов, дублирует кодогенерацию, mixed-cache-инвалидация.

## D. Приватность: «невидимка»

### D1. Хранение и семантика

- **Decision**: `users.presence_hidden BOOLEAN NOT NULL DEFAULT FALSE` (Flyway V15, PG — переживает сессии, FR-007). Переключение — №38 `GET/PUT /users/me/presence/settings {incognito}` (единый для SPA и виджета). Включение при живых подключениях: немедленная CAS-публикация `offline` аудитории (ровно одно переключение, edge) и заморозка: пока включён, события переходов X не публикуются (снапшот-ответ — `offline`). Выключение: если фактически онлайн — публикация `online`; иначе ничего (аудитория уже видит `offline`). Оба перехода инкрементируют `rev`. Сам «невидимка» читает статусы аудитории без ограничений (№36 не фильтруется его собственным режимом).
- **Rationale**: Настройка per-user (не per-device, edge «мультидевайс-невидимка») и переживает сессии → durable PG (II). «Неотличимо от офлайна» реализуется одним механизмом: снапшот всегда отвечает `offline`, события заморожены — посторонний не может различить. Блок-пара уже исключена из аудитории (C1), взаимность соблюдена.
- **Alternatives considered**: (1) хранение флага в Redis — отвергнуто: настройка переживает сессии (FR-007), Redis-эфемерность противоречит; (2) семантика «показывать last-seen» вместо заморозки — вне scope (YAGNI, нет last-seen в v1); (3) гранулярные списки видимости — вне v1 (spec Assumptions).

### D2. Взаимодействие с гистерезисом

- **Decision**: Переключение «невидимки» — не более одной смены наблюдаемого статуса (edge): включение публикует `offline` немедленно (обход offq — как logout: гарантированность состояния), offq-записи пользователя при включённом режиме публикуются «в никуда» (CAS уже `offline` → no-op). Выключение при погашенном offq-окне — просто публикация фактического статуса.
- **Rationale**: CAS по `presence:pub` делает все пути сходимости однозначными; отдельные машины состояний не нужны (VII).
- **Alternatives considered**: прогонять переключение режима через offq — отвергнуто: лишние 45 c задержки и возможные двойные переключения (нарушение edge «не более одной смены»).

## E. Клиент (SPA + виджет)

### E1. Отображение

- **Decision**: Общий компонент `PresenceIndicator` (точка + текстовая/aria-метка): `online` (зелёная, «онлайн»), `offline` (серая, «офлайн»), `unknown` (нейтрально-серая/скрытая, «статус неизвестен») — до первого снапшота и для `unknown`-ответов (clarify: ложный «офлайн» до данных недопустим). Точки интеграции: `ChatListItem` (только direct), заголовок окна 1:1-чата, `ContactList` (панель 004 US5). В группах UI отсутствует (clarify). Состояние — `presenceStore` (Map<userId,{status,rev}>), наполнение: снапшот поверхностей на (re)connect + `presence.updated` из `useRealtime` слиянием по `max(rev)`; E2E-сходимость по US1-5.
- **Rationale**: Единая библиотека компонентов SPA/виджета (конституция IV); a11y-метка — требование clarify (2026-10-01, дальтоники/скринридеры).
- **Alternatives considered**: вычисление «нейтрально» внутри каждого листа — отвергнуто: три поверхности × два клиента = шесть реализаций одного правила (SRP/DRY).

### E2. Клиентский heartbeat

- **Decision**: `sse.ts`: на фрейм `connected` сохранить `connectionId` и запустить интервал 30 c → `POST heartbeat`; 404 `presence_connection_not_found` → немедленный reconnect SSE (регистрация истекла — канал, вероятно, мёртв); перед unload — `navigator.sendBeacon` не вводится (v1: истечение по TTL достаточно, YAGNI).
- **Rationale**: Единственный клиентский долг presence — поддержание своей регистрации; всё остальное — серверные гарантии.
- **Alternatives considered**: `sendBeacon`/`fetch keepalive` при закрытии вкладки для мгновенного «офлайн» — отвергнуто: выгода — секунды против окна гистерезиса, который и так скроет разрыв; усложняет lifecycle (VII).

## F. Наблюдаемость (FR-009)

- **Decision**: Micrometer: counter `webchat_presence_events_published_total{status}`, distribution-переиспользование `webchat_realtime_push_seconds{event=presence.updated}` (латентность доставки), counter `webchat_presence_hysteresis_suppressed_total`, gauge `webchat_presence_online_users` (атомарный Redis-счётчик `presence:online:count`, поддерживаемый в тех же Lua-переходах, экспорт — периодическое чтение).
- **Rationale**: SC-001/SC-002/SC-008 проверяются на реальных данных; переиспользование таймера 004 даёт латентность presence-кадров без новой трубы.
- **Alternatives considered**: gauge как ZCARD `presence:watch` — отвергнут: содержит и истёкших до чистки (смещение), счётчик переходов точен по построению.

## G. Параметры контракта (фиксация)

| Параметр | Значение | Основание |
|---|---|---|
| TTL регистрации | 90 c | 3× интервал heartbeat — устойчив к 2 потерянным heartbeat'ам |
| Интервал client heartbeat | 30 c (рекомендация контракта) | ~43k RPS на 1M CCU (§Load plan.md) |
| Окно гистерезиса «офлайн» | 45 c (default, конфиг `presence.hysteresis`) | FR-004 |
| Дебаунс «онлайн» | 0 (мгновенно; CAS против эхо) | SC-001 ≤2 c |
| Гарантия обнаружения тишины | ≤ TTL + гистерезис = 135 c | SC-003 |
| Batch снапшота | ≤ 200 userIds | parity с лимитом групп 006 |
| Интервал поллеров | 1 c (внутреннее, не контракт) | достаточен для SC-001/SC-003 |

Все значения — поля `presence.*` в `application.yml`; тест-профиль ужимает TTL/гистерезис до секунд (SC-002/SC-003 исполнимы в CI).
