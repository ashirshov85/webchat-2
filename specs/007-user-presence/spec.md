# Feature Specification: Присутствие пользователей (статус «онлайн»)

**Feature Branch**: `007-user-presence`

**Created**: 2026-10-01

**Status**: Draft

**Input**: User description: "Пользователь видит статус присутствия собеседников: «онлайн» ⟺ есть живое подключение к реалтайм-каналу (хотя бы одно устройство/сессия пользователя). Изменения статуса приходят в реальном времени заинтересованным клиентам (пиры открытых чатов, контакты — границы уточняет clarify), без широковещательного шума. Сигнал устойчив к флапу соединений (реконнекты метро/лифта не дребезжат статусом — дебаунс/гистерезис). Состояние присутствия — только во внешнем хранилище (Redis-ключи с TTL, продлеваемые heartbeat; self-expiry при падении инстанса), инстансы stateless. Правила приватности (кому виден мой статус, режим «невидимки») — решения clarify-раунда. Мультидевайс: онлайн при ≥1 живого соединения."

## Clarifications

### Session 2026-10-01

- Q: Как в v1 отображать присутствие в групповых чатах (список «Чаты» и окно группы)? → A: Вариант A — индикатор только в личных чатах (элемент списка + заголовок 1:1-чата); в группах UI присутствия в v1 нет, доставка событий в аудиторию групповых чатов (FR-003) не меняется.
- Q: Что показывает индикатор присутствия до получения первого снимка статусов (вход/загрузка)? → A: Вариант A — нейтральное состояние «неизвестно» (индикатор не отображается либо нейтрально-серый); отображение «офлайн» до прихода снимка недопустимо.
- Q: Должен ли статус передаваться не только цветом индикатора (дальтоники, скринридеры)? → A: Вариант A — точка + доступная подпись: текстовая метка или aria-метка («онлайн»/«офлайн»/нейтрально), озвучиваемая скринридером; для SPA и виджета единообразно.
- Q: Должен ли индикатор присутствия отображаться в панели «Контакты» (004 US5), помимо списка «Чаты» и заголовка личного чата? → A: Вариант B — да, индикатор отображается и в элементах списка «Контакты» (панель 004 US5); отображение в групповых чатах по-прежнему вне объёма v1.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Индикатор «онлайн» у собеседников с realtime-обновлением (Priority: P1)

Пользователь видит статус присутствия собеседников в элементах списка «Чаты», в заголовке окна открытого чата и в элементах списка «Контакты» (панель 004 US5; решение clarify-раунда от 2026-10-01): «онлайн» — пока у собеседника есть хотя бы одно живое подключение к реалтайм-каналу (любое его устройство/сессия), «офлайн» — когда последнее живое подключение потеряно. Изменения приходят в реальном времени, без перезагрузки: собеседник подключился — индикатор зажёгся; отключился — погас через окно стабилизации (US2). Мультидевайс: пользователь с несколькими устройствами считается онлайн, пока живо хотя бы одно его соединение. Наблюдатель, подключившийся к реалтайм-каналу (вход, переподключение), сразу получает актуальные статусы своей аудитории, а не журнал изменений.

**Why this priority**: Это минимальный жизнеспособный продукт фичи — сам видимый и обновляемый в реальном времени сигнал присутствия; без него анти-флап, самоистечение состояния и приватность не имеют предмета.

**Independent Test**: Проверяется вручную и автотестом: два пользователя открывают общий чат; второй подключается к реалтайм-каналу с любого устройства — у первого индикатор становится «онлайн» без перезагрузки; второй закрывает все свои устройства (или истекает его регистрация) — индикатор гаснет; повторное подключение первого наблюдателя показывает актуальный статус обоих.

**Acceptance Scenarios**:

1. **Given** наблюдатель и собеседник с общим чатом, **When** собеседник устанавливает живое подключение к реалтайм-каналу, **Then** у наблюдателя индикатор собеседника (список «Чаты», заголовок чата, список «Контакты») становится «онлайн» без перезагрузки.
2. **Given** собеседник онлайн, **When** теряется его последнее живое подключение и окно стабилизации (US2) истекает без восстановления, **Then** у наблюдателя индикатор становится «офлайн».
3. **Given** собеседник онлайн на двух устройствах, **When** одно устройство отключается, **Then** индикатор остаётся «онлайн» (мультидевайс: онлайн при ≥1 живого соединения).
4. **Given** наблюдатель подключается (вход, переподключение после разрыва), **When** подписка установлена, **Then** он получает актуальные статусы своей аудитории на текущий момент, а не последовательность прошлых изменений.
5. **Given** одно и то же изменение статуса доставлено наблюдателю повторно (дубль кадра, рефетч после реконнекта), **When** клиент обрабатывает событие, **Then** отображаемое состояние сходится без искажений (идемпотентность).

### User Story 2 - Устойчивость статуса к флапу соединений: дебаунс и гистерезис (Priority: P2)

Короткие обрывы и восстановления связи (метро, лифт, переключение Wi-Fi↔LTE) не дребезжат индикатором: пока разрыв короче окна гистерезиса, наблюдатель не видит смены статуса вообще. Переход «офлайн → онлайн» публикуется оперативно после появления живого подключения (короткий дебаунс от защиты событий-эхо); переход «онлайн → офлайн» откладывается на окно гистерезиса — восстановление хотя бы одного подключения в окне отменяет публикацию. Долгий разрыв даёт ровно одно переключение в «офлайн» и одно возвращение при реконнекте.

**Why this priority**: Ценность индикатора — доверие к нему: мигающий статус хуже отсутствия. Это качественное уточнение сигнала US1, самостоятельно тестируемое сценарным прогоном, поэтому P2.

**Independent Test**: Проверяется автотестом-сценарием «метро»: серия из ≥10 разрывов/восстановлений, каждый короче окна гистерезиса — наблюдатель видит 0 смен индикатора; единичный разрыв длиннее окна — ровно один переход «онлайн → офлайн» и один возврат.

**Acceptance Scenarios**:

1. **Given** собеседник онлайн, **When** его соединение рвётся и восстанавливается в пределах окна гистерезиса (повторно, многократно), **Then** наблюдатель видит 0 смен индикатора за всю серию.
2. **Given** собеседник офлайн, **When** у него появляется живое подключение, **Then** статус «онлайн» публикуется оперативно (в пределах короткого дебаунса, значение — в API-контракте).
3. **Given** собеседник онлайн, **When** его последнее соединение потеряно на время дольше окна гистерезиса, **Then** наблюдатель видит ровно одно переключение в «офлайн» (не раньше истечения окна).
4. **Given** в окне гистерезиса чередуются разные устройства собеседника (одно отключилось, другое подключилось), **Then** статус остаётся «онлайн» без промежуточного «офлайн».

### User Story 3 - Самоистечение присутствия при сбоях: внешнее состояние, stateless-инстансы (Priority: P2)

Состояние присутствия живёт только во внешнем хранилище с автоматическим истечением срока и продлевается heartbeat-ом подключений: падение или рестарт любого инстанса не оставляет пользователя навсегда «онлайн» — регистрация сама истекает, и статус становится «офлайн» без явного события выхода. Инстансы не держат состояние (конституция II): подключения одного пользователя могут обслуживаться разными инстансами одновременно, и все наблюдатели видят один и тот же статус; масштабирование и перекидка подключений между инстансами не искажают сигнал.

**Why this priority**: Отказоустойчивость и корректность при масштабировании — конституционное требование и явное требование фичи; при этом сценарий US1 без него работает в штатном режиме, поэтому P2.

**Independent Test**: Проверяется автотестом «крэш инстанса»: heartbeat прекращается без явного отключения (имитация падения) — статус становится «офлайн» у всех наблюдателей не позднее срока регистрации + окно гистерезиса; одновременно kill/restart инстанса с подключениями других пользователей не искажает их статус (реконнекты поглощаются US2).

**Acceptance Scenarios**:

1. **Given** пользователь онлайн и его регистрации продлеваются heartbeat-ом, **When** heartbeat прекращается (инстанс/клиент умер без явного отключения), **Then** регистрации самоистекают, и статус становится «офлайн» для всех наблюдателей не позднее срока регистрации + окно гистерезиса.
2. **Given** пользователь с подключениями на двух инстансах, **When** один инстанс падает, **Then** его статус остаётся «онлайн» (жива регистрация второго инстанса) и не «дребезжит» за пределами соглашений US2.
3. **Given** рестарт/перекидка инстансов под нагрузкой, **When** подключения мигрируют, **Then** наблюдаемые статусы сходятся к факту («≥1 живой регистрации») без систематических ложных «офлайн».
4. **Given** массовое падение инстанса с последующим штормом реконнектов, **When** большинство пользователей возвращается в пределах окна гистерезиса, **Then** шторм событий присутствия подавлен: наблюдатели видят минимальное число переключений, система не деградирует.

### User Story 4 - Приватность видимости статуса и режим «невидимки» (Priority: P3)

Статус пользователя по умолчанию виден его аудитории видимости: всем, с кем у него есть общий чат (личный или групповой), и всем, у кого он в списке контактов. Пользователь может в любой момент включить режим «невидимки»: для всей аудитории он отображается «офлайн» (неотличимо от настоящего офлайна), при этом сам видит актуальные статусы своей аудитории. Блокировка (004 FR-020) взаимно исключает видимость статусов пары. Политика непроницаема: посторонний (вне аудитории, заблокированная пара) не получает ни событий присутствия, ни статуса через API.

**Why this priority**: Приватность — требование конституции (принцип V) и явная цель фичи, но не блокирует базовую ценность US1–US3, поэтому P3.

**Independent Test**: Проверяется автотестами адресации: пользователь вне аудитории (и заблокированная пара) не получает ни одного события присутствия и получает нейтральный ответ при запросе статуса через API; «невидимка» виден окружающим как «офлайн», сам видит актуальные статусы.

**Acceptance Scenarios**:

1. **Given** пользователь, не входящий в аудиторию видимости собеседника (нет общего чата, собеседника нет в его контактах), **When** собеседник меняет статус, **Then** пользователь не получает события, а запрос статуса через API не раскрывает его.
2. **Given** пользователь включил режим «невидимки», **When** он подключён к реалтайм-каналу, **Then** его аудитория видит его «офлайн» (неотличимо от реального), при этом сам он видит актуальные статусы своей аудитории.
3. **Given** заблокированная пара (004 FR-020), **When** любой из них меняет статус, **Then** второй не видит изменений и не может запросить статус; в общем групповом чате остальные участники статусы друг друга видят.
4. **Given** любой клиент пытается получить статус вне политики (посторонний, заблокированная пара), **When** выполняется запрос, **Then** ответ не раскрывает информацию о присутствии (единая семантика «нет доступа» без различения «офлайн» и «скрыто»).
5. **Given** пользователь онлайн, **When** он выключает «невидимку», **Then** аудитория сразу видит его «онлайн»; **When** включает — видит «офлайн» (режим действует на пользователя целиком, не на устройство).

### Edge Cases

- Устройства пользователя закрываются по одному — статус не меняется, пока живо последнее; закрытие последнего запускает окно гистерезиса, и только затем публикуется «офлайн».
- Реконнект того же устройства создаёт новую регистрацию до истечения старой — дубль регистрации не искажает статус (онлайн остаётся онлайн), осиротевшая регистрация самоистекает.
- Разрыв ровно на границе окна гистерезиса — допускается либо одно переключение «офлайн→онлайн», либо ноль (клиентские часы и порядок доставки не обязаны различать); недопустимо дребезжание (≥2 переключений) на серию.
- Наблюдатель офлайн в момент изменений собеседника — при подключении видит только актуальный снимок; «офлайн→онлайн→офлайн» за время его отсутствия не отображается.
- Первый снимок ещё не получен (вход, загрузка списка чатов, задержка/сбой рефетча) — индикатор нейтрален («неизвестно»); ложный «офлайн» до данных не отображается; по приходе снимка состояние сходится к актуальному.
- Logout на одном устройстве при живом втором — статус остаётся «онлайн»; logout на последнем — «офлайн» без ожидания полного окна (явное отключение обрабатывается сразу).
- Вкладка/устройство «зависли»: соединение формально живо, heartbeat не продлевается клиентом — регистрация истекает по сроку, статус корректен без явного разрыва.
- Смена статуса участника большой группы (до 200 участников, 006) — каждый наблюдатель получает одно событие на пользователя (не копию на каждый общий чат); суммарный фанаут остаётся в пределах аудитории видимости.
- Массовые реконнекты после падения инстанса — гистерезис агрегирует серию: большинство вернувшихся не порождает событий вовсе; публикации ограничены наблюдаемыми переключениями.
- Событие присутствия доставлено до применения снимка при реконнекте наблюдателя (гонка кадр/рефетч) — итоговое состояние клиента сходится к серверному (идемпотентность, сведение к последнему значению).
- Пользователь удаляет чат / его исключают из группы (004/006) — он покидает аудиторию видимости по этому основанию; событие о статусе ему больше не доставляется (сходимость в пределах короткого окна, как 006 FR-010).
- «Невидимка» у пользователя с несколькими устройствами — режим действует на пользователя целиком, а не на устройство; расхождение «у себя вижу онлайн, другие видят офлайн» не является ошибкой.
- Включение «невидимки» при живых подключениях — аудитория видит «офлайн»; события последующих его подключений/отключений аудитории не публикуются, пока режим включён (статус для окружающих «заморожен» как офлайн).
- Включение/выключение «невидимки» не должно дребезжать чужие индикаторы сверх соглашений US2: переключение режима отражается не более чем одной сменой отображаемого статуса.
- Добавление пользователя в контакты (004) открывает видимость его статуса добавившему — аудитория вычисляется по текущему состоянию чатов/контактов и сходится без перезапуска клиента.
- Контакт в списке «Контакты», недоступный по политике приватности (заблокированная пара, FR-007), отображается с нейтральным индикатором («неизвестно») — не «онлайн»/«офлайн»; после разблокировки состояние сходится к актуальному.

## Requirements *(mandatory)*

### Functional Requirements

Модель и сигнал присутствия:

- **FR-001**: Система MUST вычислять статус присутствия пользователя как «онлайн» тогда и только тогда, когда у пользователя есть хотя бы одно живое подключение к реалтайм-каналу (мультидевайс: любое устройство/сессия пользователя); при исчезновении последнего живого подключения статус MUST переходить в «офлайн». Присутствие — только текущее состояние: история изменений статуса MUST NOT накапливаться как пользовательская сущность и не показывается.
- **FR-002**: Живость подключения MUST определяться регистрацией с ограниченным сроком, регулярно продлеваемой heartbeat-ом клиента; регистрация с истёкшим сроком MUST автоматически исключаться из расчёта статуса (самоистечение — без необходимости явного события отключения). Явное закрытие подключения (выход из аккаунта, закрытие по команде клиента) MUST исключать регистрацию незамедлительно. Числовые параметры (интервал heartbeat, срок регистрации) фиксируются в API-контракте.
- **FR-003**: Изменения статуса MUST доставляться в реальном времени заинтересованным клиентам событиями присутствия по существующему реалтайм-каналу пользователя (004 №18) — без широковещательной рассылки: событие о пользователе X получают только клиенты его аудитории видимости — пользователей, у которых есть общий чат с X (личный или групповой) или X есть в их списке контактов (решение specify-раунда, Q1=A). Клиент, подключающийся после изменений, MUST получать актуальный статус (снимок) на момент подписки, а не журнал изменений.

Устойчивость и анти-флап:

- **FR-004**: Сигнал присутствия MUST быть устойчив к флапу соединений: переход «офлайн → онлайн» публикуется оперативно после появления живого подключения (короткий дебаунс); переход «онлайн → офлайн» публикуется с гистерезисом — отложено на фиксированное окно (значение по умолчанию — 45 секунд, фиксируется в API-контракте), и восстановление хотя бы одного живого подключения в окно отменяет публикацию (наблюдатели не видят смены вовсе). Для внешнего наблюдателя серия разрывов/восстановлений короче окна MUST давать ноль наблюдаемых переключений; разрыв длиннее окна — ровно одно переключение. Окно гистерезиса не изменяет семантику FR-001 — только задержку публикации.

Состояние и масштабирование:

- **FR-005**: Состояние присутствия (регистрации подключений и производный статус) MUST храниться только во внешнем хранилище с автоматическим истечением срока (конституция II: инстансы stateless): падение или рестарт любого инстанса MUST оставлять систему в корректном состоянии — регистрации умершего инстанса самоистекают, и статус становится «офлайн» не позднее срока регистрации + окно гистерезиса; подключения одного пользователя MAY одновременно обслуживаться разными инстансами без расщепления статуса (единый вид для всех наблюдателей). Выбор конкретной технологии хранения — решение plan-раунда.

Отображение и контракт:

- **FR-006**: Клиенты (standalone SPA и встраиваемый виджет — единый публичный API, конституция IV) MUST отображать статус присутствия собеседника индикатором в элементе списка «Чаты» и в заголовке окна чата — только для личных (1:1) чатов, — а также в элементах списка «Контакты» панели слева (004 US5; решение clarify-раунда от 2026-10-01, вариант B); в групповых чатах отображение присутствия в v1 отсутствует (решение clarify-раунда от 2026-10-01), при этом аудитория доставки событий (FR-003) не сужается. Актуальный статус MUST быть доступен и через запрос API (описан в OpenAPI-контракте) — без различения личных и групповых оснований видимости. Повторно доставленное событие присутствия MUST обрабатываться идемпотентно — состояние клиента сходится без искажений. До получения первого снимка статусов индикатор MUST отображаться нейтрально («неизвестно»: скрыт или нейтральная метка), а не «офлайн» (решение clarify-раунда от 2026-10-01); при задержке/недоступности снимка нейтральное состояние сохраняется до получения данных. Статус MUST передаваться не только цветом: индикатор сопровождается доступной подписью — текстовой меткой или aria-меткой («онлайн»/«офлайн»/нейтрально), озвучиваемой скринридером (решение clarify-раунда от 2026-10-01).

Приватность:

- **FR-007**: Политика приватности присутствия (решение specify-раунда, Q2=A): по умолчанию статус пользователя виден всей его аудитории видимости (FR-003); пользователь MAY в любой момент включать и выключивать режим «невидимки», действующий на пользователя целиком (не на устройство): при включённом режиме его статус для аудитории отображается «офлайн», неотличимо от реального (события его подключений/отключений аудитории не публикуются), при этом сам пользователь видит актуальные статусы своей аудитории без ограничений; блокировка (004 FR-020) взаимно исключает видимость статусов пары. События присутствия и статус через API MUST предоставляться только аудитории, разрешённой политикой (с учётом «невидимки» и блокировок); для всех остальных ответ MUST NOT раскрывать информацию о присутствии (единая семантика «нет доступа», не различающая «офлайн» и «скрыто»). Настройка «невидимки» MUST сохраняться между сессиями пользователя.

Контракт и наблюдаемость:

- **FR-008**: Все операции и события присутствия MUST быть описаны в публичном OpenAPI-контракте — источнике истины; изменения публичных интерфейсов MUST сохранять обратную совместимость (конституция IV).
- **FR-009**: Система MUST предоставлять наблюдаемость фичи: текущее число онлайн-пользователей, количество опубликованных событий присутствия и латентность их доставки, количество переключений, подавленных гистерезисом, — по этим сигналам выполнение Success Criteria проверяется в эксплуатации.

### Key Entities *(include if feature involves data)*

- **Присутствие (presence-статус)**: текущее (не историческое) производное состояние пользователя — «онлайн»/«офлайн»; вычисляется из живых регистраций подключений; хранится только во внешнем хранилище с автоматическим истечением.
- **Регистрация подключения**: запись об одном живом подключении устройства/сессии пользователя к реалтайм-каналу; имеет ограниченный срок, продлеваемый heartbeat-ом; самоистекает без продления; исключается при явном закрытии.
- **Событие присутствия**: realtime-событие «пользователь X — онлайн/офлайн», адресованное только аудитории видимости X; идемпотентно обрабатывается клиентами; в истории чатов не сохраняется.
- **Аудитория видимости**: множество пользователей, которым разрешено видеть статус данного пользователя: имеющие с ним общий чат (личный или групповой) или добавившие его в свои контакты; сужается блокировками (взаимно) и не распространяется на «невидимку».

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 95% опубликованных изменений статуса видимы заинтересованным онлайн-клиентам не позднее 2 секунд.
- **SC-002**: Сценарий «метро» (автоматизированный тест): серия из ≥10 разрывов/восстановлений, каждый короче окна гистерезиса, — наблюдатель видит 0 смен индикатора; единичный разрыв длиннее окна — ровно 1 переход в «офлайн» и 1 возврат при реконнекте.
- **SC-003**: При прекращении heartbeat без явного отключения (имитация падения инстанса) статус становится «офлайн» для всех наблюдателей не позднее чем за «срок регистрации + окно гистерезиса» — 100% случаев в автоматизированном тесте.
- **SC-004**: 100% событий присутствия доставляются только внутри аудитории видимости: посторонние клиенты не получают ни одного события и не могут раскрыть статус через API — подтверждается автоматизированными тестами адресации и приватности.
- **SC-005**: Мультидевайс: при закрытии устройств по одному статус остаётся «онлайн», пока живо ≥1 подключение, и меняется на «офлайн» только после потери последнего — 100% в автоматизированном тесте.
- **SC-006**: Подключившийся/переподключившийся клиент видит актуальные статусы своей аудитории не позднее 2 секунд в 95% случаев.
- **SC-007**: Присутствие укладывается в конституционные бюджеты (принцип II): расчёт нагрузки (аудитория × события, фанаут при массовых реконнектах) приводится в plan.md; нагрузочный smoke-прогон с присутствием не показывает деградации доставки сообщений (полномасштабная валидация пиков — платформенная фича 016).
- **SC-008**: Метрики наблюдаемости (FR-009) доступны в эксплуатации — по ним SC-001–SC-006 проверяются на реальных данных.

## Assumptions

- Механизмы фич 002–006 доступны и переиспользуются без изменений: аутентификация и сессии, реалтайм-канал событий пользователя (004 №18) с реконнект-циклом 005 (стабильный reconnect — предусловие анти-флапа), личные и групповые чаты, контакты и блокировки, единый список «Чаты».
- Присутствие не вводит новых каналов доставки: события присутствия — новый тип событий в существующем реалтайм-канале пользователя.
- Модель статуса бинарная («онлайн»/«офлайн»); «был(а) недавно», время последнего визита, индикаторы набора текста — вне объёма фичи (индикаторы набора — вне scope по ROADMAP; YAGNI).
- Числовые параметры (интервал heartbeat, срок регистрации, дебаунс «онлайн», окно гистерезиса 45 с) — разумные дефолты; фиксируются в API-контракте, изменение — через правку спецификации.
- Аудитория видимости и режим «невидимки» зафиксированы решениями specify-раунда от 2026-10-01: Q1=A (аудитория — общий чат ∪ «есть в контактах наблюдающего»), Q2=A («невидимка» в v1: скрывает от всех, сам пользователь чужие статусы видит; блокировка взаимно скрывает статусы пары).
- Гранулярные настройки видимости (списки разрешения/запрета, видимость «только контактам») — вне объёма v1 (YAGNI); могут быть добавлены отдельной фичей.
- Отображение присутствия в групповых чатах (индикаторы участников, сводка «N онлайн») — вне объёма v1 (решение clarify-раунда от 2026-10-01, вариант A): аудитория доставки событий при этом не сужается; групповой UI может быть добавлен отдельной фичей на готовой доставке.
- Вне объёма: push-уведомления вне приложения об изменениях статуса, история присутствия за период, производные статусы («на созвоне» — фича 009).
- Выбор конкретного внешнего хранилища и механики TTL/heartbeat (упомянутые в описании Redis-ключи) — решение plan-раунда в рамках конституции II; спецификация технологию не навязывает.
- Полномасштабные нагрузочные прогоны пиковых бюджетов (1M CCU) — платформенная задача фичи 016; в рамках 007 — расчёт в plan.md и smoke-проверки.
- «Понятная ошибка» и ответы API — машиночитаемые коды проблем RFC 9457 из таблицы кодов API-контракта фичи; перечень фиксируется при проектировании плана (конвенция 004/006).
