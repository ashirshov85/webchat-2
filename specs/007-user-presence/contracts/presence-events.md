# Presence Realtime Events Contract (007)

**Date**: 2026-10-01 | Канал: существующий SSE №18 `GET /api/v1/users/me/events` (004 realtime-channel.md) | Спека: FR-003, FR-004, FR-006

Новых каналов доставки нет (Assumptions): присутствие — новые типы кадров в существующем per-user потоке. Семантика канала неизменна: at-most-once, строго server→client, один поток на устройство/сессию, Bearer-гейт.

## 1. Opening-фрейм `connected`

Сразу после `retry: 3000` сервер отправляет:

```text
event: connected
data: {"connectionId":"7c9e6679-7425-40de-944b-e07fc1f90ae7"}
```

- `connectionId` (UUID) — идентификатор регистрации подключения; используется клиентом в heartbeat №37 (presence-api.md §2).
- Живёт вместе с поток­ом: реконнект выдаёт новый connectionId; старая регистрация самоистекает по TTL (edge «дубль регистрации»).
- Обратная совместимость: клиенты, не знающие `connected`, игнорируют неизвестный `event:` (контракт 004 §3) — кадр безопасен для всех действующих потребителей.

## 2. Событие `presence.updated`

Публикуется в `rt:user:{наблюдатель}` каждому члену аудитории видимости субъекта (data-model §1.4: общий чат ∪ «субъект в контактах наблюдающего» − блок-пары − сам субъект); «невидимка» замораживает исходящие события субъекта (FR-007).

```text
event: presence.updated
data: {"userId":"<subject-uuid>","status":"online","rev":42}
```

| Поле | Тип | Контракт |
|---|---|---|
| `userId` | UUID | субъект смены (не наблюдатель) |
| `status` | `online` \| `offline` | опубликованное значение (гистерезис-задержанное для `offline`, немедленное для `online`) |
| `rev` | int64 | монотонная ревизия; строгое возрастание per-user |

Правила обработки (FR-006 идемпотентность, edge «гонка кадр/рефетч»):
- применять только `rev` строго больше последнего применённого для данного userId (дубль кадра, задержавшийся кадр, устаревший снапшок №36 — no-op);
- событие одного субъекта доставляется каждому наблюдателю один раз на переход, независимо от числа общих чатов (edge «до 200 участников»: один фанаут на пользователя);
- неизвестные `status`/лишние поля — игнорируются по общим правилам канала.

## 3. Параметры анти-флапа (FR-004, research §G/B1)

| Параметр | Значение | Наблюдаемое следствие |
|---|---|---|
| Окно гистерезиса `offline` | **45 c** (default; `presence.hysteresis`) | серия разрывов < 45 c → 0 событий; разрыв > окна → ровно одно `offline` |
| Дебаунс `online` | немедленно (CAS против эхо) | «онлайн» видим ≤ 2 c (SC-001) |
| Отмена публикации | восстановление ≥1 регистрации в окне | событие не отправляется вовсе; метрика suppressed (FR-009) |
| Logout | обход окна (per-session) | немедленное `offline` без гистерезиса — только при потере последней регистрации (002: logout отзывает одну сессию; edge «мультидевайс-logout») |

## 4. Снимок при (re)connect (FR-003, clarify 2026-10-01)

Сервер неpush'ит снапшок при открытии потока: клиент запрашивает №36 (presence-api.md §1) для отображаемых поверхностей в существующем цикле 005 `on SSE (re)open → sync → render`. Полный снимок аудитории при подключении не доставляется (бюджеты II); сходимость события/снапшота — по `rev` (§2).

## 5. Наблюдаемость (FR-009)

Кадры `presence.updated` проходят существующий пайплайн метрик: `webchat_realtime_push_seconds{event=presence.updated}` (латентность publish/dispatch — SC-001), `webchat_presence_events_published_total{status}`, `webchat_presence_hysteresis_suppressed_total`, gauge `webchat_presence_online_users` (SC-008).
