# Quickstart: Личный диалог в реальном времени с exactly-once доставкой

**Feature**: 004-direct-messaging-core | **Date**: 2026-09-20

Руководство по end-to-end проверке фичи вручную и автотестами. Ссылки на детали:
[контракт API](./contracts/api-contract.md), [реалтайм-канал](./contracts/realtime-channel.md),
[модель данных](./data-model.md), [решения](./research.md).

## 1. Предпосылки

- JDK 21, Node 24 + pnpm, Docker (Testcontainers и локальная инфраструктура).
- Клон репозитория, ветка `004-direct-messaging-core`.
- Два завершённых аккаунта (фича 002): `alice@example.com`/`alice` и `bob@example.com`/`bob`
  (создать через `/register` → Mailpit → `/set-password`, [002 quickstart](../../002-user-registration/quickstart.md)).

## 2. Локальная инфраструктура и запуск

```bash
docker compose -f deploy/local/docker-compose.yml up -d   # PostgreSQL 17 :5432, Redis 7 :6379, Mailpit :8025
./gradlew bootRun                                          # workdir backend/ — Flyway применяет V10–V11
pnpm --dir frontend dev                                    # SPA :5173, /api → :8080
```

Переменные окружения — как в 002 (`SPRING_DATASOURCE_*`, `SPRING_DATA_REDIS_*`, `AUTH_JWT_*`,
`APP_PUBLIC_BASE_URL`). Новые настройки: `chats.message.max-length=4096`,
`chats.message.page-size=50`, `chats.rate-limit.messages-per-minute=30`,
`chats.realtime.heartbeat=15s` (значения по умолчанию совпадают с контрактом).

Далее: логины двух пользователей (два браузера / приватное окно) → мессенджер на `/`.
HTTP-примеры ниже — с `Authorization: Bearer <accessToken>` каждого из них.

## 3. Сценарии проверки

### 3.1 Обмен в реальном времени и статусы (US1) — SC-001, SC-005

1. Bob открывает диалог (панель «Контакты» → поиск `alice@example.com` → добавить → клик).
2. Alice отправляет «Привет»: у неё сразу «отправляется», после `201` — ✓ (доставлено).
3. У Bob (онлайн) сообщение появляется без обновления страницы ≤ 2 с (SSE `message.created`).
4. Пустой текст/пробелы и 4097 символов → `400 text_blank`/`text_too_long`, в чате ничего нет;
   ровно 4096 (после trim) — проходит (edge).
5. Третий пользователь Carol: `GET/POST /chats/{chatId}…` чужого диалога → `403 not_participant`
   на каждом ресурсе (FR-002).

### 3.2 Exactly-once и порядок (US2) — SC-002, SC-003

1. Двойной клик «отправить» / повторный `POST /chats/{id}/messages` с тем же `clientMessageId`
   → второй ответ `200` с той же записью (`id`, `seq`); в истории один экземпляр.
2. Автотест `MessagingDeliveryIT`: параллельные ретраи одного id, обрывы (повтор POST после
   недошедшего ответа), порядок `seq` у обоих участников, между перезагрузками.
3. Bob офлайн → Alice пишет N сообщений → Bob входит, открывает диалог: всё на месте, без
   дублей; `GET /chats/{id}/messages` обеими сторонами — одна последовательность.
4. Alice пишет со второго устройства (параллельная сессия): исходящее появляется там по
   `message.created` в её собственный поток (US2-6).
5. Закрыть приложение до подтверждения (перезагрузить вкладку в момент «отправляется») →
   после входа сообщение автоматически доотправляется тем же id — один экземпляр (outbox).

### 3.3 История и пагинация (US3) — SC-004

1. Чат с 120 сообщениями: открытие — последние 50; прокрутка вверх подгружает по 50
   (`before=<seq>`, `nextBefore`), до начала.
2. Запрос за началом истории → `200 {messages: []}` без `nextBefore` (граница).
3. Повторный вход → порядок идентичен прежнему; все серверные сообщения — ✓.
4. Пустой диалог → корректное пустое состояние.

### 3.4 Прочтения и двойные галочки (US4) — SC-007

1. Отправка → у Alice ✓; Bob открывает диалог (сообщение отображено) → у Alice ✓✓ ≤ 2 с
   (`chat.read`), без перезагрузки.
2. Пока Bob не открывал диалог — остаётся ✓.
3. Bob перезаходит и листает историю → отмечается прочитанным (включая подгруженные страницы).
4. Повторные `POST /read` с меньшим/равным `upToSeq` → `204`, статус не откатывается
   (монотонность/идемпотентность — `ReadReceiptsIT`).

### 3.5 Панель «Чаты»/«Контакты», контакты, удаление (US5)

1. Список «Чаты»: сортировка по последнему сообщению (исходящее тоже поднимает чат — Q40),
   чаты без сообщений ниже; бейдж непрочитанных, «99+» при >99; сброс по прочтению.
2. Переключение «Чаты» ↔ «Контакты»; сортировка контактов по логину/email (FR-015).
3. Поиск: точный `ALICE@EXAMPLE.COM` находит (регистронезависимо); частичный/несуществующий —
   пусто без ошибок; `@`-правило (email vs username).
4. Повторное `POST /contacts` того же пользователя → `200`, дубля в списке нет.
5. Удаление контакта → чат и история сохраняются, переписка продолжается (FR-017).
6. `DELETE /chats/{id}` у Alice: чат исчез у Alice (включая её локальные «отправляется»),
   у Bob сохранён; новое сообщение от Bob → чат снова у Alice **без** старой истории (FR-021).
7. Незнакомец Carol пишет Bob → чат появляется у Bob автоматически, ответ без добавления
   контакта (FR-019).
8. Себя: `POST /contacts {self}` и `POST /chats/ensure {self}` → `422 self_forbidden`.

### 3.6 Контрактный клиент и реалтайм-канал (US6)

1. `curl -N -H "Authorization: Bearer …" -H "Accept: text/event-stream"
   http://localhost:8080/api/v1/users/me/events` → кадры `retry:`, события §2–3
   [realtime-channel.md](./contracts/realtime-channel.md), heartbeat `:ka` каждые 15 с.
2. Скрипт по контракту (без внутренних интерфейсов): ensure → подписка → отправка → приём
   кадра `message.created` (схема совпадает) → повторная отправка того же id → нет дубля.
3. Конвейер контракта: `vacuum lint` → `pnpm --dir frontend generate:api` без drift →
   `oasdiff` без breaking (additive 0.4.0).

### 3.7 Блокировка (FR-020) — `BlockingIT` + вручную

1. Alice блокирует Bob (`PUT /users/{bob}/block`): у Alice метка «заблокирован» на чате;
   у Bob чат без пометок.
2. Отправка Bob → Alice: `403 you_are_blocked` (Bob явно уведомлён); Alice → Bob:
   `403 chat_blocked_by_you`; записей нет.
3. История обоим доступна; просмотр Alice → статусы Bob замирают (✓ не становится ✓✓);
   бейдж Alice не растёт/не сбрасывается (Q).
4. Повторный `PUT` и `DELETE` без блока → `204` (идемпотентность, edge).
5. Разблокировка → отправка/прочтения/бейдж работают; история цела.
6. Контакты независимы: контакт Alice→Bob переживает блок; Bob может добавить Alice (Q).
7. Блокировка при открытых диалогах/активных SSE-подписках обоих (Edge): в поток Bob события
   прочтений не приходят, неявная доставка исключена — состояние обоих сходится к заблокированному.

### 3.8 Флуд-лимит и клиентские ретраи (FR-011/FR-012)

1. 31-е сообщение за минуту → `429 flood_limit` + `Retry-After`; записи в БД нет.
2. SPA: сообщение остаётся «отправляется» с индикацией отсчёта; после окна — автоповтор тем же
   id → один экземпляр; 30/мин — равномерное наполнение бакета (допустим всплеск ≤30).
3. Отклонённая навсегда отправка (блокировка получателя после начала ретрая) → «не отправлено»
   + ошибка; ручной повтор и локальное удаление доступны, автоповторов нет (Q).

## 4. Автотесты и наблюдаемость

- Backend: `./gradlew check` (workdir `backend/`) — IT из [research.md §13](./research.md)
  (доставка/порядок, история, прочтения, блокировки, контакты, удаление, флуд, SSE, membership).
- Frontend: `pnpm --dir frontend test` — outbox/галочки/панель/SSE-ридер.
- Метрики (SC-008) на `http://localhost:8080/actuator/prometheus`:
  `webchat_message_ack_seconds`, `webchat_realtime_push_seconds`, `webchat_message_dedup_total`,
  `webchat_send_rejected_total{reason=…}` — растут в сценариях 3.2/3.7/3.8; warn-логи
  отклонённых отправок — в JSON-выводе backend (без текста сообщений).
- Нагрузочный smoke (SC-001/005/008): `docker run --rm -i grafana/k6 run - < load/k6/messaging.smoke.js`
  — профиль: пары VU, отправка+подтверждение, SSE-приём; критерий: p95 ≤ 2 с, флуд-ветка —
  только `429`, без 5xx.
