# Contract: Реалтайм-канал SSE ( часть публичного OpenAPI)

**Feature**: 004-direct-messaging-core | **Источник истины**: `contracts/openapi.yaml`
(операция №18 + `components.schemas.MessageCreatedEvent` / `ChatReadEvent`)

Реалтайм-канал — часть публичного API (FR-022, US6): любой контрактный клиент (SPA, виджет,
сторонний) подключается к одному потоку событий пользователя и работает по тем же схемам,
что и REST. Решения и обоснование — [research.md §1, §2, §9](../research.md).

## 1. Подключение

- `GET /api/v1/users/me/events`, заголовки `Authorization: Bearer <accessToken>` +
  `Accept: text/event-stream`. Ответ: `200`, `Content-Type: text/event-stream`,
  `X-Accel-Buffering: no`.
- Аутентификация — тем же Bearer-токеном, что и REST (5-минутный access JWT). Нативный
  `EventSource` не применяется (не умеет заголовки): клиент читает поток `fetch` +
  `ReadableStream` в своём API-слое с единым авто-refresh (токен в URL запрещён — конституция V).
- Поток **на пользователя**, а не на чат: мультиплексирует события всех диалогов; каждое
  устройство/сессия открывает свой поток (US2-6). Канал строго server→client — отправка
  сообщений выполняется REST-операцией №16 (подтверждение записи = HTTP-ответ).
- Живучесть: сервер шлёт SSE-поле `retry: 3000` в первом кадре и heartbeat-комментарий
  `:ka` каждые 15 с (конфиг `chats.realtime.heartbeat`).

## 2. Фрейминг (SSE, текст по спецификации WHATWG)

```text
retry: 3000

event: message.created
data: {"chatId":"7dc5…","message":{"id":"0b0f…","chatId":"7dc5…","senderId":"9a2c…","text":"Привет","seq":128,"createdAt":"2026-09-20T12:00:00.123Z"}}

event: chat.read
data: {"chatId":"7dc5…","readUpToSeq":128,"byUserId":"9a2c…"}

:ka
```

`data` — JSON одной строкой (одна `data:`-строка на кадр; без переносов внутри), кодировка UTF-8.
Неизвестные клиенту `event:`-типы обязаны игнорироваться (прямая совместимость, US6-3).

## 3. События

### 3.1 `message.created`

Новое сообщение записано на сервере (FR-007). Публикуется **обоим** участникам: получателю —
для отображения, отправителю — для остальных его устройств/сессий (сходимость US2-6). Клиент
дедуплицирует по `message.id` (идемпотентный рендер — at-most-once канал + exactly-once хранение).

| Поле | Тип | Комментарий |
|---|---|---|
| `chatId` | uuid | диалог события |
| `message` | `Message` | та же схема, что в №16/№15 (`id, chatId, senderId, text, seq, createdAt`) |

Свои исходящие с другого устройства клиент рендерит сразу со статусом «доставлено» (сервер
подтвердил запись до публикации).

### 3.2 `chat.read`

Собеседник просмотрел сообщения диалога до `readUpToSeq` включительно (FR-010). Отправитель
помечает свои исходящие `seq ≤ readUpToSeq` двойной галочкой (монотонно — событие приходит только
при продвижении водяного знака; повторные/меньшие значения не публикуются, US4-5).

| Поле | Тип | Комментарий |
|---|---|---|
| `chatId` | uuid | диалог |
| `readUpToSeq` | int64 | новый водяной знак читавшего |
| `byUserId` | uuid | кто прочитал |

Подавление при блокировке (FR-020): пока блок действует, событие **не публикуется** в канал
блокирующего (просмотр истории блокирующим не двигает статусы) и не публикуется в канал
заблокированного (активность блокирующего не раскрывается). После разблокировки — обычное
поведение.

## 4. Переподключение и сходимость (FR-009)

- Канал — at-most-once: кадр, пропущенный при обрыве, не воспроизводится. Клиент при каждом
  (пере)подключении — после бэкоффа (1с…30с, джиттер; старт по `retry:`) — выполняет рефетч
  `GET /chats` и `GET /chats/{id}/messages` открытого чата; пропущенные события восполняются,
  порядок/дубли исключены серверным `seq` и дедупом по `id` (SC-002/003).
- Источник истины — REST/PG; канал — оптимизация латентности (SC-005/007 ≤ 2 с).
- Курсорный delta-sync при переподключении («догони с seq N») — фича 005 (ROADMAP); до неё
  рефетч достаточен и безопасен.

## 5. Отражение в openapi.yaml

- `paths./api/v1/users/me/events.get`: operationId `streamUserEvents`, tag `realtime`,
  Bearer; ответ `200` `text/event-stream` с `description`, излагающим фрейминг §2 и события §3.
- `components.schemas.MessageCreatedEvent` / `ChatReadEvent` — payloads §3 (те же имена полей);
  примеры кадров — в `examples` операций.
- Изменение состава событий/полей — только additive (конституция IV: breaking changes — через
  версионирование; unknown-event-ignoring §2 — механизм прямой совместимости).
