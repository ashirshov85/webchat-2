# Research: Личный диалог в реальном времени с exactly-once доставкой

**Feature**: 004-direct-messaging-core | **Date**: 2026-09-20

Разрешение всех открытых вопросов Technical Context фичи 004. Контекст: стек и конвейер
зафиксированы 001–003 (Kotlin 2.2 + Spring Boot 3.5 / Gradle KTS, React 19 + TS strict,
OpenAPI 3.1 + codegen + drift/breaking CI, PG 17 + Flyway + Spring JDBC, Redis 7 + Bucket4j +
Lettuce, stateless-поды в K8s). Существуют аутентификация (Bearer access JWT ES256 5 мин +
refresh-ротация) и зарегистрированные пользователи. Реалтайм-транспорта и сущностей
диалогов/сообщений в проекте нет — вводятся этой фичей.

---

## 1. Реалтайм-транспорт: SSE (Server-Sent Events), поток событий пользователя

**Решение**:
- Канал реального времени — **один SSE-поток на пользователя** `GET /api/v1/users/me/events`
  (`text/event-stream`), а не подписка на отдельный чат. Поток мультиплексирует события всех
  диалогов пользователя: `message.created` (новое сообщение в любом чате — и исходящее с других
  устройств того же пользователя), `chat.read` (собеседник прочитал до `readUpToSeq`) и
  серверный heartbeat (комментарий-keepalive каждые 15 с).
- Реализация: Spring MVC `SseEmitter` на Servlet-async (Tomcat NIO) — без реактивного стека и
  без новых зависимостей; `spring-boot-starter-web` уже в classpath.
- Направление: канал строго server→client. Отправка сообщений — только REST POST с
  идемпотентным ключом (FR-004): подтверждение записи — HTTP-ответ, а не событие канала.

**Обоснование**: поток событий односторонний по требованиям (отправка идёт через REST ради
подтверждения записи и идемпотентности; duplex не нужен). SSE — обычный HTTP/1.1 chunked-ответ:
описуем в OpenAPI как GET с typed-схемами событий (FR-022, US6), проходит через прокси/ingress
без апгрейд-инфраструктуры, имеет встроенную семантику `retry:`/автопереподключения в клиентах.
Поток на пользователя (а не на чат) закрывает одним соединением: новые сообщения всех чатов,
прочтения, обновление списка «Чаты» (бейджи/позиции), мультидевайсность (US2-6 — каждое
устройство открывает свой поток) и будущие групповые чаты (006) без смены протокола.

**Альтернативы отклонены**: **WebSocket** — двунаправленность не нужна (отправка — REST ради
exactly-once-подтверждения); кадры WS не выражаются в OpenAPI (потребовался бы AsyncAPI или
самописная документация — нарушен API-First-источник-истины FR-022); требует upgrade-конфигурации
nginx/ingress и стопки spring-boot-starter-websocket. **STOMP поверх WS** — брокерные
подписки/ACK-и не нужны при потоке на пользователя; дополнительная зависимость и семантика —
YAGNI. **Поллинг/long-polling** — нарушает SC-005 (≤ 2 с) и плодит нагрузку списком.
**gRPC-стриминг** — не встраивается в браузерный SPA без grpc-web-прокси; вне контракта OpenAPI.

## 2. Фанаут между инстансами: Redis Pub/Sub, канал на пользователя

**Решение**:
- После коммита транзакции записи сообщения/прочтения бэкенд публикует компактный JSON-конверт
  в Redis Pub/Sub-канал **`rt:user:{userId}`** каждого адресата (получатель — для отображения;
  отправитель — для остальных его устройств/сессий, US2-6).
- Каждый инстанс держит Lettuce-подписки на каналы только тех пользователей, у которых на нём
  есть живые SSE-соединения (динамическая подписка при подключении, отписка при закрытии
  последнего соединения пользователя). Локальный диспетчер рассыпает конверт по `SseEmitter`-ам.
- Доставка Pub/Sub — at-most-once: событие, пропущенное обрывом SSE-соединения, **не
  воспроизводится**; клиент при (пере)подключении выполняет рефетч открытого чата (сообщения
  `?before=`) и списка чатов — состояние сходится к серверному (FR-009). Курсорный delta-sync
  («догони с seq N») — фича 005 (ROADMAP), здесь не вводится.

**Обоснование**: источник истины — PostgreSQL; канал — только уведомление «что-то изменилось +
минимальный payload для горячего рендера». At-most-once на канале + рефетч на реконнекте —
проще и дешевле персистентных очередей, при этом пользовательские гарантии (SC-002/003: без
дублей, порядок, сходимость) обеспечиваются серверным `seq` и идемпотентным рендером по
`message.id` (клиент дедуплицирует по id). Инстансы остаются stateless (конституция II):
реестр emitters — транспортное состояние соединения, не бизнес-состояние; любой инстанс serveит
любое соединение. Расчёт нагрузки — §12.

**Альтернативы отклонены**: **Kafka** — вводить брокер ради fan-out уведомлений при
неперсистентной семантике — операционный вес без потребности (VII); история и так в PG.
**Redis Streams** — персистентность/группы потребителей не нужны (клиент всё равно рефетчит по
серверному курсору; durable-канал — 005, если рефетч окажется дорогим).**Только in-memory
(Spring ApplicationEvent)** — доставка между инстансами невозможна (нарушение FR-007 при
масштабировании). **PostgreSQL LISTEN/NOTIFY** — одно соединение на нотификацию, хрупко при
пулах; pgbouncer-френдли семантики хуже Redis-каналов.

## 3. Порядок и дедупликация: клиентский UUID = PK, серверный `seq` bigserial

**Решение**:
- `messages.id` — **UUID, сгенерированный клиентом** (Key Entities: «уникальный ID генерируется
  клиентом»); это и публичный идентификатор сообщения, и ключ дедупликации: PK.
- `messages.seq` — серверный **`bigserial`** (на 004 — глобальная IDENTITY одного узла),
  назначается в INSERT. Порядок в чате = `ORDER BY seq`; одинаков для обоих участников
  и стабилен между загрузками (FR-006, US2-3), т.к. назначается один раз на сервере и
  не меняется.
- **Область монотонности — чат, а не глобус**: `seq` нигде не сравнивается между разными
  чатами (курсор `before`, водяные знаки `last_read_seq`/`deleted_up_to_seq`, `chats.last_seq`,
  непрочитанные — всё внутри одного чата), уникальность ограничена составным
  `UNIQUE (chat_id, seq)`; глобальный `UNIQUE (seq)` не вводится. Поэтому масштабный путь —
  ко-локация по `chat_id` (шард/партиция = чат целиком) с локальной аллокацией `seq`:
  пер-чатная монотонность сохраняется при любом шардинге; одноузловая IDENTITY — лишь
  простейший аллокатор этого контракта (лестница аллокации и watermark-миграция — §12).
- Отправка (в одной транзакции PG): membership → быстрый дедуп-lookup по `id` (fast-path: запись
  уже есть → вернуть её с `200`, независимо от блокировок/лимитов — ретрай завершается
  сходимостью) → проверка блокировки → флуд-бакет → валидация текста →
  `INSERT … ON CONFLICT (id) DO NOTHING RETURNING`; пустой результат → `SELECT` по id и `200`
  (дубликат-ретрай); расхождение `chat_id`/`sender_id` существующей записи с запросом → `409`
  (коллизия/чужой id). Новая запись → `201` + после коммита публикация событий (§2).
- Пагинация истории: курсор `before=<seq>` (эксклюзивно), страница 50 (FR-008); ответ содержит
  `nextBefore` (seq самой старой записи страницы) или отсутствует/`null` на исчерпании.

**Обоснование**: одноузловая IDENTITY избавляет от per-chat счётчика с `SELECT FOR UPDATE`
(точка конкуренции горячих чатов) и даёт lock-free назначение порядка. От последовательности
требуется **только пер-чатная** монотонность — глобальная монотонность не является контрактом
(см. выше), поэтому замена аллокатора при шардинге (per-shard sequences, §12) не меняет
наблюдаемых гарантий (SC-003). Курсор по `seq` (а не по `created_at` или UUID) —
детерминирован и индексно-дружелюбен `(chat_id, seq DESC)`. Дедуп-lookup перед
лимитами/блокировками гарантирует: любой ретрай уже записанного сообщения всегда возвращает
ту же запись (US2-1/2, US2-7), даже если блокировка включилась после записи.

**Альтернативы отклонены**: per-chat gap-free `seq` через строку-счётчик — блокировка записи
счётчика сериализует отправки в чате, gap-free не требуется ничем в спеке; остаётся запасным
вариантом аллокации при шардинге, если watermark-миграция §12 нежелательна (счётчик
ко-лоцируется с чатом). Упорядочивание по `created_at` — одинаковые таймстемпы/часовые сдвиги
ломают строгий порядок (SC-003). Упорядочивание по UUIDv7 — требует конкретного формата от
клиентов и ломается при UUIDv4. Snowflake-подобные ID — уникальность без координации, но лишь
приблизительная упорядоченность: строгий порядок чата потребовал бы локального tie-break —
сложность без выгоды против локальной sequence. Дедуп по составному
`(chat_id, sender_id, client_id)` с серверным surrogate-PK — дополнительный индекс и двойная
адресация (публичный id ≠ ключ) без выгоды: владение коллизией проверяется сравнением полей
записи (практическая вероятность случайной коллизии UUID ничтожна; злонамеренный чужой id
отсекается 409).

## 4. Per-user удаление чата: водяной знак `deleted_up_to_seq`

**Решение**:
- История сообщений — одна на диалог (общая таблица `messages`), но видимость per-user:
  `chat_participants.deleted_up_to_seq` (по умолчанию 0). Сообщение видно участнику ⟺
  `seq > deleted_up_to_seq`. `DELETE /chats/{id}` атомарно: `deleted_up_to_seq = ` текущий
  максимальный `seq` чата + флаг `hidden = true` (скрывает пустые/без-сообщений чаты из списка).
- Непрочитанный счётчик и «последнее сообщение» чата считаются только по видимым сообщениям
  (`seq > deleted_up_to_seq`); бейдж после удаления обнуляется естественно (нет видимых — нет
  непрочитанных).
- Новое входящее (`seq` > водяного знака) снова показывает чат в списке; удалённая история не
  восстанавливается (FR-021). Локальный клиентский outbox этого чата очищается (клиентская
  операция, §10). `POST /chats/ensure` для пары (клик по контакту после удаления) возвращает
  тот же чат и снимает `hidden` — история остаётся скрытой водяным знаком (FR-018: клик по
  контакту всегда ведёт к единому диалогу).
- Второй участник не затронут (его `chat_participants`-строка без изменений).

**Обоснование**: O(1) запись при удалении вместо массового `DELETE`/per-recipient строк;
инвариант «удалённое не восстанавливается» выполняется по построению (seq только растёт).
Симметрично работает и для будущих групповых чатов (006).

**Альтернативы отклонены**: per-recipient копии/матрица видимости `message_recipients(message_id,
user_id, deleted_at)` — 2× записей на каждое сообщение, write amplification на 100k msg/s
(§12). Физический `DELETE` строк — уничтожает историю второго участника (нарушение FR-021)
либо требует ветвления хранилища на пару. Отдельная таблица `deleted_chats` с таймстемпом —
эквивалент водяного знака, но требует join-а ещё одной сущности и не покрывает «пустой чат»
без флага hidden.

## 5. Прочтения: водяной знак `last_read_seq`, события идемпотентны по построению

**Решение**:
- `chat_participants.last_read_seq` (по умолчанию 0). Сообщение «прочитано» ⟺
  `seq ≤ last_read_seq` собеседника. Клиент шлёт `POST /chats/{id}/read {upToSeq}` (seq
  последнего отображённого сообщения; троттлируется клиентом, шлётся при рендере новых
  сообщений и загрузке страниц истории).
- Сервер: `UPDATE … SET last_read_seq = GREATEST(last_read_seq, :upToSeq) WHERE chat_id=… AND
  user_id=… AND last_read_seq < :upToSeq` — условный UPDATE даёт идемпотентность и монотонность
  (rowcount=0 → ничего не менять, US4-5); если строка обновилась и нет действующей блокировки
  от читающего (§6) → после коммита publish `chat.read {chatId, readUpToSeq}` в канал
  собеседника (реалтайм-двойная галочка, SC-007).
- Отправитель рендерит галочки: `seq ≤ peerReadUpToSeq` (из `GET /chats/{id}` и событий
  `chat.read`) → ✓✓; иначе записано → ✓. «Доставлено» — клиентский статус после `201/200`
  на отправке (US1-1). Пересчёт «прочитано» по водяному знаку не пишет per-message строки и
  не может откатиться.
- Непрочитанные чата: `COUNT(*) WHERE seq > last_read_seq AND seq > deleted_up_to_seq AND
  sender_id != me` — вычисляется в запросе списка чатов (§8), бейдж «99+» — клиентский рендер.

**Обоснование**: per-message квиты (`message_reads`) дают write на каждое прочтение и требуют
отдельной сверстки диапазонов; водяной знак — одна строка на участника, O(1) update, естественная
монотонность (GREATEST) и полная идемпотентность повторных событий (требование US4-5/Q).

**Альтернативы отклонены**: `message_reads(message_id, read_at)` — десятки тысяч лишних записей,
агрегация «до какого seq прочитано» на каждый рендер галочек; «read receipts per message event»
в канале — размножение событий без новой информации.

## 6. Блокировка: семантика FR-020 на паре таблиц и подавлений

**Решение**:
- `user_blocks(blocker_id, blocked_id, PK(pair), created_at)`; `PUT/DELETE /users/{id}/block`
  идемпотентны (`ON CONFLICT DO NOTHING` / `DELETE` без rowcount-требований → 204; edge spec).
- Отправка: блок действует в **обе стороны**. Проверка до INSERT: если блокирует отправитель →
  `403` код `chat_blocked_by_you` («вы заблокировали получателя»); если блокирует получатель →
  `403` код `you_are_blocked` (явное уведомление заблокированного, Q/FR-020). Записей не
  создаётся; отклонение логируется (SC-008) и **не** публикуется в канал заблокированного
  (факт блокировки не раскрывается нигде, кроме самой попытки отправить).
- Прочтения: `POST /read` от участника, блокирующего собеседника, **не advancing** водяной знак
  и не публикует `chat.read` (просмотр истории блокирующим не двигает статусы — Q). Прочтения
  заблокированного (он же не может отправлять, но читать-просматривать может) — тоже подавлены:
  событие не доставляется блокирующему (не раскрывать активность), водяной знак заблокированного
  двигается без публикации (безвредно: после разблокировки статус корректен, монотонность
  сохранена — Q).
- Бейдж непрочитанных у блокирующего «замирает» **натурально**, без специального хранилища:
  числитель (видимые непрочитанные) неизменен — новых сообщений быть не может (отправка запрещена
  обеим сторонам), знаменатель (`last_read_seq`) неизменен (прочтения подавлены). После
  разблокировки обычное поведение возобновляется (Q, FR-020).
- `GET /chats` / `GET /chats/{id}` включают `blockedByMe` (метка «заблокирован» у блокирующего);
  поле «кто заблокировал меня» **отсутствует** — заблокированный видит чат без пометки (Q).
- Контакты и блокировки независимы: ни `PUT block`, ни `DELETE contact` друг друга не касаются
  (Q); заблокированный может добавлять блокирующего в контакты — `contacts` не проверяет блоки.

**Обоснование**: все наблюдаемые эффекты FR-020 выводятся из одной таблицы + двух подавлений
(отправка/публикация прочтений) — без новых сущностей и без leakage-полей в API. Идемпотентность
PUT/DELETE — повторные блокировки/разблокировки безопасны (edge spec).

**Альтернативы отклонены**: двусторонняя блокировка одной строкой — ломает односторонность
(спека: блокировка односторонняя). Отдельная «замороженная копия бейджа» — избыточна: заморозка
следует из запрета отправки + подавления прочтений. Скрытие чата у заблокированного — прямо
запрещено спекой (Q: чат остаётся без пометки).

## 7. Флуд-лимит: Bucket4j + Redis, 30 сообщений/мин на пользователя

**Решение**:
- Переиспользуется инфраструктура 002 (`bucket4j_jdk17-redis-lettuce`, `LettuceBasedProxyManager`):
  бакет `rl:user:msgsend:{userId}` — 30 токенов, равномерное наполнение 30/60с (конфиг
  `chats.rate-limit.messages-per-minute`, значение продублировано в контракте FR-011).
- Проверяется в `MessageService` **после** дедуп-lookup (ретрай уже записанного сообщения не
  потребляет токены и не получает 429 — сходимость US2-1) и **до** INSERT. Отклонение — `429`
  problem+json c `Retry-After` (секунды до доступного токена) и кодом `flood_limit`; записей нет;
  warn-лог + метрика (SC-008). Ключ по userId (не IP/sid): лимит per-user по FR-011, мультидевайс
  суммируется естественной общей бакет-строкой в Redis (конституция II — состояние вне процесса).
- Клиент (FR-012): 429 — временнáя ошибка → автоповтор тем же `id` в момент из `Retry-After`,
  с индикацией отсчёта; статус остаётся «отправляется».

**Обоснование**: переиспользование готового семейства `rl:*` (002) — нулевые новые зависимости;
token bucket допускает короткий всплеск ≤30 и затем 1 сообщение/2с — соответствует «не более 30
в минуту». Порядок «дедуп → флуд» нужен для сценария «двойной клик» (US2-2: второй клик не
штрафуется) и «ретрай после 429» (после успешной записи повтор — не штраф).

**Альтернативы отклонены**: фиксированное окно INCR+EXPIRE (race, скачки на границе окна);
проверка флуда до дедупа — ретраи и двойные клики получают ложные 429 (нарушение US2-1/2);
лимит per-connection/per-device — обходится мультидевайсом, противоречит «на пользователя».

## 8. Список «Чаты» и панель «Контакты»: серверная сортировка, клиентский рендер

**Решение**:
- `GET /api/v1/chats` — один запрос: JOIN `chats` + оба `chat_participants` (свой — состояние,
  peer — не нужен) + peer `users` + `user_blocks` (свой блок) + агрегаты по `messages`
  (максимум `seq`/`created_at`/превью последнего видимого, счётчик непрочитанных — по §4/§5
  фильтрам). Сортировка: `last_message_at DESC NULLS LAST` — любое последнее сообщение
  (входящее или исходящее, Q40) поднимает чат; чаты без видимых сообщений — ниже (FR-014).
  Исключены: `hidden = true` и не имеющие видимых сообщений.
- «99+» — клиентский рендер при `unreadCount > 99`; сервер шлёт точное число (≤ 4-значного int).
- `GET /api/v1/contacts?sort=login|email` — серверная al-сортировка по выбранному полю
  (`ORDER BY lower(username)` / `lower(email)`, FR-015); клиент переключает параметр.
- Обновления панели в реальном времени: события `message.created` / `chat.read` уже несут
  `chatId` + данные для позиционирования и бейджа; клиент обновляет список локально
  (пересортировка по `lastMessage.createdAt`), полная синхронизация — рефетчем при
  (пере)подключении SSE (§2).

**Обоснование**: один list-endpoint с агрегатами покрывает FR-013/014/015 и Q; для UI панели
достаточно событийной инкрементальности + рефетча на реконнекте (до 005).

**Альтернативы отклонены**: отдельные endpoints `/chats/{id}/unread` и `/chats/{id}/last-message`
— N+1 запросов; WebSocket-«диффы списка» — протокольный вес, покрываемый событиями §1;
сортировка контактов на клиенте — расходится с требованием переключаемого поля на сервере,
дублирует логику.

## 9. SSE-аутентификация, переподключение и описание в OpenAPI

**Решение**:
- Аутентификация потока — тем же `Authorization: Bearer` (JWT 5 мин), что и для REST: клиент —
  собственный SSE-ридеров на **`fetch` + `ReadableStream`** (парсинг `event:`/`data:`/`retry:`
  вручную), встроенный в существующий `apiFetch`-слой (единый refresh на 401, single-flight 002).
  Токен в query-string **запрещён** (утечки в логи прокси — конституция V).
- Переподключение: экспоненциальный backoff (1с…30с, джиттер); после каждого (пере)открытия
  клиент рефетчит список чатов и сообщения открытого чата (сходимость FR-009; пропуск at-most-once
  событий восполняется). Сервер шлёт `retry: 3000` и heartbeat-комментарий каждые 15 с
  (конфиг `chats.realtime.heartbeat`), чтобы прокси/K8s не рвали простаивающий поток.
- Инфраструктура: ответ с `X-Accel-Buffering: no`; для ingress — отключение буферизации на
  маршруте `/api/v1/users/me/events` (аннотация). Таймауты прокси ≥ 5 мин (поток живой за счёт
  heartbeat; реконнект — норма).
- **OpenAPI**: путь описан как обычный GET (Bearer, `200` `text/event-stream`); фрейминг SSE и
  обе схемы событий (`MessageCreatedEvent`, `ChatReadEvent`) — в `components.schemas` с
  примерами кадров; нормативное описание — [contracts/realtime-channel.md](./contracts/realtime-channel.md).
  Это выполняет FR-022/US6 (контракт — источник истины, включая реалтайм) без AsyncAPI.
- Мультидевайс: несколько потоков одного пользователя независимы (registry per-user — список
  emitters); `message.created` публикуется и отправителю (его другие устройства рендерят
  исходящее сразу, US2-6).

**Альтернативы отклонены**: нативный `EventSource` — не умеет заголовки (понадобился бы токен
в URL — запрещено) и не интегрируется с refresh-интерцептором. Одноразовый ticket в query
(«SSE-ticket» endpoint) — дополнительный механизм и окно утечки; fetch-ридер проще при уже
имеющемся client.ts. WebSocket-jwt-subprotocol — вне OpenAPI, см. §1.

## 10. Клиентский outbox неподтверждённых сообщений (FR-012)

**Решение**:
- Локальное хранилище — `localStorage` ключ `webchat.chats.outbox.<userId>` (per-аккаунт;
  access-токен в памяти, refresh уже в localStorage — модель 002): массив записей
  `{clientMessageId, chatId, text, state: sending | failed, errorCode?, retryAt?}`.
- Жизненный цикл: отправка → запись `sending` + немедленный рендер «отправляется» →
  `201/200` → удаление записи (сообщение теперь в серверной истории) → галочка «доставлено».
  Ошибка сети/таймаут — остаётся `sending`, автоповтор с backoff (1с…30с) тем же id. `429` —
  остаётся `sending`, `retryAt = now + Retry-After`, UI-отсчёт «повтор через Nс» (Q). Ошибка
  `403 you_are_blocked` / `409` / `400` (не временные) → `state=failed` («не отправлено»),
  автоповторы прекращаются, показывается ошибка; действия: ручной повтор (тот же id — FR-004
  гарантирует сходимость) или локальное удаление записи (Q).
- Флеш при старте/входе: все `sending` записи ретраятся при загрузке мессенджера (US2-7 —
  «повторный вход ретраит тем же ID»); `failed` — нет (ждут ручного действия).
- Удаление чата (FR-021): purge записей этого `chatId` из outbox, ретраи прекращаются.
- Рендер: сообщения outbox (`sending`/`failed`) отображаются в конце чата (по времени создания
  записи) после серверных; реордеринг после подтверждения — по `seq`.

**Обоснование**: localStorage переживает перезагрузку/закрытие (требование Q: «сохраняется на
клиенте и автоматически ретраится при следующем запуске»); один ключ на аккаунт прост для
отладки; размер мал (4096 символов × десятки записей). Дискретные состояния соответствуют
спеке: «отправляется» → «доставлено» (подтверждение) и терминальное «не отправлено» (Q).

**Альтернативы отклонены**: IndexedDB — асинхронный API и схемное бремя ради ≤100 коротких строк
(YAGNI); хранение в памяти — теряется при закрытии приложения (прямое нарушение Q);
Dexie/localForage — обёртки над уже избыточным IndexedDB. Разделение ключей per-chat — N ключей,
гонки параллельных вкладок без выигрыша.

## 11. Observability (SC-008)

**Решение** (Micrometer/OTel-стек 001, без новых зависимостей):
- Метрики: `webchat_message_ack_seconds` (таймер: приход POST → 201/200 — SC-001);
  `webchat_realtime_push_seconds` (коммит → publish → отправка кадра SSE — SC-005);
  `webchat_message_dedup_total` (счётчик ON CONFLICT-попаданий — доля дедупликаций);
  `webchat_send_rejected_total{reason=flood|blocked_by_you|you_are_blocked|validation}`;
  `webchat_read_advanced_total` (обновления водяного знака — SC-007).
- Логи: structured warn на каждое отклонение отправки (флуд FR-011, блокировка FR-020) — userId,
  chatId, код; без текста сообщений (PII-минимизация, конституция V).
- Трейсинг: send→publish→SSE-отправка в одном trace (OTel 001).

**Обоснование**: прямое покрытие SC-001–SC-008 измеримыми сигналами; всё — стандартные
инструменты уже развёрнутого LGTM-стека.

## 12. Расчёт нагрузки под бюджеты конституции (SC-006)

- **Сообщения/запись**: 100k msg/s (пик-бюджет) × ~1 INSERT + 2 индекса (`messages`) —
  вертикальный PG 17 на NVMe держит ~30–50k простых INSERT/s ⇒ 004 закрывает ядро продукта
  (десятки тысяч msg/s) и укладывается в бюджет **горизонтальным путём** по лестнице
  ко-локации `chat_id` (индексы ведут `chat_id`: `(chat_id, seq DESC)`, `(chat_id, sender_id)`;
  уникальность порядка — составная `UNIQUE (chat_id, seq)`, §3):
  1. **Declarative partitioning** (один узел; `hash(chat_id)` и/или по времени) — вводится
     как есть: глобальная IDENTITY продолжает работать на общем узле, приложение не меняется.
  2. **Многоузловой шард** (Citus/сегменты) — глобальная sequence без центральной координации
     невозможна; аллокация `seq` переводится на **per-shard sequences с одноразовой
     watermark-инициализацией** (`START WITH > max(messages.seq)` на момент разрезания):
     каждый шард выдаёт значения выше любых ранее записанных ⇒ пер-чатная монотонность
     продолжающихся чатов сохраняется; коллизии значений между шардами безвредны — `seq`
     не сравнивается межчатово (§3). SQL-паттерны приложения не меняются; меняются DDL
     (IDENTITY → seq, назначаемый шардом) и миграционный шаг — фиксируется при проектировании
     шардирования. Запасной вариант — per-chat счётчик, ко-лоцированный с чатом (§3).
  Осознанный масштабный план, а не немедленное внедрение (VII: не строим кластер до нагрузки).
- **Фанаут**: ≤ 2 Redis PUBLISH на сообщение (каналы отправителя и получателя) ⇒ ≤ 200k pub/s
  при пике. Redis pub/sub single-node ~1M msg/s; кластеризация/SSUBSCRIBE — при росте.
- **SSE-соединения**: 1M CCU ⇒ ~1M сокетов (по одному на устройство) ÷ ~50k async-соединений
  на инстанс (Tomcat NIO, ~2GB heap без буферов на кадр) ≈ 20 инстансов — горизонтально,
  поды stateless (реестр emitters реплицирован неявно через pub/sub-подписки).
- **Чтения**: список чатов — 1 агрегатный запрос на панель + событийные обновления; история —
  index-only scan `(chat_id, seq DESC) LIMIT 50`. 12-месячная retention: `created_at` на
  `messages`, архивные партиции по времени — инфраструктурная операция (конституция Perf).
- **Вывод**: solution укладывается в бюджеты при описанном горизонтальном масштабировании
  хранилища; SSE/фанаут — вертикально независимы от записи. Закреплено в SC-006 (проверяется
  k6-профилем [quickstart §4.10] и раёт-калькуляцией выше).

## 13. Тестирование (VI)

- **Backend IT** (Testcontainers PG+Redis, `@SpringBootTest(RANDOM_PORT)`, реальный HTTP):
  `MessagingDeliveryIT` — дедуп по id (параллельные и последовательные ретраи, двойной POST),
  порядок у обоих участников, пагинация до/за границей истории, exactly-once при обрыве
  (имитация: повторный POST после 5xx-недостижения); `RealtimeSseIT` — WebTestClient читает
  SSE-поток, asserting кадры `message.created`/`chat.read` и heartbeat; `ReadReceiptsIT` —
  монотонность/идемпотентность (повторный read, меньший upToSeq), реалтайм двойной галочки;
  `BlockingIT` — обе стороны, коды ошибок, заморозка бейджа/прочтений, разблокировка;
  `ContactsIT` — поиск точный lower(), self-ошибка, идемпотентное добавление, удаление
  контакта ≠ удаление чата; `ChatDeletionIT` — водяной знак, реаппир чата, outbox-очистка
  (контракт клиента), независимость второго участника; `FloodLimitIT` — 31-е сообщение/мин →
  429 + Retry-After, отсутствие записи, ретрай после окна → 201; `ChatAccessIT` — не-участник →
  403/404 на все ресурсов (FR-002).
- **Frontend** (Vitest+RTL): outbox-логика (временно/терминально, тот же id, флуд-отсчёт, purge
  при удалении чата), рендер галочек/бейджа «99+»/метки «заблокирован», переключение
  «Чаты»/«Контакты», SSE-ридер (парсинг кадров, реконнект-событие).
- **Контракт**: конвейер 001 (vacuum → codegen drift → oasdiff, additive 0.4.0); SS-канал
  проверяется схемами событий в IT (payload против схем).
- **Нагрузочный smoke**: k6 (`load/k6/messaging.smoke.js`) — профиль: 2 VU-пользователя,
  отправка + SSE-получение, метрики SC-001/005; флуд-сценарий → только 429 (без 5xx).
