## Детальные результаты

### §3.1 Обмен в реальном времени и статусы — SC-001, SC-005

1. ✅ Bob: поиск `alice@example.com` → 200 (точное совпадение); `POST /contacts` → 201;
   `POST /chats/ensure` → 201 `ChatView`; открытие диалога 200.
2. ✅ Alice отправила «Привет»: `201` `Message{seq:1}` за 0.170 с (SC-001 ≤ 2 с — с запасом).
3. ✅ Bob (SSE подписан до отправки): кадр `message.created` получен через ~0.32 с после
   POST (SC-005 ≤ 2 с), payload = `Message` из ответа №16.
4. ✅ Валидация: `""` и `"   "` → 400 `text_blank`; 4097 символов → 400 `text_too_long`;
   edge «ровно 4096 после trim» (пробел + 4096 символов) → 201, `len(text)=4096`; в истории
   только валидные записи (2+1).
5. ✅ Carol на чужом диалоге: `GET /chats/{id}`, `GET …/messages`, `POST …/messages`,
   `POST …/read`, `DELETE /chats/{id}` — все → 403 `not_participant` (FR-002).

### §3.2 Exactly-once и порядок — SC-002, SC-003

1. ✅ Повторный `POST` того же `clientMessageId` → `200` с той же записью (`id`, `seq:1`,
   исходный текст — конфликт текста не меняет запись); в истории один экземпляр.
2. ✅ Автотест `webchat.backend.chats.MessagingDeliveryIT` — зелёный (параллельные ретраи,
   обрывы, порядок `seq`, межперезагрузочная стабильность).
3. ✅ Bob офлайн: Alice отправила 5 сообщений (seq 4–8); после «входа» Bob — 8 записей у
   обеих сторон, списки идентичны, дублей нет, `seq` desc.
4. ✅ Вторая сессия Alice (SSE): все 5 своих исходящих получила как `message.created` (US2-6).
5. ✅ Outbox-ретрай: оборванный id → повтор `201`/`200`, в истории ровно 1 экземпляр.

### §3.3 История и пагинация — SC-004

1. ✅ Чат доведён до 120 сообщений. Первая страница без `before`: ровно 50 (seq 120–71),
   `nextBefore: 71`; прокрутка: 50 + 50 + 20, всего 120, все id уникальны, seq покрывают
   1..120 без пропусков.
2. ✅ Запрос за началом (`before=1`): `200 {messages: []}`, `nextBefore` отсутствует.
3. ✅ Повторный вход: первая страница побайтово идентична (те же id/seq в том же порядке).
4. ✅ Пустой диалог (bob-carol): `200 {messages: []}`; в списке чатов — без `lastMessage`.

### §3.4 Прочтения и двойные галочки — SC-007

1. ✅ Отправка (seq 121) → `POST /read {upToSeq:121}` → 204 → кадр `chat.read` в потоке
   Alice за 0.23 с (SC-007 ≤ 2 с); `ChatView.peerReadUpToSeq`: 0 → 121.
2. ✅ До прочтения `peerReadUpToSeq` оставался 0 (✓ не становится ✓✓ без просмотра).
3. ✅ Листание истории: `read` при каждой подгруженной странице (3 × 204).
4. ✅ Повтор `read` с равным и меньшим `upToSeq` → 204; водяной знак не откатился (121);
   в потоке Alice суммарно 1 кадр `chat.read` (монотонность). Автотест `ReadReceiptsIT`
   зелёный.

### §3.5 Панель «Чаты»/«Контакты», контакты, удаление (US5)

1. ✅ `GET /chats`: чат с последним сообщением (alice, seq 121) выше чата без сообщений
   (carol, `lastMessage: null`); бейдж после прочтения — 0 (сброс); у получателя 101
   непрочитанное от незнакомца (см. п. 7) — значение >99 для клиентского «99+».
2. ✅ `GET /contacts?sort=login|email` — 200; `sort=bogus` → 400 `invalid_sort`.
3. ✅ Поиск: `ALICE@EXAMPLE.COM` → найдена (регистронезависимо); `ALICE` (без `@`) → по
   username; частичный `alice@examp` и несуществующий → 200 `[]` без ошибок (`@`-правило).
4. ✅ Повторный `POST /contacts` того же пользователя → 200; в списке 1 запись (без дубля).
5. ✅ `DELETE /contacts/{alice}` → 204; чат и история не затронуты (FR-017).
6. ✅ `DELETE /chats/{id}` у Alice → 204: чат исчез из списка Alice, у Bob сохранён;
   новое сообщение Bob (seq 122) → чат снова у Alice с `unreadCount: 1`, история видна
   только с seq 122 (водяной знак FR-021); повторный DELETE → 204 (идемпотентно).
7. ✅ Незнакомец: Bob удалил чат с Carol; Carol (не в контактах) отправила 101 сообщение →
   чат появился у Bob автоматически с `lastMessage` и `unreadCount: 101`; Bob ответил без
   добавления контакта → 201 (FR-019).
8. ✅ Себя: `POST /contacts {self}` → 422 `self_forbidden`; `POST /chats/ensure {self}` →
   422 `self_forbidden`.

### §3.6 Контрактный клиент и реалтайм-канал (US6)

1. ✅ `curl -N` SSE: первый кадр `retry: 3000`; `Content-Type: text/event-stream`;
   `X-Accel-Buffering: no`; heartbeat `:ka` ×3 за 35 с наблюдения (каждые 15 с).
2. ✅ Строго-по-контракту скрипт: ensure → подписка → отправка → приём `message.created`;
   payload валидирован против схемы (`chatId` + `Message` с uuid/int64/ISO-полями, состав
   полей точный) → повторная отправка того же id → 200, та же запись, один экземпляр.
3. ✅ Конвейер: `vacuum lint -e` — 0 errors; `pnpm --dir frontend generate:api` — drift
   отсутствует (`git diff --exit-code` чист); `oasdiff breaking` base(0.3.0) → current(0.4.0):
   «No breaking changes», additive minor.

### §3.7 Блокировка (FR-020) — BlockingIT + вручную

1. ✅ `PUT /users/{bob}/block` → 204; у Alice `blockedByMe: true`; у Bob чат без пометок
   (`blockedByMe: false`, полей «кто заблокировал меня» нет — leakage отсутствует).
2. ✅ Bob → Alice: 403 `you_are_blocked`; Alice → Bob: 403 `chat_blocked_by_you`; последний
   seq не изменился — записей нет.
3. ✅ История доступна обоим; просмотр Alice (`POST /read` → 204): `peerReadUpToSeq` у Bob
   не двигался (0 → 0) — статусы замерли; `chat.read` Bob не получил; бейдж Alice не растёт.
   Read заблокированного Bob: водяной знак у Alice двигается локально (121 → 225), но событие
   в канал блокирующего не публикуется.
4. ✅ Повторный `PUT` → 204; `DELETE` без действующего блока → 204 (идемпотентность).
5. ✅ Разблокировка: отправка Bob → 201 + `message.created` у Alice; прочтение → `chat.read`;
   бейдж Alice 2 → 0 по прочтению; история цела (seq 226, 225, …).
6. ✅ Контакты независимы: Bob добавил Alice во время блокировки (201); контакты обеих
   сторон живы после блокировки/разблокировки.
7. ✅ Блокировка при открытых SSE-подписках обоих: за окно наблюдения — 0 кадров событий в
   обоих потоках (только heartbeat), неявная доставка исключена, состояние сошлось к
   заблокированному.

### §3.8 Флуд-лимит и клиентские ретраи (FR-011/FR-012)

1. ✅ 31-я отправка в минутном окне → `429` `flood_limit` + `Retry-After` (сек до токена);
   отвергнутый `clientMessageId` в истории отсутствует (записи в БД нет).
2. ✅ После окна повтор тем же id → `201` (подтверждение, что запись не создавалась) →
   повтор → `200` та же запись; один экземпляр в истории. SPA-часть (индикация отсчёта,
   автоповтор) — клиентский слой, покрыт frontend-тестами outbox; равномерность бакета
   наблюдалась при наполнении 120 сообщений (429 с малыми `Retry-After` в окне).
3. ✅ Постоянное отклонение: блокировка получателя до подтверждения → каждая попытка того же
   id → 403 `you_are_blocked` (стабильно), записи нет — клиент показывает «не отправлено» и
   прекращает автоповторы.
