# Feature Specification: Личный текстовый диалог в реальном времени с exactly-once доставкой

**Feature Branch**: `004-direct-messaging-core`

**Created**: 2026-09-20

**Status**: Draft

**Input**: User description: "Два пользователя ведут личный диалог текстовыми сообщениями в реальном времени. Сообщения доставляются гарантированно и без дублей (эффект exactly-once для пользователя): клиент генерирует уникальный ID сообщения, сервер дедуплицирует по ID, подтверждает запись клиенту, порядок сообщений сохраняется в рамках чата, повторная отправка (ретрай) безопасна и не создаёт дубликат. История переписки доступна при повторном входе. Подключение к реалтайм-каналу через публичный API (OpenAPI-контракт — источник истины). Состояние сообщений: отправляется / доставлено. Дополнение: пользователю в элементе «сообщения» показываются два статуса — доставлено и прочитано; доставлено визуализируется одной галочкой, прочитано — двойной галочкой."

## Clarifications

### Session 2026-09-20

- Q: Как пользователь начинает новый личный диалог? → A: Через панель контактов слева: поиск пользователя по email или логину → добавление в свои контакты → нажатие на контакт начинает или продолжает единый диалог пары.
- Q: Что показывает левая панель помимо контактов? → A: Один объединённый список — контакты и (в будущем) группы сортируются вместе по дате последнего полученного сообщения; непрочитанные показываются индикатором, но на порядок не влияют; элементы без переписки располагаются ниже.
- Q: Что происходит у получателя, когда ему пишет пользователь, которого нет в его контактах? → A: Диалог автоматически появляется в панели получателя при первом входящем сообщении; для чтения и ответа не нужно добавлять отправителя в контакты.
- Q: Что происходит с сообщением «отправляется» при закрытии приложения до подтверждения сервера? → A: Сообщение сохраняется на клиенте и автоматически ретраится тем же ID при следующем запуске/входе.
- Q: Какое максимальное количество символов допустимо в одном текстовом сообщении? → A: 4096 символов.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Обмен текстовыми сообщениями в личном диалоге в реальном времени (Priority: P1)

Два аутентифицированных пользователя ведут личный диалог (строгая пара «один на один») текстовыми сообщениями. Отправитель пишет текст и отправляет сообщение: оно сразу появляется у отправителя со статусом «отправляется», а после подтверждения сервером факта записи переходит в статус «доставлено». Получатель, находящийся онлайн, видит новое сообщение в чате в реальном времени, без ручного обновления. У пары пользователей всегда один и тот же общий диалог. Участник видит слева единую панель — свои контакты, упорядоченные по дате последнего полученного сообщения, — чтобы открыть переписку. Новый диалог инициируется через панель контактов слева: пользователь ищет другого пользователя по email или логину, добавляет его в свои контакты, и нажатие на контакт начинает (или продолжает) единый диалог этой пары.

**Why this priority**: Это ядро фичи и минимальный жизнеспособный продукт «личный чат»: без отправки, мгновенной доставки и видимых статусов сообщений остальные сценарии не имеют смысла.

**Independent Test**: Полностью проверяется вручную и автотестом: два пользователя открывают общий диалог; один отправляет сообщение; у отправителя статус меняется «отправляется» → «доставлено»; у онлайн-получателя сообщение появляется в реальном времени.

**Acceptance Scenarios**:

1. **Given** два аутентифицированных пользователя и получатель онлайн, **When** отправитель отправляет непустое текстовое сообщение, **Then** оно немедленно отображается у отправителя со статусом «отправляется», и после подтверждения сервером записи статус меняется на «доставлено».
2. **Given** получатель онлайн и подключён к реалтайм-каналу диалога, **When** сообщение записано на сервере, **Then** оно появляется у получателя в реальном времени без ручного обновления.
3. **Given** сервер не подтвердил запись сообщения (сбой, таймаут), **When** отправитель смотрит на чат, **Then** сообщение остаётся видимым со статусом «отправляется» и не считается доставленным.
4. **Given** пустой текст или текст длиннее 4096 символов, **When** отправитель пытается отправить сообщение, **Then** отправка отклоняется с понятной ошибкой и в чате ничего не появляется.
5. **Given** пользователь, не являющийся участником диалога, **When** пытается читать диалог или отправлять в него сообщения, **Then** доступ отклоняется (авторизация на уровне ресурса).
6. **Given** у пользователя есть переписки, **When** он входит и видит единую панель слева, **Then** элементы с перепиской упорядочены по дате последнего полученного сообщения (элементы без сообщений — ниже), и он может открыть переписку в любом из них.
7. **Given** аутентифицированный пользователь, **When** он ищет пользователя по email или логину и добавляет его в свои контакты, **Then** контакт отображается в единой панели слева, и нажатие на него открывает единый диалог пары (создавая его при первом обращении).
8. **Given** отправитель написал пользователю, у которого нет отправителя в контактах, **When** сообщение записано на сервере, **Then** диалог с отправителем автоматически появляется в панели получателя, и получатель может читать сообщение и отвечать без предварительного добавления контакта.

### User Story 2 - Гарантированная доставка без дублей с сохранением порядка (Priority: P1)

Отправитель может столкнуться с нестабильной сетью, таймаутами, повторными отправками (ретраями) и двойным нажатием «отправить». Для пользователя результат всегда один: сообщение записано ровно один раз. Клиент генерирует уникальный ID сообщения; сервер дедуплицирует по этому ID и подтверждает запись. Повторная отправка того же сообщения с тем же ID безопасна и не создаёт дубликат — клиент получает подтверждение той же записи. Порядок сообщений сохраняется в рамках чата: оба участника видят одну и ту же последовательность, не меняющуюся при перезагрузках.

**Why this priority**: Гарантия «не теряется, не дублируется, порядок стабилен» — неотъемлемое качество продукта и конституционное требование (принцип III); без неё диалог непригоден для общения.

**Independent Test**: Проверяется автоматизированными тестами доставки: (а) повторная отправка с тем же ID (симуляция ретрая и двойного клика) не создаёт второй экземпляр; (б) в чате и в истории ровно один экземпляр каждого сообщения; (в) последовательность сообщений одинакова у обоих участников и между загрузками.

**Acceptance Scenarios**:

1. **Given** отправленное сообщение, для которого клиент не получил подтверждение (таймаут, обрыв связи), **When** клиент повторяет отправку с тем же уникальным ID, **Then** в чате остаётся ровно один экземпляр сообщения, а клиент получает подтверждение той же записи.
2. **Given** отправитель дважды инициирует отправку одного сообщения, **When** обе попытки уходят с одним и тем же ID, **Then** получатель видит одно сообщение, а не два.
3. **Given** несколько сообщений, отправленных подряд одним или обоими участниками, **When** они доставляются и загружаются из истории, **Then** порядок внутри чата одинаков для обоих участников и не меняется при повторных загрузках.
4. **Given** получатель был офлайн в момент отправки, **When** он подключается и открывает диалог, **Then** все записанные сообщения доступны ему — ничего не потеряно и нет дублей.
5. **Given** соединение участника с реалтайм-каналом прервалось и восстановилось, **When** канал снова готов, **Then** состояние чата сходится к серверному: без потерь, дублей и изменения порядка.
6. **Given** один пользователь работает с нескольких устройств (параллельные сессии), **When** в диалоге появляются новые сообщения, **Then** состояние чата сходится во всех сессиях пользователя без дублей и потерь.
7. **Given** приложение отправителя закрыто (сессия завершена) до подтверждения записи сообщения, **When** пользователь снова входит, **Then** неподтверждённое сообщение автоматически отправляется повторно с тем же уникальным ID, и в результате в чате остаётся ровно один экземпляр сообщения.

### User Story 3 - История переписки доступна при повторном входе (Priority: P2)

Пользователь закрывает приложение или завершает сессию и позже входит снова. Вся переписка личного диалога доступна: при открытии чата пользователь видит последние сообщения в правильном порядке, а длинная история подгружается по частям при прокрутке — вплоть до начала переписки.

**Why this priority**: История делает диалог инструментом длительного общения, а не одноразовым сеансом; при этом реалтайм-обмен уже ценен и без неё, поэтому приоритет ниже первых двух историй.

**Independent Test**: Проверяется вручную и автотестом: участники обмениваются сообщениями; один выходит и входит снова; при открытии диалога видны последние сообщения в исходном порядке; прокрутка подгружает более старые части до начала переписки.

**Acceptance Scenarios**:

1. **Given** диалог содержит много сообщений, **When** участник повторно входит и открывает диалог, **Then** он видит последние сообщения и может по частям загрузить более старые — до начала переписки.
2. **Given** участник повторно вошёл и читает историю, **When** сообщения отображаются, **Then** их порядок совпадает с тем, что был виден ранее, и каждое записанное сообщение имеет статус «доставлено».
3. **Given** диалог пуст, **When** участник открывает его, **Then** отображается корректное пустое состояние без ошибок.
4. **Given** запрос более старой части истории выходит за начало переписки, **When** клиент запрашивает следующую часть, **Then** возвращается пустой результат без ошибок (корректная граница пагинации).

### User Story 4 - Статус «прочитано»: отправитель видит, что сообщение просмотрено (Priority: P2)

Отправитель видит свои исходящие сообщения в диалоге с индикаторами статуса: «доставлено» — одна галочка, «прочитано» — двойная галочка. Сообщение становится «прочитано», когда получатель просматривает его: сообщение отображается получателю в открытом диалоге (включая чтение истории при повторном входе). Если получатель онлайн, галочки у отправителя обновляются в реальном времени, без перезагрузки. Индикаторы статуса показываются только на исходящих сообщениях пользователя; входящие сообщения получателя отображаются без галочек.

**Why this priority**: Индикатор «прочитано» завершает цикл общения — отправитель знает, что сообщение не только записано сервером, но и увидено получателем; опирается на уже работающую доставку и просмотр, поэтому приоритет P2.

**Independent Test**: Проверяется вручную и автотестом: отправитель отправляет сообщение — после подтверждения записи одна галочка; получатель открывает диалог и просматривает сообщение — у отправителя двойная галочка без перезагрузки; пока получатель не открывал диалог, остаётся одна галочка.

**Acceptance Scenarios**:

1. **Given** записанное сообщение отображается получателю в открытом диалоге, **When** получатель его просматривает, **Then** у отправителя статус меняется с «доставлено» (одна галочка) на «прочитано» (двойная галочка).
2. **Given** отправитель и получатель онлайн, **When** получатель просматривает сообщение, **Then** статус у отправителя обновляется в реальном времени, без перезагрузки.
3. **Given** получатель офлайн либо не открывал диалог после отправки, **When** отправитель смотрит на чат, **Then** у сообщения остаётся одна галочка «доставлено».
4. **Given** получатель повторно входит и читает историю диалога, **When** сообщения отображаются ему, **Then** они отмечаются прочитанными, и отправитель видит двойные галочки.
5. **Given** сообщение уже в статусе «прочитано», **When** происходят повторные открытия диалога, переподключения или дубли событий прочтения, **Then** статус не откатывается к «доставлено» и не меняется некорректно (статус монотонен, события идемпотентны).
6. **Given** диалог получателя открыт в момент прихода нового сообщения, **When** сообщение отображается получателю, **Then** оно сразу отмечается прочитанным после отображения.

### User Story 5 - Подключение к реалтайм-каналу через публичный API-контракт (Priority: P3)

Реалтайм-канал (события новых сообщений диалога) — часть публичного API и описан в OpenAPI-контракте, который является источником истины. Клиенты проекта (standalone SPA, встраиваемый виджет) и любой сторонний клиент, следующий контракту, подключаются к каналу и работают с сообщениями через одни и те же публичные интерфейсы: отправка подчиняется тем же правилам уникальности ID и дедупликации, события канала соответствуют контрактным схемам.

**Why this priority**: Принцип API-First и встраиваемость — стратегическая цель проекта, но уже один клиент, построенный строго по контракту, проверяет его на практике, поэтому приоритет ниже пользовательских сценариев обмена.

**Independent Test**: Проверяется автотестом контракта: реалтайм-канал и операции сообщений описаны в OpenAPI-контракте; клиент, построенный строго по контракту (без внутренних интерфейсов), успешно подключается, отправляет и получает сообщения.

**Acceptance Scenarios**:

1. **Given** клиент, построенный строго по OpenAPI-контракту, подключён к реалтайм-каналу диалога участника, **When** в диалоге записывается новое сообщение, **Then** клиент получает событие нового сообщения, соответствующее контрактной схеме.
2. **Given** клиент, построенный строго по контракту, отправляет сообщение с уникальным ID через контрактную операцию, **When** сервер подтверждает запись, **Then** подтверждение соответствует контракту, а повторная отправка с тем же ID не создаёт дубликат.
3. **Given** контракт публичного API обновляется, **When** выпускается новая версия, **Then** обратная совместимость публичных интерфейсов сообщений и реалтайм-канала сохраняется (breaking changes — только через версионирование по конституции).

### Edge Cases

- Обрыв связи в момент отправки, когда клиент не знает, записано ли сообщение — безопасный ретрай с тем же ID, дублей нет.
- Закрытие приложения или завершение сессии до подтверждения записи — сообщение сохраняется локально и автоматически ретраится тем же ID при следующем входе; дублей нет.
- Двойная отправка (двойной клик, повторная попытка интерфейса) — дубликат не создаётся.
- Одновременная отправка сообщений обоими участниками — единый и стабильный порядок в чате.
- Получатель офлайн либо переподключение к реалтайм-каналу — сходимость состояния без потерь и дублей.
- Параллельные сессии одного пользователя — конвергенция состояния во всех сессиях.
- Текст ровно 4096 символов проходит; превышающий (4097+) — отклоняется; пустой текст отклоняется.
- Попытка неучастника читать диалог или писать в него — отказ без раскрытия содержимого.
- Попытка открыть диалог с несуществующим пользователем — понятная ошибка.
- Входящее сообщение от пользователя вне списка контактов получателя — диалог автоматически появляется в панели получателя.
- Поиск пользователя по email/логину без совпадений — корректный пустой результат без ошибок.
- Повторное добавление уже имеющегося контакта — дубликат в панели контактов не создаётся.
- Очень длинная история — корректная пагинация, включая запрос за границей начала переписки.
- Интенсивная отправка сообщений (флуд) — ограничение частоты, не создающее записей при отклонении.
- Открытие диалога с большим количеством непрочитанных сообщений — все отображённые сообщения корректно отмечаются прочитанными (включая подгруженные части истории).
- Повторные или дублирующиеся события прочтения, переподключения участников — статус «прочитано» монотонен и не откатывается к «доставлено».
- Сообщение приходит в момент, когда диалог получателя уже открыт, — прочитано сразу после отображения.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять аутентифицированным пользователям личный диалог «один на один»; для пары пользователей существует ровно один диалог, и оба участника имеют равный доступ на чтение и отправку.
- **FR-002**: Система MUST предоставлять участнику единую панель слева: контакты пользователя (и в будущих фичах группы) в одном списке, упорядоченные по дате последнего полученного сообщения; непрочитанные сообщения отображаются индикатором (бейджем) и не влияют на порядок; элементы без переписки располагаются после элементов с сообщениями.
- **FR-003**: Доступ к диалогу (чтение, отправка, реалтайм-подписка) MUST быть разрешён только участникам этого диалога; всем остальным — отказ на уровне каждого ресурса.
- **FR-004**: Клиент MUST генерировать уникальный ID каждого сообщения; система MUST дедуплицировать записи по этому ID: повторная запись того же ID не создаёт новый экземпляр, а возвращает подтверждение уже существующей записи.
- **FR-005**: Система MUST подтверждать клиенту факт записи сообщения; до подтверждения сообщение отображается отправителю со статусом «отправляется», после подтверждения — «доставлено», после просмотра получателем — «прочитано». Статусы «доставлено» и «прочитано» визуализируются в элементе сообщения: одна галочка и двойная галочка соответственно; индикаторы отображаются только на исходящих сообщениях пользователя; смена статусов монотонна (не откатывается назад).
- **FR-006**: Система MUST сохранять порядок сообщений в рамках одного чата: последовательность одинакова для обоих участников и стабильна при повторных загрузках.
- **FR-007**: Система MUST доставлять новые сообщения онлайн-получателю через реалтайм-канал без ручного обновления; сообщение для офлайн-получателя MUST быть доступно из истории при подключении.
- **FR-008**: Система MUST сохранять историю переписки диалога и предоставлять её при повторном входе участника с постраничной загрузкой более старых сообщений.
- **FR-009**: При переподключении клиента (обрыв связи, повторный вход, новая сессия) состояние чата MUST сходиться к серверному: без потерь, дублей и изменения порядка.
- **FR-010**: Реалтайм-канал и операции над сообщениями и диалогами MUST быть описаны в публичном OpenAPI-контракте — источнике истины; изменения публичных интерфейсов MUST сохранять обратную совместимость.
- **FR-011**: Система MUST валидировать текст сообщения: непустой и не длиннее 4096 символов (значение фиксируется в API-контракте); невалидная отправка отклоняется с понятной ошибкой.
- **FR-012**: Система MUST ограничивать частоту отправки сообщений (защита от флуда); превышение отклоняется с понятной ошибкой и не создаёт записей.
- **FR-013**: Система MUST отмечать сообщение «прочитано», когда оно отображается получателю в открытом диалоге, включая просмотр истории при повторном входе; до этого момента сообщение остаётся «доставлено».
- **FR-014**: Изменение статуса на «прочитано» MUST доставляться отправителю в реальном времени; события прочтения идемпотентны — повторная обработка не откатывает и не искажает статус.
- **FR-015**: Система MUST предоставлять пользователю поиск других пользователей по email или логину и добавление найденного пользователя в его личный список контактов; контакты отображаются в единой панели слева.
- **FR-016**: Нажатие на контакт в единой панели слева MUST открывать единый диалог пары пользователей, создавая диалог при первом обращении; повторные обращения всегда ведут к одному и тому же диалогу.
- **FR-017**: Диалог MUST автоматически отображаться в единой панели получателя при первом входящем сообщении от пользователя, отсутствующего в его контактах; чтение и ответ не требуют предварительного добавления отправителя в контакты.
- **FR-018**: Клиент MUST локально сохранять неподтверждённые сообщения (статус «отправляется») и автоматически повторять их отправку с тем же уникальным ID при следующем запуске приложения или повторном входе; результат сходится к одному экземпляру сообщения.

### Key Entities

- **Диалог (личный чат)**: беседа ровно двух пользователей; для пары участников существует единственный диалог; содержит упорядоченную историю сообщений; доступен только участникам.
- **Сообщение**: единица переписки; ключевые атрибуты: уникальный ID (генерируется клиентом), диалог, отправитель, текст, момент записи сервером, позиция в порядке чата, факт и момент прочтения получателем; пользовательские статусы: «отправляется» (до подтверждения записи), «доставлено» (после подтверждения, одна галочка), «прочитано» (после просмотра получателем, двойная галочка).
- **Участник**: аутентифицированный пользователь, связанный с диалогом; пользователи и аутентификация существуют в системе с фичи регистрации (002).
- **Контакт**: односторонняя запись в личном списке контактов пользователя, созданная через поиск по email или логину; отображается в единой панели слева; нажатие на контакт ведёт к единому диалогу пары (пользователь ↔ контакт).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 95% сообщений при нормальной сети получают статус «доставлено» не позднее 2 секунд после нажатия отправки.
- **SC-002**: В сценариях ретраев, двойных отправок и переподключений пользователи наблюдают 0 дублей — каждое сообщение отображается ровно одним экземпляром (подтверждается автоматизированными тестами доставки).
- **SC-003**: Порядок сообщений в рамках чата одинаков у обоих участников и между повторными загрузками в 100% прогонов автоматизированных тестов.
- **SC-004**: При повторном входе последние сообщения диалога видимы не позднее 3 секунд после открытия чата; загрузка каждой более старой части истории занимает не более 3 секунд.
- **SC-005**: Онлайн-получатель видит новое сообщение не позднее 2 секунд с момента подтверждения записи отправителю в 95% случаев.
- **SC-006**: Решение укладывается в бюджеты масштабируемости конституции (одновременные пользователи, сообщения в секунду, stateless-сервисы) — подтверждается расчётом в plan.md и нагрузочными тестами.
- **SC-007**: У онлайн-отправителя статус сообщения меняется на «прочитано» (двойная галочка) не позднее 2 секунд с момента отображения сообщения получателю в 95% случаев.

## Assumptions

- Аутентификация, сессии и зарегистрированные пользователи существуют (фича 002); данная фича не решает вход и регистрацию.
- Статус «доставлено» (одна галочка) означает подтверждение сервером записи сообщения; статус «прочитано» (двойная галочка) — факт отображения сообщения получателю в открытом диалоге, а не иное толкование (прочтение «в уме» не отслеживается); индикатор набора текста, редактирование и удаление сообщений — вне рамок этой фичи.
- Поддерживаются только текстовые сообщения; другие типы контента (изображения, видео, виджеты) — отдельные фичи через расширяемую систему типов контента.
- Диалог строго двух участников; групповые чаты вне рамок.
- Панель слева — единый объединённый список: личные контакты пользователя (и в будущем группы) сортируются вместе по дате последнего полученного сообщения; группы относятся к фиче групповых чатов (006) и вне рамок этой фичи.
- E2EE-беседы вне рамок этой фичи и описываются отдельно.
- Ограничение длины текста зафиксировано: 4096 символов; параметры пагинации выбираются как разумные отраслевые значения и фиксируются в API-контракте.
- Реалтайм-доставка в рамках фичи означает доставку онлайн-клиенту в приложении/виджете; push-уведомления вне приложения (web push, email) — вне рамок.
