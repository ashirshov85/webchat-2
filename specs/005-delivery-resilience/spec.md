# Feature Specification: Устойчивость доставки при разрывах соединения и пиковой нагрузке

**Feature Branch**: `005-delivery-resilience`

**Created**: 2026-09-23

**Status**: Draft

**Input**: User description: "При разрыве соединения и переподключении клиент синхронизирует пропущенные сообщения по курсору последнего полученного, без дублей и пропусков. Оффлайн — исходящие сообщения ставятся в очередь и отправляются при восстановлении связи с сохранением идемпотентности. Индикаторы непрочитанных сообщений по чатам. Под пиковой нагрузкой система деградирует контролируемо: backpressure на отправителя, rate limiting, graceful degradation вместо отказа. Доставка в пределах бюджета 100 000 сообщений/сек."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Синхронизация пропущенных сообщений при переподключении (Priority: P1)

Пользователь теряет связь с чатом (обрыв сети, переход в тоннель, засыпание устройства). Пока он отключён, собеседники продолжают писать. При восстановлении соединения клиент сообщает серверу позицию последнего полученного сообщения (курсор) по каждому чату и получает всё, что было пропущено: без дублей и без пропусков, в исходном порядке в рамках каждого чата. Уже показанные пользователю сообщения не появляются повторно.

**Why this priority**: Гарантия «ничего не потеряно и ничего не задублировано» — ядро доверия к мессенджеру; без неё остальные сценарии бессмысленны. Это основной механизм до-доставки, на который опираются остальные истории.

**Independent Test**: Разорвать соединение, отправить в чат N сообщений от собеседника, восстановить соединение — в диалоге появляются ровно N новых сообщений, каждое один раз, в порядке отправки. Ценность доставляется уже этой проверкой.

**Acceptance Scenarios**:

1. **Given** пользователь находится в диалоге и получает сообщения в реальном времени, **When** соединение обрывается и восстанавливается, **Then** все сообщения, пришедшие за время разрыва, дозагружаются ровно по одному разу каждый, в порядке отправки в рамках чата.
2. **Given** соединение было разорвано на несколько часов и по чатам пользователя накопилось 200+ пропущенных сообщений в нескольких чатах, **When** соединение восстанавливается, **Then** синхронизация выполняется по всем чатам пользователя порциями (пагинацией), без потери и дублирования, с индикацией процесса.
3. **Given** сервер доставил клиенту одно и то же сообщение повторно (например, повторная доставка после не подтверждённого клиентом получения), **When** клиент обрабатывает доставку, **Then** сообщение отображается пользователю один раз.
4. **Given** во время синхронизации соединение снова обрывается на середине, **When** соединение восстанавливается, **Then** синхронизация возобновляется с позиции последнего фактически полученного сообщения и завершается без дублей и пропусков.
5. **Given** курсор пользователя указывает на сообщение, которое больше недоступно в активной истории (например, чат удалён собеседником или история ушла в архив по сроку хранения), **When** выполняется синхронизация, **Then** сервер продолжает доставку со старейшей доступной позиции этого чата и явно сообщает клиенту о точке обрезки, а не возвращает ошибку всего запроса.
6. **Given** разрыв соединения произошёл до получения пользователем ни одного сообщения в только что появившемся чате, **When** соединение восстанавливается, **Then** чат появляется в списке вместе со всей накопившейся перепиской.

### User Story 2 - Оффлайн-очередь исходящих сообщений (Priority: P2)

Пользователь пишет сообщения без сети (или сервер недоступен). Каждое исходящее сообщение сохраняется на клиенте со статусом «отправляется» и ставится в очередь. При восстановлении связи очередь автоматически отправляется на сервер в исходном порядке; каждое сообщение уходит с тем же уникальным ID, с которым было создано, поэтому повторные попытки доставки не создают дубликатов (идемпотентность). Очередь переживает закрытие приложения и перезапуск устройства.

**Why this priority**: Отправка без сети — ожидаемое поведение мессенджера; пользователь не должен различать «есть сеть / нет сети» на этапе набора текста. Опирается на ID-идемпотентность из фичи 004, но ценность самостоятельна.

**Independent Test**: Отключить сеть, отправить 3 сообщения, закрыть и reopen приложение, восстановить сеть — все 3 сообщения доставляются собеседнику ровно по одному разу, в порядке отправки.

**Acceptance Scenarios**:

1. **Given** пользователь без сети отправляет сообщение, **When** оно создаётся, **Then** оно видно в диалоге со статусом «отправляется» и сохранено в локальной очереди.
2. **Given** в очереди несколько сообщений и сеть восстановилась, **When** выполняется отправка, **Then** сообщения уходят в порядке постановки в очередь (в рамках одного чата) и получают статус «доставлено» по подтверждению сервера.
3. **Given** при отправке очередного сообщения из очереди сервер уже принял его (подтверждение потерялось из-за нового разрыва), **When** клиент повторяет отправку, **Then** у собеседника сообщение появляется один раз (дедупликация по ID).
4. **Given** сообщение из очереди получает от сервера постоянный отказ (например, получатель заблокировал отправителя, чат удалён), **When** отказ получен, **Then** сообщение переходит в терминальный статус «не отправлено» с показом ошибки, автоматические повторы прекращаются; остальные сообщения очереди обрабатываются дальше.
5. **Given** приложение закрыто с непустой очередью, **When** пользователь снова открывает приложение (даже без немедленной сети), **Then** очередь сохранена и видна со статусами; при появлении сети отправка продолжается автоматически.
6. **Given** при восстановлении сети клиент «догоняет» лимит отправки (30 сообщений в минуту на пользователя), **When** очередь рассыпается быстрее лимита, **Then** отправка выполняется с учётом лимитного окна (отложенно, с теми же ID), без потери сообщений очереди и без обхода лимита.

### User Story 3 - Индикаторы непрочитанных сообщений по чатам (Priority: P3)

Для каждого чата в списке чатов пользователь видит числовой счётчик непрочитанных сообщений. Сообщения, полученные в реальном времени и дозагруженные синхронизацией после разрыва, одинаково увеличивают счётчики. При открытии чата и прочтении сообщений счётчик этого чата сбрасывается, а у отправителя появляются двойные галочки.

**Why this priority**: Непрочитанные — ключевой сигнал «вас ждут ответы»; без корректного счёта после оффлайн-периода пользователь теряет ориентацию. Зависит от синхронизации (Story 1), поэтому P3.

**Independent Test**: Получить сообщения в двух чатах (одно в реальном времени, одно после переподключения), не открывая их — счётчики обоих чатов увеличиваются; открыть чаты — счётчики сбрасываются, у отправителей появляются двойные галочки.

**Acceptance Scenarios**:

1. **Given** у пользователя есть чаты без новых сообщений, **When** в один из чатов приходит новое сообщение, **Then** на чате появляется числовой счётчик непрочитанных, увеличивающийся на единицу.
2. **Given** пользователь был оффлайн и пропустил сообщения в нескольких чатах, **When** выполняется синхронизация, **Then** счётчики этих чатов увеличиваются на фактическое число пропущенных сообщений (ни «всплытия прочитанными», ни задвоенного счёта).
3. **Given** чат открыт с непрочитанными, **When** пользователь видит сообщения, **Then** счётчик чата сбрасывается, у отправителей формируются события «прочитано» (двойная галочка).
4. **Given** число непрочитанных в чате велико, **When** отображается счётчик, **Then** показывается «99+» вместо точного числа, а внутренний счёт хранит точное значение.
5. **Given** действует блокировка в диалоге (фича 004), **When** приходят сообщения от заблокированного пользователя, **Then** поведение бейджа соответствует спецификации 004 (бейдж «заморожен» — не растёт и не сбрасывается до разблокировки).
6. **Given** пользователь читает пропущенные сообщения, дозагруженные постранично, и листает историю, **When** прочитаны не все страницы, **Then** счётчик уменьшается на фактически прочитанное, а не сбрасывается целиком.

### User Story 4 - Контролируемая деградация под пиковой нагрузкой (Priority: P4)

Под нагрузкой, приближающейся к бюджету системы (100 000 сообщений/сек), система не отказывает внезапно, а деградирует предсказуемо и поэтапно: сначала растёт задержка доставки, затем к отправителям применяется backpressure (система просит замедлиться) и rate limiting (временный отказ с понятной ошибкой и указанием, когда повторить); уже принятые сервером сообщения доставляются в приоритете и не теряются. После спада пика система возвращается к нормальным показателям без ручного вмешательства.

**Why this priority**: Устойчивость к пику защищает всех пользователей, но требует, чтобы базовые механизмы доставки уже работали; это надстройка над Stories 1–2. При этом нагрузочный бюджет — конституционное требование проекта.

**Independent Test**: Нагрузочный тест: подать поток сообщений, превышающий плановую пропускную способность, — система отвечает временными отказами с указанием задержки, ни одно принятое сообщение не теряется и не дублируется, после снижения потока показатели возвращаются к норме.

**Acceptance Scenarios**:

1. **Given** входящий поток сообщений приближается к границе бюджета 100 000 сообщений/сек, **When** пропускная способность исчерпывается, **Then** задержка доставки растёт раньше, чем начинаются отказы в приёме (деградация плавная, не обрыв).
2. **Given** система перегружена, **When** отправитель превышает свою долю ресурсов, **Then** он получает явный временный отказ (backpressure) с указанием задержки до повтора; повтор по истечении задержки тем же ID не создаёт дубликат.
3. **Given** применяются ограничения под пиком, **When** пользователь отправляет сообщения, **Then** его собственный лимит отправки (30 сообщений в минуту) продолжает действовать и не может быть обойдён через повторы.
4. **Given** сервер принял сообщение к доставке (подтверждение отправителю сформировано), **When** нагрузка продолжает расти, **Then** это сообщение доставляется получателю — приём новых не вытесняет доставку принятых; потерь и дублей нет.
5. **Given** пик миновал, **When** входящий поток возвращается к обычному, **Then** задержки и отказы сходят на нет без ручного вмешательства (рекавери), очереди рассасываются.
6. **Given** под пиком часть функций требует жертвовать, **When** выбирается, чем пожертвовать, **Then** приоритет сохраняется у доставки принятых сообщений и синхронизации критических состояний; второстепенное (индикаторы присутствия, массовые рассылки уведомлений) деградирует первым.

### Edge Cases

- Разрыв соединения длится дольше окна активной истории (сообщения ушли в архив по сроку 12 месяцев): синхронизация продолжается со старейшей доступной позиции с явной меткой обрезки, а не падает ошибкой.
- «Скачок» соединения (многократные разрыв-восстановление в секундах): клиент не запускает параллельных конкурирующих синхронизаций; курсор монотонен.
- Часы клиента сбиты или переведены: корректность порядка и границ синхронизации определяется серверной позицией сообщений, а не временем клиента.
- Оффлайн-очередь достигла лимита хранения на клиенте (по умолчанию 1000 сообщений): пользователь явно уведомлён; новые сообщения в очередь принимаются с предупреждением о вытеснении старейших неподтверждённых.
- Сообщение из оффлайн-очереди окончательно отклонено навсегда-временной причиной (блокировка) — обрабатывается по правилам фичи 004 (терминальный статус «не отправлено»), очередь не блокируется.
- Одновременная отправка из оффлайн-очереди и реалтайм-отправка в один чат после восстановления сети: порядок в рамках чата определяется фактическим порядком принятия сервером.
- Синхронизация и события «прочитано» приходятся на один момент (пользователь открыл чат во время дозагрузки): счётчик не уходит в минус и не задваивается.
- Сервер частично доступен (часть инстансов перегружена): клиент получает консистентный результат — либо полные данные, либо явный временный отказ с повтором, но никогда не «частичный список как полный».
- Курсор клиента «из будущего» относительно позиции чата (данные восстановлены из резервной копии): сервер не возвращает ошибку всему запросу, а обрабатывает корректно идентифицируемую часть и сообщает о рассинхронизации по затронутым чатам.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST поддерживать по каждому чату каждого пользователя курсор последнего полученного сообщения и по запросу клиента возвращать все сообщения этого чата, следующие за курсором.
- **FR-002**: Синхронизация после переподключения MUST обеспечивать эффект exactly-once для пользователя: каждое пропущенное сообщение доставляется ровно один раз, без пропусков, с сохранением порядка в рамках чата.
- **FR-003**: Синхронизация MUST выполняться по всем чатам пользователя одним механизмом (не отдельным ручным действием по каждому чату) и поддерживать постраничную дозагрузку больших объёмов.
- **FR-004**: Дубликаты доставки (повторная отправка одного сообщения сервером или повтор запроса клиентом) MUST подавляться дедупликацией по уникальному ID сообщения; повторные попытки безопасны и не порождают дублей.
- **FR-005**: Клиент MUST ставить исходящие сообщения в локальную очередь при недоступности сети, сохранять её между запусками приложения и автоматически отправлять при восстановлении связи в порядке постановки (в рамках чата), с исходными ID.
- **FR-006**: Постоянный отказ сервера на сообщение из очереди (блокировка, удалённый чат, недопустимое содержимое) MUST переводить это сообщение в терминальный статус «не отправлено» с показом ошибки пользователю и прекращением автоматических повторов; обработка остальных сообщений очереди продолжается.
- **FR-007**: Система MUST вести счётчики непрочитанных сообщений по каждому чату; и реальные, и дозагруженные синхронизацией сообщения одинаково увеличивают счётчики.
- **FR-008**: Прочтение сообщений MUST сбрасывать счётчик соответствующего чата на фактически прочитанное число и формировать события «прочитано» для отправителей; отображение «99+» не искажает внутренний счёт.
- **FR-009**: Под нагрузкой система MUST применять backpressure к отправителям: явный временный отказ с указанием задержки до повтора, а не молчаливое ожидание или обрыв.
- **FR-010**: Система MUST применять rate limiting к отправке сообщений (включая лимит 30 сообщений в минуту на пользователя из фичи 004) и сохранять его действие под пиковой нагрузкой, исключая обход через повторы.
- **FR-011**: Деградация под нагрузкой MUST быть поэтапной и предсказуемой: сначала рост задержки, затем ограничение приёма новых сообщений; уже принятые к доставке сообщения доставляются в приоритете и не теряются.
- **FR-012**: Система MUST устойчиво доставлять сообщения в пределах бюджета 100 000 сообщений/сек (подтверждается нагрузочным тестом), сохраняя гарантии отсутствия потерь и дублей.
- **FR-013**: После спада пиковой нагрузки система MUST самостоятельно возвращаться к штатным показателям задержки и отказов (самовосстановление, без ручного вмешательства).
- **FR-014**: Система MUST предоставлять наблюдаемость механизмов фичи: метрики и логи доставки (в т.ч. потери/дубли/порядок при разрывах), синхронизации по курсору, размеров и рассасывания очередей, срабатываний backpressure/rate limiting, счётчиков непрочитанных.

### Key Entities *(include if feature involves data)*

- **Курсор синхронизации (Sync Cursor)**: позиция последнего сообщения, фактически полученного пользователем в чате; принадлежит паре «пользователь — чат»; монотонно движется вперёд; служит отправной точкой дозагрузки пропущенного.
- **Элемент оффлайн-очереди (Queued Outgoing Message)**: исходящее сообщение, созданное клиентом при недоступности сети; хранит уникальный ID сообщения, содержимое, целевой чат, порядок постановки и текущий клиентский статус («отправляется» / «доставлено» / «не отправлено»).
- **Счётчик непрочитанных (Unread Counter)**: число непрочитанных сообщений чата для конкретного пользователя; точное внутреннее значение с отображением «99+» при больших числах; сбрасывается/уменьшается по факту прочтения.
- **Сигнал backpressure (Backpressure Signal)**: временный отказ в приёме отправки, адресованный конкретному отправителю, с указанием задержки до допустимого повтора; идемпотентен по отношению к повторной отправке того же ID.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: При разрывах соединения любой длительности (от секунд до часов) и переподключении пользователь получает 100 % пропущенных сообщений — 0 пропусков и 0 дубликатов при отображении (проверяется интеграционными тестами с принудительными разрывами в разных точках пути доставки).
- **SC-002**: Все сообщения, созданные пользователем оффлайн, доставляются получателям при восстановлении связи ровно по одному разу каждая, в порядке отправки в рамках чата, включая сценарий закрытия приложения до восстановления сети.
- **SC-003**: После синхронизации счётчики непрочитанных по чатам совпадают с фактическим числом непрочитанных сообщений; прочтение приводит счётчики и события «прочитано» у отправителей к консистентному состоянию.
- **SC-004**: Система выдерживает устойчивый поток 100 000 сообщений/сек с доставкой без потерь и дублей (нагрузочный тест; конституционный бюджет).
- **SC-005**: При входном потоке сверх пропускной способности доля внезапных (без явного backpressure-сигнала) отказов равна нулю: отправители всегда получают либо приём, либо временный отказ с указанием задержки; система не переходит в полный отказ.
- **SC-006**: После снятия пиковой нагрузки показатели доставки (задержка, доля отказов) возвращаются к штатным значениям в течение 5 минут без вмешательства оператора.
- **SC-007**: Ни одно сообщение, подтверждённое отправителю как принятое, не теряется и не дублируется у получателя ни в штатном, ни в перегруженном режиме.

## Assumptions

- Многоустройственность (несколько параллельных сессий одного пользователя с раздельной синхронизацией) вне объёма данной фичи; курсор и счётчики непрочитанных ведутся на пользователя, одна активная сессия.
- Суммарный (агрегированный по всем чатам) индикатор непрочитанных вне объёма данной фичи; счётчики ведутся только по отдельным чатам.
- Механизмы фичи 004 доступны и переиспользуются: уникальные client-generated ID сообщений, серверная дедупликация, статусы «отправляется/доставлено/прочитано», лимит 30 сообщений в минуту на пользователя, терминальный статус «не отправлено».
- Окно активной истории для синхронизации по умолчанию соответствует хранению 12 месяцев (конституция); более старые сообщения доступны через архив, но не через reconnect-синхронизацию.
- Лимит локальной оффлайн-очереди по умолчанию — 1000 сообщений на пользователя (с уведомлением при вытеснении старейших неподтверждённых); значение может уточняться на этапе планирования.
- Групповые чаты (фича 006) и E2EE-беседы (фича 011) на момент данной фичи не реализованы; механизм синхронизации проектируется расширяемым на них, но их специфика в объём не входит.
- Двойные галочки «прочитано» и заморозка бейджа при блокировке соответствуют уточнениям фичи 004 и здесь не переопределяются.
- Требования к разрывам включают как обрывы сети клиента, так и недоступность сервера/промежуточных компонентов: пользовательский эффект (нет потерь и дублей) одинаков.
