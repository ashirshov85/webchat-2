# Contract: Протокол синхронизации доставки (курсоры, ack, догоняющая дозагрузка)

**Feature**: 005-delivery-resilience | **Источник истины**: `contracts/openapi.yaml`
(операции №25/№26, расширение №15; схемы `DeliveryAckRequest`, `SyncRequest`, `SyncResponse`,
`SyncChatDelta`, `MessagePage.nextAfter`)

Нормативное описание клиент-серверного протокола устойчивой доставки: позиция доставки
продвигается подтверждениями (ack) клиента; пропущенное дозагружается pull'ом по курсору;
непрочитанные и статусы сходятся с сервером. Решения и обоснование —
[research.md §1–§4, §7](../research.md); модель данных — [data-model.md](../data-model.md).
Реалтайм-канал (SSE №18) — без изменений 004 ([realtime-channel.md 004](../../004-direct-messaging-core/contracts/realtime-channel.md));
настоящий протокол сосуществует с ним: realtime — оптимизация латентности, курсорный pull —
гарантия полноты.

## 1. Координаты и инварианты

- **Курсор** чата — `per-chat seq` последнего фактически полученного сообщения (серверный `seq`
  из 004; монотонный номер, назначаемый при приёме). Принадлежит паре «пользователь–чат».
- **Серверная позиция доставки** `delivered_up_to_seq` (PG) движется **только** операцией ack
  (№25): ни SSE-кадр, ни sync-ответ её не пишут. Идемпотентна и монотонна (GREATEST).
- **Клиентский курсор** (localStorage) = эхо успешного ack: применяется монотонно (только max);
  единственная перемотка назад — ремонт по `serverUpToSeq` (§5). При переподключении клиент
  передаёт карту курсоров в №26; сервер использует её как нижнюю границу своей позиции
  (эффективный курсор = `max(клиентский, серверный)`).
- **Нижняя граница дозагрузки** чата: `GREATEST(deleted_up_to_seq, окно активной истории)` —
  per-user удаление 004 не восстанавливается; удаление чата собеседником границу не меняет.
  Окно 12 мес (конституция) до реализации archival (009) фактически не отсекает.
- **Порядок и границы** определяются только серверным `seq`; часы клиента не участвуют.
- **Дедупликация** — по `message.id` (клиент, идемпотентный рендер 004): повторная доставка
  тем же ID отображается один раз (US1-3); повтор pull-запроса безопасен.
- Мультидевайс вне объёма (Assumptions): один активный клиент на пользователя.

## 2. Ack — `POST /api/v1/users/me/delivery-ack` (№25)

- Тело: `{acks: [{chatId: uuid, upToSeq: int64 ≥ 1}], ≤ 100 элементов}` → `204`.
- Семантика: батчевое монотонное продвижение позиции доставки вызывающего
  (`GREATEST`-обновление строк участника; повтор/меньшее значение — без эффекта). Одна
  транзакция: чужой `chatId` → `403 not_participant`, несуществующий → `404 chat_not_found`,
  `upToSeq > chats.last_seq` → `400 invalid_up_to_seq` — **весь батч отклоняется**, частичных
  эффектов нет.
- Источники ack клиента:
  - **realtime**: применённые кадры `message.created` подтверждаются дебаунс-батчером
    (флаш ≤ 1 с; `upToSeq = max(seq)` по каждому чату); неуспешный ack ретраится следующим
    флашем;
  - **догоняющая синхронизация**: каждая применённая страница (№26-дельта или №15 `after`)
    → ack с `upToSeq = max(seq страницы, truncatedUpToSeq)`;
  - **точка обрезки**: `truncatedUpToSeq` ack'ается как обычная позиция (§5).
- Ack не порождает realtime-событий (позиция — приватное состояние).

## 3. Догоняющая синхронизация — `POST /api/v1/users/me/sync` (№26)

Safe/idempotent query-операция (POST — per-chat карта курсоров в теле). Тело:
`{cursors: [{chatId, upToSeq}], chatLimit?: 1–50 (default 20), messageLimit?: 1–50 (default 50)}`.

Ответ `200 SyncResponse`:

```json
{
  "chats": [
    {
      "chatId": "7dc5…", "peer": {…}, "blockedByMe": false,
      "startAfterSeq": 128,
      "truncatedUpToSeq": 42,
      "messages": [ {…Message asc…} ],
      "hasMore": true,
      "peerReadUpToSeq": 100,
      "unreadCount": 7,
      "lastSeq": 260
    }
  ],
  "moreChats": false
}
```

- В `chats` — только чаты с недоставленным (эффективный курсор < максимальный видимый seq),
  **по последней активности DESC** (первыми — чаты с самыми новыми сообщениями), до `chatLimit`;
  `moreChats: true` — недоставленные чаты остались. Чужие/несуществующие `chatId` в `cursors`
  молча игнорируются (per-user операция; в отличие от атомарного батча №25).
- Дельта чата: `startAfterSeq` — эффективный курсор возобновления (после обрезки/ремонта —
  клиент продвигает локальный курсор до него до применения сообщений); `messages` — ascending,
  `(startAfterSeq, …]` до `messageLimit`, только видимые (`seq > deleted_up_to_seq`), включая
  исходящие пользователя; `hasMore` — хвост за пределами страницы; `peerReadUpToSeq` —
  накопленные оффлайн статусы собственных сообщений (✓✓); `unreadCount` — серверный счётчик
  с учётом страницы; `lastSeq` — текущий `chats.last_seq`.
- Пропущенные поля (`truncatedUpToSeq`, `desynced`) отсутствуют, когда явление не возникло.
- Операция **не** двигает позицию доставки; консистентность ответа — один снимок чтения:
  либо полный корректный ответ, либо 5xx/503 (повтор); «частичный список как полный» исключён
  (`hasMore`/`moreChats` вычислены в том же снимке).

### 3.1 Клиентский цикл (нормативный алгоритм)

```text
on SSE (re)open → flushPendingReads()            (№17 по каждой записи pendingReads)
                 → если in-flight sync: ждать (single-flight)
                 → цикл A:
                     resp = №26(cursors, 20, 50)
                     для каждой дельты (по порядку):
                       курсор[chat] = startAfterSeq              (self-heal)
                       если truncatedUpToSeq: отметить обрезку в UI
                       render(messages) по seq, дедуп по id      (гонка с realtime безопасна)
                       ack(max(последний seq страницы | truncatedUpToSeq))
                       курсор[chat] = подтверждённая позиция
                     если hasMore у чата → цикл B по чату:
                       page = №15(chat, after=курсор, limit=50)
                       render + ack + курсор, пока nextAfter присутствует
                     если resp.moreChats → повтор цикла A (курсоры обновлены)
                 → синхронизация завершена (индикатор погас)
```

- **Single-flight**: параллельные конкурирующие синхронизации запрещены (edge «скачок
  соединения»); обрыв посреди цикла — курсор остаётся на последней подтверждённой позиции,
  следующий `(re)open` возобновляет с неё (US1-4).
- Realtime работает параллельно: кадры, пришедшие во время дозагрузки, применяются немедленно
  (дедуп по id); сообщения, подтверждённые realtime-ack, не вернутся в следующем №26
  (эффективный курсор уже продвинут).

## 4. Per-chat дозагрузка — `GET /chats/{chatId}/messages?after=<seq>` (№15, расширение)

- `after` (эксклюзивный, int64 ≥ 0) — ascending-режим: страницы `(after, after+limit]` по
  `seq ASC`, ответ содержит `nextAfter` (seq последней записи страницы; отсутствует, когда
  новее нет). `before` (DESC, 004) — без изменений; `after` и `before` вместе → `400
  mixed_cursors`. `limit` 1–50 (default 50). Видимость — по `deleted_up_to_seq` вызывающего.
- Источник для продолжения `hasMore`-чатов из №26; также применим автономно (любой контрактный
  клиент).

## 5. Обрезка и ремонт

- **Обрезка** (курсор ниже нижней границы: per-user удаление чата 004, возврат чата новым
  входящим, курсор 0 нового чата): дельта несёт `truncatedUpToSeq = effectiveLower`,
  `startAfterSeq = effectiveLower`, сообщения ниже не возвращаются; клиент ack'ает
  `max(страница, truncatedUpToSeq)` — позиция доставки и курсор закрепляются на точке обрезки;
  сообщения ниже точки — недоступные, в счётчик непрочитанных не входят; удалённая история не
  восстанавливается; удаление чата собеседником на синхронизацию не влияет.
- **«Курсор из будущего»** (клиентский `upToSeq` противоречит серверным данным — восстановление
  из резервной копии): всему запросу ошибки нет; по затронутым чатам дельта несёт
  `desynced: true` + `serverUpToSeq` (фактическая серверная позиция), клиент отматывает
  локальный курсор на `serverUpToSeq` и продолжает штатно; остальные чаты обрабатываются как
  обычно.

## 6. Непрочитанные и прочтения

- Серверно-авторитарный счётчик: `unread = COUNT(входящих, seq > max(last_read,
  deleted_up_to_seq), seq <= min(last_seq, delivered_up_to_seq))` — растёт по ack доставки
  (realtime и sync одинаково), уменьшается по прочтению; отображение «99+» — клиентский рендер.
- **Оффлайн-прочтения**: клиент пишет per-chat watermark `pendingReads[chatId] = upToSeq`
  **до** попытки `POST /chats/{id}/read` (№17) и удаляет после `204`; на reconnect — флаш всех
  записей через идемпотентный №17 (серверный GREATEST делает повтор безопасным); серверный
  счётчик сходится с фактически прочитанным, у отправителей формируются ✓✓ (`chat.read`, 004).
  Применимо к ранее синхронизированным сообщениям (`upToSeq ≤ delivered` клиента).
- Открытие чата во время дозагрузки: прочтение применяется к фактически отображённому
  (watermark), счётчик не уходит в минус (нижняя граница формулы — GREATEST с `last_read_seq`).

## 7. Оффлайн-очередь отправки и временные отказы (клиентская сторона)

- Отправка без сети / при временном отказе — сообщение сразу пишется в персистентную очередь
  (localStorage, переживает перезапуск) со статусом «отправляется» и отображается в диалоге.
- `503 server_busy` (№16, backpressure) и `429 flood_limit` обрабатываются одинаково
  **прозрачно**: запись остаётся «отправляется», повтор тем же `clientMessageId` в момент
  `Retry-After`; ошибка пользователю не показывается (FR-009/FR-010). Сетевые ошибки/5xx/401 —
  backoff 1с…30с тем же ID, бессрочно. Терминальный статус «не отправлено» — только постоянный
  отказ (403/409/400 — как 004) или вытеснение при переполнении очереди (лимит 1000; старейшие
  `sending` → «не отправлено», причина `queue_overflow`, уведомление пользователю).
- Флаш очереди при восстановлении связи — FIFO per-chat; лимитное окно 30/мин соблюдается
  планировщиком (`retryAt`), лимит не обходится повторами (флуд-бакет на сервере).
- Порядок в рамках чата определяется фактическим порядком принятия сервером (edge «одновременная
  отправка из очереди и реалтайм»).

## 8. Backpressure на отправке — `503 server_busy` (№16, дополнение)

- Временный отказ в приёме отправки при перегрузке: `503` `application/problem+json`
  `errors: {chat: [server_busy]}` + `Retry-After` (сек ≥ 1). Деградация поэтапна: сначала рост
  задержки, затем отказы; принятые (201/200) доставляются в приоритете и не теряются; после
  спада пика — самовосстановление.
- Дедуп-фастпас стоит раньше admission: повтор **уже принятого** сообщения тем же ID всегда
  возвращает `200` записи (никогда 503/429) — ретраи сходятся, повторы не создают дубликатов.
- Перегруженный (деградированный) режим наблюдаем: от первого backpressure/rate-limit-сигнала
  до рассасывания очередей (метрики `webchat_backpressure_*`, SC-004).
