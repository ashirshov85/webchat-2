# Data Model: Устойчивость доставки при разрывах соединения и пиковой нагрузке

**Feature**: 005-delivery-resilience | **Date**: 2026-09-23

Единственное новое долговечное состояние — PostgreSQL 17, миграция **V12__delivery_sync.sql**
(одна колонка на существующей таблице + backfill; конвенции 002/004: snake_case, CHECK-инварианты,
GREATEST-монотонность водяных знаков). Redis 7 — без изменений (`rl:user:msgsend:*`,
`rl:user:search:*`, `rt:user:{userId}` из 002/004). Пользователи/чаты/сообщения/блокировки —
сущности 002/004, здесь только расширяются. Клиентские хранилища — localStorage (курсоры,
pendingReads, outbox).

Диаграмма связей (дельта к 004):

```text
users (002) ──< chat_participants >── chats ──< messages
                    │  + delivered_up_to_seq   (004, без изменений)
                    │    (V12: позиция доставки, движется только ack №25)
                    └── выводно: unreadCount = f(last_read, deleted, delivered, last_seq)

client localStorage:
  webchat.sync.cursors.<userId>      {chatId: seq}   — локальный курсор (эхо ack, монотонный)
  webchat.sync.pendingReads.<userId> {chatId: seq}   — оффлайн «прочитано» (флаш №17)
  webchat.chats.outbox.<userId>      [OutboxRecord]  — 004 + лимит 1000 / queue_overflow

in-memory per-instance (транспортное, сброс безопасен — конституция II):
  GradientAdmissionLimiter           in-flight/лимит/EWMA латентности → 503 №16
```

---

## Сущность 1: Позиция доставки / курсор синхронизации (Sync Cursor)

Серверное представление курсора — колонка строки участника; клиентское — localStorage-эхо ack.
Пара «пользователь–чат», значение = seq последнего **подтверждённо полученного** сообщения
(FR-001, Key Entities).

| Поле | Тип | Валидация / инварианты |
|---|---|---|
| `chat_participants.delivered_up_to_seq` | bigint NOT NULL DEFAULT 0 | CHECK `>= 0`; монотонна — только вперёд: `UPDATE … SET delivered_up_to_seq = GREATEST(delivered_up_to_seq, :upToSeq) WHERE chat_id=… AND user_id=… AND delivered_up_to_seq < :upToSeq`; rowcount 0 — без эффекта (идемпотентно); двигается **только** операцией №25 (ack) — ни sync-ответ, ни realtime-кадр её не пишут |

**Операции**:
- **№25 ack** `{acks: [{chatId, upToSeq}] ≤ 100}`: батч GREATEST-обновлений в одной транзакции;
  предварительная проверка membership всех chatId (чужой → `403 not_participant`, несуществующий
  → `404 chat_not_found` — весь батч отклоняется, частичных эффектов нет). `upToSeq` сверх
  `chats.last_seq` → `400 invalid_up_to_seq` (как №17 в 004). Источники: realtime-батчи
  (дебаунс ≤ 1 с), страницы sync/ascending-истории, точка обрезки.
- **Чтение** (без записи): №26 sync и №15 `after` используют эффективный курсор
  `startAfterSeq = GREATEST(клиентский upToSeq, серверная позиция)` — серверная позиция не
  «верит» клиенту сверх фактов: клиентский курсор применяется к серверному состоянию как
  нижняя граница через GREATEST; «будущий» курсор чинится per-chat (§3 сущности 2).
- **Backfill V12**: `UPDATE chat_participants SET delivered_up_to_seq =
  GREATEST(last_read_seq, deleted_up_to_seq)` — прочитанное/удалённое заведомо «позади»;
  непрочитанный хвост становится недоставленным и доедет первым sync'ем (объём = unread-задел
  на момент миграции).

**Переходы состояния** (сводно; клиентская зеркальная машина — курсор в localStorage):

```text
delivered_up_to_seq: 0 … last_seq — монотонно вперёд только ack'ом
  ack(upToSeq ≤ delivered)        → без эффекта (повтор/дубль доставки)
  ack(upToSeq > delivered ≤ last) → delivered = upToSeq
  sync-ответ / SSE-кадр           → НЕ двигает (до ack клиентом применённой страницы)
  точка обрезки T > delivered     → delivered = T (клиент ack'ает max(страница, T))
  «будущий» курсор (backup)       → сервер не откатывает delivered; клиент отматывает
                                    локальный курсор на serverUpToSeq (ремонт клиента)
```

## Сущность 2: Дельта синхронизации (SyncChatDelta — выводная, не хранится)

Результат №26 по одному чату; все поля вычисляются в одном снимке чтения (консистентность
«частичный список как полный» исключён — edge).

| Поле | Тип | Валидация / инварианты |
|---|---|---|
| `chatId` / `peer` / `blockedByMe` | uuid / PublicUser / boolean | как №12 (004) |
| `startAfterSeq` | int64 ≥ 0 | эффективный курсор возобновления: `max(клиентский, серверный)` после ремонта/обрезки; клиент продвигает локальный курсор до него |
| `truncatedUpToSeq?` | int64 ≥ 1 | присутствует только при обрезке: `startAfterSeq = GREATEST(deleted_up_to_seq, окно_истории) > исходный курсор`; сообщения ниже — недоступные (не непрочитанные); клиент ack'ает точку (закрепление позиции на ней) |
| `messages` | Message[] ≤ messageLimit | ascending `seq`, строго `(startAfterSeq, …]`, только видимые (`seq > deleted_up_to_seq`), включая исходящие пользователя (порядок/контекст) |
| `hasMore` | boolean | в чате осталось сообщений сверх страницы: `lastSeq > seq(messages.last)` (true и при пустой странице с хвостом ниже границы видимости — невозможно: граница уже учтена) |
| `peerReadUpToSeq` | int64 ≥ 0 | водяной знак собеседника — догоняющая синхронизация статусов ✓✓ собственных сообщений (FR-003, US3-8) |
| `unreadCount` | int64 ≥ 0 | серверный счётчик с учётом применённой страницы (сущность 4) |
| `lastSeq` | int64 ≥ 0 | `chats.last_seq` — детект хвоста клиентом |
| `desynced?` + `serverUpToSeq` | boolean / int64 | только при «курсоре из будущего» (клиентский > `lastSeq` при видимых данных или > серверной позиции): ремонт — клиент отматывает локальный курсор на `serverUpToSeq`; остальной ответ штатный |

Порядок чатов в ответе: по последней активности DESC (`chats.last_seq DESC`, tie-break
`created_at DESC, chat_id`) — первыми догружаются чаты с самыми новыми сообщениями (FR-003).
Отбор: чаты участника с `max(видимый seq) > эффективный курсор` (недоставленное есть), до
`chatLimit` (1–50, default 20); остаток — `moreChats: true`.

## Сущность 3: Счётчик непрочитанных (Unread Counter — выводный, серверно-авторитарный)

| Аспект | Правило |
|---|---|
| Формула | `unread(user, chat) = COUNT(messages WHERE chat_id = chat AND sender_id != user AND seq > GREATEST(last_read_seq, deleted_up_to_seq) AND seq <= LEAST(chats.last_seq, delivered_up_to_seq))` |
| Источник истины | сервер (FR-007): вычисляется в №12 (список) и №26 (дельты); клиент отображает/кэширует локально оптимистично и сходится к серверному значению |
| Динамика realtime | кадр применён → ack (дебаунс ≤ 1 с) → `delivered` растёт → счётчик растёт (US3-1) |
| Динамика reconnect | заморожен на время оффлайна (позиция не движется); sync-страница → ack → растёт до фактического числа пропущенных (US3-2) — ни «всплытия прочитанными», ни задвоения (счётчик выводной, не инкрементальный) |
| Прочтение | №17 GREATEST `last_read_seq` (004, без изменений) → уменьшается на фактически прочитанное, включая постраничное (US3-6: watermark растёт по мере прокрутки) |
| Обрезка | сообщения ниже `truncatedUpToSeq` не входят (нижняя граница формулы — FR-003/US1-5) |
| Блокировка | «заморозка» 004 сохраняется натурально (нет новых сообщений, прочтения подавлены) — US3-5 |
| «99+» | клиентский рендер при > 99; внутренний счёт точный (004, без изменений) |

## Сущность 4: Элемент оффлайн-очереди (Queued Outgoing Message — клиентская, эволюция 004)

| Поле | Тип | Валидация / инварианты |
|---|---|---|
| `clientMessageId` | uuid | как 004: ключ идемпотентности, ретраи тем же ID сходятся (№16 дедуп) |
| `chatId` / `text` | uuid / string | без изменений |
| `state` | `sending \| failed` | `failed` — терминальный (004) **или** вытеснение (новое) |
| `errorCode?` | string | контрактный код постоянного отказа **или** клиентский `queue_overflow` |
| `retryAt?` | epoch ms | 429 `flood_limit` (004) **и** новый 503 `server_busy` — Retry-After |

**Лимит и вытеснение (FR-005)**: максимум 1000 записей на пользователя (константа клиента);
при превышении новые записи принимаются, **старейшие `sending`** (начало массива) вытесняются:
`state = failed`, `errorCode = 'queue_overflow'`, автоповторы прекращаются, сообщение остаётся
видимым в диалоге; пользователь уведомляется баннером. Вытесненное повторно в очередь не
принимается (ручной retry тем же ID допустим — идемпотентность сохранена). `failed`-записи
не вытесняются.

**Классификация ошибок отправки** (эволюция 004): сеть/таймаут/401/5xx → `sending` + backoff
1с…30с; `429 flood_limit` → `sending` + `retryAt = now + Retry-After` (004); **`503 server_busy`
→ то же, что 429** (прозрачная очередь, без ошибки пользователю — FR-009); прочие 4xx (400/403/
404/409) → `failed` терминально (FR-006, 004). Повторы при временных отказах бессрочны; никаких
эскалаций по времени (clarify).

**Порядок**: массив = порядок постановки; флаш FIFO per-chat (чат не ждёт чужой блокировки);
порядок в чате на сервере = фактический порядок принятия (edge: одновременная отправка из
очереди и реалтайм).

## Сущность 5: Оффлайн-событие «прочитано» (PendingRead — клиентская, новая)

| Поле | Тип | Валидация / инварианты |
|---|---|---|
| `chatId` | uuid | ключ карты |
| `upToSeq` | int64 ≥ 1 | локальный watermark «прочитано, но не подтверждено сервером»; монотонен локально |

Хранилище `webchat.sync.pendingReads.<userId>`; запись — **до** попытки №17, удаление — после
`204`; переживает перезапуск. Флаш на reconnect через идемпотентный №17 (GREATEST — повторный
флаш после потери ответа безопасен, FR-008/US3-7). Оффлайн-прочтение касается только ранее
синхронизированных сообщений (US3-7: `upToSeq ≤ delivered` локально).

## Сущность 6: Сигнал backpressure (Backpressure Signal — выводной + in-memory)

| Аспект | Правило |
|---|---|
| Представление | HTTP `503` + `errors: {chat: [server_busy]}` + `Retry-After` (сек ≥ 1) на №16; идемпотентен к повтору тем же `clientMessageId` (дедуп-фастпас №16 стоит до admission — ретрай принятого сообщения никогда не получает 503, FR-009) |
| Состояние лимитера | in-memory per-instance: `in-flight`, `limit` (AIMD по gradient латентности), EWMA латентности пути PG-коммита; границы `delivery.backpressure.{min-limit,max-limit,…}`; сброс/рестарт безопасен — состояние самовосстанавливается измерением (транспортное, конституция II по прецеденту SSE-реестра 004) |
| Retry-After | `ceil(in-flight × EWMA / max(limit,1))`, минимум 1 с — оценка рассасывания очереди |
| Порядок в №16 | дедуп-фастпас → **admission** → membership → валидация → флуд (429) → блокировки → INSERT; флуд-токены не сгорают на shed'ах — после спада лимит 30/мин действует и не обходится повторами (FR-010) |
| Деградация поэтапно | 1) рост латентности (естественная очередь; p99 ≤ 2 с в деградированном режиме — SC-004); 2) 503 с Retry-After (SC-005: 0 «молчаливых» отказов); принятые доставляются в приоритете (путь доставки без admission — US4-4); рекавери AIMD ≤ 5 мин (SC-006, FR-013) |

## Сущность 7: Redis / SSE (без изменений 004 — перечисление)

| Ключ/канал | Назначение в 005 |
|---|---|
| `rl:user:msgsend:{userId}` | флуд-30/мин — действует под пиком, не обходится (FR-010); порядок относительно admission — сущность 6 |
| `rt:user:{userId}` | `message.created`/`chat.read` — realtime-доставка параллельно pull-синхронизации; кадр не двигает позицию (только ack); клиент дедуплицирует по `message.id` (гонка sync↔realtime безопасна) |

Новых ключей/каналов нет; сброс Redis допустим ( durability — PG, 004).

## Выводные представления API (не хранятся)

- **SyncChatDelta** — сущность 2; **SyncResponse** `{chats: […], moreChats: boolean}`.
- **DeliveryAckRequest/Item** `{acks: [{chatId, upToSeq}]}` (≤ 100).
- **AscendingPage** №15 `?after=`: `{messages: […]` (ascending), `nextAfter?: int64}` —
  добавлено к MessagePage опционально (additive); `after` и `before` взаимоисключающи.
- **ChatListItem.unreadCount** — формула сущности 3 (описание в контракте уточнено, схема
  прежняя).
- Клиентские курсоры `webchat.sync.cursors.<userId>`: `{chatId: seq}` — эхо ack, монотонно
  (кроме документированной перемотки по `serverUpToSeq`).

## Миграция

- **V12__delivery_sync.sql**: `ALTER TABLE chat_participants ADD COLUMN delivered_up_to_seq
  bigint NOT NULL DEFAULT 0` + `CHECK (delivered_up_to_seq >= 0)` + backfill `UPDATE … SET
  delivered_up_to_seq = GREATEST(last_read_seq, deleted_up_to_seq)`. Существующие таблицы 002/004
  больше не меняются; down-path не предусмотрен (Flyway, конвенция 002).

Индексы: ack-обновления идут по PK `(chat_id, user_id)`; для отбора недоставленных чатов в №26
нужен список строк участника по `user_id` (PK ведёт `chat_id`, полный скан нецелесообразен) —
в V12 добавляется `CREATE INDEX ix_chat_participants_user ON chat_participants (user_id)`
(десятки строк на пользователя, top-N доранжируется по `chats.last_seq`).
