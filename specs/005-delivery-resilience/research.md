# Research: Устойчивость доставки при разрывах соединения и пиковой нагрузке

**Feature**: 005-delivery-resilience | **Date**: 2026-09-23

Разрешение всех открытых вопросов Technical Context фичи 005. Контекст: стек и конвейер
зафиксированы 001–004 (Kotlin 2.2 + Spring Boot 3.5 / Gradle KTS, React 19 + TS strict,
OpenAPI 3.1 + codegen + drift/breaking CI, PG 17 + Flyway + Spring JDBC, Redis 7 + Bucket4j +
Lettuce, stateless-поды в K8s). Существуют (004): личные диалоги с серверным `seq` bigserial
(per-chat монотонность), клиентские UUID + дедупликация (`ON CONFLICT` по PK), SSE-поток событий
пользователя `GET /users/me/events` (at-most-once) с рефетчем на реконнекте, водяные знаки
`last_read_seq` / `deleted_up_to_seq`, флуд-лимит 30/мин (Bucket4j + Redis), клиентский outbox
в localStorage (состояния sending/failed, ретраи тем же ID), метрики Micrometer/OTel.
Мультидевайс вне объёма (Assumptions): курсор и счётчики — на пользователя, одна активная сессия.

## 1. Позиция доставки: колонка `delivered_up_to_seq`, продвигаемая только ack

**Решение**:
- Новая колонка `chat_participants.delivered_up_to_seq bigint NOT NULL DEFAULT 0`
  (миграция **V12**), CHECK `>= 0`. Семантика: последнее сообщение, **фактически полученное**
  пользователем в чате (подтверждённое ack'ом) — это и есть серверное представление курсора
  (Key Entities: Sync Cursor). Монотонность — только вперёд, обновление
  `SET delivered_up_to_seq = GREATEST(delivered_up_to_seq, :upToSeq) WHERE … AND
  delivered_up_to_seq < :upToSeq` — идемпотентно и гонкобезопасно, тем же паттерном, что
  `last_read_seq` (004 §5); rowcount = 0 — состояние не меняется, повторные ack безопасны.
- **Ack-операция №25** `POST /api/v1/users/me/delivery-ack`, тело `{acks: [{chatId, upToSeq}], …}`
  (до 100 элементов): батчевое GREATEST-обновление строк участников вызывающего → `204`.
  Один endpoint на все источники ack: realtime-доставки, страницы догоняющей синхронизации,
  страницы ascending-истории (`after`). Ошибка одного элемента (чужой chat / несуществующий) →
  `403/404` по всему запросу (атомарность батча упрощает клиенту выводы; частичные эффекты
  исключены — edge «сервер частично доступен»).
- Ack не публикует событий realtime: позиция доставки — приватное состояние пользователя,
  никто другой его не потребляет (непрочитанные считаются из неё на лету; «доставлено» у
  отправителя в 004 — факт записи сервером, не получение получателем — без изменений).
- Backfill V12: `delivered_up_to_seq = GREATEST(last_read_seq, deleted_up_to_seq)` — прочитанное
  заведомо доставлено; ниже точки удаления ничего не доставляется. Непрочитанный хвост станет
  «недоставленным» и доедет первым sync'ем после деплоя — корректно и ограничено (объём =
  непрочитанный backlog на момент миграции).

**Обоснование**: одна bigint-колонка на пару «пользователь–чат» — O(1) запись на батч доставок
(амортизация N:1: ack шлётся на батч realtime-кадров/страницу, не на кадр), никакого per-message
хранилища квит (write amplification на 100k msg/s недопустим — конституция II; прецедент отклонения
per-recipient строк — 004 §4). GREATEST-паттерн уже испытан `last_read_seq` (идемпотентность,
монотонность, гонкобезопасность). Ack как отдельная операция (а не продвижение внутри sync-ответа)
точно выражает FR-001 «позиция движется только по подтверждениям»: потеря ответа синхронизации
не двигает курсор — повтор запроса возвращает те же сообщения (US1-4: возобновление с последней
фактически полученной позиции).

**Альтернативы отклонены**: per-message delivery-квитанции (`message_deliveries`) — запись на каждое
сообщение (2× write path), агрегация диапазонов на каждый подсчёт; продвижение позиции самим
sync-ответом (без ack) — потеря ответа = пропуск (нарушение US1-4); Redis-хранилище позиции —
нарушение конституции II (долговечное состояние вне процесса должно быть в PG; Redis сбрасываем);
курсор только на клиенте (сервер не хранит) — серверно-авторитарный счётчик непрочитанных (FR-007)
требует серверной позиции.

## 2. Догоняющая синхронизация: агрегированный pull по курсору (№26) + per-chat `after` (№15)

**Решение**:
- **№26** `POST /api/v1/users/me/sync` (safe/idempotent query-операция; POST — тело с per-chat
  картой курсоров, неограниченное GET-query): тело `{cursors: [{chatId, upToSeq}], chatLimit?
  (1–50, по умолчанию 20), messageLimit? (1–50, по умолчанию 50)}`. Ответ `SyncResponse`:
  - `chats: [SyncChatDelta]` — только чаты с недоставленным (эффективный курсор < максимального
    видимого seq), **по последней активности DESC** (первыми — чаты с самыми новыми сообщениями,
    FR-003), до `chatLimit`:
    - `chatId`, `peer`, `blockedByMe`;
    - `startAfterSeq` — эффективный курсор, с которого возобновлена доставка (может отличаться от
      присланного после ремонта/обрезки — клиент продвигает свой локальный курсор);
    - `truncatedUpToSeq?` — присутствует, только если была обрезка (§3): точка обрезки, сообщения
      ниже — недоступные (не непрочитанные), курсор/позиция доставки продвигаются на неё;
    - `messages: [Message]` — ascending по seq, `(startAfterSeq, …]` до `messageLimit`;
    - `hasMore` — в этом чате осталось больше `messageLimit`;
    - `peerReadUpToSeq` — текущий водяной знак прочтения собеседника: догоняющая синхронизация
      статусов собственных сообщений (✓✓, накопленные оффлайн — FR-003/US3-8);
    - `unreadCount` — серверный счётчик после применения страницы (клиент сверяется);
    - `lastSeq` — последний seq чата (детект «хвост за пределами страницы»);
    - `desynced?` + `serverUpToSeq` — ремонт «курсора из будущего» (§3).
  - `moreChats: boolean` — недоставленные чаты остаются за пределами `chatLimit`.
- **Продолжение внутри чата**: расширяется существующее №15 опциональным курсором
  `?after=<seq>&limit=` — ascending-страница `(after, …]` по `seq ASC` + `nextAfter` в ответе
  (отсутствует при исчерпании). `before` (DESC) сохраняется без изменений — прокрутка истории
  вглубь. Additive: существующие клиенты не затронуты.
- **Цикл клиента** (нормативно — [contracts/sync-protocol.md](./contracts/sync-protocol.md)):
  на `(re)open` SSE → single-flight №26 с локальными курсорами → рендер дельт (дедуп по
  `message.id`, порядок по seq) → ack №25 по каждой применённой странице → чаты с `hasMore`
  догружаются №15 `after` (страница → рендер → ack) → при `moreChats` повтор №26 с обновлёнными
  курсорами → синхронизация завершена, realtime уже работал параллельно (пропущенное за время
  дозагрузки доедет следующим циклом или realtime-кадром — дедуп по id делает гонку безопасной).
- Realtime-доставки ack'аются тем же №25: клиент применяет кадры `message.created` и дебаунсом
  (≤ 1 с, батч по всем чатам) подтверждает `upToSeq = max(seq)` по каждому чату; неуспешный ack
  ретраится следующим флашем (GREATEST делает повторы безопасными).

**Обоснование**: clarify зафиксировал pull; агрегированный endpoint одним запросом решает
«по всем чатам одним механизмом» (FR-003) и возвращает правильный порядок обхода (последняя
активность — сервер знает `chats.last_seq`), а per-chat `after` переиспользует индекс
`(chat_id, seq)` и существующий путь №15 без нового endpoint'а на чат.   Пагинация двухуровневая: `chatLimit`
гарантирует bounded-ответ (200+ сообщений в десятках чатов не рвут соединение), `messageLimit` —
bounded-страница. Точный бюджет SC-008 (200 сообщений ≤ 10 с p95) при странице 50 = 4 страницы
(1 × №26 + 3 × №15) + 4 ack — миллисекунды на страницу (индексный range-scan), запас на порядок.

**Альтернативы отклонены**: push-replay от сервера (сервер хранит per-user backlog и «догоняет»
сам) — clarify выбрал pull; durable per-user очереди (Kafka/Redis Streams) — операционный вес
без потребности: источник истины PG, pull по индексу дешевле (VII, прецедент 004 §2);
per-chat sync-endpoint — N запросов + клиент сам собирает порядок обхода (нарушение FR-003
«одним механизмом»); синхронизация одним гигантским ответом — unbounded payload; continuation-
token в №26 — курсоры уже являются токенами, отдельный курсор ввёл бы вторую систему координат.

## 3. Границы дозагрузки: обрезка и «курсор из будущего»

**Решение**:
- **Нижняя граница** доставки в чате: `lower = GREATEST(deleted_up_to_seq, история-окно)`; окно
  12 месяцев — конституционное, archival ещё не реализован (009/ROADMAP), поэтому фактически
  граница = `deleted_up_to_seq` на горизонте фичи; формула фиксируется в протоколе, ввод archival
  добавит второе слагаемое без смены механики. Удаление чата **собеседником** границу не меняет
  (per-user семантика 004).
- **Обрезка** (`effectiveLower > cursor`, включая курсор 0 у «вернувшегося» чата): сервер
  начинает доставку с `effectiveLower` и явно сообщает точку `truncatedUpToSeq = effectiveLower`
  в дельте. Позиция доставки при этом движется **тем же законом — только ack'ом** (§1): клиент
  ack'ает `upToSeq = max(страница, truncatedUpToSeq)`, и серверное GREATEST закрепляет позицию
  на точке обрезки; в дельте `startAfterSeq = effectiveLower`, сообщения ниже не возвращаются
  и в непрочитанные не входят (FR-003). Спека («сервер MUST продвигать позицию доставки и курсор
  на точку обрезки и явно сообщать клиенту эту точку») выполняется парой «дельта сообщает
  точку + ack закрепляет»: после первого цикла sync+ack позиция = точке обрезки — устойчиво
  и согласовано с моделью ack.
- **«Курсор из будущего»** (курсор клиента > `chats.last_seq` — восстановление из резервной
  копии): всему запросу ошибки нет; по затронутым чатам `desynced: true` + `serverUpToSeq =
  фактическая серверная позиция` (min(курсор, last_seq) с учётом границы), дельта пустая или с
  доступным хвостом; клиент отматывает локальный курсор на `serverUpToSeq` и продолжает штатно.
  Курсор каждого чата сравнивается с серверной позицией и фактическими данными; остальные чаты
  обрабатываются штатно — «корректно идентифицируемая часть» (edge).
- **«Сервер частично доступен»**: №26 и №15 — одиночные PG-транзакции чтения: либо полный
  консистентный ответ, либо `5xx`/`503` (клиент повторяет); «частичный список как полный»
  невозможен по построению — флаги `hasMore`/`moreChats` вычисляются в том же снимке, что и
  страницы (edge).

**Обоснование**: переиспользование водяного знака `deleted_up_to_seq` (004) как нижней границы —
нулевое новое состояние; обрезка через явную точку в дельте + ack сохраняет единый закон
движения позиции (только ack) и даёт клиенту детерминированный self-heal (`startAfterSeq`,
`truncatedUpToSeq`). Ремонт «будущего» курсора per-chat без ошибки запроса — требование edge;
`serverUpToSeq` достаточно для локальной перемотки (мультидевайс вне объёма — перемотывать
больше некому).

**Альтернативы отклонены**: продвижение позиции сервером внутри №26 (без ack) — ломает US1-4
(потерянный ответ = пропуск); отдельный endpoint «точка обрезки» — вторая операция ради одного
поля; ошибка 409/422 на «будущий» курсор — запрещена edge-случаем; «догрузка ниже точки
удаления с фильтрацией» — восстанавливает удалённую историю (нарушение FR-021/004).

## 4. Серверно-авторитарные непрочитанные (FR-007)

**Решение**:
- Формула (выводная, не хранится): `unread(user, chat) = COUNT(messages WHERE sender_id != user
  AND seq > GREATEST(last_read_seq, deleted_up_to_seq) AND seq <= LEAST(chats.last_seq,
  delivered_up_to_seq))`. Отличие от 004 — верхняя граница `delivered_up_to_seq`: непрочитанные —
  только из **доставленного** (позиция доставки — база счётчика, clarify). Ниже точки обрезки —
  недоступные, не непрочитанные (нижняя граница формулы).
- Динамика: realtime — кадр применён → ack → позиция растёт → счётчик растёт (пара «кадр+ack»
  укладывается в бюджеты доставки: ack дебаунс ≤ 1 с, счётчик сходится на следующем refetch/дельте);
  оффлайн — позиция заморожена, счётчик на сервере не растёт, при reconnect дозагрузка+ack
  поднимают его до фактического (US3-2: «после синхронизации увеличивается на фактическое число»);
  прочтение — существующий GREATEST `last_read_seq` (№17) уменьшает счётчик; блокировка —
  «заморозка» 004 сохраняется натурально (нет новых сообщений, прочтения подавлены).
- Клиент: локальный оптимистичный бейдж (кадры+дельты) со сверкой с `unreadCount` из №12/№26;
  «99+» — рендер при > 99 (004, без изменений); внутренний счёт точный.
- Оффлайн-прочтения (FR-008): клиент пишет персистентный per-chat watermark
  `webchat.sync.pendingReads.<userId>` (`{chatId: upToSeq}`) **до** попытки №17 и удаляет после
  `204`; при сети №17 идёт штатно (троттлинг 004), при её отсутствии watermark остаётся; на
  reconnect `useSync` флашит все pendingReads через №17 (идемпотентный GREATEST — повторный флеш
  после потери ответа безопасен). Серверный счётчик сходится, у отправителей загораются ✓✓
  (публикация `chat.read` — без изменений 004, включая подавление при блокировке).

**Обоснование**: счётчик остаётся выводным запросом (COUNT по индексу `(chat_id, seq)` с
водяными знаками — 004 §8), новое хранение не вводится; ack-ограниченность — прямое следствие
clarify («позиция доставки — база для счётчика»). PendingReads как watermark per chat (а не
журнал событий) — идемпотентность по построению (GREATEST на сервере), O(1) хранение, переживает
перезапуск (localStorage).

**Альтернативы отклонены**: материализованный счётчик-колонка (инкрементальный UPDATE на каждое
сообщение/прочтение) — write amplification и рассинхрон при сбоях; вывод «непрочитано = всё
видимое непрочитанное» (без delivered) — противоречит clarify (база — позиция доставки);
журнал оффлайн-прочтений (list of events) — дубль водяного знака, идемпотентность сложнее.

## 5. Оффлайн-очередь: лимит 1000, вытеснение, прозрачная очередь при отказах (FR-005/FR-009/FR-010)

**Решение**:
- Outbox 004 (localStorage, массив в порядке постановки) получает **лимит 1000** записей
  (`sending` + `failed`; константа клиента, Assumptions допускают уточнение). При превышении:
  **старейшие неподтверждённые** (`sending`, в порядке массива) вытесняются — переводятся в
  терминальный статус `failed` с `errorCode = 'queue_overflow'`, остаются видимыми в диалоге,
  автоповторы прекращаются; пользователь уведомляется (баннер). Повторное принятие вытеснённого
  в очередь не выполняется (ручной retry тем же ID остаётся — FR-004 даёт сходимость, новая
  постановка = тот же ID, дубля не будет).
- **Прозрачная очередь при временных отказах в онлайне**: классификация ошибок в `useOutbox`
  расширяется кодом `503 server_busy` (№16, §6) — обрабатывается как `429 flood_limit`:
  запись остаётся `sending`, `retryAt = now + Retry-After`, ошибки пользователю не видно
  (FR-009); собственный лимит 30/мин (429) — уже так (004, FR-010). Повторы при затяжных
  временных отказах — бессрочные тем же ID, backoff 1с…30с (существующий) или `Retry-After`
  сервера; терминальный статус — только постоянный отказ (403/409/400 — 004) или вытеснение.
- **Порядок**: флаш очереди при восстановлении сети — FIFO per-chat (обход массива, отправка
  сообщений чата в порядке постановки, параллельные чаты не блокируют друг друга); лимитное
  окно/Retry-After соблюдаются естественным планировщиком (retryAt). Порядок в чате на сервере
  определяется фактическим порядком принятия (edge) — клиентский порядок постановки сохраняется
  для последовательных успешных отправок.

**Обоснование**: вытеснение старейших `sending` — детерминированная политика из спеки (Edge
Cases); переиспользование терминального статуса `failed` 004 (единая ветка рендера «не
отправлено» + причина) минимизирует новые клиентские состояния; `503`-как-flood в классификаторе
— одна строка, остальная механика (retryAt, отсчёт, автоповтор тем же ID) уже существует и
протестирована в 004.

**Альтернативы отклонены**: отказ в приёме новых сообщений при полной очереди — хуже UX и не
предусмотрен спекой (спека: «принимаются с предупреждением о вытеснении»); вытеснение `failed`
записей — терминальные статусы неприкосновенны (edge: «повторное принятие вытесненного не
выполняется», но ручные записи не трогаем); отдельная очередь в IndexedDB — YAGNI (прецедент
004 §10: объём ≤ 1000 × 4096 символов в localStorage).

## 6. Backpressure: адаптивный admission-контроль на пути отправки (№16)

**Решение**:
- **Сигнал**: HTTP `503` `application/problem+json`, код `errors: {chat: [server_busy]}`,
  заголовок `Retry-After` (секунды, ≥ 1) — на **отправке** №16. Отличается от `429 flood_limit`
  (per-user лимит 30/мин): 503 — перегрузка общего пути, тоже временный отказ с указанием
  задержки (FR-009/SC-005). Клиент обрабатывает прозрачно (§5).
- **Механизм**: per-instance **адаптивный concurrency-лимитер** на пути `MessageService.send`
  (порт `SendAdmissionGate`, вызов сразу после дедуп-фастпаса):
  - счётчик in-flight отправок + семафор с текущим лимитом;
  - измерение латентности пути (PG-коммит → ack; тот же сигнал, что `webchat_message_ack_seconds`);
  - gradient = EWMA(латентность) / базовая латентность (медиана первых минут после старта,
    конфиг): при gradient > порога лимит сжимается мультипликативно (×0.9), иначе растёт
    линейно (+1) до max — AIMD; границы в конфиге `delivery.backpressure.*` (по умолчанию
    `min-limit=4`, `max-limit=64`, `latency-baseline=50ms` — начальная база латентности
    PG-коммита, уточняется медианой первых минут после старта);
  - in-flight ≥ лимит → shed: `503` + `Retry-After = ceil((in-flight − лимит + 1) × EWMA /
    пул_потоков… )` — упрощённо `ceil(in-flight × EWMA_латентности / лимит)`; сек, ≥ 1.
  - Поэтапность (FR-011) возникает естественно: сначала растёт латентность (очередь Tomcat +
    PG), затем при исчерпании адаптивного лимита начинаются явные 503; SSE-фанаут и доставка
    принятых идут отдельным путём без admission — «принятые доставляются в приоритете»
    (US4-4); второстепенное (presence/рассылки) не реализовано — hook задокументирован
    (US4-6, 015+).
- **Порядок проверок №16** (эволюция цепочки 004 §3): дедуп-фастпас (ретрай сходится всегда) →
  admission (503) → membership → валидация → флуд-бакет (429) → блокировки → INSERT. Admission
  до флуда: в перегрузе пользователь видит 503 (система), не 429 (личный лимит); токены флуда
  не сгорают на shed'ах — после спада 30/мин по-прежнему действует и не обходится повторами
  (FR-010: свежие отправки, дошедшие до INSERT, платят токен — 004 без изменений).
- **Stateless/флот**: лимитер in-memory per-instance (транспортное состояние, как SSE-реестр
  004 — конституция II: рестарт/сброс безопасен, состояние самовосстанавливается измерением);
  LB распределяет нагрузку — суммарный shed-эффект флотский. Общая Redis-координация не вводится
  (лишний round-trip на каждом отправке; согласованность per-instance достаточна для контролируемой
  деградации).
- **Рекавери** (FR-013): AIMD возвращает лимит по мере рассасывания; метрики (§8) показывают
  возврат; вмешательство оператора не требуется.

**Обоснование**: собственный ~100-строчный AIMD/gradient-лимитер — минимальная проверенная
идея (Netflix Concurrency-Limits, Vendure/Spring-паттерны) без новой зависимости (VII); сигнал —
латентность PG-пути, единая причина перегрузки на этом сервисе; 503+Retry-After — RFC-семантика
«сервис временно перегружен», отличимая от 429 per-user; in-memory допустимо конституцией по
прецеденту реестра SSE (004 plan II).

**Альтернативы отклонены**: **Kafka/брокер между API и PG** — перепроектирование ядра доставки
ради пика (VII; 004 §2 уже отклонял Kafka для фанаута); **Resilience4j RateLimiter/CircuitBreaker**
— фиксированные ставки/не адаптивны к латентности, новая зависимость ради коробки, поведение
которой всё равно настраивается под gradient; **Netflix concurrency-limits** — тянет
динамик-архитектуру конфигурации (archaius) ради одного класса; **Tomcat maxThreads как единственный
контроль** — даёт рост латентности, но без явного сигнала отправителю (нарушение SC-005
«0 молчаливых отказов»: таймауты — это молчаливый отказ); **общий Redis-счётчик in-flight** —
сериализация всех отправок через Redis на 100k msg/s — сама точка перегрузки; **shed по CPU** —
лаг индикатора, не отражает очередь PG.

## 7. Клиентские курсоры, single-flight и устойчивость к «скачкам» соединения

**Решение**:
- Локальные курсоры: `webchat.sync.cursors.<userId>` = `{chatId: seq}` (последняя подтверждённая
  ack'ом позиция — клиент пишет её сразу после успешного №25, включающего страницу/обрезку).
  Монотонность: новое значение применяется только если > текущего (max); источники продвижения:
  ack-успех, `truncatedUpToSeq`, `serverUpToSeq`-перемотка (последняя может отмотать назад —
  единственное исключение, ремонт «из будущего»).
- Single-flight: `useSync` держит флаг in-flight на весь цикл (№26 → №15/ack повторы); новый
  `(re)open` SSE во время цикла не запускает параллельный — завершение цикла само по себе
  сходится (реалтайм-кадры применялись параллельно, дедуп по id). Разрыв посреди цикла: таймеры
  ack/страниц прерываются, курсор остался на последней подтверждённой позиции — следующий цикл
  возобновляется с неё (US1-4); параллельных конкурирующих синхронизаций нет (edge).
- Часы клиента не участвуют: порядок/границы — только серверный seq (edge «сбиты часы»);

**Обоснование**: курсор = ack-эхо делает клиента и сервера симметричными (GREATEST на обеих
сторонах, кроме документированного ремонта); single-flight + монотонность закрывают «скачок»
соединения без новых механизмов; localStorage переживает перезапуск (мультидевайс вне объёма —
конфликтов записи нет).

**Альтернативы отклонены**: курсоры в памяти — теряются при перезапуске (нарушение духа FR-005
для получения); dedup-журнал всех ID сообщений — неограниченный рост; AbortController-отмена
страниц — не нужна: страницы идемпотентны, отмена = просто игнор.

## 8. Observability (FR-014)

**Решение** (Micrometer/OTel-стек 001, без новых зависимостей):
- Метрики сервера:
  - `webchat_delivery_ack_seconds` — таймер №25 (батч: применение GREATEST-обновлений);
  - `webchat_sync_request_seconds{outcome}` — таймер №26 (полный/продолжение);
  - `webchat_sync_messages_delivered_total` — счётчик сообщений, отданных дельтами/ascending-
    страницами (объём догоняющей синхронизации);
  - `webchat_sync_truncated_total` / `webchat_sync_desynced_total` — счётчики обрезок/ремонтов;
  - `webchat_backpressure_rejections_total` — счётчик 503 (SC-005: доля внезапных отказов =
    connection-errors без 503 — 0);
  - `webchat_backpressure_limit` (gauge) / `webchat_backpressure_inflight` (gauge) — состояние
    лимитера (SC-006: рекавери виден как возврат лимита);
  - доставка: существующий `webchat_realtime_push_seconds` (коммит→кадр); отдельной серверной
    метрики end-to-end p99 (приём→отображение) не вводится — клиентский ack не является моментом
    отображения; бюджет SC-004 (p99 ≤ 500 мс / ≤ 2 с) проверяется нагрузочным тестом
    (k6: send→SSE-кадр у получателя).
- Логи: warn на shed (503: userId, chatId, Retry-After — без текста), info на обрезке/десинке
  (chatId, точка) — PII-минимизация 004.
- Трейсинг: №25/№26 — стандартные спаны авто-инструментации; span-линк send→publish сохранён.

**Обоснование**: прямое покрытие SC-001–SC-008 измеримыми сигналами; клиентские состояния
(очередь, вытеснение) и сходимость непрочитанных (выводная величина, сервер — источник истины;
проверяется `UnreadConvergenceIT` и UI) наблюдаемы тестами и UI, серверных метрик не требуют.

## 9. Пагинация ascending в №15: деталь контракта

`after` и `before` взаимно исключающи (`400 mixed_cursors` при обоих) — два независимых режима
одного endpoint'а: `after` — ascending `(after, after+limit]` + `nextAfter` (sync/догрузка новых),
`before` — descending `[before-limit, before)` + `nextBefore` (история вглубь, 004 без
изменений). Лимит 1–50 общий. Видимость: ascending-режим respects `deleted_up_to_seq` (сообщения
ниже — 404-подобное «недоступно»? нет: они просто не возвращаются; если весь диапазон ниже
границы — пустая страница, а точку обрезки клиент уже знает из №26).

## 10. Нагрузочная валидация и бюджеты (FR-012/SC-004, конституция II/VI)

- **Расчёт** (дополнение к лестнице 004 §12): новая запись на сообщение — одна GREATEST-строка
  `chat_participants` **на батч доставок** (амортизация ≥ 10:1 при дебаунс-ack), т.е. путь записи
  100k msg/s не меняется (INSERT `messages` + `chats.last_seq` — как в 004); ack-батчи ≤
  (пользователи × чаты × 1/с) — на горизонте одной сессии на пользователя это ≤ 10k строк/с при
  1M CCU — на порядки ниже бюджета записи PG; sync — range-scan `(chat_id, seq)` страницей 50 +
  сортировка недоставленных чатов по `chats.last_seq` (индекс; top-N по пользователю — десятки
  строк). SSE-фанаут без изменений (~2 PUBLISH/сообщение — 004 §12). Вывод: решение не
  регрессирует лестницу масштабирования; 100k msg/s достигается тем же горизонтальным путём
  (партиции → шард per-shard seq), admission (§6) держит деградацию контролируемой до его
  завершения.
- **k6-сценарий** `load/k6/delivery-resilience.js` (сборка `load/k6` с k6/x/sse — 004):
  1. **Разрывы** (SC-001/SC-002/SC-008): пара VU; принудительные обрывы SSE в разных точках
     (после send-ack до кадра; посреди sync-цикла; между страницами); аудит по seq: получено
     ровно по одному, порядок монотонен; дозагрузка 200 сообщений — p95 ≤ 10 с; offline-паттерн
     (отправка без сети → reconnect) — тот же аудит.
  2. **Насыщение** (SC-005/006/007, FR-011): ramp `K6_TARGET_RPS` сверх пропускной способности
     dev-стенда (PG справляется ~десятки тысяч INSERT/s — 004 §12): пороги — отсутствие
     connection-errors/timeouts без предшествующего 503/429 (0 «молчаливых» отказов), все отказы
     несут `Retry-After`, принятые (201/200) доставляются получателю без потерь/дублей, после
     ramp-down — возврат латентности к базе ≤ 5 мин.
  3. **Бюджетный профиль**: тот же сценарий с `K6_TARGET_RPS=100000`, длительность `K6_DURATION`
     — исполняется распределённым k6 на масштабированной инфраструктуре (шаг лестницы); в dev/CI
     не прогоняется физически — закреплено за 014 (ROADMAP), параметры и пороги готовы (SC-004:
     10 мин устойчивого потока, p99 ≤ 500 мс / ≤ 2 с в деградации).
- **Обоснование**: 004 установил прецедент: бюджеты подтверждаются расчётом в plan + smoke на
  достижимом масштабе + полнообъёмная валидация в 014; 005 добавляет профиль насыщения, т.к.
  механизмы деградации — предмет фичи: их семантика (монотонность, явность отказа, рекавери)
  проверяется на любом масштабе, коэффициенты — бюджетным прогоном.

**Альтернативы отклонены**: «прогнать 100k msg/s на dev-стенде» — физически невозможен
(вертикальный PG ~30–50k INSERT/s — 004 §12; distributed k6 + шардированный кластер — не существует
до 014); «уменьшить бюджет» — противоречит конституции II; «нативно ограничить 30k и объявить
деп limитом» —Rate limiting ≠ backpressure: бюджет требует graceful degradation выше пропускной
способности, что и реализовано.

## 11. Тестирование (VI)

- **Backend IT** (Testcontainers PG+Redis, реальный HTTP):
  - `DeliveryAckIT` — GREATEST-монотонность (повтор/меньшее/параллельные), батч из разных чатов,
    чужой chat → 403, лимит элементов → 400;
  - `SyncIT` — полнота/порядок дельт (мульти-чатовый backlog), порядок по последней активности,
    пагинация (chatLimit/messageLimit/hasMore/moreChats), обрезка по `deleted_up_to_seq`
    (truncatedUpToSeq + исключение из непрочитанных), «будущий» курсор (desynced/serverUpToSeq,
    остальные чаты обработаны), peerReadUpToSeq в дельте, пустой результат при полном курсоре;
  - `AscendingHistoryIT` — №15 `after`: страницы/границы/nextAfter, mixed_cursors, видимость;
  - `UnreadConvergenceIT` — realtime-цикл (кадр→ack→рост), sync-цикл (страница→ack→рост до
    фактического), прочтение оффлайн-паттерном (№17 после reconnect), заморозка при блокировке;
  - `BackpressureIT` — шедулимый gate (тестовый профиль: низкие лимиты): 503+Retry-After,
    порядок дедуп→admission→flood (ретрай записанного не получает 503; свежая отправка платит
    флуд-токен только после admission), AIMD-восстановление лимита после спада.
- **Frontend** (Vitest+RTL): cursors (монотонность, self-heal по точке обрезки/десинку),
  single-flight useSync (нет параллельных циклов, возобновление по обрыву), ack-батчер (дебаунс,
  retry, GREATEST-клиент), pendingReads (переживание перезапуска, идемпотентный флаш), outbox
  (вытеснение queue_overflow при лимите, 503-прозрачность, FIFO per-chat), индикаторы
  (SyncIndicator, 99+, ✓✓ из дельт).
- **Контракт**: конвейер 001 (vacuum → codegen drift → oasdiff; additive 0.5.0); сценарии
  quickstart прогоняются curl-скриптом по контракту.
- **Нагрузочный**: §10.
