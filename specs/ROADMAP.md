# WebChat — дорожная карта фич для SDD-цикла Spec Kit

Последовательный список фич. Каждая фича — один вызов `/speckit.specify` (одна фича
за вызов), далее полный цикл: `/speckit.clarify` → `/speckit.plan` → `/speckit.tasks`
→ `/speckit.implement` → `/speckit.checklist`. Порядок реализации — строго сверху вниз:
каждая фича опирается на предыдущие.

Каталоги специфик будут создаваться как `specs/NNN-<short-name>` (sequential numbering).

## Фаза 0 — Фундамент

### 001. project-foundation
**Заголовок**: Каркас проекта, CI/CD и базовая инфраструктура

**Описание для `/speckit.specify`**:
Создать каркас проекта веб-чата: монорепозиторий с backend-сервисом (Kotlin 2.x +
Spring Boot 3.x) и frontend-приложением (React + TypeScript, strict), Docker-образы и
базовые манифесты Kubernetes, CI/CD-пайплайн (сборка, линт, тесты, деплой) с первой
фичи. Настроить пайплайн публичного OpenAPI-контракта с генерацией TypeScript-типов
для фронтенда и базовую observability (структурированные логи, распределённый
трейсинг, метрики latency/throughput/errors). Все сервисы stateless. Бизнес-функций
в этой фиче нет.

**Состав**:
- Скелеты backend/frontend, общие линт/формат/тест-раннеры
- CI/CD: build → lint → unit/integration tests → docker build → deploy (dev)
- Каркас OpenAPI-контракта + codegen TS-типов
- Observability: structured logging, tracing, metrics-эндпоинт
- Манифесты K8s (deployments, services, ingress)

**Зависимости**: —

## Фаза 1 — Идентичность и доступ

### 002. user-registration
**Заголовок**: Регистрация с email-подтверждением и вход по паролю

**Описание для `/speckit.specify`**:
Зарегистрированный пользователь регистрируется по username и email, подтверждает
регистрацию переходом по ссылке из письма, затем задаёт и подтверждает пароль.
Вход по username/email и паролю выдаёт короткоживущий токен сессии и refresh-токен.
Доступ ко всем API чата — только для аутентифицированных пользователей. Транзакционные
email отправляются через внешний email-сервис. На публичных endpoints — rate limiting
и защита от флуда. Пароли хранятся только в хешированном виде (современный алгоритм
с солью). Восстановление пароля по email-ссылке.

**Состав**:
- Сущность User (username, email, статус, пароль-хеш)
- Флоу: регистрация → письмо со ссылкой → ввод+подтверждение пароля
- Логин/логаут, JWT access + refresh, ротация refresh
- Транзакционный email-шлюз
- Rate limiting на register/login/reset
- Reset password по email

**Зависимости**: 001

### 003. sso-identity-providers
**Заголовок**: SSO и интеграции с identity-провайдерами

**Описание для `/speckit.specify`**:
Вход через внешние identity-провайдеры по OIDC/OAuth2 как равноправная альтернатива
паролю. Пользователь может привязать внешний IdP-аккаунт к существующему аккаунту
и входить любым из способов. Поддержка конфигурации нескольких провайдеров
(endpoints, client id/secret в secret manager), автоматическое создание аккаунта
при первом входе через IdP при совпадении email. Единая модель сессий/токенов
с фичей 002.

**Состав**:
- OIDC authorization code flow (+ PKCE)
- Линковка/анлинковка IdP-аккаунтов
- JIT-аккаунт по email при первом SSO-входе
- Конфигурация провайдеров, секреты вне репозитория

**Зависимости**: 002

## Фаза 2 — Ядро обмена сообщениями

### 004. direct-messaging-core
**Заголовок**: Личные текстовые чаты — вертикальный срез с exactly-once доставкой

**Описание для `/speckit.specify`**:
Два пользователя ведут личный диалог текстовыми сообщениями в реальном времени.
Сообщения доставляются гарантированно и без дублей (эффект exactly-once для
пользователя): клиент генерирует уникальный ID сообщения, сервер дедуплицирует
по ID, подтверждает запись клиенту, порядок сообщений сохраняется в рамках чата,
повторная отправка (ретрай) безопасна и не создаёт дубликат. История переписки
доступна при повторном входе. Подключение к реалтайм-каналу через публичный API
(OpenAPI-контракт — источник истины). Состояние сообщений: отправляется / доставлено.

**Состав**:
- Сущности Chat (personal), Message (текст), Membership
- Realtime-канал доставки (брокер сообщений, stateless-сервисы)
- Client message ID, дедупликация, подтверждение записи, ретраи
- Порядок в рамках чата, персистентность
- Список чатов, история с пагинацией (базовая)
- Публичный API: chats, messages, realtime-подписка

**Зависимости**: 002

### 005. delivery-resilience
**Заголовок**: Устойчивость доставки при нестабильном соединении и нагрузке

**Описание для `/speckit.specify`**:
При разрыве соединения и переподключении клиент синхронизирует пропущенные
сообщения по курсору последнего полученного, без дублей и пропусков. Оффлайн —
исходящие сообщения ставятся в очередь и отправляются при восстановлении связи
с сохранением идемпотентности. Индикаторы непрочитанных сообщений по чатам.
Под пиковой нагрузкой система деградирует контролируемо: backpressure на
отправителя, rate limiting, graceful degradation вместо отказа. Доставка
в пределах бюджета 100 000 сообщений/сек.

**Состав**:
- Reconnect-синхронизация по курсору (missed messages)
- Оффлайн-очередь отправки на клиенте
- Непрочитанные счётчики, сброс при прочтении
- Backpressure, rate limiting, graceful degradation
- Интеграционные тесты: потеря/дубль/порядок при разрывах

**Зависимости**: 004

### 006. group-chats
**Заголовок**: Групповые чаты с ролями и member-авторизацией

**Описание для `/speckit.specify`**:
Пользователь создаёт групповой чат, добавляет участников (из списка своих контактов),
назначает роли: owner, admin, member. Owner/admin управляют участниками, названием и настройками чата. Все API проверяют членство в чате на уровне каждого
запроса (авторизация по ресурсу). Сообщения, доставка и синхронизация из фич
004/005 работают в группах без изменений. Публичные списки/метаданные чатов видны
только участникам.

**Состав**:
- Роли и права (owner/admin/member)
- Добавление/удаление участников
- Membership-check на всех endpoints
- Метаданные чата (название)
- Лимиты на размер группы

**Зависимости**: 005

## Фаза 3 — Присутствие и полировка UI

### 007. user-presence
**Заголовок**: Присутствие пользователей (presence «онлайн»)

**Описание для `/speckit.specify`**:
Пользователь видит статус присутствия собеседников: «онлайн» ⟺ есть живое подключение
к реалтайм-каналу (хотя бы одно устройство/сессия пользователя). Изменения статуса
приходят в реальном времени заинтересованным клиентам (пиры открытых чатов, контакты —
границы уточняет clarify), без широковещательного шума. Сигнал устойчив к флапу
соединений (реконнекты метро/лифта не дребезжат статусом — дебаунс/гистерезис).
Состояние присутствия — только во внешнем хранилище (Redis-ключи с TTL, продлеваемые
heartbeat; self-expiry при падении инстанса), инстансы stateless. Правила приватности
(кому виден мой статус, режим «невидимки») — решения clarify-раунда. Мультидевайс:
онлайн при ≥1 живого соединения.

**Состав**:
- Presence-сигнал на базе SSE-соединений (registry per-user + Redis TTL-ключи)
- События `presence.changed` выборочным подписчикам; `peerOnline` в ChatView/ChatListItem
- Дебаунс/гистерезис смены статуса (anti-flap)
- Приватность видимости статуса (правила, «невидимка» — clarify)
- Тесты: мультидевайс, крэш инстанса (TTL), флап-устойчивость

**Зависимости**: 004, 005 (стабильный reconnect-цикл — предусловие анти-флапа)

### 008. chat-window-styling
**Заголовок**: Стилизация окна чата по дизайн-макету

**Описание для `/speckit.specify`**:
Действующий мессенджер (наследие фич 004–007: личные чаты, группы с ролями, presence,
outbox/синхронизация, контакты) приводится к утверждённому статическому прототипу
`tmp/chats.html` («Aethergram»: стимпанк-палитра auth-экрана, шрифты Old Standard TT /
Cormorant SC / Anonymous Pro, корпус-«машина» с окантовкой и заклёпками, фоновые
паттерны, зерно/виньетка). Точное соответствие типографике, сетке, отступам и палитре
для всех поверхностей: сайдбар (поиск, список чатов с аватарами, бейджами «99+», меткой
«заблокирован», временем последнего сообщения) и окно чата (заголовок с аватаром,
статусом и кнопками, лента с пузырями и штампами ✓/✓✓, композер). Табы «Чаты»/«Контакты»
сайдбара убираются: главное меню кнопкой у поиска (Мой профиль / Контакты / Создать
групповой чат), контакты — модальное окно (поиск, добавление точным совпадением,
сортировка, блокировка, удаление чата/контакта), «Мой профиль» — модальная форма
(username/email readonly + инкогнито, API 007). Поверх рескина добавляется UI-слой без
изменения API: аватары с инициалами (из username, октагональные у групп) и
presence-точкой, время сообщений и разделители дат (createdAt уже в контрактах), тосты,
модальные окна и контекстные меню, мобильный burger-drawer, звуковые оповещения
отправки/приёма (WebAudio, без персистентной настройки), состояние «заблокирован»
в композере. Сохраняются и стилизуются все функции 005–007: статусы outbox («не отправлено»,
повтор/удаление, переполнение очереди, отсчёт ретрая флуд-лимита), индикатор
синхронизации, пагинация истории, роли групп и ростер-действия, описание группы,
presence «неизвестно», страницы настроек. Контракты API и доменная логика не меняются.
Typing-индикатор, lastSeen, отображаемые имена и переключатель звука per-chat —
фича 008a; поиск по сообщениям — 013.

**Состав**:
- Design tokens из прототипа: типографика, сетка, отступы, палитра, фоны/паттерны
- Сайдбар: главное меню, поиск, список чатов (аватары, бейджи «99+», метки, время, превью)
- Контакты: модальное окно из главного меню (поиск, добавление, сортировка, блокировка, удаление)
- «Мой профиль»: модальная форма, инкогнито (API 007), username/email readonly
- Лента сообщений: пузыри, штампы ✓/✓✓, время, разделители дат, «отправляется»/«не отправлено»
- Композер: обычное состояние, ошибки валидации, отсчёт повтора, состояние «заблокирован»
- Модальные окна, контекстные меню, тосты, базовые звуки отправки/приёма (WebAudio); мобильная адаптация (burger + drawer)
- Стилизация состояний 005–007 (outbox, синхронизация, группы, presence, настройки)
- Пустые/загрузочные/ошибочные состояния окна чата
- Тесты визуальной регрессии ключевых экранов (screenshot/storybook)

**Зависимости**: 004–007 (текущий UI мессенджера); прототип `tmp/chats.html` — внешний артефакт

### 008a. social-signals
**Заголовок**: Typing-индикатор, «был в сети», отображаемые имена и per-chat звук

**Описание для `/speckit.specify`**:
Функциональность прототипа `tmp/chats.html`, не вошедшая в 008 из-за необходимости
расширения API и realtime-событий. (1) Typing-индикатор: собеседник видит «X печатает…»
(в группах — с именем конкретного участника) с дебаунсом начала/завершения; сигнал
эфемерный, через realtime только участникам чата, не персистентен. (2) lastSeen: статус
«Был в сети — {дата, время}» при offline (время последней активности presence-канала,
интеграция с TTL-моделью 007) — в заголовке чата и списке контактов; инкогнито скрывает
lastSeen. (3) Отображаемые имена: пользователь задаёт имя профиля (displayName,
редактирование в «Мой профиль»); контакт можно переименовать персонально (alias поверх
профильного имени); инициалы аватаров — из имени с фолбэком на username; отображаемые
имена используются в списках чатов/контактов, группах и поиске пользователей.
(4) Переключатель звуковых оповещений чата (per-chat, кнопка-«звонок» в заголовке из
макета): настройка хранится на сервере и синхронизируется между устройствами
пользователя. Все изменения API — аддитивные (новые поля и события в публичном
OpenAPI-контракте), обратная совместимость сохраняется. Поиск по сообщениям в фичу не
входит (остаётся в 013).

**Состав**:
- Событие `user.typing` (start/stop) в realtime-канале; индикатор «печатает…» с дебаунсом
- lastSeen в presence-модели (Redis) и API; отображение «Был в сети — …»; скрытие при инкогнито
- displayName пользователя: поле, редактирование, отдача в публичных представлениях
- Персональное переименование контакта (contact alias) + API
- Инициалы аватаров из отображаемого имени, фолбэк на username
- Переключатель звука per-chat: серверная настройка в API, синхронизация между устройствами

**Зависимости**: 007 (presence-модель), 008 (UI-паттерны и макет)

### 008b. auth-ux-polish
**Заголовок**: Вход, сброс, смена пароля и стартовый контакт admin

**Описание для `/speckit.specify`**:
Полировка auth-флоу и управление паролем. (1) После успешного входа по паролю —
редирект на страницу чата (сейчас после логина пользователь остаётся на /login);
учёт параметра returnTo — паритет с SSO-флоу 003. (2) На странице логина — вариант
сброса пароля: ссылка на существующий флоу восстановления по email-ссылке из 002,
без изменения API. (3) В профиле пользователя («Мой профиль» из 008) — смена пароля:
ввод текущего пароля + новый с подтверждением; клиентская валидация (совпадение,
политика паролей как в 002) и серверная проверка старого пароля; аддитивный endpoint
смены пароля с rate limiting, пароли только в хешированном виде; поведение сессий и
refresh-токенов после смены пароля (инвалидация прочих устройств) фиксируется clarify.
(4) Онбординг новых пользователей: сразу после успешной регистрации в контакты
автоматически добавляется системный контакт admin (гарантированное существование
аккаунта admin — seed при развёртывании); добавление идемпотентно, дублей не создаёт.

**Состав**:
- Редирект после логина на страницу чата; returnTo-паритет с SSO
- Ссылка сброса пароля на странице логина → флоу 002 (без изменения API)
- Аддитивный endpoint смены пароля (старый + новый), проверка старого, rate limiting
- Форма смены пароля в «Мой профиль»: поля, валидация, ошибки, подтверждение
- Политика сессий/refresh-токенов при смене пароля (границы — clarify)
- Автодобавление контакта admin при регистрации (идемпотентно); seed аккаунта admin

**Зависимости**: 002 (флоу входа и восстановления), 008 (модальная форма «Мой профиль»)

## Фаза 4 — Видео

### 009. video-conferences
**Заголовок**: Видеоконференции до 1000 одновременных

**Описание для `/speckit.specify`**:
Из любого чата можно создать видеоконференцию; участники чата подключаются по
ссылке-приглашению. Поддержка 1:1 и групповых конференций (речь + видео + демонстрация
экрана), с управлением участниками (мьют микрофона/камеры, право слова, роли
модератора). Многопользовательская раздача через SFU (проверенное готовое решение,
выбор фиксируется в plan.md). До 1000 одновременных конференций в рамках инфраструктуры.
Адаптивное качество под полосу/нагрузку, корректное завершение и освобождение
ресурсов.

**Состав**:
- Создание конференции из чата, инвайт-ссылка, список участников
- WebRTC-подключение через SFU
- Управление участниками, роли модератора
- Демонстрация экрана, мьют
- Адаптивное качество; лимиты и квоты на конференцию

**Зависимости**: 006

## Фаза 5 — Контент и виджеты

### 010. media-messages
**Заголовок**: Расширяемая система виджетов контента + изображения и видео

**Описание для `/speckit.specify`**:
Типы контента сообщений реализуются как расширяемая система виджетов/плагинов, а
не хардкодом в ядре. Реализовать первые виджеты: изображение (с превью и полноэкранным
просмотром) и видео (с превью и встроенным плеером). Медиа-файлы загружаются через
отдельный upload-флоу с лимитами размера/типа, хранятся в объектном хранилище,
в сообщении передаётся ссылка + метаданные для превью. Добавление нового типа
контента не требует изменения ядра доставки сообщений.

**Состав**:
- Плагин-архитектура типов контента (схема, рендер, валидация)
- Upload медиа (лимиты, mime-проверка, object storage)
- Виджеты «изображение» и «видео» (превью, viewer, плеер)
- Превью в списке сообщений, отложенная загрузка

**Зависимости**: 006

### 011. interactive-widgets
**Заголовок**: Интерактивные виджеты: кнопки, таблицы, календари, голосования

**Описание для `/speckit.specify`**:
Расширить систему виджетов интерактивными типами сообщений: кнопки (в т.ч.
группы кнопок с действиями), таблицы, календарь (просмотр и выбор слота),
голосование (варианты, голос одним из вариантов, публичные результаты, закрытие
голосования). Состояние виджета (например, результаты голосования) обновляется
у всех участников чата в реальном времени. Виджеты строятся на плагин-архитектуре
фичи 010 без изменений ядра.

**Состав**:
- Виджет «кнопки» + механизм действий
- Виджет «таблица»
- Виджет «календарь» (слоты, выбор)
- Виджет «голосование» (голосование, результаты live, закрытие)
- Реалтайм-обновление состояния виджетов

**Зависимости**: 010

## Фаза 6 — История и поиск

### 012. history-retention-archival
**Заголовок**: Хранение истории 12 месяцев и архивация старых сообщений

**Описание для `/speckit.specify`**:
Сообщения хранятся в горячем хранилище 12 месяцев; более старые автоматически
архивируются в холодное хранилище (по политике retention) и остаются доступны
пользователю по запросу, но с большей задержкой. Пагинация и бесшовная прокрутка
истории в UI работают по обоим слоям без видимого шва для пользователя. Ретеншн-
политика и границы архивации конфигурируемы. Удаление по запросу пользователя/GBPR
— out of scope (отдельная фича при необходимости).

**Состав**:
- Горячее/холодное хранилище сообщений
- Фоновая archival-политика (12 мес, конфигурируемо)
- Прозрачная пагинация через слои
- Миграция существующих данных

**Зависимости**: 011

### 013. full-text-search
**Заголовок**: Полнотекстовый поиск по активной и архивной истории

**Описание для `/speckit.specify`**:
Полнотекстовый поиск по содержимому сообщений всех чатов пользователя, в которых
он участник (authorization на уровне результатов). Поиск покрывает и активную,
и архивную историю. Результаты сниппетами с подсветкой совпадений, фильтры по
чату/участнику/периоду. Индексация новых сообщений — близко к реальному времени.
95% поисковых запросов возвращают результат менее чем за 1 секунду.

**Состав**:
- Поисковый индекс (текст сообщений, метаданные)
- Поисковый API + UI (фильтры, сниппеты, пагинация)
- Индексация активной + архивной истории
- Фильтрация результатов по правам доступа

**Зависимости**: 012

## Фаза 7 — Приватность и E2EE

### 014. e2ee-private-chats
**Заголовок**: Приватные E2EE-беседы для привилегированных пользователей

**Описание для `/speckit.specify`**:
Привилегированные пользователи (право выдаётся ролями/разрешениями на уровне
аккаунта) могут создавать отдельные приватные беседы со сквозным шифрованием.
Ключи генерируются и хранятся только на клиентах; сервер не имеет технической
возможности расшифровать содержимое (передаются только шифротексты и публичные
материалы ключей). История E2EE-бесед не хранится на бекенде: при переподключении
синхронизация только живых сообщений. Приглашение участника — безопасная передача
ключей через сервер без раскрытия содержимого, с верификацией отпечатков ключей.

**Состав**:
- RBAC: право на E2EE-беседы
- Протокол key management (генерация, обмен, верификация fingerprint)
- E2EE-беседа: шифротекст на сервере, ключи на клиентах
- Без истории на бекенде, синхронизация только живых сообщений
- Индикаторы «E2EE» в UI, предупреждения при смене ключей

**Зависимости**: 006

## Фаза 8 — Встраивание

### 015. embeddable-widget
**Заголовок**: Встраиваемый виджет чата для сторонних приложений

**Описание для `/speckit.specify`**:
Чат встраивается в другое веб-приложение через JS SDK (iframe или inline-режим),
используя то же публичное API, что и standalone SPA. Аутентификация во встроенном
контексте: передача токена/SSO-флоу от приложения-хоста. Настраиваемый внешний вид
(тема, размеры, язык), события lifecycle для хоста. Изоляция безопасности: CSP,
origin-restrictions, корректная работа в sandbox-iframe.

**Состав**:
- JS SDK + snippet встраивания (iframe/inline)
- Auth в embedded-контексте (token handoff, SSO)
- Темы/кастомизация, lifecycle-события
- Security: CSP, allowlist доменов, sandbox
- Переиспользование модуля presence из `frontend/src/presence/` (индикатор,
  №36–38, переключатель «невидимки») — верификация единообразия SPA/виджет (007 FR-007)
- Документация для интеграторов

**Зависимости**: 003, 005, 007, 010

## Фаза 9 — Масштаб и финализация

### 016. scale-hardening
**Заголовок**: Нагрузочная валидация и горизонтальное масштабирование до бюджета

**Описание для `/speckit.specify`**:
Провести нагрузочное тестирование и довести систему до проектных бюджетов:
1 000 000 одновременных пользователей, 100 000 сообщений/сек, 1 000 одновременных
видеоконференций. Реализовать горизонтальное масштабирование всех сервисов
(stateless по построению), шардирование чатов/пользователей по узлам, автомасштабирование
по метрикам нагрузки. Подтвердить exactly-once доставку под пиковой нагрузкой
(тесты на потерю/дубль/порядок). Зафиксировать деградационные сценарии и алерты
по SLO.

**Состав**:
- Нагрузочные тесты (users, msg/s, conferences)
- Шардирование и автомасштабирование
- Exactly-once под нагрузкой (верификация)
- Capacity-план, SLO/алерты, деградационные сценарии

**Зависимости**: все предыдущие

## Вне scope (YAGNI, конституция VII)

- Push-уведомления мобильных платформ
- Боты, интеграции с внешними мессенджерами
- Модерация контента, антиспам-модели
- Удаление данных по запросам (может быть выделено отдельной фичей)

## Как использовать

1. `bash .specify/scripts/bash/create-new-feature.sh <short-name>` или прямой вызов
   `/speckit.specify <описание из карточки фичи>` — по одной фиче за вызов.
2. Пройти полный SDD-цикл для фичи, пометить статус в `specs/NNN-<short-name>/tasks.md`.
3. Перечисленные здесь описания — отправная точка; `spec.md` уточнит границы фичи
   (clarify может их сузить, но не расширять scope).
4. Нарушение конституции (stateless, exactly-once, API-first, budgets) — блокер
   на этапе `/speckit.checklist`.
