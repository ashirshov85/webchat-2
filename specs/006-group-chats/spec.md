# Feature Specification: Групповые чаты с ролями и member-авторизацией

**Feature Branch**: `006-group-chats`

**Created**: 2026-09-25

**Status**: Approved

**Input**: User description: "Пользователь создаёт групповой чат, добавляет участников (из списка своих контактов), назначает роли: owner, admin, member. Owner/admin управляют участниками, названием и настройками чата. Все API проверяют членство в чате на уровне каждого запроса (авторизация по ресурсу). Сообщения, доставка и синхронизация из фич 004/005 работают в группах без изменений. Публичные списки/метаданные чатов видны только участникам."

## Clarifications

### Session 2026-09-25

- Q: Как вычислять условие «прочитано» (FR-012), если участник, состоявший в группе на момент доставки сообщения, покидает её, не прочитав сообщение? → A: Пересчёт по текущему составу — вышедшие/исключённые участники исключаются из условия; «прочитано» остаётся достижимым.
- Q: Остаются ли сообщения участника в истории группы при его исключении (а не самостоятельном выходе)? → A: Да — сообщения остаются с сохранением атрибуции, как и при самостоятельном выходе (единая семантика для выхода и исключения).
- Q: Что показывает счётчик непрочитанных повторно добавленному участнику за сообщения, отправленные за время его отсутствия? → A: Водяной знак сохраняется — непрочитаны все сообщения после его последнего прочтения (включая период отсутствия).
- Q: Что показывает счётчик непрочитанных участнику, впервые добавленному в группу, за сообщения, отправленные до его добавления? → A: 0 — водяной знак инициализируется позицией группы на момент добавления; история до добавления доступна постранично, но непрочитанной не считается.
- Q: Должен ли исключённый участник получить явное событие «вы исключены из группы» до закрытия его realtime-подписки? → A: Да — сервер доставляет исключённому финальное событие исключения по его активной подписке, затем закрывает её (клиент детерминированно убирает группу из списка «Чаты» без поллинга).
- Q: Какую семантику хранения данных имеет удаление группы владельцем — физическое или мягкое (скрытие с хранением по сроку)? → A: Физическое (hard-delete): сообщения, членства, водяные знаки и счётчики стираются; в журнале административных операций сохраняется только факт удаления (кто, когда) без содержимого.
- Q: Должны ли события изменения группы (состав, роли, метаданные) сохраняться в истории чата как системные сообщения, видимые при последующих загрузках истории? → A: Нет — только realtime-события и актуальное состояние; история группы содержит только пользовательские сообщения (модель 004 без изменений).
- Q: Что происходит с группами, которыми владеет пользователь, при удалении или блокировке его аккаунта платформой? → A: Вне объёма 006 — поведение определяется будущей платформенной фичой управления аккаунтами; в 006 фиксируется только граница.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Создание группового чата и добавление участников из контактов (Priority: P1)

Аутентифицированный пользователь создаёт групповой чат: задаёт название (и при желании краткое описание) и сразу или позже добавляет участников — выбором из своего списка контактов (фича 004). Создатель становится единственным владельцем (роль owner); все добавленные изначально получают роль member. Добавленным участникам группа сразу видна в списке «Чаты» с названием и составом участников; переписка в группе включается пользовательским сценарием US2 (тот же приоритет P1).

**Why this priority**: Это минимальный жизнеспособный продукт фичи: без возможности создать группу и собрать в неё людей остальные сценарии (роли, управление, приватность) не имеют предмета.

**Independent Test**: Проверяется вручную и автотестом: пользователь создаёт группу с названием, добавляет двух своих контактов; группа с корректным названием и составом появляется в списке «Чаты» у всех троих. Отправка и доставка сообщений проверяются Independent Test US2 (P1); acceptance-сценарии US1 (1–5) переписку не включают.

**Acceptance Scenarios**:

1. **Given** аутентифицированный пользователь с непустым списком контактов, **When** он создаёт группу с названием и добавляет участников из своих контактов (в том числе нескольких за одну операцию), **Then** группа создаётся, каждый добавленный становится участником с ролью member, а создатель — с ролью owner.
2. **Given** группа создана, **When** добавленный участник открывает приложение, **Then** группа отображается в его списке «Чаты» (едином списке личных и групповых чатов, 004 FR-014) с названием группы и счётчиком участников; полный состав с ролями доступен в карточке группы.
3. **Given** пользователь пытается добавить в группу пользователя, отсутствующего в его списке контактов, **When** выполняется добавление, **Then** операция отклоняется с понятной ошибкой, участник не добавляется.
4. **Given** название группы пустое (после обрезки пробелов) или длиннее 64 символов, **When** создаётся группа, **Then** операция отклоняется с понятной ошибкой валидации.
5. **Given** в группе уже 200 участников (включая владельца), **When** owner/admin пытается добавить ещё одного, **Then** операция отклоняется с понятной ошибкой лимита.

### User Story 2 - Переписка в группе с гарантиями доставки фич 004/005 без изменений (Priority: P1)

Любой участник группы пишет текстовые сообщения; все остальные участники получают их в реальном времени. Действуют все гарантии фич 004/005 без изменений: уникальный клиентский ID и дедупликация (нет дублей), подтверждение записи, порядок в рамках чата, история с постраничной загрузкой, статусы «отправляется / доставлено / прочитано», курсорная синхронизация после переподключения, оффлайн-очередь отправки, счётчики непрочитанных по группе, флуд-лимит 30 сообщений в минуту на пользователя, контролируемая деградация под нагрузкой.

**Why this priority**: Ценность группы — общение в ней; гарантии exactly-once и устойчивой доставки — конституционное требование (принцип III), распространяемое на группы.

**Independent Test**: Проверяется вручную и автотестами доставки: трое участников обмениваются сообщениями (в том числе при разрывах связи и повторных входах); каждый видит каждую запись ровно один раз, в одинаковом порядке; непрочитанные считаются корректно и сбрасываются при прочтении.

**Acceptance Scenarios**:

1. **Given** группа с несколькими участниками, **When** один участник отправляет сообщение, **Then** оно в реальном времени появляется у всех остальных участников, а у отправителя меняет статус «отправляется» → «доставлено» (одна галочка) после подтверждения сервером.
2. **Given** повторная отправка того же сообщения с тем же уникальным ID (ретрай, двойное нажатие), **When** сервер обрабатывает отправку, **Then** каждый участник видит сообщение ровно один раз (дедупликация по ID, 004 FR-004).
3. **Given** участник был офлайн, **When** он переподключается, **Then** все пропущенные сообщения группы доставляются по курсору — без потерь, дублей и нарушения порядка (005 FR-001–FR-003); счётчик непрочитанных группы сходится с фактом.
4. **Given** участник повторно входит в приложение, **When** открывает группу, **Then** история доступна с постраничной загрузкой более старых сообщений (50 на страницу, 004 FR-008).
5. **Given** исходящее сообщение участника группы, **When** все остальные текущие участники группы просмотрели его, **Then** у отправителя появляется «прочитано» (двойная галочка); статус монотонен и не откатывается.
6. **Given** участник отправляет сообщения быстрее лимита 30 сообщений в минуту, **When** лимит исчерпан, **Then** поведение совпадает с 004/005 (прозрачная очередь, отправка тем же ID после открытия окна).

### User Story 3 - Роли и управление участниками (Priority: P2)

Владелец управляет ролями: назначает участников администраторами (admin) и снимает админство, передаёт владение (роль owner) другому участнику — сам при этом становится admin. Owner и admin управляют составом: добавляют участников из своих контактов и исключают их. Действует иерархия: admin может исключать только обычных участников (member) и не может трогать других админов и владельца; управлять ролями может только owner. Изменения состава и ролей немедленно отражаются у всех участников.

**Why this priority**: Роли и управление — отличие группы от простого чата, но группа уже полноценно работает без них (US1–US2), поэтому приоритет ниже.

**Independent Test**: Проверяется вручную и автотестом: owner назначает участника admin; новый admin добавляет и исключает member; попытка admin исключить другого admin отклоняется; owner передаёт владение — прежний owner становится admin и теряет права owner.

**Acceptance Scenarios**:

1. **Given** owner группы, **When** он назначает участника администратором, **Then** роль участника меняется на admin и это сразу видно всем участникам в списке состава.
2. **Given** admin группы, **When** он добавляет участника из своих контактов или исключает участника с ролью member, **Then** операция выполняется; **When** он пытается исключить другого admin или owner либо изменить чьи-либо роли, **Then** операция отклоняется с понятной ошибкой (иерархия ролей).
3. **Given** member группы, **When** он пытается добавить, исключить участника или изменить роль, **Then** операция отклоняется с понятной ошибкой прав.
4. **Given** owner передаёт роль owner участнику группы, **When** передача выполнена, **Then** новый владелец получает полные права, прежний становится admin; в группе всегда ровно один owner.
5. **Given** изменение состава или ролей, **When** остальные участники онлайн, **Then** они видят изменение в реальном времени, без перезагрузки.

### User Story 4 - Управление названием и настройками группы (Priority: P2)

Owner и admin изменяют метаданные группы: название и краткое описание. Ограничения валидации те же, что при создании. Изменения немедленно распространяются всем участникам: новое название отображается в списке «Чаты» и в заголовке группы у каждого участника. Участник с ролью member менять метаданные не может.

**Why this priority**: Название — основной идентификатор группы в списке чатов; управление им требуется сразу после появления групп, но не блокирует обмен сообщениями, поэтому P2.

**Independent Test**: Проверяется вручную и автотестом: admin переименовывает группу — все участники онлайн видят новое название в списке «Чаты» и заголовке без перезагрузки; member получает отказ при попытке переименования.

**Acceptance Scenarios**:

1. **Given** owner или admin группы, **When** он изменяет название или описание, **Then** изменение сохраняется и в реальном времени отображается всем участникам (список «Чаты», заголовок группы).
2. **Given** member группы, **When** он пытается изменить название или описание, **Then** операция отклоняется с понятной ошибкой прав.
3. **Given** новое название пустое (после обрезки пробелов) или длиннее 64 символов, либо описание длиннее 256 символов, **When** выполняется изменение, **Then** операция отклоняется с понятной ошибкой валидации.

### User Story 5 - Приватность группы: членство проверяется на каждом запросе (Priority: P2)

Группа и её содержимое доступны только участникам. Любой запрос к ресурсу группы — чтение сообщений и истории, отправка, realtime-подписка, список участников, метаданные, операции управления — авторизуется по факту членства на момент запроса: не-участник получает отказ, не раскрывающий лишних сведений о группе. Публичных списков и каталогов групп нет; метаданные и состав видны только участникам. После исключения или выхода доступ прекращается немедленно, активные realtime-подписки закрываются сервером.

**Why this priority**: Приватность — требование конституции (принцип V: авторизация на уровне каждого ресурса) и явное требование фичи; при этом сама проверка встраивается в уже работающие сценарии, поэтому P2.

**Independent Test**: Проверяется автотестами авторизации: для каждой операции ресурса группы (№28–№35) не-участник получает отказ (операции №30/№33 реализуются в User Story 6 — матрица по ним замыкается там); после исключения участника все его прежние запросы отклоняются, активная подписка закрывается; группа не обнаруживается поиском пользователей/контактов.

**Acceptance Scenarios**:

1. **Given** аутентифицированный пользователь, не являющийся участником группы, **When** он запрашивает сообщения, историю, состав, метаданные группы, пытается отправить сообщение или подписаться на realtime-канал, **Then** каждый запрос отклоняется: операции групп (№28–№35) — единым `404 group_not_found` (существование не раскрывается), пути сообщений 004 (№15–№17) — по семантике 004 (`404 chat_not_found`/`403 not_participant`, оговорка FR-008).
2. **Given** участник исключён (или вышел) из группы, **When** он повторяет любой из прежних запросов, **Then** доступ отклоняется так же, как для не-участника.
3. **Given** у исключённого участника была активная realtime-подписка на группу, **When** исключение выполняется, **Then** сервер доставляет ему финальное событие «вы исключены» и закрывает подписку в пределах короткого окна (не позднее 5 секунд) без доставки последующих событий.
4. **Given** любые списки/поиск в системе, **When** не-участник ищет группы, **Then** группа не появляется в результатах (публичного каталога групп не существует).

### User Story 6 - Выход из группы и удаление группы (Priority: P3)

Участник (member или admin) в любой момент может покинуть группу самостоятельно; его сообщения остаются в истории группы, доступ он теряет. Владелец не может просто выйти: чтобы покинуть группу, он сначала передаёт владение другому участнику (US3). Владелец может удалить группу целиком — она исчезает у всех участников, подписки и счётчики удаляются.

**Why this priority**: Завершение жизненного цикла делает модель группы целостной, но не требуется для основного сценария использования, поэтому P3.

**Independent Test**: Проверяется вручную и автотестом: member покидает группу — исчезает из состава, теряет доступ, его сообщения остаются; owner передаёт владение и выходит; owner удаляет группу — у всех участников чат исчезает из списка «Чаты».

**Acceptance Scenarios**:

1. **Given** участник с ролью member или admin, **When** он покидает группу, **Then** он исчезает из состава, теряет доступ к группе, его ранее отправленные сообщения остаются в истории для остальных.
2. **Given** владелец пытается покинуть группу без передачи владения, **When** выполняется выход, **Then** операция отклоняется с понятной ошибкой и подсказкой передать владение или удалить группу.
3. **Given** владелец передал владение (US3) и стал admin, **When** он покидает группу, **Then** выход выполняется как для обычного участника.
4. **Given** владелец группы, **When** он удаляет группу, **Then** группа и её история исчезают у всех участников, realtime-подписки закрываются, участники получают событие удаления группы.

### Edge Cases

- Достигнут лимит 200 участников — добавление отклоняется с понятной ошибкой; повторные попытки не создают записей (граница лимита).
- Повторное добавление уже состоящего в группе участника — идемпотентно: дубля в составе не создаётся, возвращается текущее состояние.
- Повторное добавление вышедшего/исключённого (если он остался контактом добавляющего) — допустимо; повторно добавленному доступна вся сохранённая история группы; водяной знак прочтения сохраняется — непрочитаны сообщения, отправленные после его последнего прочтения.
- Первое добавление участника в группу с уже накопленной историей — водяной знак инициализируется точкой добавления: бейдж непрочитанных стартует с 0, вся прежняя история доступна постраничной загрузкой.
- Добавление самого себя в группу — невозможно: создатель уже участник (owner), операция отклоняется с понятной ошибкой.
- Назначение admin или передача владения пользователю, не являющемуся участником группы, — отклоняется (сначала нужно добавить участника).
- Передача владения самому себе — отклоняется как бессмысленная операция; owner остаётся один.
- Назначение роли (№34) владельцем самому себе — отклоняется (`self_forbidden`): смена собственной роли owner (self-demote) нарушила бы инвариант «ровно один owner»; смена роли владельца возможна только передачей владения (№35, FR-003).
- Попытка owner исключить самого себя операцией исключения (№32) — отклоняется (`self_forbidden`): выход владельца — только через №33 после передачи владения (FR-005); инвариант «ровно один owner» не нарушается.
- Исключение и одновременный выход одного и того же участника (конкуренция операций) — результат один: участник исключён; состояние состава сходится без дублей.
- Группа из одного владельца (участники не добавлены или все вышли): отправка сообщений возможна, сообщение видно только отправителю; статус «прочитано» не выставляется, пока кроме отправителя нет ни одного участника.
- Участник, не прочитавший сообщение, покидает группу (выход или исключение) — он исключается из условия «прочитано»; двойная галочка остаётся достижимой для остальных.
- Блокировка (004) между двумя участниками группы — не влияет на групповой чат: оба остаются участниками и обмениваются сообщениями группы; блокировка действует только в личном диалоге пары.
- Одновременное переименование двумя admin — применяется одна из операций атомарно (последняя подтверждённая), состав метаданных не «смешивается».
- Удаление группы при открытых окнах группы у участников — UI корректно отражает исчезновение чата (событие удаления), без «зависших» состояний.
- Попытка управления (добавление/исключение/роли/метаданные) исключённым в этот же момент участником — отклоняется авторизацией, изменения не применяются.

## Requirements *(mandatory)*

### Functional Requirements

Группа и создание:

- **FR-001**: Система MUST позволять аутентифицированному пользователю создавать групповой чат с обязательным названием (непустым после обрезки пробелов, не длиннее 64 символов; значение фиксируется в API-контракте) и опциональным описанием (не длиннее 256 символов). Создатель MUST становиться участником группы с ролью owner; при создании можно сразу добавить начальный состав из контактов создателя (FR-002).
- **FR-002**: Добавление участников в группу MUST выполняться только участниками с ролями owner или admin и только из личного списка контактов добавляющего (фича 004). Добавляемый MUST получать роль member. Размер группы MUST быть ограничен 200 участниками (включая владельца; значение фиксируется в API-контракте); превышение отклоняется с понятной ошибкой. Повторное добавление состоящего в группе MUST быть идемпотентным (без дубля в составе). Повторно добавленному (после выхода/исключения) участнику MUST быть доступна вся сохранённая история группы; его водяной знак прочтения MUST сохраняться — непрочитанными считаются все сообщения, отправленные после его последнего прочтения (включая период отсутствия).

Роли и права:

- **FR-003**: Система MUST поддерживать роли участников группы: owner (ровно один), admin, member. Назначение и снятие роли admin, а также передача роли owner другому участнику MUST выполняться только текущим owner; предыдущий owner при передаче MUST становиться admin. Роли MUST назначаться только действующим участникам группы; владелец MUST NOT назначать или изменять роль самому себе (№34/№35 → `self_forbidden`).
- **FR-004**: Права в группе MUST определяться иерархией ролей: owner владеет всеми операциями; admin добавляет участников (FR-002), исключает участников с ролью member и изменяет метаданные (FR-007); исключение admin или owner доступно только owner; исключение не может быть направлено на самого себя — выход исключительно через FR-005 (№33), для owner — после передачи владения; member читает и отправляет сообщения и может покинуть группу. Операции управления (добавление/исключение, роли, метаданные) MUST быть запрещены для member и отклоняться с понятной ошибкой прав.
- **FR-005**: Участник с ролью admin или member MUST иметь возможность покинуть группу (самоудаление из состава); его ранее отправленные сообщения MUST оставаться в истории группы. Сообщения исключённого участника MUST также оставаться в истории с сохранением атрибуции (единая семантика выхода и исключения). Владелец MUST NOT иметь возможность покинуть группу без предварительной передачи владения — попытка отклоняется с понятной ошибкой.
- **FR-006**: Владелец MUST иметь возможность удалить группу: группа и её история исчезают для всех участников, realtime-подписки закрываются, участникам доставляется событие удаления группы. Удаление MUST быть физическим (hard-delete): сообщения группы, членства, водяные знаки и счётчики непрочитанных стираются из хранилища; сохраняется только запись в журнале административных операций (FR-017) — факт удаления (кто, когда) без содержимого сообщений.

Метаданные:

- **FR-007**: Владелец и admin MUST иметь возможность изменять название и описание группы; валидация — та же, что при создании (FR-001). Изменения MUST отображаться участникам в реальном времени и при последующих загрузках; member метаданные не изменяет (FR-004).

Авторизация по ресурсу и приватность:

- **FR-008**: Каждый запрос к ресурсу группы (чтение сообщений и истории, отправка, realtime-подписка, состав участников, метаданные, операции управления) MUST проверять членство запрашивающего в этой группе на момент запроса; не-участнику доступ MUST быть запрещён. Неразглашение: операции групп (№28–№35) отвечают не-участнику (включая бывшего) и для несуществующей группы единым `404 group_not_found` — факт существования не раскрывается (№27 — создание, ресурса группы ещё нет); пути сообщений 004 (№15–№17) сохраняют семантику 004 без изменений (`404 chat_not_found` / `403 not_participant`, конвенция 004 — FR-002 и api-contract 004): различие кодов не раскрывает состава и содержимого группы. Для операций управления, помимо членства, MUST проверяться роль (FR-003–FR-004).
- **FR-009**: Метаданные группы (название, описание), состав участников и их роли, события и содержимое группы MUST быть видны только участникам; публичных каталогов и поиска групп не существует — группа не обнаруживается для не-участников.
- **FR-010**: При выходе, исключении или удалении группы доступ MUST прекращаться немедленно: последующие запросы отклоняются (FR-008), доставка событий группы адресату MUST прекращаться сервером не позднее 5 секунд после события (пользовательский realtime-поток мультиплексирует все чаты и физически не закрывается — «закрытие подписки» логическое).

Сообщения, доставка и синхронизация (фичи 004/005 без изменений):

- **FR-011**: Все механизмы сообщений фич 004/005 MUST работать в групповых чатах без изменений: валидация текста (4096 символов), уникальный клиентский ID и дедупликация, подтверждение записи, порядок в рамках чата (per-chat seq), история с постраничной загрузкой (50 сообщений), курсорная синхронизация после переподключения, оффлайн-очередь отправки, backpressure и флуд-лимит (30 сообщений в минуту на пользователя). Новое сообщение группы MUST доставляться в реальном времени всем текущим участникам группы, кроме отправителя.
- **FR-012**: Статусы сообщений в группе MUST следовать модели 004: «отправляется» до подтверждения, «доставлено» (одна галочка) после подтверждения записи, «прочитано» (двойная галочка) — когда все текущие участники группы, кроме отправителя, просмотрели его (per-member водяные знаки фичи 005); участники, покинувшие группу (выход/исключение) до прочтения, исключаются из условия — статус остаётся достижимым. Статус «прочитано» монотонен: не откатывается и не сбрасывается добавлением новых участников (водяной знак первого добавления инициализируется позицией группы — FR-013). Единственное исключение — повторное добавление участника, вышедшего без прочтения (сохранение водяного знака, FR-002): он снова входит в условие «прочитано», значение `othersReadUpToSeq` (MIN водяных знаков активных) может снизиться, и на новых сессиях/устройствах сообщения после его последнего прочтения отображаются как «доставлено»; в live-сессии клиент удерживает достигнутый максимум и откат не отрисовывает (realtime-group-events.md §3.7). В группе из одного отправителя статус «прочитано» не выставляется.
- **FR-013**: Счётчики непрочитанных сообщений (005) MUST вестись на пару «участник — группа» с той же семантикой: серверно-авторитарный счётчик, отображение «99+» при больших числах, уменьшение на фактически прочитанное. При первом добавлении участника водяной знак прочтения MUST инициализироваться позицией группы на момент добавления: сообщения, отправленные в группе до добавления, доступны через историю (FR-011), но непрочитанными не считаются (бейдж стартует с 0); при повторном добавлении действует сохранение водяного знака (каноническое описание семантики — FR-002).
- **FR-014**: Групповые чаты MUST отображаться в едином списке «Чаты» (004 FR-013–FR-014) вместе с личными: сортировка по дате последнего сообщения, числовой бейдж непрочитанных, поиск по названию в окне поиска списка чатов.

События группы и контракт:

- **FR-015**: Изменения состава (добавление, исключение, выход), ролей, метаданных и удаление группы MUST доставляться участникам в реальном времени событиями по существующему realtime-каналу; клиент отражает их без перезагрузки. События группы MUST NOT сохраняться в истории чата как системные сообщения: история группы содержит только пользовательские сообщения (модель 004 без изменений); офлайн-участник при подключении получает актуальное состояние (состав, роли, метаданные) и пропущенные сообщения, но не журнал событий. Исключённый участник MUST получать финальное событие «вы исключены» по своей активной подписке до её закрытия сервером (FR-010) — оно является последним событием по этой подписке. Повторная обработка события (дубль доставки) MUST быть идемпотентной — состояние клиента сходится без искажений.
- **FR-016**: Операции и события групповых чатов MUST быть описаны в публичном OpenAPI-контракте — источнике истины; изменения публичных интерфейсов MUST сохранять обратную совместимость.
- **FR-017**: Система MUST предоставлять наблюдаемость фичи: журнал административных операций группы (кто, что и когда изменил — состав, роли, метаданные, удаление) и метрики — отказы авторизации по группам, распределение размеров групп, доставка сообщений в группах; по этим сигналам можно проверить выполнение Success Criteria.

### Key Entities *(include if feature involves data)*

- **Групповой чат**: беседа от 1 до 200 аутентифицированных пользователей с общими метаданными (название, описание) и единой историей сообщений; содержит ровно одного владельца; отображается в списке «Чаты» каждого участника; создаётся пользователем, удаляется владельцем; доступна только участникам.
- **Участие (членство)**: связь «пользователь — групповой чат» с ролью (owner / admin / member); является единственным основанием доступа к ресурсам группы; прекращение участия (выход, исключение, удаление группы) немедленно закрывает доступ.
- **Роль**: атрибут участия с иерархией прав owner > admin > member; owner — единственный, управляет ролями и передачей владения; admin управляет составом (только member) и метаданными; member читает, пишет и может выйти.
- **Событие группы**: системное realtime-событие об изменении состава, ролей, метаданных или удалении группы, доставляемое текущим участникам; идемпотентно обрабатывается клиентами.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 95% сообщений в групповых чатах получают статус «доставлено» не позднее 2 секунд после нажатия отправки (та же планка, что в 004, распространённая на группы).
- **SC-002**: В групповом обмене и синхронизации (разрывы, повторные входы, повторные отправки) пользователи наблюдают 0 дублей и 0 потерь — каждое сообщение отображается ровно одним экземпляром в одинаковом порядке у всех участников (подтверждается автоматизированными тестами доставки).
- **SC-003**: 100% запросов не-участников к ресурсам группы (все операции контракта: сообщения, история, состав, метаданные, подписка, управление) отклоняются — подтверждается автоматизированными тестами авторизации по каждой операции.
- **SC-004**: 95% изменений состава, ролей и метаданных группы видимы онлайн-участникам не позднее 2 секунд.
- **SC-005**: p90 сценария «создание группы + добавление до 10 участников» — не более 60 секунд суммарно при 10 параллельных VU (k6-сценарий A, quickstart §3.1).
- **SC-006**: После исключения/выхода участника доставка событий группы ему прекращается не позднее 5 секунд (логическое закрытие подписки — физический поток пользователя не рвётся), а все последующие запросы отклоняются (100%).
- **SC-007**: Группы до 200 участников работают в пределах конституционных бюджетов доставки (stateless-сервисы, горизонтальное масштабирование) — подтверждается расчётом в plan.md и k6 smoke-проверками с групповыми чатами; полномасштабная валидация пиковых бюджетов — платформенная задача фичи 016 (ROADMAP).
- **SC-008**: Система предоставляет минимальные сигналы наблюдаемости (FR-017): журнал административных операций групп и метрики авторизации/размеров/доставки — по ним выполнение SC-001–SC-007 проверяется в эксплуатации.

## Assumptions

- Механизмы фич 002–005 доступны и переиспользуются без изменений: аутентификация и сессии; контакты, поиск пользователей и блокировки; диалоги, сообщения, статусы, флуд-лимит 30 сообщений/мин; курсоры, reconnect-синхронизация, оффлайн-очередь, счётчики непрочитанных, backpressure.
- Участники добавляются только из личного списка контактов добавляющего (граница фичи по ROADMAP); приглашения по ссылке, публичные/открытые группы, поиск и каталог групп — вне объёма фичи.
- Аватары групп, приватность-настройки видимости группы, ограничение отправки «только админам» и прочие расширенные настройки — вне объёма; настройки группы в этой фиче ограничены названием и описанием.
- Блокировки фичи 004 действуют только в личных диалогах пары и не влияют на групповые чаты (участие и обмен сообщениями в общей группе возможны).
- События группы (состав, роли, метаданные, удаление) не создают системных сообщений в истории: история содержит только пользовательские сообщения, модель 004 не расширяется типом «системное сообщение»; отображение «кто и когда изменил группу» в ленте — вне объёма фичи.
- Поведение групп при удалении/блокировке аккаунта владельца или участника — вне объёма 006: удаление и блокировка аккаунтов — отдельные платформенные фичи по ROADMAP (фича 002 выводит их за scope); их контракт определит судьбу членств и владения.
- Количественные параметры (лимит 200 участников, название ≤64, описание ≤256 символов, окно закрытия подписок ≤5 секунд) — разумные дефолты, зафиксированы в FR и подлежат закреплению в API-контракте; изменение — через правку спецификации.
- Семантика «прочитано» в группе (двойная галочка при прочтении всеми текущими участниками, кроме отправителя; вышедшие/исключённые из условия исключаются) выбрана как минимальное расширение модели водяных знаков 004/005; детализация «кто именно прочитал» (списки прочитавших) — вне объёма фичи.
- Удаление группы владельцем включено как необходимое завершение жизненного цикла; удаление — физическое (hard-delete, FR-006): конституционный стандарт хранения истории 12 месяцев применяется к существующим чатам и не сохраняет содержимое удалённых владельцем групп (журнал админ-операций хранит только факт удаления без содержимого); per-user сокрытие групповой переписки (аналог FR-021 фичи 004 для личных чатов) — вне объёма.
- Контент сообщений — только текст (как в 004); медиа и виджеты — фичи 010/011.
- Полномасштабные нагрузочные прогоны пиковых бюджетов конституции (1M CCU / 100k msg/s) — платформенная cross-cutting-задача фичи 016; в рамках 006 — расчёт в plan.md и k6 smoke с групповыми чатами (SC-007).
- «Понятная ошибка» во всех FR означает машиночитаемый код проблемы RFC 9457 (`application/problem+json`) из таблицы кодов API-контракта фичи (см. contracts/api-contract.md); перечень кодов фиксируется при проектировании плана.
