# Research: Групповые чаты с ролями и member-авторизацией

**Feature**: 006-group-chats | **Date**: 2026-09-25

Исходные неизвестные Technical Context разрешены исследованием кодовой базы 001–005 (хранилище
V10/V12, пути `chats/`/`sync/`/`realtime/`, контракт 0.5.0) и спеки 006. Формат каждого пункта:
**Решение / Обоснование / Альтернативы**.

---

## §1. Модель хранения групп: единая таблица `chats` с дискриминатором

**Решение**: группа — строка `chats` с `kind='group'`, `title`, `description` и NULL-парой
`user_low_id/user_high_id`; личные диалоги — `kind='direct'` с прежней парой. Сообщения групп —
те же `messages` (FK `chat_id`), per-chat `seq`, дедуп по клиентскому ID.

**Обоснование**: FR-011 требует работу механизмов 004/005 «без изменений» — единое хранилище даёт
её буквально: `last_seq`-кэш, INSERT-путь с дедуп-фастпасом/admission/флудом, история №15 с
`before`/`after`, ack №25 и sync №26 (join по `chat_participants`) достаются группам без дублирования
кода. Авторизация по ресурсу (FR-008) сводится к одной point-проверке active-строки участника.
Миграция — additive (V14): пара становится nullable; парный `UNIQUE (user_low_id, user_high_id)`
не мешает группам, т.к. PG default `NULLS DISTINCT` — строки с NULL не конфликту­ют; существующий
CHECK `user_low_id < user_high_id` на NULL-ах даёт UNKNOWN → проходит. Новые CHECK-и закрепляют
shape: `kind='direct'` ⟺ пара NOT NULL; `kind='group'` ⟺ пара NULL, `title` нормализован
(trim, 1–64), `description` ≤ 256 или NULL.

**Альтернативы**: (а) отдельные таблицы `group_chats`/`group_members` + полиморфный FK сообщений —
отклонено: ломает `UNIQUE (chat_id, seq)`, дублирует пути отправки/истории/sync, вдвое больше
миграций; (б) отдельная `group_messages` — отклонено: дублирование всего конвейера доставки,
нарушение «004/005 без изменений»; (в) OTS-решение (матричные комнаты и т.п.) — отклонено конституцией
VII (ядро уже построено, встраиваемость требует собственного контракта IV).

## §2. Членство и роли: `role`/`state` на `chat_participants`, инвариант владельца

**Решение**: две колонки на `chat_participants`: `role varchar(16) NULL` ('owner'|'admin'|'member';
NULL у личных) и `state varchar(16) NOT NULL DEFAULT 'active'` ('active'|'removed'). Членство группы
⟺ строка с `state='active'`. Выход/исключение — `UPDATE … SET state='removed', role='member'`
(строка сохраняется вместе с `last_read_seq`/`delivered_up_to_seq`/`deleted_up_to_seq` — семантика
повторного добавления FR-002: водяной знак сохраняется). Повторное добавление — реактивация той же
строки (`state='active'`, роль 'member', водяные знаки не трогаем, `hidden=false`). Первое
добавление — INSERT с инициализацией `last_read_seq = delivered_up_to_seq = chats.last_seq`
(бейдж с 0, история до добавления доступна, но непрочитанной не считается — FR-013), 
`deleted_up_to_seq = 0`. Инвариант «ровно один owner» — частичный уникальный индекс
`CREATE UNIQUE INDEX … ON chat_participants (chat_id) WHERE role='owner'`; передача владения —
в одной транзакции demote (owner→admin) THEN promote (member→owner), что не нарушает индекс ни в
одной точке. Лимит 200 — `SELECT count(*) WHERE state='active'` под `FOR UPDATE` строки `chats`
(сериализует конкурентные добавления, без advisory-lock'ов). Идемпотентность добавления —
активная строка уже есть → no-op, возврат текущего состава (FR-002); добавление самого себя →
`400 self_forbidden` (edge: операция «добавить» себя бессмысленна — создатель уже участник).

**Обоснование**: минимальная дельта к проверенной per-user строке 004/005 — все водяные знаки,
счётчики и sync уже живут на ней; удаление строки уничтожило бы водяные знаки повторного
добавления. Личные чаты не трогаются: их строки всегда `state='active'`, `role=NULL` — пути 004
не фильтруют по state и не меняются.

**Альтернативы**: (а) отдельная таблица `group_members` + архив членств — отклонено: join на каждом
запросе сообщений, дублирование water-mark-логики; (б) soft-delete через `removed_at timestamptz`
вместо `state` — эквивалентно, но каждая проверка становится NULL-сравнением + отдельная роль
всё равно нужна; (в) enforce «один owner» только сервисом — отклонено: гонка двух transfer'ов
нарушала бы инвариант; индекс даёт гарантию хранилищем (прецедент — CHECK-и 002/004).

## §3. «Прочитано» и непрочитанные в группе: MIN-водяной знак остальных

**Решение**: статус ✓✓ отправителя выводится из `othersReadUpToSeq(user, chat) = MIN(last_read_seq)`
по активным участникам, кроме пользователя (0, если других нет — группа из одного отправителя: ✓✓
не выставляется, FR-012/edge). Проекция добавляется в №13 `ChatView` и №26 `SyncChatDelta`
(group-вариант; заменяет `peerReadUpToSeq` личного чата). Событие №17 `chat.read` в группе
публикуется всем активным участникам, кроме читавшего (каждый клиент пересчитывает свои ✓✓);
монотонность — GREATEST-обновление водяного знака читавшего (004) + монотонность MIN по
активному составу. Вышедшие/исключённые исключаются из условия натурально: их строки выпадают из
`state='active'`-фильтра MIN (clarify 2026-09-25, FR-012). Добавление нового участника не сбрасывает
✓✓: его `last_read_seq` инициализируется `last_seq` (FR-013), MIN не падает ниже уже достигнутого
уровня только если новый участник инициализирован позади — на практике инициализация позицией
группы выше уже прочитанного прочими; формально ✓✓ «откат» возможен лишь в момент добавления
участника с сохранённым старым водяным знаком (повторное добавление) — семантика FR-002 осознанная:
непрочитаны сообщения после его последнего прочтения, статус сообщения монотонен в UI клиента
(клиент не отрисовывает откат ✓✓, хранит max; зафиксировано в контракте событий). Счётчик
непрочитанных — формула 005 без изменений на строке (user, chat): инициализация `last_read_seq =
last_seq` даёт «бейдж с 0»; повторное добавление сохраняет и счётчик сходится по доставке.

**Обоснование**: единственный источник истины — уже существующие per-member водяные знаки 004/005;
MIN — O(активный состав ≤200) по частичному индексу, вычисляется только при чтении проекций
(№13/№26/№17-ответ), не на каждом событии.

**Альтернативы**: (а) per-message `message_reads` (кто именно прочитал) — отклонено: списки
прочитавших вне объёма (Assumptions), таблица ростом N×M; (б) серверный «групповой» водяной знак
в `chats` — отклонён: не выражает «все, кроме отправителя» (у каждого отправителя своя планка);
(в) публикация `chat.read` только отправителям непрочитанных хвостов — оптимизация потока событий
отклонена по YAGNI (≤199 адресатов, ≤200 участников; рычаг задокументирован в §4).

## §4. Realtime: фанаут по списку участников, финальное событие, «закрытие подписки» ≤5 с

**Решение**: транспорт не меняется — per-user каналы `rt:user:{userId}` + конверт
`{"event","data"}` (RedisRealtimePublisher 004). Операция (отправка/чтение/изменение состава/
ролей/метаданных/удаление) берёт снимок активных участников в своей транзакции и post-commit
публикует каждому адресату (порт расширяется методами group-событий и fanout-списком для
`message.created`/`chat.read`). Состав событий №18: `group.updated`, `group.member.added`,
`group.member.removed`, `group.role.changed`, `group.deleted` — текущим участникам;
`group.you_removed {groupId, reason: 'kicked'|'left'}` — исключённому/вышедшему на ЕГО канал
(финальное событие группы по его подписке, FR-015); `group.deleted` — всем бывшим участникам
(снимок до CASCADE). «Закрытие realtime-подписки» ≤5 с (FR-010/US5-3) — **логическое**: поток
пользователя (№18) мультиплексирует все его чаты и физически не закрывается; после коммита
удаления состава события группы в канал не-участника больше не публикуются (все последующие
операции берут состав из активных строк) — окно фактически равно латентности публикации
(миллисекунды ≪ 5 с). Гонка порядка: сообщение, закоммиченное ДО исключения, может быть
опубликовано ПОСЛЕ `group.you_removed` (post-commit паблиши независимы); клиент обязан после
`you_removed` игнорировать события этой группы и удалить её из «Чатов» — идемпотентная сходимость
FR-015; at-most-once канал это допускает (004 §4). Дубль доставки события обрабатывается
идемпотентно (клиент применяет состояние, а не дельту).

Расчёт усиления (SC-007, конституция II): сообщение группы размера M → M−1 публикаций Redis
PUBLISH (O(1) каждая; конверт ~0.3–1 КБ). Предел: 100k msg/s × 199 ног = ~19.9M pub/s — за
пределами одиночного Redis; реальные ограничения сверху: флуд 30 msg/min/user ⇒ группа ≤
M×30/мин сообщений; средний размер группы ≪ 200 (типовой микс 004-масштаба). Рычаги
масштабирования (точки расширения без смены контракта — SSE-кадры те же): (1) групповой канал
`rt:chat:{groupId}` — 1 PUBLISH на сообщение, инстансы релеят локальным участникам (вводится при
потребности, потребует членство-индекс локальных сессий); (2) подавление `chat.read`-фанаута
только отправителям непрочитанных хвостов; (3) выделенный pub/sub-шард Redis. k6 smoke
(`load/k6/group-chats.js`) валидирует: группа 200 участников, переписка + изменения состава,
SC-001 (доставка ≤2 с), SC-004 (видимость изменений ≤2 с), монотонность seq/0 дублей; полнообъёмный
прогон — 016 (прецедент 004/005).

**Обоснование**: переиспользование транспорта 004 целиком (динамическая подписка инстансов,
heartbeat, at-most-once + рефетч-сходимость) — нулевая новая инфраструктура (VII); список адресатов
уже нужен операции в транзакции (авторизация/состав).

**Альтернативы**: (а) физическое закрытие SSE исключённого — отклонено: поток общий, рвёт остальные
чаты пользователя; событие `you_removed` достаточно (клиент детерминирован, без поллинга — clarify);
(б) групповой канал прямо сейчас — отклонён по YAGNI: требует членство-индекса на инстансе и
UNSUBSCRIBE-протокола, усилие не обосновано дымовым масштабом (зафиксирован как рычаг); (в)
Redis Streams с replay — отклонено: дублирует pull-синхронизацию 005 (курсоры уже обеспечивают
сходимость).

| №17 `POST /read` | без изменений контракта; группа: событие всем активным, кроме читавшего |

| Outbox/курсоры/флуд/admission | без изменений (chatId-агностичны); клиентские ошибки 403/404/422 групп — терминальные, маппинг как в 004 |

**Обоснование**: периметр изменений — только гейт членства и проекции; все долговременные гарантии
(exactly-once, порядок, курсоры) наследуются хранилищем (§1). Nullable-переход `peer`/`blockedByMe`/`peerReadUpToSeq` помечен в
api-contract.md; oasdiff-прогон в quickstart подтверждает отсутствие breaking по правилам
конвейера 001 (расширение nullable + optional-поля = minor).
Уточнение границы: group-элемент может появиться в №12/№26 существующего (0.5.0) клиента и
без его действий — при добавлении пользователя в группу другим участником; для старого
клиента это UI-деградация (элемент с `peer:null` может отображаться некорректно), но не
протокольный разрыв: неизвестное поле `type` игнорируется, серверная авторизация и приватность
не меняются, чужие группы не раскрываются. Окно смешанных версий — деплойментное ограничение.

`/chats/{id}/group` вместо `/groups` — отклонён: управление жизненным циклом отдельной сущности,
cleaner tag.

## §7. Hard-delete группы и журнал административных операций (FR-006/FR-017)

**Решение**: удаление — одна транзакция: снимок активного состава → `DELETE FROM chats WHERE id=…`
(CASCADE сносит `messages`, `chat_participants` — водяные знаки/счётчики стираются, FR-006) →
запись `group_admin_log (action='group_deleted', actor, created_at)` → post-commit `group.deleted`
бывшим участникам. `group_admin_log` — БЕЗ FK на `chats` (переживает удаление; `group_id` —
plain uuid), `actor_id`/`target_user_id` FK → users, `action` CHECK-enum: `group_created`,
`title_changed`, `description_changed`, `member_added`, `member_removed`, `member_left`,
`admin_granted`, `admin_revoked`, `ownership_transferred`, `group_deleted`; append-only
(нет UPDATE/DELETE-путей). Публичного API чтения журнала в 006 нет (FR-017 — наблюдаемость:
журнал для эксплуатации/аудита, доступ — SQL/observability; вынесение в API — будущая фича по
требованию, YAGNI).

**Обоснование**: CASCADE уже существует в V10 (messages/participants) — физическое удаление одной
командой, без пакетной обработки; журнал без содержимого сообщений (приватность V, clarify
2026-09-25).

**Альтернативы**: (а) soft-delete с retention — отклонён спекой (clarify: hard-delete); (б) журнал
в логах приложения — отклонён: FR-017 требует журнала операций (запрашиваемость), логи —
дополнительно (structured logging 001 остаётся); (в) FK с `ON DELETE SET NULL` — отклонён:
теряется group_id в факте удаления.

## §8. Наблюдаемость (FR-017, SC-008)

**Решение**: (1) журнал §7; (2) метрики Micrometer: counter `webchat_group_authz_denials_total`
(tags: operation) — отказы membership/ролей по каждой группе-операции; summary/histogram
`webchat_group_size` (распределение размеров активных групп — обновляется на add/remove);
counter `webchat_group_message_fanout_total` + timer `webchat_group_message_fanout_seconds`
(доставка сообщений групп: ноги и латентность post-commit фанаута, SC-001). Дополнительно таймеры
HTTP-путей и realtime-push 004 наследуются тегами путей. Structured-лог warn на отказы приватности
— ids без содержимого (прецедент 004).

**Альтернативы**: экспорт журнала в Loki как «метрики» — отклонён: FR-017 формулирует оба сигнала
(журнал + метрики); отдельный сервис аудита — отклонён по YAGNI.

## §9. Нагрузочная валидация (SC-007)

**Решение**: `load/k6/group-chats.js`: сценарий A — создание группы + добавление до 10 участников
из контактов (SC-005: p90 ≤60 с суммарно), переписка с замером «отправлено→доставлено» (SC-001 ≤2 с);
сценарий B — изменения состава/ролей/метаданных под онлайн-участниками (SC-004 ≤2 с); сценарий C —
authz-отказы (SC-003: не-участник по каждой операции); сценарий D — smoke 200-участниковой группы:
заполнение состава, волна сообщений, контроль 0 дублей/порядка seq, закрытие `you_removed` ≤5 с
(SC-006). Параметризация — env (`K6_BASE_URL`, `K6_GROUP_SIZE`, `K6_MESSAGE_RPS`). Полнообъёмный
прогон пиковых бюджетов (1M CCU / 100k msg/s) — 016 (Расчёт §4; прецедент 004/005 — plan.md
Constraints/Complexity Tracking).

**Альтернативы**: встроить групповые сценарии в `delivery-resilience.js` — отклонено: разные
пороги/сущности; отдельный файл повторяет конвенцию фичапапки `load/k6/`.

## §10. Frontend-архитектура

**Решение**: модуль `src/groups/` (components: создание, инфо-панель, состав с ролями, пикер
контактов, контролы выхода/удаления; hooks: `useGroup`/`useGroupMembers`/`useGroupRealtime`).
`useGroupRealtime` — идемпотентный редьюсер событий §4 (state-применение, не дельты; после
`you_removed`/`deleted` — удаление группы из локального состояния и игнор поздних событий группы).
Эволюция `chats/`: `ChatListItem`/`ChatListPanel` — type-дискриминация (название/кол-во участников,
поиск по названию в существующем окне поиска, FR-014), `MessageList` — атрибуция отправителей и ✓✓
по `othersReadUpToSeq` (клиент держит max — без визуального отката, §3), `useChatList` — реакция на
события состава/удаления. Outbox/курсоры/sync-хуки — без изменений (chatId-агностичны). Роли UI:
видимость действий по `myRole` (иерархия FR-004); ошибки сервера рендерятся понятно (US3/US4).

**Обоснование**: группы — отдельная фича-область (SRP), интеграция со списком/окном — через
существующие хуки-точки; никакого нового глобального стора (YAGNI, прецедент 004/005).

**Альтернативы**: (а) отдельный маршрут `/groups` — отклонён: FR-014 требует единый список «Чаты»;
(б) вынести member-панель в общий стейт-менеджер (Redux) — отклонено: серверно-авторитарное
состояние + локальный кэш хуков достаточен (004-паттерн).
