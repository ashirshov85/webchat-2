# Feature Specification: Регистрация с email-подтверждением, вход по паролю и управление сессиями

**Feature Branch**: `002-user-registration`

**Created**: 2026-09-11

**Status**: Draft

**Input**: User description: "Зарегистрированный пользователь регистрируется по username и email, подтверждает регистрацию переходом по ссылке из письма, затем задаёт и подтверждает пароль. Вход по username/email и паролю выдаёт короткоживущий токен сессии и refresh-токен. Доступ ко всем API чата — только для аутентифицированных пользователей. Транзакционные email отправляются через внешний email-сервис. На публичных endpoints — rate limiting и защита от флуда. Пароли хранятся только в хешированном виде (современный алгоритм с солью). Восстановление пароля по email-ссылке."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Регистрация аккаунта с подтверждением email и заданием пароля (Priority: P1)

Новый пользователь указывает username и email. Система проверяет уникальность обоих значений и отправляет на указанный email письмо со ссылкой подтверждения. Переход по ссылке активирует регистрацию и переводит пользователя к шагу задания пароля: пользователь вводит пароль и его подтверждение, после чего аккаунт считается полностью созданным и готовым к входу. Аккаунт без подтверждённого email и заданного пароля не может входить в чат.

**Why this priority**: Это точка входа в систему идентичности; без создания аккаунта невозможен ни один другой сценарий фичи, включая вход и защищённый доступ к API.

**Independent Test**: Полностью проверяется вручную и автотестом: заполнение формы регистрации → получение письма → переход по ссылке → задание и подтверждение пароля → попытка входа успешна. Каждый шаг наблюдаем (статус аккаунта, письмо, экран пароля).

**Acceptance Scenarios**:

1. **Given** указаны свободные username и корректный email, **When** отправлена форма регистрации, **Then** создаётся аккаунт в статусе «ожидает подтверждения», письмо со ссылкой подтверждения уходит на указанный email, пароль при этом ещё не задан.
2. **Given** аккаунт в статусе «ожидает подтверждения», **When** пользователь переходит по ссылке из письма до истечения её срока действия, **Then** email подтверждается и пользователю предлагается задать пароль.
3. **Given** подтверждённый email, **When** пользователь вводит пароль и совпадающее подтверждение, удовлетворяющие политике паролей, **Then** аккаунт переходит в статус «активен» и вход становится возможен.
4. **Given** username или email уже используется другим аккаунтом (любого статуса — активным или ожидающим завершения), **When** отправлена форма регистрации, **Then** регистрация отклоняется с понятным сообщением и указанием занятого поля (username/email), без раскрытия статуса держателя, письмо не отправляется.
5. **Given** регистрация не завершена (нет подтверждения email или пароля), **When** предпринимается попытка войти, **Then** вход отклоняется с сообщением о необходимости завершить регистрацию.
6. **Given** письмо не получено, **When** пользователь запрашивает повторную отправку, **Then** новое письмо соответствующего шага регистрации (подтверждение email или задание пароля) отправляется не чаще разрешённого интервала (защита от флуда).

### User Story 2 - Вход по username/email и паролю с выдачей токенов сессии (Priority: P1)

Активированный пользователь входит, указывая пароль и либо username, либо email. При успешном входе система выдаёт короткоживущий токен сессии и refresh-токен. Когда срок жизни токена сессии истекает, клиент продлевает сессию по refresh-токену без повторного ввода пароля; использование refresh-токена ротирует его (старый перестаёт действовать). Пользователь может завершить сессию (выйти), после чего оба токена перестают действовать.

**Why this priority**: Вход — единственный способ получить доступ к чату для пользователя с паролем; ротация refresh — базовая защита сессий, требуемая конституцией.

**Independent Test**: Проверяется автотестом API: вход валидными credentials → получены оба токена; доступ по токену сессии работает; после истечения его TTL доступ по нему отклоняется, продление по refresh выдаёт новую пару; повторное использование уже ротированного refresh отклоняется; после logout оба токена недействительны.

**Acceptance Scenarios**:

1. **Given** активный аккаунт, **When** пользователь вводит корректный пароль и username, **Then** вход успешен и выдаются короткоживущий токен сессии и refresh-токен.
2. **Given** активный аккаунт, **When** пользователь вводит корректный пароль и email вместо username, **Then** вход также успешен (оба идентификатора равноправны).
3. **Given** неверный пароль или несуществующий идентификатор, **When** выполняется попытка входа, **Then** возвращается единая обобщённая ошибка, не раскрывающая, что именно неверно (защита от перечисления аккаунтов).
4. **Given** истёкший токен сессии и действительный refresh-токен, **When** клиент запрашивает продление, **Then** выдаётся новая пара токенов, старый refresh-токен ротируется и повторно не принимается.
5. **Given** активная сессия, **When** пользователь выполняет выход, **Then** токен сессии и refresh-токен отзываются и дальнейшее их использование отклоняется.

### User Story 3 - Доступ к API чата только для аутентифицированных пользователей (Priority: P1)

Любой запрос к API чата выполняется от имени конкретного аутентифицированного пользователя. Запрос без токена, с просроченным, отозванным или недействительным токеном отклоняется с единообразной ошибкой «не аутентифицирован». Аутентифицированный запрос выполняется с известной системой идентичностью пользователя, которую API использует для авторизации на уровне каждого ресурса (принадлежность/членство). Публичными остаются только endpoints самого процесса аутентификации (регистрация, повторная отправка писем, подтверждение, вход, продление сессии, восстановление пароля).

**Why this priority**: Требование безопасности конституции: весь чат закрыт для неаутентифицированных пользователей; без этого границы системы не определены.

**Independent Test**: Проверяется автотестом: обращение к каждому endpoint API чата без токена и с недействительным токеном отклоняется; с валидным токеном — проходит. Список публичных endpoints зафиксирован и полон.

**Acceptance Scenarios**:

1. **Given** запрос к любому endpoint API чата без токена, **When** запрос выполняется, **Then** возвращается ошибка «не аутентифицирован», ресурс не изменяется.
2. **Given** запрос с просроченным, отозванным или иным недействительным токеном, **When** запрос выполняется, **Then** возвращается та же ошибка «не аутентифицирован».
3. **Given** запрос с валидным токеном сессии, **When** запрос выполняется, **Then** система связывает запрос с владельцем токена и выполняет авторизацию на уровне запрошенного ресурса.
4. **Given** endpoints регистрации, повторной отправки писем, подтверждения, входа, продления сессии и восстановления пароля, **When** к ним обращаются без токена, **Then** они доступны без аутентификации, и никаких иных публичных endpoints у API чата нет.

### User Story 4 - Восстановление пароля по email-ссылке (Priority: P2)

Пользователь, забывший пароль, указывает свой email и получает письмо со ссылкой восстановления. Переход по ссылке (одноразовой, с ограниченным сроком действия) ведёт на экран задания нового пароля с подтверждением. После смены пароля вход по старому паролю становится невозможен, а все активные сессии пользователя отзываются. Запрос восстановления для незарегистрированного email не раскрывает этого факта (единый ответ «если аккаунт существует, письмо отправлено»).

**Why this priority**: Восстановление важно для доступности аккаунтов, но не блокирует работу уже зарегистрированных пользователей; опирается на механику писем и пароля из US1.

**Independent Test**: Проверяется автотестом: запрос сброса → письмо со ссылкой → новый пароль по ссылке → вход с новым паролем успешен, со старым — отклонён, прежние сессии отозваны.

**Acceptance Scenarios**:

1. **Given** активный аккаунт, **When** пользователь запрашивает восстановление по своему email, **When** письмо получено и пользователь переходит по ссылке до истечения срока, **Then** ему предлагается задать новый пароль с подтверждением.
2. **Given** новый пароль задан по ссылке восстановления, **When** пользователь пытается войти, **Then** вход со старым паролем отклоняется, с новым — успешен; все прежние сессии и refresh-токены пользователя отозваны.
3. **Given** ссылка восстановления уже использована или истекла, **When** по ней повторно открывают экран смены пароля, **Then** смена отклоняется с предложением запросить новую ссылку.
4. **Given** email не принадлежит ни одному аккаунту, **When** запрашивается восстановление, **Then** система отвечает так же, как для существующего email (без раскрытия факта отсутствия аккаунта), и письмо не отправляется.
5. **Given** многократные запросы восстановления в короткий интервал, **When** превышен лимит, **Then** лишние запросы ограничиваются защитой от флуда (см. US5).

### User Story 5 - Защита публичных endpoints от флуда и подбора (Priority: P2)

Все публичные endpoints (регистрация, повторная отправка письма, вход, запрос восстановления) ограничены по частоте обращений — на источник запроса и на аккаунт/email. При превышении лимита запросы временно отклоняются с понятным сообщением и указанием, когда можно повторить. Многократные неудачные попытки входа в один аккаунт приводят к прогрессирующей задержке или временной блокировке подбора пароля. Ограничение работает консистентно при горизонтальном масштабировании (лимиты не «сбрасываются» добавлением экземпляров).

**Why this priority**: Прямое требование конституции к публичным endpoints; защищает предыдущие сценарии, поэтому реализуется вместе с ними, но может проверяться независимо от деталей писем.

**Independent Test**: Автотестом: серия запросов сверх лимита к каждому публичному endpoint получает отказ «слишком много запросов»; неудачные входы в один аккаунт замедляются/блокируются; валидный трафик под лимитом не затрагивается.

**Acceptance Scenarios**:

1. **Given** публичный endpoint (регистрация / повторная отправка письма / вход / восстановление), **When** количество запросов от одного источника за интервал превышает лимит, **Then** избыточные запросы отклоняются с сообщением о лимите, а не выполняются.
2. **Given** серия неудачных попыток входа для одного аккаунта, **When** количество неудач превышает порог, **Then** последующие попытки входа для этого аккаунта замедляются или временно блокируются, корректный пароль после блокировки по-прежнему работает после её окончания.
3. **Given** лимиты превышены на одном экземпляре системы, **When** те же запросы направляются на другой экземпляр, **Then** ограничение продолжает действовать (общий учёт, не в памяти одного процесса).
4. **Given** обычный пользователь с нормальной частотой обращений, **When** он проходит регистрацию/вход/восстановление, **Then** лимиты ему незаметны.

### User Story 6 - Отправка транзакционных писем через внешний email-сервис (Priority: P2)

Все письма фичи (подтверждение регистрации, повторная отправка, восстановление пароля) отправляются через внешний email-сервис, подключённый как заменяемый шлюз. Недоступность email-сервиса не «роняет» публичные endpoints: запрос принимается, ошибка доставки видна операторам через метрики/логи, а сбой доставки не приводит к потере возможности повторить отправку. Содержимое писем — понятные пользователю текст и ссылка с ограниченным сроком действия.

**Why this priority**: Email — зависимость внешнего провайдера; сценарий нужен для надёжности US1/US4, но сама механика регистрации/входа тестируема и при подмене шлюза.

**Independent Test**: Автотестом с подменяемым шлюзом: вызовы отправки идут через внешний сервис; при его ошибке endpoint не падает, сбой наблюдаем в метриках; письмо содержит рабочую одноразовую ссылку.

**Acceptance Scenarios**:

1. **Given** событие, требующее письма (регистрация, повторная отправка, восстановление), **When** оно наступает, **Then** письмо передаётся внешнему email-сервису с корректным адресатом и ссылкой.
2. **Given** внешний email-сервис недоступен или возвращает ошибку, **When** пользователь выполняет действие, **Then** запрос не завершается системной ошибкой, сбой фиксируется в observability (логи/метрики), пользователь может повторить отправку позже.
3. **Given** письмо доставлено, **When** пользователь переходит по ссылке, **Then** ссылка работает только один раз и только до истечения срока действия.

### Edge Cases

- Что если пользователь не завершил регистрацию и пытается повторно зарегистрироваться с тем же username/email? — При полном совпадении пары (username + email) с незавершённой регистрацией повторная отправка формы возобновляет её (аннулирует прежние ссылки, отправляет новое письмо следующего незавершённого шага — подтверждения email или задания пароля), а не создаёт дубликат аккаунта; при частичном пересечении (занят только username или только email) регистрация отклоняется с указанием поля.
- Что если ссылка подтверждения/восстановления истекла или уже использована? — Действие отклоняется, пользователю предлагается запросить новую ссылку; повторное использование невозможно.
- Что если email подтверждён, но срок действия ссылки/токена задания пароля истёк до его задания? — Аккаунт остаётся в статусе «ожидает задания пароля» и не может войти (FR-003); повторная отправка или повторная регистрация той же парой выдаёт новую ссылку задания пароля (те же cooldown и лимиты), прежняя аннулируется.
- Что при вводе несовпадающего подтверждения пароля? — Пароль не устанавливается, пользователь получает понятное сообщение об ошибке.
- Что если токен сессии скомпрометирован? — Короткий срок жизни ограничивает окно; выход отзывает токены; смена пароля отзывает все сессии пользователя.
- Что если refresh-токен украден и использован раньше владельца? — Ротация при каждом использовании делает кражу обнаруживаемой: повторное применение ротированного refresh отклоняется и отзывает цепочку сессии.
- Что при одновременном входе с нескольких устройств? — Параллельные сессии разрешены; каждая живёт независимо и завершается своим выходом; смена пароля отзывает все.
- Что при попытке перечисления аккаунтов (какие username/email существуют)? — Ответы регистрации и входа не раскрывают лишнего; восстановление отвечает одинаково для существующих и несуществующих email.
- Что при удалении/опечатках в email? — Регистрация с некорректным по формату email отклоняется сразу валидацией.
- Что если письмо ушло в спам/не доставлено и срок ссылки истёк? — Пользователь запрашивает повторную отправку (с лимитом), получает свежую ссылку.
- Как система ведёт себя при отказе СУБД/email-сервиса в момент подтверждения? — Операция идемпотентна по эффектам: повторный переход/повтор запроса не создаёт дублей, действие выполняется ровно один раз (повтор после успешного завершения отклоняется единообразной ошибкой, а не «завершает действие» повторно).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST позволять создать аккаунт по паре username + email при условии уникальности обоих значений среди пользователей; username и email проходят валидацию формата.
- **FR-002**: Система MUST отправлять на email одноразовую ссылку подтверждения регистрации с ограниченным сроком действия и MUST предоставлять повторную отправку письма с защитой от флуда.
- **FR-003**: Система MUST требовать задания и подтверждения пароля после подтверждения email и MUST блокировать вход до полной активации аккаунта (подтверждённый email + заданный пароль).
- **FR-004**: Пароли MUST удовлетворять политике: длина 8–128 символов; значение не пустое и не из одних пробелов; вне топ-листа распространённых слабых паролей (конкретный список фиксируется конфигурацией на этапе планирования); отлично от username и email аккаунта. Пароли MUST храниться исключительно в виде хеша, полученного современным адаптивным алгоритмом медленного хеширования с индивидуальной солью; открытый пароль нигде не сохраняется и не логируется.
- **FR-005**: Система MUST аутентифицировать пользователя по паролю и идентификатору — username или email — и возвращать единообразную ошибку при неверных данных, не раскрывающую существование аккаунта.
- **FR-006**: При успешном входе система MUST выдавать короткоживущий токен сессии и refresh-токен; refresh-токен MUST ротироваться при каждом использовании, а его повторное использование MUST отклоняться и отзывать цепочку сессии.
- **FR-007**: Система MUST отклонять любой запрос к API чата без действительного токена сессии, за исключением зафиксированного списка публичных endpoints процесса аутентификации.
- **FR-008**: Система MUST отправлять все транзакционные письма (подтверждение, повторная отправка, восстановление пароля) через внешний email-сервис за заменяемым шлюзом; сбой доставки MUST наблюдаться в метриках/логах и не должен обрушивать публичные endpoints.
- **FR-009**: Система MUST применять rate limiting по источнику запроса и по аккаунтам/email на всех публичных endpoints и MUST обеспечивать прогрессирующее замедление/временную блокировку при серии неудачных попыток входа; лимиты MUST действовать консистентно при горизонтальном масштабировании (состояние во внешнем хранилище, не в памяти процесса).
- **FR-010**: Система MUST поддерживать восстановление пароля по одноразовой email-ссылке с ограниченным сроком действия; после смены пароля MUST отзываться все сессии и refresh-токены пользователя и MUST отклоняться вход по старому паролю.
- **FR-011**: Система MUST позволять пользователю завершить сессию (выход) с отзывом токена сессии и связанного refresh-токена.
- **FR-012**: Система MUST обеспечивать идемпотентность эффектов операций подтверждения email и смены пароля по ссылке: повторное применение ссылки не порождает новых эффектов и дублей; повторное применение уже использованной/истёкшей ссылки отклоняется единообразной ошибкой с предложением запросить новую.
- **FR-013**: Все решения аутентификации (успешный/неуспешный вход, подтверждение, смена пароля, отзыв сессий) MUST фиксироваться в журнале событий безопасности без записи секретов (паролей, токенов) в открытом виде.

### Key Entities *(include if feature involves data)*

- **User (аккаунт)**: идентичность пользователя; атрибуты: username (уникален), email (уникален), статус (ожидает подтверждения / ожидает задания пароля / активен), хеш пароля с солью (после задания), момент создания/активации. Не хранит пароль в открытом виде.
- **Email Verification Token**: одноразовая ссылка подтверждения регистрации; связан с User; имеет срок действия и состояние (активен / использован / истёк).
- **Password Setup Token**: одноразовый токен задания пароля после подтверждения email (выдаётся ответом confirm; повторно отправляется ссылкой при истечении); связан с User; имеет срок действия и состояние; применение устанавливает пароль и активирует аккаунт.
- **Password Reset Token**: одноразовая ссылка восстановления пароля; связан с User; имеет срок действия и состояние; применение меняет пароль и отзывает сессии.
- **Session (пара токенов)**: короткоживущий токен сессии + связанный refresh-токен; принадлежит User; поддерживает ротацию refresh, отзыв по выходу и массовый отзыв при смене пароля.
- **Transactional Email**: письмо, отправленное через внешний email-сервис (подтверждение / повторная отправка / восстановление); фиксируется для наблюдаемости доставки.

Терминологическое соответствие: «Email Verification Token» / «Password Setup Token» / «Password Reset Token» — логические представления единой сущности `OneTimeToken` (различаются `purpose` = `email_verification` / `password_setup` / `password_reset`); статусы User: «ожидает подтверждения» = `pending_email_confirmation`, «ожидает задания пароля» = `awaiting_password`, «активен» = `active`; «Session (пара токенов)» реализуется таблицами `sessions` + `refresh_tokens` (цепочка поколений refresh) — см. data-model.md §1–§4.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь проходит полный путь регистрации (форма → письмо → пароль) за 5 минут или менее, а письмо со ссылкой доставляется в течение 2 минут в 95% случаев.
- **SC-002**: 100% обращений к API чата без действительного токена сессии отклоняются ошибкой «не аутентифицирован» (проверяется по всему зафиксированному перечню endpoints).
- **SC-003**: 95-й перцентиль серверной задержки успешного входа (POST /auth/login, без учёта сети клиента) составляет не более 500 мс при профиле нагрузки из плана; искусственные задержки защиты от подбора (SC-004) в метрику не входят; истёкший токен сессии прозрачно продлевается по refresh-токену без повторного ввода пароля.
- **SC-004**: При серии из 10 и более неудачных попыток входа в один аккаунт в течение минуты подбор пароля эффективно ограничивается (замедление/блокировка), при этом валидный владелец сохраняет возможность войти после снятия ограничения.
- **SC-005**: Ни в одном хранилище, логе или выгрузке системы не обнаруживается открытый пароль пользователя (проверяется аудитом: хранение только хеша с индивидуальной солью).
- **SC-006**: Не менее 90% пользователей, запросивших восстановление пароля, успешно входят с новым паролем с первой попытки после прохождения ссылки из письма — post-launch KPI (измеряется после запуска по журналу auth_events; buildable-часть — сам механизм восстановления по FR-010, отдельной задачи не требует).
- **SC-007**: При недоступности внешнего email-сервиса публичные endpoints остаются доступными (не возвращают системных ошибок), 100% сбоев доставки фиксируются в observability, а повторная отправка работает после восстановления сервиса.
- **SC-008**: Публичные endpoints выдерживают заранее установленный профиль нагрузки аутентификации (регистрации/входы в пике) с контролируемой деградацией: превышения лимитов отклоняются корректно, а не приводят к отказу сервиса целиком.

## Assumptions

- SSO/OIDC-вход и интеграции с identity-провайдерами — отдельная фича (003 sso-identity-providers дорожной карты) и в этот scope не входят; модель сессий/токенов строится так, чтобы SSO мог быть добавлен позже без переделки.
- Конкретный срок жизни токена сессии, refresh-токена, ссылок из писем и точные пороги rate limiting фиксируются на этапе планирования как конфигурируемые параметры; в спецификации значима только «короткоживучесть» сессии и одноразовость/ограниченный срок ссылок.
- Регистрирующиеся пользователи имеют доступ к своему email; доставка писем зависит от внешнего провайдера, поэтому надёжность подтверждается метриками доставки, а не гарантией 100%.
- В SC-001 «доставка» письма означает передачу внешнему email-шлюзу (outbox → `sent`), измеряется таймером `email_delivery_duration` из плана; целевое 95% ≤ 2 мин — post-launch SLA по этой метрике. Полный путь регистрации ≤ 5 мин обеспечивается отсутствием искусственных задержек (resend-cooldown первому письму не мешает) и подтверждается функциональными тестами.
- Валидация username ограничивается разумным минимумом (длина, допустимый алфавит, уникальность); правила нормализации email (регистронезависимость) уточняются в плане.
- Параллельные сессии одного пользователя с разных устройств разрешены; управление устройствами/просмотр активных сессий — вне scope этой фичи.
- Блокировка учётной записи администратором, удаление аккаунта и GDPR-удаление — вне scope (в дорожной карте помечены отдельными фичами).
- Инфраструктура фичи 001 (CI/CD, observability, OpenAPI-конвейер) доступна и используется; новые endpoints попадают в публичный контракт с генерацией типов.
- Изменение email и пароля из профиля (для уже вошедшего пользователя), кроме восстановления по ссылке, — вне scope, если не потребуется на clarify.
- Незавершённые (неподтверждённые) регистрации не удаляются автоматически: занятые ими username/email недоступны до завершения регистрации; GC брошенных pending-аккаунтов — вне scope этой фичи (YAGNI, при необходимости — отдельная задача).
