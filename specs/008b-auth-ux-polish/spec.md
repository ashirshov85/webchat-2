# Feature Specification: Полировка auth-флоу и управление паролем

**Feature Branch**: `008b-auth-ux-polish`

**Created**: 2026-10-11

**Status**: Draft

**Input**: User description: "Полировка auth-флоу и управление паролем. (1) После успешного входа по паролю — редирект на страницу чата (сейчас после логина пользователь остаётся на /login); учёт параметра returnTo — паритет с SSO-флоу 003. (2) На странице логина — вариант сброса пароля: ссылка на существующий флоу восстановления по email-ссылке из 002, без изменения API. (3) В профиле пользователя («Мой профиль» из 008) — смена пароля: ввод текущего пароля + новый с подтверждением; клиентская валидация (совпадение, политика паролей как в 002) и серверная проверка старого пароля; аддитивный endpoint смены пароля с rate limiting, пароли только в хешированном виде; поведение сессий и refresh-токенов после смены пароля (инвалидация прочих устройств) фиксируется clarify. (4) Онбординг новых пользователей: сразу после успешной регистрации в контакты автоматически добавляется системный контакт admin (гарантированное существование аккаунта admin — seed при развёртывании); добавление идемпотентно, дублей не создаёт."

## Clarifications

### Session 2026-10-11

- Q: Как должна вести себя смена пароля в «Мой профиль» для пользователей без локального пароля (JIT-аккаунты SSO из фичи 003, у которых пароль никогда не задавался)? → A: Скрывать форму смены пароля для аккаунтов без пароля; показывать подсказку «задать пароль через восстановление по email» (флоу 002).
- Q: Должны ли существующие пользователи, зарегистрированные до внедрения этой фичи, тоже автоматически получать стартовый контакт admin при развёртывании? → A: Нет — только новые регистрации после внедрения, бэкфилла нет.
- Q: Должен ли отзыв сессий прочих устройств (FR-008) выполняться, если новый пароль совпадает с текущим? → A: Да — отзыв прочих сессий при любой успешной смене, включая совпадающий пароль.
- Q: Должно ли автодобавление стартового контакта admin выполняться синхронно в момент регистрации или допустима асинхронная обработка события с задержкой появления контакта? → A: Асинхронно по событию регистрации + идемпотентная проверка-дубль при первом входе/первом запросе контактов (self-healing fallback).
- Q: Должен ли refresh-токен текущей сессии ротироваться сразу после успешной смены пароля? → A: Да — в ответе смены пароля текущей сессии выдаётся новый refresh-токен, прежний отзывается; пользователь остаётся вошедшим.
- Q: Должен ли топ-лист слабых паролей проверяться клиентской валидацией до отправки? → A: Нет — детерминированные правила (совпадение, длина, пробелы, username/email) проверяет клиент; топ-лист проверяет сервер (400 `too_common`), чтобы не утекать словарём в клиентский бандл; сообщение остаётся понятным.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Редирект на чат после парольного входа с учётом returnTo (Priority: P1)

Пользователь с активным аккаунтом входит по паролю на странице входа. После успешного входа система немедленно переводит его на главную страницу чата (маршрут по умолчанию) — вместо текущего поведения, когда пользователь остаётся на странице входа. Если вход был инициирован с глубинного экрана приложения (пользователь перенаправлен на вход с запомненным путём возврата `returnTo`), после успешного входа он возвращается по этому пути. Поведение паритетно SSO-флою фичи 003: тот же смысл параметра, те же правила безопасности (только относительный путь внутри приложения) и тот же фолбэк на маршрут по умолчанию.

**Why this priority**: Парольный вход — базовый сценарий каждого пользователя; сейчас он визуально «зависает» на странице входа, что ломает весь дальнейший путь. Это дефект основного флоу, а не улучшение.

**Independent Test**: Полностью проверяется вручную и автотестом: (а) вход валидными credentials со страницы входа → пользователь оказывается на странице чата; (б) инициированный с глубинного экрана вход с `returnTo` → возврат по указанному пути; (в) вход с небезопасным `returnTo` → возврат на маршрут по умолчанию. Ничего кроме этого сценария не требуется.

**Acceptance Scenarios**:

1. **Given** пользователь на странице входа без параметра возврата, **When** вводит корректный идентификатор и пароль, **Then** вход выполняется и пользователь оказывается на главной странице чата; на странице входа он не остаётся.
2. **Given** неаутентифицированное обращение к защищённому маршруту, при котором пользователь перенаправлен на вход с сохранением пути возврата (`returnTo` — относительный путь внутри приложения), **When** пользователь успешно входит по паролю, **Then** он возвращается на исходный маршрут.
3. **Given** параметр возврата отсутствует, пуст или не является безопасным относительным путём внутри приложения (абсолютный URL, путь вовне приложения, некорректная запись), **When** вход успешен, **Then** применяется маршрут по умолчанию (страница чата); переход на внешние адреса исключён (защита от open redirect).
4. **Given** неверные credentials, **When** выполняется попытка входа, **Then** пользователь остаётся на странице входа с понятной ошибкой (текущее поведение 002 без изменений); переходов не происходит.
5. **Given** вход через SSO-провайдера (фича 003), **When** флоу завершается успешно, **Then** поведение возврата не изменяется (регрессии нет — паритет, а не переделка).

### User Story 2 - Смена пароля в «Мой профиль» (Priority: P1)

Вошедший пользователь открывает «Мой профиль» (модальная форма фичи 008) и может сменить пароль: вводит текущий пароль, новый пароль и его подтверждение. Клиентская валидация до отправки проверяет совпадение нового пароля и подтверждения и соответствие политики паролей фичи 002 (та же политика, что при регистрации и восстановлении). Сервер проверяет текущий пароль и применяет новый. Неверный текущий пароль отклоняется; операция защищена ограничением частоты (rate limiting); пароль хранится только в хешированном виде; смена фиксируется в журнале безопасности. После успешной смены сессии и refresh-токены прочих устройств пользователя отзываются — вошедшим остаётся только устройство, с которого выполнена смена, причём его refresh-токен ротируется (выдаётся новый, прежний отзывается).

**Why this priority**: Самостоятельная смена пароля — базовая защита аккаунта (подозрение на компрометацию, гигиена паролей), ожидаемая пользователями от любого зрелого мессенджера и вытекающая из конституции (V). Не зависит от email-флоу и доступна каждому вошедшему.

**Independent Test**: Полностью проверяется вручную и автотестом: вошедший пользователь меняет пароль из профиля → выход → вход по новому паролю успешен, по старому отклонён. Ошибочные варианты (неверный текущий пароль, несовпадение подтверждения, слабый новый пароль, превышение лимита попыток) отклоняются с понятными сообщениями.

**Acceptance Scenarios**:

1. **Given** вошедший пользователь, **When** открывает «Мой профиль» и выбирает смену пароля, **Then** доступны поля: текущий пароль, новый пароль, подтверждение нового пароля.
2. **Given** введён верный текущий пароль и валидный новый пароль с совпадающим подтверждением, **When** отправлена смена, **Then** пароль применяется, пользователь получает подтверждение об успехе; дальнейший вход по старому паролю отклоняется, по новому — успешен.
3. **Given** текущий пароль неверен, **When** отправлена смена, **Then** смена отклоняется с понятным сообщением; новый пароль не применяется.
4. **Given** новый пароль и подтверждение не совпадают, либо новый пароль нарушает детерминированные правила политики 002 (длина вне 8–128, пустой/из одних пробелов, совпадает с username или email аккаунта), **When** пользователь пытается отправить форму, **Then** ошибка показывается клиентской валидацией с понятным сообщением до обращения к серверу.
4a. **Given** новый пароль входит в топ-лист распространённых слабых паролей, **When** форма отправлена, **Then** сервер отклоняет её ответом 400 с кодом `too_common`, и форма показывает понятное сообщение; список на клиент не передаётся.
5. **Given** серия попыток смены пароля (успешных или неудачных) сверх установленного лимита, **When** лимит превышен, **Then** избыточные запросы временно отклоняются с указанием, когда можно повторить; лимит действует консистентно при горизонтальном масштабировании (конвенция 002).
6. **Given** смена пароля выполнена, **When** проверяется журнал событий безопасности, **Then** событие зафиксировано без паролей и токенов в открытом виде (конвенция 002).
7. **Given** пароль изменён, **When** проверяется хранилище, **Then** новый пароль присутствует только в виде хеша с индивидуальной солью (тот же механизм хеширования, что в 002); открытый пароль нигде не сохраняется и не логируется.
8. **Given** у пользователя активны сессии на двух устройствах, **When** пароль сменён на первом устройстве, **Then** сессия и refresh-токены второго устройства отозваны (требуется повторный вход с новым паролем), а сессия первого устройства остаётся действующей с ротированным refresh-токеном (новый выдан, прежний отозван) (FR-008).

### User Story 3 - Ссылка сброса пароля на экране входа (Priority: P2)

Пользователь, забывший пароль, с экрана входа попадает в существующий флоу восстановления пароля по email-ссылке (фича 002): на странице входа размещается ссылка сброса пароля («Забыли пароль?» или эквивалентная по смыслу), открывающая форму запроса восстановления. API и семантика восстановления не меняются — меняется только доступность входа во флоу с экрана входа.

**Why this priority**: Небольшая, но замыкающая полировка пути «забыл пароль»: без ссылки пользователь без знания URL не попадает во флоу; при этом сама механика восстановления уже работает (002) и от этой истории не зависит.

**Independent Test**: Проверяется вручную и автотестом: ссылка видна на странице входа; клик открывает форму запроса восстановления по email; прохождение флоу до входа с новым паролем работает без изменений (регрессия 002 отсутствует).

**Acceptance Scenarios**:

1. **Given** страница входа, **When** пользователь ищет способ сброса пароля, **Then** ссылка сброса пароля видна и различима.
2. **Given** клик по ссылке сброса, **When** он выполнен, **Then** открывается форма запроса восстановления по email (существующий флоу 002).
3. **Given** пользователь проходит флоу восстановления, **When** задаёт новый пароль по ссылке из письма, **Then** поведение идентично фиче 002: единый ответ для существующих и несуществующих email, одноразовость и срок ссылки, отзыв сессий — без изменений API и семантики.

### User Story 4 - Стартовый контакт admin для новых пользователей (Priority: P2)

Сразу после успешной регистрации нового пользователя в его список контактов автоматически добавляется системный контакт admin — у каждого нового пользователя с первого входа есть адресат для вопросов и первый живой диалог. Аккаунт admin гарантированно существует: он создаётся процедурой начального наполнения (seed) при развёртывании. Добавление выполняется асинхронно по событию завершения регистрации; идемпотентная проверка-дубль при первом входе/первом запросе контактов (self-healing fallback) гарантирует видимость admin к первому входу даже при сбое доставки события. Добавление идемпотентно: повторные срабатывания (ретраи, повторная доставка события, срабатывание фолбэка) не создают дублей. Стартовый контакт — обычная запись контакта (семантика 004), которой пользователь управляет стандартно.

**Why this priority**: Онбординг улучшает первый опыт, но не блокирует работу системы; опирается на готовую модель контактов 004 и требует лишь гарантированного существования admin.

**Independent Test**: Полностью проверяется вручную и автотестом: завершение регистрации нового пользователя → при первом входе admin присутствует в списке контактов ровно один раз; повторная фиксация события регистрации не создаёт дубль; после развёртывания аккаунт admin существует, повторные запуски не создают дублей.

**Acceptance Scenarios**:

1. **Given** развёртывание системы, **When** оно завершено, **Then** аккаунт admin существует и активен; повторные развёртывания/перезапуски не создают дублей и не перезаписывают существующий аккаунт (seed идемпотентен).
2. **Given** новый пользователь завершил регистрацию (аккаунт активен), **When** он впервые входит и открывает контакты, **Then** admin присутствует в списке контактов ровно один раз.
3. **Given** событие завершения регистрации срабатывает повторно (повторная доставка, ретрай), **When** выполняется повторное автодобавление, **Then** дубль контакта не создаётся.
4. **Given** событие завершения регистрации не доставлено (сбой обработки), **When** пользователь впервые входит и открывает контакты, **Then** идемпотентная проверка-дубль (self-healing fallback) добавляет admin ровно один раз.
5. **Given** пользователь удалил admin из своих контактов, **When** автодобавление уже выполнено при регистрации, **Then** admin не добавляется повторно автоматически (автодобавление — только в момент регистрации).
6. **Given** admin добавлен как стартовый контакт, **When** пользователь открывает диалог и пишет admin'у, **Then** работает обычная механика личного чата пары (фича 004) — особых правил для системного контакта нет.

### Edge Cases

- Что если `returnTo` — абсолютный внешний URL, путь вовне приложения или некорректно закодирован? — Применяется фолбэк на маршрут по умолчанию; переход вовне приложения исключён (защита от open redirect, паритет с 003).
- Что если смена пароля выполняется на устройстве A, пока на устройстве B активна сессия? — Сессии и refresh-токены прочих устройств отзываются (FR-008): устройство B требует повторного входа с новым паролем; текущее устройство A остаётся вошедшим, его refresh-токен ротируется (новый выдан, прежний отозван).
- Что если новый пароль совпадает с текущим? — Допускается, если удовлетворяет политике 002 (в её перечне нет запрета на совпадение со старым паролем); такая операция считается успешной сменой — отзыв сессий прочих устройств (FR-008) выполняется на общих основаниях.
- Что если превышен лимит попыток смены пароля? — Временный отказ с указанием повтора (rate limiting, консистентный при масштабировании), а не отказ сервиса; валидный пользователь может сменить пароль после снятия ограничения.
- Что если при развёртывании username «admin» уже занят существующим аккаунтом? — Seed не перезаписывает и не повреждает существующие данные; отсутствие разрушительных действий (идемпотентность).
- Что если пользователь регистрируется через SSO (JIT-аккаунт фичи 003)? — Новый аккаунт получает стартовый контакт admin по той же механике (единая точка создания аккаунтов) — допущение, см. Assumptions.
- Что если регистрация не завершена (нет подтверждения email или пароля)? — Стартовый контакт не добавляется; только активный аккаунт.
- Что если пользователь сбрасывает пароль по email-ссылке (фича 002), а не из профиля? — Семантика 002 сохраняется полностью (включая отзыв всех сессий); clarify-решение FR-008 касается только смены из профиля.
- Что если у вошедшего пользователя нет локального пароля (JIT-аккаунт SSO 003)? — Форма смены пароля в «Мой профиль» скрыта; показывается подсказка «задать пароль через восстановление по email» (флоу 002, FR-013 фичи 003).
- Что если seed не выполнился в момент развёртывания, а регистрация нового пользователя уже происходит? — Автодобавление не создаёт аккаунт admin и не ломает регистрацию; отказ наблюдаем (логи/метрики), добавление повторяется идемпотентно (следующее срабатывание события, восстановление seed, либо проверка-дубль при первом входе/запросе контактов).
- Что если пользователь зарегистрировался до внедрения этой фичи? — Стартовый контакт admin задним числом не добавляется (бэкфилла нет); автодобавление действует только для регистраций после развёртывания фичи (FR-011).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST переводить пользователя на главную страницу чата после успешного входа по паролю; оставление пользователя на странице входа после успешного входа недопустимо.
- **FR-002**: Парольный вход MUST поддерживать параметр возврата `returnTo` с поведением, паритетным SSO-флою 003: относительный путь внутри приложения применяется после успешного входа; отсутствующий, пустой или небезопасный путь — фолбэк на маршрут по умолчанию; переход на внешние адреса исключён (защита от open redirect).
- **FR-003**: На странице входа MUST быть размещена ссылка сброса пароля, ведущая в существующий флоу восстановления пароля по email-ссылке фичи 002; API и семантика восстановления не изменяются.
- **FR-004**: «Мой профиль» (модальная форма фичи 008) MUST предоставлять аутентифицированному пользователю смену пароля: ввод текущего пароля, нового пароля и подтверждения нового пароля; для аккаунтов без локального пароля (JIT-аккаунты SSO фичи 003) форма смены пароля MUST быть скрыта — отображается подсказка задать пароль через восстановление по email-ссылке фичи 002 (паритет с FR-013 фичи 003); серверная ветка «смена без текущего пароля» не вводится.
- **FR-005**: Клиентская валидация формы смены пароля MUST до отправки проверять детерминированные правила политики фичи 002: совпадение нового пароля и подтверждения, длину 8–128 символов, отличие от пустой/пробельной строки, отличие от username и email аккаунта; нарушения показываются понятными сообщениями. Топ-лист распространённых слабых паролей проверяется сервером: пароль из списка отклоняется ответом 400 с кодом `too_common`, отображаемым формой понятным сообщением; сам список на клиент не поставляется (исключение утечки словаря в бандл).
- **FR-006**: Сервер MUST проверять текущий пароль при смене и отклонять операцию при неверном текущем пароле с понятным сообщением; после успешной смены вход по старому паролю MUST быть невозможен, по новому — успешен.
- **FR-007**: Операция смены пароля MUST добавляться в публичный API-контракт строго аддитивно (обратная совместимость сохраняется — конвенция 004/008a) и MUST быть защищена rate limiting (по пользователю и источнику запроса), действующим консистентно при горизонтальном масштабировании (конвенция 002); превышение лимита отклоняется временной ошибкой с указанием повтора.
- **FR-008**: После успешной смены пароля из профиля система MUST отзывать все сессии и refresh-токены пользователя на прочих устройствах, сохраняя действующей только текущую сессию (устройство, с которого выполнена смена): пользователь остаётся вошедшим на нём, прочие устройства требуют повторного входа уже с новым паролем; refresh-токен текущей сессии MUST ротироваться — в ответе успешной смены выдаётся новый refresh-токен, прежний отзывается; поведение единообразно и для парольных, и для SSO-сессий пользователя; совпадение нового пароля с прежним не отменяет отзыв (успешная операция считается успешной сменой).
- **FR-009**: Пароли при смене MUST обрабатываться и храниться исключительно в хешированном виде тем же механизмом, что в 002 (современный адаптивный алгоритм медленного хеширования с индивидуальной солью); открытый пароль нигде не сохраняется и не логируется.
- **FR-010**: События смены пароля (успешные и неуспешные попытки) MUST фиксироваться в журнале событий безопасности без секретов (паролей, токенов) в открытом виде (конвенция 002).
- **FR-011**: Система MUST автоматически добавлять системный контакт admin в контакты нового пользователя сразу после успешной регистрации; автодобавление выполняется асинхронно по событию завершения регистрации, а идемпотентная проверка-дубль при первом входе/первом запросе контактов (self-healing fallback) MUST гарантировать видимость стартового контакта к первому входу; добавление MUST быть идемпотентным — повторные срабатывания (включая повторную доставку события и срабатывание фолбэка) не создают дублей; задним числом для аккаунтов, существовавших на момент развёртывания фичи, стартовый контакт не добавляется (бэкфилл отсутствует — автодобавление действует только для регистраций после развёртывания).
- **FR-012**: Аккаунт admin MUST гарантированно существовать: процедура начального наполнения (seed) при развёртывании создаёт его при отсутствии; seed MUST быть идемпотентным — повторные запуски не создают дублей и не перезаписывают существующий аккаунт.
- **FR-013**: Стартовый контакт admin MUST вести себя как обычный контакт модели 004 (единый диалог пары, стандартные действия контакта): автодобавление не вводит особых правил; пользователь может удалить его стандартным действием, повторное автоматическое добавление после удаления не выполняется.

### Key Entities *(include if feature involves data)*

- **Системный аккаунт admin**: специальный аккаунт, создаваемый seed'ом при развёртывании; гарантированно существует в каждом окружении; зарезервированный username («admin»); выполняет роль стартового адресата для новых пользователей.
- **Стартовый контакт**: запись в списке контактов нового пользователя, ссылающаяся на системный аккаунт admin; создаётся автоматически в момент завершения регистрации; идемпотентно; после создания управляется пользователем как обычный контакт (модель контактов 004).
- **Смена пароля (операция)**: операция аутентифицированного пользователя «текущий пароль + новый с подтверждением»; серверная проверка текущего пароля; фиксируется в журнале безопасности; связана с существующими сущностями «Пароль (хеш)» и «Session (пара токенов)» фичи 002.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% успешных парольных входов завершаются переходом на страницу чата или на запрошенный безопасный `returnTo`-путь; ни один успешный вход не оставляет пользователя на странице входа.
- **SC-002**: Не менее 95% пользователей, инициировавших смену пароля из профиля с корректными данными, завершают её с первой попытки; типичная смена занимает не более 1 минуты.
- **SC-003**: 100% пользователей, завершивших регистрацию, видят admin в списке контактов при первом входе — ровно одна запись у каждого (0 дублей), включая сценарии повторной доставки события регистрации и сбоя его доставки (срабатывает self-healing fallback).
- **SC-004**: Аудит безопасности подтверждает: пароли в хранилище и логах только в хешированном виде (0 открытых паролей); попытки смены ограничены rate limiting с контролируемой деградацией (временные отказы вместо отказа сервиса); все попытки смены отражены в журнале безопасности без секретов.
- **SC-005**: Изменения не нарушают существующие флоу — SSO-вход и возврат по `returnTo` (003), восстановление по ссылке (002), вход/выход/ротация refresh-токенов (002), контакты и личные чаты (004): регрессионный прогон зелёный; публичный API-контракт изменён только аддитивно.

## Assumptions

- «Успешная регистрация» = достижение аккаунтом активного статуса по флою 002 (подтверждённый email + заданный пароль); незавершённые регистрации стартовый контакт не получают. JIT-аккаунты SSO (003) считаются новыми пользователями и тоже получают стартовый контакт (единая точка создания аккаунтов).
- Username системного аккаунта — «admin»; точные атрибуты seed-аккаунта (email, способ задания и ротации его пароля, поведение в окружениях без email-доставки) фиксируются на этапе планирования; seed идемпотентен и не выполняет разрушительных действий над существующими данными.
- Политика паролей наследуется из 002 без изменений; смена на пароль, совпадающий с прежним, не запрещается (в политике 002 такого ограничения нет).
- `returnTo` при парольном входе — клиентская механика по образцу применения возврата в 003 (параметр запроса входа; применение после успешного входа; безопасность пути проверяется так же); изменение login-endpoint'а 002 не требуется, если иное не потребуется на планировании.
- Поведение сессий при восстановлении пароля по ссылке из 002 (отзыв всех сессий и refresh-токенов) не меняется; после смены пароля из профиля отзываются только прочие устройства — текущая сессия сохраняется (решение clarify зафиксировано в FR-008).
- Смена email, удаление аккаунта, управление устройствами и просмотр активных сессий — вне scope этой фичи.
- Экраны и формы (ссылка сброса, форма смены пароля в «Мой профиль») наследуют действующий дизайн-язык фичи 008; визуальная детализация — на этапе планирования.
- Инфраструктура фич 001–008 (контрактный конвейер, observability, seed-механика развёртывания) доступна и используется.
