# Feature Specification: SSO — вход через внешние identity-провайдеры (OIDC/OAuth2)

**Feature Branch**: `003-sso-identity-providers`

**Created**: 2026-09-16

**Status**: Draft

**Input**: User description: "Вход через внешние identity-провайдеры по OIDC/OAuth2 как равноправная альтернатива паролю. Пользователь может привязать внешний IdP-аккаунт к существующему аккаунту и входить любым из способов. Поддержка конфигурации нескольких провайдеров (endpoints, client id/secret в secret manager), автоматическое создание аккаунта при первом входе через IdP при совпадении email. Единая модель сессий/токенов с фичей 002."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Вход через внешнего провайдера с единой сессией (Priority: P1)

Пользователь с привязанной внешней идентичностью входит без пароля: на экране входа он выбирает одного из включённых провайдеров, аутентифицируется на стороне провайдера и возвращается в чат уже вошедшим. Система выдаёт ту же пару токенов (короткоживущий токен сессии + refresh-токен), что и при входе по паролю: продление по refresh с ротацией, выход с отзывом обоих токенов и все остальные свойства сессий фичи 002 работают одинаково. Способ входа не влияет на права и доступ к API: сессия, созданная через IdP, равноправна парольной.

**Why this priority**: Это ядро фичи — равноправная альтернатива паролю; без работающего входа через провайдера остальные сценарии (JIT, привязки) не имеют смысла.

**Independent Test**: Автотестом полного флоу с эмулируемым провайдером: старт входа через провайдера → аутентификация → возврат → получена пара токенов, идентичная по свойствам парольной; продление по refresh ротирует токен; logout отзывает оба токена; доступ к защищённому API работает по токену сессии.

**Acceptance Scenarios**:

1. **Given** на экране входа отображаются включённые провайдеры, **When** пользователь выбирает провайдера и успешно аутентифицируется у него, **Then** он возвращается в приложение вошедшим: создаётся сессия и выдаётся пара токенов того же формата и с теми же свойствами, что при парольном входе.
2. **Given** сессия создана через провайдера, **When** срок токена сессии истекает и клиент продлевает её по refresh-токену, **Then** продление работает так же, как для парольного входа, включая ротацию refresh-токена.
3. **Given** сессия создана через провайдера, **When** пользователь выполняет выход, **Then** токен сессии и refresh-токен отзываются, дальнейшее их использование отклоняется.
4. **Given** у пользователя есть и пароль, и привязанная внешняя идентичность, **When** он входит любым из способов, **Then** обе сессии дают одинаковый доступ ко всем API чата.
5. **Given** пользователь отменяет согласие у провайдера или провайдер возвращает ошибку, **When** происходит возврат в приложение, **Then** вход не выполняется, показывается понятная ошибка, состояние аккаунта не меняется.

### User Story 2 - Первый вход через IdP: автосвязывание или автоматическое создание аккаунта (Priority: P1)

Пользователь, у которого ещё нет внешних привязок, впервые входит через провайдера. Если провайдер подтверждает email пользователя и в системе уже есть активный аккаунт с таким email, внешняя идентичность автоматически привязывается к этому аккаунту и вход выполняется в него. Если аккаунта с таким email нет, система автоматически создаёт активный аккаунт (JIT): email берётся от провайдера, уникальный username генерируется системой, внешняя идентичность сразу привязывается — пользователь попадает в чат без ручной регистрации, писем и задания пароля. Если провайдер не подтверждает email или не возвращает его, автоматическое связывание и создание не выполняются.

**Why this priority**: Автоматическое создание/связывание по email — явно заявленная ценность фичи (бесшовный первый вход); вместе с US1 образует минимальный жизнеспособный сценарий.

**Independent Test**: Автотестом с эмулируемым провайдером: первый вход с подтверждённым email, отсутствующим в системе, → создан активный аккаунт с привязкой; первый вход с подтверждённым email существующего активного аккаунта → вход выполнен в этот аккаунт, привязка добавлена; вход с неподтверждённым email → ничего не создаётся и не связывается.

**Acceptance Scenarios**:

1. **Given** в системе нет аккаунта с email E и провайдер подтверждает email E, **When** пользователь впервые входит через этого провайдера, **Then** автоматически создаётся активный аккаунт с email E и системой-сгенерированным уникальным username, внешняя идентичность привязывается к нему, вход выполняется; ручные шаги регистрации не требуются.
2. **Given** существует активный аккаунт с email E (созданный по паролю в фиче 002) и провайдер подтверждает email E, **When** пользователь впервые входит через этого провайдера, **Then** внешняя идентичность автоматически привязывается к существующему аккаунту и вход выполняется именно в него; новый аккаунт не создаётся.
3. **Given** провайдер не подтверждает email или не возвращает его, **When** пользователь пытается войти впервые (внешняя идентичность не привязана ни к одному аккаунту), **Then** автоматическое создание и связывание не выполняются, показывается понятное сообщение с предложением войти по паролю и привязать провайдера в настройках.
4. **Given** существует не завершивший регистрацию (pending) аккаунт с email E, **When** пользователь впервые входит через провайдера с подтверждённым email E, **Then** автосвязывание и JIT-создание не выполняются (дубль email невозможен, активация в обход задания пароля недопустима); пользователю предлагается завершить регистрацию по ссылке из письма (фича 002).
5. **Given** JIT-аккаунт создан без пароля, **When** выполняется попытка входа по паролю для него, **Then** вход отклоняется; пользователь может задать пароль через механизм восстановления пароля из фичи 002, после чего оба способа входа доступны.
6. **Given** сгенерированный username конфликтует с существующим, **When** создаётся JIT-аккаунт, **Then** система подбирает другой уникальный username; для пользователя это незаметно.

### User Story 3 - Ручное управление привязками внешних IdP (Priority: P2)

Аутентифицированный пользователь управляет внешними привязками своего аккаунта: инициирует привязку дополнительного провайдера (проходя полный флоу аутентификации у провайдера, чем доказывает контроль над внешним аккаунтом) и отвязывает ненужные. Список подключённых провайдеров с их email отображается в настройках безопасности. Отвязка разрешена только если у аккаунта остаётся хотя бы один способ входа (пароль или другая привязка) — система не даёт пользователю заблокировать себя. Email аккаунта при привязке/отвязке не меняется.

**Why this priority**: Ручная привязка нужна, когда email аккаунта и провайдера различаются (автосвязывание не сработает); не блокирует вход через уже привязанных провайдеров, поэтому P2.

**Independent Test**: Автотестом API: вошедший пользователь привязывает провайдера → идентичность появляется в списке привязок и становится способом входа; отвязка → вход через этого провайдера отклоняется; попытка отвязать последний способ входа → отклоняется.

**Acceptance Scenarios**:

1. **Given** аутентифицированный пользователь, **When** он инициирует привязку провайдера и успешно аутентифицируется у него, **Then** внешняя идентичность привязывается к его аккаунту и отображается в списке подключённых; вход через этого провайдера становится возможен.
2. **Given** внешняя идентичность (провайдер + идентификатор пользователя у провайдера) уже принадлежит другому аккаунту, **When** пользователь пытается привязать её, **Then** привязка отклоняется с понятной ошибкой, без раскрытия деталей чужого аккаунта.
3. **Given** у аккаунта есть пароль и одна внешняя привязка, **When** пользователь отвязывает провайдера, **Then** привязка удаляется, вход по паролю остаётся доступен, вход через отвязанного провайдера отклоняется.
4. **Given** у аккаунта нет пароля (JIT-аккаунт) и осталась единственная внешняя привязка, **When** пользователь пытается её отвязать, **Then** отвязка отклоняется — нельзя удалить последний доступный способ входа; перед этим пользователю предлагается сначала задать пароль.
5. **Given** привязываемый провайдер возвращает email, отличный от email аккаунта, **When** пользователь выполняет привязку, **Then** привязка разрешается (контроль над обеими сторонами подтверждён), email аккаунта не изменяется.

### User Story 4 - Конфигурация нескольких провайдеров, секреты в secret manager (Priority: P2)

Система одновременно поддерживает несколько включённых внешних провайдеров: каждый задаётся конфигурацией (отображаемое имя, endpoints, client id, признак включённости), а client secret и прочие секретные значения хранятся исключительно в secret manager и никогда — в коде или репозитории. Экран входа перечисляет всех включённых провайдеров; выключение провайдера убирает его из перечня, не затрагивая остальные способы входа и уже существующие привязки. Ошибка конфигурации одного провайдера не влияет на вход через остальных и по паролю.

**Why this priority**: Возможность нескольких провайдеров — заявленное требование, но сам вход (US1–US2) проверяем и с одним настроенным провайдером; конфигурационная механика — P2.

**Independent Test**: Автотестом/аудитом: при ≥2 настроенных провайдерах экран входа перечисляет обоих и вход работает через каждого; секрет провайдера отсутствует в коде, конфигах репозитория и логах; при выключении провайдера он исчезает из перечня и его флоу отклоняется.

**Acceptance Scenarios**:

1. **Given** настроены и включены два и более провайдеров, **When** пользователь открывает экран входа, **Then** отображаются все включённые провайдеры, и вход возможен через каждого из них.
2. **Given** провайдер сконфигурирован, **When** система обращается к нему, **Then** client secret и другие секреты читаются из secret manager и нигде не встречаются в коде, репозитории и логах.
3. **Given** провайдер выключен, **When** пользователь открывает экран входа, **Then** провайдер не отображается; прямая попытка начать его флоу отклоняется; существующие привязки и остальные способы входа не затронуты.
4. **Given** у провайдера неверный secret, недоступные endpoints или истёкший client id, **When** выполняется попытка входа через него, **Then** пользователь получает понятную ошибку, сбой фиксируется в observability, вход через остальных провайдеров и по паролю продолжает работать.

### User Story 5 - Защита SSO-флоу и устойчивость при сбоях провайдера (Priority: P2)

Публичные endpoints SSO-флоу защищены rate limiting'ом по источнику запроса (консистентно при горизонтальном масштабировании, как в фиче 002). Диалог с провайдером защищён от подделки межсайтовых запросов и повторного использования ответов провайдера: подделанный или повторённый ответ отклоняется, сессия не создаётся. Недоступность провайдера обрабатывается грациозно: пользователь получает понятную ошибку за разумное время, парольный вход и остальные провайдеры не деградируют, сбой виден операторам. Все события SSO (входы, привязки, отвязки, JIT-создания, ошибки) фиксируются в журнале безопасности без секретов.

**Why this priority**: Прямое требование безопасности конституции к публичным endpoints и SSO; защищает сценарии US1–US4, проверяется независимо от деталей конкретных провайдеров.

**Independent Test**: Автотестом: серия запросов к SSO-endpoints сверх лимита отклоняется; callback с изменённым/повторённым параметром защиты отклоняется без создания сессии; при недоступном провайдере (таймаут) вход завершается понятной ошибкой, парольный вход работает, событие фиксируется в журнале/метриках.

**Acceptance Scenarios**:

1. **Given** публичные endpoints SSO-флоу, **When** количество запросов от одного источника превышает лимит, **Then** избыточные запросы отклоняются с сообщением о лимите; учёт лимитов общий для всех экземпляров системы.
2. **Given** ответ провайдера подделан или воспроизведён повторно (проверка целостности флоу не проходит), **When** выполняется завершение входа, **Then** запрос отклоняется, сессия и привязка не создаются.
3. **Given** провайдер недоступен или отвечает с ошибкой, **When** пользователь пытается войти через него, **Then** в пределах разумного времени возвращается понятная ошибка без системного сбоя; вход по паролю и через остальных провайдеров работает; сбой наблюдаем в метриках/логах.
4. **Given** происходит любое событие SSO (успешный/неуспешный вход, привязка, отвязка, JIT-создание), **When** событие завершается, **Then** оно фиксируется в журнале событий безопасности без записи секретов и токенов в открытом виде.

### Edge Cases

- Что если у аккаунта не осталось ни пароля, ни привязок? — Невозможно по построению: отвязка последнего способа входа блокируется (US3-4); пользователь без пароля (JIT) обязан оставить хотя бы одну привязку.
- Что если один и тот же внешний аккаунт пытаются привязать два пользователя? — Внешняя идентичность принадлежит не более чем одному аккаунту; вторая привязка отклоняется (US3-2). Если нужен переход между аккаунтами — сначала отвязка владельцем.
- Что если два разных провайдера возвращают один и тот же подтверждённый email? — Обе идентичности связываются/создаются на одном аккаунте с этим email (уникальность email сохраняется, FR-003).
- Что если провайдер сменил email пользователя после привязки? — Привязка идентична по идентификатору пользователя у провайдера, а не по email: вход продолжает работать в тот же аккаунт; email аккаунта не перезаписывается.
- Что если JIT-аккаунт хочет войти по паролю, но пароля нет? — Отклоняется; пароль задаётся через восстановление по email из фичи 002 (US2-5).
- Что если email у провайдера не подтверждён, а аккаунт с таким email существует? — Автосвязывание не выполняется (защита от захвата аккаунта через неподтверждённый email); пользователь входит по паролю и привязывает провайдера вручную.
- Что если во время OIDC-флоу пользователь открыл несколько вкладок/начал несколько флоу? — Каждый флоу проверяется независимо; завершение «чужого» или повторное завершение отклоняется проверкой целостности (US5-2).
- Что если провайдер возвращает email в другой нормализации (регистр, пробелы)? — Сопоставление email выполняется по канонической нормализации, как в фиче 002; дублей из-за регистра не возникает.
- Что если провайдер не возвращает уникального идентификатора пользователя? — Такой провайдер считается некорректно настроенным: флоу отклоняется, событие фиксируется в observability.
- Что если секрет провайдера скомпрометирован/ротирован? — Секрет заменяется в secret manager без изменения кода; старые флоу завершить нельзя после смены (проверка целостности), привязки сохраняются.
- Что если во время завершения флоу (callback) система недоступна/происходит рестарт? — Операции завершения флоу идемпотентны по эффектам: повторный callback не создаёт дублей привязок или аккаунтов.
- Что если пользователь с паролем потерял доступ к внешнему аккаунту? — Использует парольный вход; внешняя привязка не мешает и может быть отвязана (если не последняя — а пароль есть).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST поддерживать вход через любого включённого внешнего identity-провайдера по стандартному флоу OIDC authorization code flow с PKCE как равноправную альтернативу входу по паролю.
- **FR-002**: Успешный вход через провайдера MUST создавать сессию по единой модели фичи 002: короткоживущий токен сессии + refresh-токен с ротацией при каждом использовании, отзыв по выходу, полный отзыв при смене пароля; способ входа MUST НЕ влиять на права и доступ к API.
- **FR-003**: При первом входе через провайдера с подтверждённым им email система MUST: при наличии активного аккаунта с совпадающим (по канонической нормализации) email — автоматически привязать внешнюю идентичность к этому аккаунту и выполнить вход в него; при отсутствии аккаунта — автоматически создать активный аккаунт (JIT) с этим email и сгенерированным уникальным username, привязать идентичность и выполнить вход; в обоих случаях без ручных шагов регистрации.
- **FR-004**: Автоматическое связывание и JIT-создание MUST выполняться только при подтверждении email провайдером; в остальных случаях — отказ с понятным сообщением и предложением войти по паролю и привязать провайдера вручную.
- **FR-005**: Аутентифицированный пользователь MUST иметь возможность привязать к своему аккаунту внешнюю идентичность (пройдя аутентификацию у провайдера) и отвязать её; система MUST запрещать отвязку последнего доступного способа входа (пароль или внешняя привязка).
- **FR-006**: Внешняя идентичность (провайдер + уникальный идентификатор пользователя у провайдера) MUST принадлежать не более чем одному аккаунту; попытка привязки уже занятой идентичности MUST отклоняться без раскрытия деталей аккаунта-владельца.
- **FR-007**: Система MUST поддерживать одновременную конфигурацию нескольких провайдеров; для каждого задаются отображаемое имя, endpoints, client id и состояние (включён/выключен); client secret и другие секреты MUST храниться исключительно в secret manager и нигде не появляться в коде, репозитории и логах.
- **FR-008**: Перечень включённых провайдеров MUST быть доступен на экране входа без аутентификации; публичный перечень endpoints без аутентификации расширяется соответствующими SSO-endpoints (начало флоу, завершение флоу, перечень провайдеров), точный список фиксируется в API-контракте.
- **FR-009**: Публичные SSO-endpoints MUST быть защищены rate limiting'ом по источнику запроса, консистентным при горизонтальном масштабировании (состояние во внешнем хранилище, как в фичи 002); диалог с провайдером MUST быть защищён от подделки межсайтовых запросов и повторного использования ответов провайдера.
- **FR-010**: Отказ или недоступность провайдера MUST обрабатываться грациозно: понятная пользователю ошибка в пределах разумного времени, отсутствие влияния на парольный вход и остальных провайдеров, фиксация сбоя в observability (логи/метрики).
- **FR-011**: Все события SSO (успешный/неуспешный вход, привязка, отвязка, JIT-создание аккаунта, ошибки флоу) MUST фиксироваться в журнале событий безопасности без секретов и токенов в открытом виде.
- **FR-012**: Операции завершения флоу (callback, привязка, JIT-создание) MUST быть идемпотентны по эффектам: повторное выполнение не создаёт дублей аккаунтов, привязок или сессий.
- **FR-013**: Для JIT-аккаунта без пароля вход по паролю MUST отклоняться; задание пароля MUST быть возможно через механизм восстановления пароля фичи 002.

### Key Entities *(include if feature involves data)*

- **Identity Provider (конфигурация провайдера)**: внешний провайдер идентичности; атрибуты: уникальный код, отображаемое имя, endpoints, client id, состояние (включён/выключен), признак доверия подтверждённым email. Секрет (client secret) хранится в secret manager по ссылке, вне БД приложения и репозитория.
- **External Identity (внешняя идентичность)**: привязка внешнего аккаунта к аккаунту WebChat; атрибуты: провайдер, уникальный идентификатор пользователя у провайдера, email от провайдера на момент входа/привязки, момент привязки. Принадлежит ровно одному User; пара (провайдер, идентификатор) уникальна в системе.
- **User (аккаунт, расширение фичи 002)**: может иметь ноль или более внешних идентичностей; JIT-аккаунт создаётся сразу в активном статусе с email от провайдера и сгенерированным username, без пароля; инвариант: у активного аккаунта есть хотя бы один способ входа (пароль или внешняя привязка).
- **Session (сессия, расширение фичи 002)**: единая сущность сессий фичи 002; расширяется признаком способа создания (пароль / конкретный провайдер) для журнала и отображения; все свойства (ротация refresh, отзыв, параллельные сессии) наследуются без изменений.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь с привязанной внешней идентичностью проходит вход через провайдера за не более чем 3 взаимодействия с приложением (выбор провайдера — аутентификация у провайдера — возврат в чат); 95% первых входов через провайдера завершаются успешно без обращения в поддержку.
- **SC-002**: 100% операций API чата, доступных парольной сессии, доступны и равноправны для сессии, созданной через провайдера (проверяется автотестами по всему перечню endpoints); продление, ротация refresh и logout работают идентично.
- **SC-003**: Не менее 90% новых пользователей, впервые входящих через провайдера с подтверждённым email, попадают в чат автоматически (JIT или автосвязывание) без единого ручного шага регистрации.
- **SC-004**: Аудитом подтверждается: ни один client secret или иной секрет провайдера не обнаруживается в коде, репозитории, конфигурационных файлах и логах; 100% секретов хранятся в secret manager.
- **SC-005**: При недоступности любого провайдера 100% попыток входа через него завершаются понятной ошибкой не более чем за 5 секунд (без «вечного ожидания» и системных ошибок), парольный вход и остальные провайдеры не деградируют, 100% сбоев фиксируются в observability.
- **SC-006**: Подделанные или повторно воспроизведённые ответы провайдера отклоняются в 100% случаев без создания сессий, привязок или аккаунтов (проверяется автотестами на подмену и повтор).
- **SC-007**: SSO-endpoints выдерживают установленный профиль нагрузки входа с контролируемой деградацией: превышения лимитов rate limiting отклоняются корректно и консистентно при горизонтальном масштабировании, а не приводят к отказу сервиса.

## Assumptions

- Поддерживается только OIDC (authorization code flow + PKCE); «чистый» OAuth2 без OpenID-идентичности (userinfo) не поддерживается — YAGNI; SAML и прочие протоколы — вне scope.
- Автосвязывание/JIT выполняются только при подтверждённом провайдером email (`email_verified`); для провайдеров, которым система не доверяет подтверждение email, автосвязывание отключается конфигурацией провайдера (защита от захвата аккаунта через «удобный» провайдер).
- Username JIT-аккаунта генерируется системой из email с гарантией уникальности; смена username и профиля — вне scope этой фичи.
- JIT-аккаунт не имеет пароля до явной установки через восстановление пароля (фича 002); пароль при JIT-создании не запрашивается, письмо с подтверждением email не отправляется (email уже подтверждён провайдером).
- Токены провайдера (access/refresh внешнего IdP) не сохраняются после завершения флоу — системе нужна только идентичность (YAGNI).
- Конфигурирование провайдеров — операционная процедура (конфигурация + secret manager), без UI администратора в этой фиче; включение/выключение отражается на экране входа без изменения клиентов.
- Единый logout / выход из провайдера (front-/back-channel logout), обмен утверждениями о пользователе между провайдерами — вне scope: выход из WebChat отзывает только сессию WebChat.
- Привязка провайдера с email, отличным от email аккаунта, разрешена (пользователь подтверждает контроль обеих сторон); email аккаунта при этом не меняется и на сопоставление JIT не влияет.
- Открытие экрана входа со списком провайдеров и старт SSO-флоу доступны без аутентификации; полный перечень публичных endpoints обновляется в API-контракте (расширение перечня из фичи 002).
- Нормализация email (регистронезависимость, обрезка пробелов) соответствует фиче 002; сопоставление при JIT/автосвязывании выполняется по нормализованному значению.
- Модель сессий/токенов фичи 002 не изменяется — только расширяется признаком способа входа; обратная совместимость публичного API обязательна (конституция IV).
- Встраиваемый виджет (фича 013) использует те же SSO-флоу через то же публичное API; отдельные механизмы для него не создаются.
- Блокировка администратором отдельных провайдеров для отдельных пользователей/групп, условный доступ, MFA-политики — вне scope (могут быть отдельными фичами).

## Проверка согласованности с конституцией

- Принцип V (SSO/OIDC как равноправный способ входа; секреты только в secret manager) — FR-001, FR-007, SC-004.
- Принцип II (stateless, консистентные лимиты при масштабировании) — FR-009, SC-007.
- Принцип IV (публичный API, обратная совместимость; расширение перечня публичных endpoints через контракт) — FR-008.
- Принцип VI (интеграционные тесты обязательны для SSO) — Independent Tests всех историй, SC-002, SC-006.
- Принцип VII (YAGNI: без admin-UI, без хранения внешних токенов, без single logout) — Assumptions.
