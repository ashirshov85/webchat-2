# Feature Specification: Видеоконференции в чатах (речь, видео, демонстрация экрана)

**Feature Branch**: `009-video-conferences`

**Created**: 2026-10-15

**Status**: Draft

**Input**: User description: "Из любого чата можно создать видеоконференцию; участники чата подключаются по ссылке-приглашению. Подключение участников — только членов чата: ссылка автоматически постается в чат системным сообщением (кнопка «Подключиться» = переход по ссылке), при подключении бэкенд выполняет membership-check (006) и только затем минтит токен; не-участник с чужой ссылкой получает 403. Гостевой доступ: владелец инвайт-ссылки может пустить внешнего пользователя без аккаунта — ссылка несёт подписанный nonce (JWT/HMAC), гостевой вход через узкий публичный endpoint join-by-invite (единственное исключение из «все API только для аутентифицированных»): валидация nonce → минт LiveKit JWT с урезанными grants (roomJoin, ограниченные canPublishSources); гость не имеет доступа к чату — только лёгкая join-страница с вводом имени и экран конференции, помечен как «гость» в списке участников. Безопасность гостевого входа: rate limiting на публичном endpoint (Bucket4j, паттерн 002), TTL ссылки + ревок модератором, лимит гостей на конференцию (в квоте maxParticipants), публикация гостем по умолчанию только аудио (без экрана), мгновенный кик модератором. «Зал ожидания» (вход гостей с canSubscribe: false до апрува модератором) — out of scope; кандидат в отдельный инкремент при появлении эбьюза или сценария «открытых встреч» на широкую аудиторию. Публикация гостем видео/экрана, single-use ссылок — вопросы clarify. Старт звонка — кнопками «видеозвонок» / «аудиозвонок» в заголовке чата: обе создают одну и ту же конференцию, разница только в стартовом состоянии (аудиозвонок = вход с микрофоном без камеры; камеру можно включить в любой момент — soft-режим по умолчанию, жёсткий запрет публикации видео через grant canPublishSources — вопрос clarify). Pre-join экран (требование, не clarify): перед входом в конференцию участник видит экран предпросмотра — локальное превью камеры, тумблеры стартового состояния «микрофон вкл/выкл» и «камера вкл/выкл», выбор устройств ввода/вывода, кнопка «Войти». Экран один для всех точек входа (видеозвонок, аудиозвонок, инвайт-ссылка, гость) — разница только в дефолтах: видеозвонок → камера+микрофон; аудиозвонок и переход по инвайт-ссылке → только микрофон, при этом тумблер камеры присутствует и доступен (soft-режим: аудиозвонок можно превратить в видеозвонок ещё до входа). Допустим вход с обоими выключенными — подключение без публикации треков (режим «только слушаю»), публикация включается тумблерами уже в звонке. Тумблеры отражают ограничения grants: недоступные источники (например, canPublishSources без video у гостя или «право слова») скрыты/заблокированы с пояснением. Pre-join не занимает слот участника и не публикует треки до нажатия «Войти»; выход из pre-join без входа отменяет подключение без последствий (конференция продолжает жить). Доступность — по общим стандартам UI 008. Поддержка 1:1 и групповых конференций (речь + видео + демонстрация экрана), с управлением участниками (мьют микрофона/камеры, право слова, роли модератора). Архитектура — две плоскости. Медиа-плоскость: self-hosted SFU LiveKit (готовое проверенное решение, CNCF-проект, Go; отдельный Deployment в K8s, своего кода медиа нет; выбирается вместо Jitsi/CPaaS/сборки своего SFU — фиксация выбора с обоснованием и альтернативами в research.md/plan.md по конституции VII). Контрольная плоскость: новый модуль conferences/ внутри существующего Spring Boot-монолита (stateless, по образцу chats/groups/presence), НЕ отдельный микросервис: сущность Conference в PostgreSQL (Flyway), membership-check по участникам чата (006), REST API в публичном OpenAPI-контракте (аддитивно), минт короткоживущих LiveKit JWT (room grants: roomJoin/canPublish/roomAdmin — «право слова» и роли модератора) существующей JWT-инфраструктурой, серверная модерация через LiveKit RoomService API (mute/remove), вебхуки LiveKit → события conference.started/ended в SSE-канал чата через RealtimePubSub, корректное завершение и освобождение ресурсов комнаты. Фронтенд: @livekit/components-react (React-компоненты, не iframe), модуль frontend/src/conferences/, стилизация под дизайн-систему 008. Адаптивное качество (simulcast + dynacast) из коробки; лимиты и квоты — при создании комнаты (maxParticipants) и минте токенов, значение квот — конфиг per-env."

## Clarifications

### Session 2026-10-15

- Q: Что именно ограничивает применённое модератором «право слова» у участника? → A: Ограничивает все публикации участника: аудио, видео и демонстрацию экрана (Q4=A).
- Q: Сохраняются ли модерационные ограничения участника (мьют микрофона/камеры, «право слова») после его отключения и повторного подключения к той же конференции? → A: Да, ограничения привязаны к участнику и сохраняются до конца конференции (Q5=A).
- Q: Что должен делать pre-join экран, когда браузер отклонил (или пользователь запретил) доступ к камере или микрофону? → A: Предупреждение + вход разрешён без недоступных треков (режим «только слушаю»); повторный запрос доступа — уже в звонке (Q6=A).
- Q: Как поступать, если два гостя одной конференции вводят одинаковое имя на join-странице? → A: Дубли разрешены: имя — отображаемое (неуникальное), внутренний идентификатор подключения гостя генерируется сервером уникально (Q7=A).
- Q: Какие клиентские платформы входят в объём v1 для pre-join и экрана конференции? → A: Только настольные браузеры (последние версии Chrome, Firefox, Safari, Edge); мобильный веб вне объёма v1 — кандидат в отдельный инкремент (Q8=A).
- Q: Что происходит с ролью модератора при выходе создателя (модератора по умолчанию) из конференции и в отсутствие модераторов? → A: Роли персистентны до конца конференции: модератор сохраняет права после выхода и переподключения; автопередача роли не выполняется; конференция без модераторов продолжает жить до их возвращения или завершения (Q9=A).
- Q: Может ли один пользователь одновременно участвовать в нескольких конференциях в рамках одного клиента (вкладки)? → A: Нет — одна активная конференция на клиент/вкладку: вход во вторую корректно покидает первую (слот освобождается); параллельное участие возможно через несколько вкладок, каждое подключение — отдельный слот (Q10=A).
- Q: Входит ли в объём v1 переключение устройств ввода/вывода (микрофон, камера, динамики) непосредственно во время звонка? → A: Да, переключение доступно в звонке на лету — выбор на pre-join не единственная точка (Q11=B).
- Q: Как оповещаются члены чата о входящем/идущем звонке в v1 — in-app или полноценный «звонок» с рингтоном и accept/decline? → A: Только in-app: индикатор «звонок идёт» по SSE и voluntary-вход по кнопке; рингтон, accept/decline и «пропущенные звонки» вне v1 (Q12=A).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Старт конференции из чата и подключение участников по ссылке-приглашению (Priority: P1)

Пользователь в любом своём чате (личном 1:1 или групповом, 004/006) нажимает кнопку «видеозвонок» или «аудиозвонок» в заголовке чата: создаётся конференция, привязанная к чату, и в чат автоматически постится системное сообщение со ссылкой-приглашением и кнопкой «Подключиться» (переход по ссылке). Обе кнопки создают одну и ту же конференцию — разница только в стартовых дефолтах pre-join (US2): видеозвонок → камера+микрофон, аудиозвонок → только микрофон. Подключиться могут только члены чата: при запросе доступа бэкенд проверяет членство (membership-check, 006) и только затем выдаёт короткоживущий токен; не-участник с чужой ссылкой получает отказ. Внутри конференции — речь, видео и демонстрация экрана, 1:1 и групповые; устройства ввода/вывода переключаются в звонке (Q11=B); качество адаптируется к сети (simulcast/dynacast). Выход последнего участника корректно завершает конференцию и освобождает ресурсы комнаты.

**Why this priority**: Минимальный жизнеспособный продукт фичи: без создания конференции из чата и защищённого подключения членов чата остальные сценарии (pre-join-дефолты, модерация, гости, события) не имеют предмета.

**Independent Test**: Проверяется вручную и автотестом: пользователь в личном чате нажимает «видеозвонок» — второй участник видит системное сообщение с кнопкой «Подключиться», подключается, оба видят и слышат друг друга; пользователь вне чата, открывший ссылку, получает отказ. Групповой чат — тот же сценарий с N участниками.

**Acceptance Scenarios**:

1. **Given** личный чат A–B, **When** A нажимает «видеозвонок» в заголовке чата, **Then** создаётся конференция, привязанная к чату, и в чат автоматически постится системное сообщение со ссылкой-приглашением и кнопкой «Подключиться».
2. **Given** активная конференция в групповом чате, **When** член чата нажимает «Подключиться» и подтверждает вход (US2), **Then** бэкенд проверяет его членство в чате и только после успеха выдаёт короткоживущий токен доступа; участник подключается к конференции.
3. **Given** пользователь X не состоит в чате, **When** открывает пересланную ему ссылку-приглашение и пытается подключиться, **Then** получает отказ (403) и в конференцию не попадает — обладание ссылкой не заменяет членство.
4. **Given** конференция идёт, **When** участник публикует демонстрацию экрана, **Then** остальные участники видят её (в рамках своих прав получения медиа).
5. **Given** аудиозвонок создан, **When** создатель входит в конференцию, **Then** он входит с микрофоном без камеры и может включить камеру в любой момент (soft-режим; жёсткий запрет видео не вводится — решение specify-раунда от 2026-10-15, Q3=A).
6. **Given** последний участник вышел из конференции, **When** комната опустела, **Then** конференция корректно завершается, ресурсы комнаты освобождаются, повторный переход по старой ссылке даёт «конференция завершена».

### User Story 2 - Pre-join экран: предпросмотр и стартовое состояние перед входом (Priority: P1)

Перед входом в конференцию участник (член чата или гость, из любой точки входа) видит единый экран предпросмотра: локальное превью камеры, тумблеры стартового состояния «микрофон вкл/выкл» и «камера вкл/выкл», выбор устройств ввода/вывода (микрофон, камера, динамики) и кнопку «Войти». Экран один для всех точек входа — разница только в дефолтах: видеозвонок → камера+микрофон; аудиозвонок и переход по инвайт-ссылке → только микрофон, при этом тумблер камеры присутствует и доступен (soft-режим: аудиозвонок можно превратить в видеозвонок ещё до входа). Допустим вход с обоими выключенными — подключение без публикации треков («только слушаю»), публикация включается тумблерами уже в звонке. Тумблеры отражают ограничения прав: недоступные источники (например, при «праве слова») скрыты/заблокированы с пояснением. Pre-join не занимает слот участника и не публикует треки до нажатия «Войти»; выход из pre-join без входа отменяет подключение без последствий — конференция продолжает жить. Доступность — по общим стандартам UI 008.

**Why this priority**: Прямое требование фичи (не clarify) и часть каждой точки входа: без pre-join нельзя единообразно задать стартовое состояние и защитить пользователя от случайной публикации.

**Independent Test**: Проверяется вручную и автотестом: из каждой точки входа (видеозвонок, аудиозвонок, инвайт-ссылка, гостевая ссылка) открывается один и тот же pre-join экран с корректными дефолтами; вход с выключенными тумблерами подключает без публикации треков; закрытие pre-join без «Войти» не оставляет следов.

**Acceptance Scenarios**:

1. **Given** участник переходит по ссылке из системного сообщения видеозвонка, **When** открывается pre-join, **Then** он видит локальное превью камеры, тумблеры «микрофон»/«камера» (оба включены по умолчанию), выбор устройств ввода/вывода и кнопку «Войти».
2. **Given** аудиозвонок или переход по инвайт-ссылке, **When** открывается pre-join, **Then** по умолчанию включён только микрофон; тумблер камеры присутствует и доступен — участник может включить камеру до входа.
3. **Given** участник выключил оба тумблера, **When** нажимает «Войти», **Then** он подключается к конференции без публикации треков («только слушаю») и может включить публикацию тумблерами уже в звонке.
4. **Given** у участника нет права публикации некоторого источника (например, «право слова»), **When** открывается pre-join, **Then** соответствующий тумблер скрыт или заблокирован с понятным пояснением.
5. **Given** открытый pre-join, **While** участник не нажал «Войти», **Then** треки не публикуются и слот участника не занимается.
6. **Given** участник закрыл pre-join без входа, **When** подключение отменяется, **Then** конференция продолжает жить без последствий (следов подключения нет).
7. **Given** браузер отклонил или пользователь запретил доступ к камере/микрофону, **When** участник находится на pre-join, **Then** показывается понятное предупреждение, вход остаётся доступным без недоступных треков (режим «только слушаю»); повторный запрос доступа возможен уже в звонке (Q6=A).

### User Story 3 - Управление участниками и модерация конференции (Priority: P2)

В конференции доступны управление участниками и роли модератора: модератор (по умолчанию — создатель конференции) может принудительно заглушить микрофон или отключить камеру участника, применить «право слова» (ограничение публикации медиа участником), назначить другого участника модератором, мгновенно исключить (кик) участника или гостя и завершить конференцию целиком. Принудительные действия применяются серверно и немедленно видны всем участникам; ограниченный участник видит отражение ограничения в своих тумблерах (заблокированы с пояснением). Роли модератора персистентны до конца конференции: модератор сохраняет права после выхода и повторного подключения; автопередача роли не выполняется — конференция без модераторов продолжает жить до их возвращения или завершения (Q9=A).

**Why this priority**: Групповые конференции без модерации неконтролируемы (шум, эбьюз), а гостевой сценарий (US4) явно опирается на «мгновенный кик»; при этом 1:1-звонок жизнеспособен и без модерации, поэтому P2.

**Independent Test**: Проверяется вручную и автотестом: в групповой конференции модератор глушит участника, отключает ему камеру, применяет право слова, кикает гостя и завершает конференцию — каждое действие применяется немедленно и отображается у всех.

**Acceptance Scenarios**:

1. **Given** конференция с модератором и участниками, **When** модератор глушит микрофон участника, **Then** микрофон участника принудительно выключается, состояние видно всем участникам.
2. **Given** модератор отключает камеру участника, **When** действие применено, **Then** публикация видео участника прекращается принудительно.
3. **Given** применено «право слова» к участнику, **When** участник пытается публиковать аудио/видео/экран, **Then** все публикации участника заблокированы (аудио, видео, демонстрация экрана — Q4=A); тумблеры участника отражают ограничение (заблокированы с пояснением).
4. **Given** модератор назначает участника модератором, **When** применено, **Then** тот получает права модерации конференции.
5. **Given** модератор кикает участника/гостя, **When** применено, **Then** тот немедленно отключается от конференции; повторное подключение возможно только заново по действующей ссылке (см. Edge Cases).
6. **Given** модератор завершает конференцию, **When** применено, **Then** все участники отключаются, ресурсы освобождаются, в чат доставляется событие завершения (US5).

### User Story 4 - Гостевой доступ: внешний участник без аккаунта по инвайт-ссылке (Priority: P3)

Владелец инвайт-ссылки (создатель/модератор конференции) может пригласить внешнего пользователя без аккаунта: гостевая ссылка несёт подписанный nonce с ограниченным сроком жизни; гостевой вход идёт через узкий публичный endpoint join-by-invite — единственное исключение из правила «все API только для аутентифицированных». Валидация nonce → выдача токена с ограниченными правами (подключение к комнате; источники публикации — FR-011: старт — только аудио, видео и экран включаются в звонке). Гость не имеет доступа к чату: только лёгкая join-страница с вводом имени и экран конференции; в списке участников помечен как «гость». Безопасность: rate limiting на публичном endpoint (паттерн 002), TTL ссылки и отзыв модератором, лимит гостей в рамках квоты участников конференции, мгновенный кик модератором.

**Why this priority**: Ценная возможность (собеседник без аккаунта в звонке), но конференции полностью жизнеспособны без неё; гостевой вход — единственная публичная поверхность атаки, поэтому реализуется поверх устойчивого ядра US1–US3.

**Independent Test**: Проверяется вручную и автотестом: модератор генерирует гостевую ссылку, внешний пользователь открывает её, вводит имя, попадает в конференцию с пометкой «гость» и публикацией только аудио; истёкшая/отозванная ссылка и флуд запросами отклоняются; кик отключает гостя немедленно.

**Acceptance Scenarios**:

1. **Given** активная конференция, **When** владелец инвайт-ссылки генерирует гостевую ссылку, **Then** ссылка несёт подписанный nonce с ограниченным TTL и передаётся им внешне (мессенджер, почта) — в чат автоматически не постится.
2. **Given** внешний пользователь без аккаунта открывает гостевую ссылку, **When** nonce валиден, **Then** он видит лёгкую join-страницу: ввод имени + pre-join (US2, дефолт «только микрофон»), после «Войти» подключается к конференции и помечен как «гость» в списке участников.
3. **Given** подключённый гость, **When** он пытается обратиться к чату или его истории, **Then** доступа нет — гостю доступен только экран конференции.
4. **Given** гость подключается, **When** определяется его стартовое право публикации, **Then** публикуется только аудио (без экрана); публикацию видео и экрана гость может включить тумблерами в звонке (решение specify-раунда от 2026-10-15, Q1=C).
5. **Given** гостевая ссылка истекла или отозвана модератором, **When** по ней пытаются войти, **Then** вход отклоняется с понятной ошибкой.
6. **Given** лимит участников (включая гостей) исчерпан, **When** новый участник пытается войти, **Then** отказ с понятной ошибкой лимита.
7. **Given** серия частых запросов на публичный endpoint, **When** превышен лимит rate limiting, **Then** лишние запросы отклоняются контролируемо (паттерн 002), остальные API не деградируют.
8. **Given** гостевая ссылка уже использована для входа, **When** по ней пытаются войти повторно, **Then** вход допустим, пока ссылка действительна (многоразовая в пределах TTL — решение specify-раунда от 2026-10-15, Q2=A; см. FR-012).

### User Story 5 - События жизненного цикла конференции в чате и квоты (Priority: P3)

Жизненный цикл конференции наблюдаем из чата: события начала и завершения конференции доставляются участникам чата в реальном времени (существующий SSE-канал) — члены чата видят, что «звонок идёт», даже не открывая его. Завершение корректно: при выходе последнего участника, по решению модератора или по таймауту пустой комнаты ресурсы освобождаются (медиа-комната закрывается, выданные токены перестают действовать). Лимиты и квоты применяются при создании комнаты (maxParticipants) и выдаче токенов; значения квот — конфигурация per-env (prod/dev-стенды отличаются).

**Why this priority**: События и корректное освобождение ресурсов — необходимая гигиена жизненного цикла и конституционная масштабируемость (II), но пользовательская ценность звона (US1–US4) от них напрямую не зависит, поэтому P3.

**Independent Test**: Проверяется вручную и автотестом: участник чата, не входивший в звонок, получает события начала/завершения в реальном времени; после завершения медиа-комната отсутствует, старые токены отклоняются; превышение maxParticipants отклоняется.

**Acceptance Scenarios**:

1. **Given** конференция создана и первый участник вошёл, **When** конференция фактически началась, **Then** участники чата получают событие начала конференции в реальном времени (SSE-канал чата).
2. **Given** конференция завершилась (последний вышел / модератор завершил / таймаут пустой комнаты), **When** завершение обработано, **Then** участники чата получают событие завершения.
3. **Given** пустая конференция (все вышли), **When** истёк таймаут пустой комнаты, **Then** система завершает её и освобождает ресурсы комнаты; повторное подключение по старым токенам/ссылке невозможно.
4. **Given** комната с квотой maxParticipants, **When** создаётся комната и выдаются токены, **Then** квота соблюдается на обеих точках; значение квоты задаётся конфигурацией окружения.
5. **Given** нагрузка растёт, **When** качество сети участника деградирует, **Then** качество медиа адаптируется (понижение слоёв) без обрыва подключения.

### Edge Cases

- Ссылка-приглашение члена чата переслана постороннему → членство проверяется при каждой выдаче токена (не фактом обладания ссылкой): посторонний получает 403; выход участника из чата лишает его возможности переподключиться.
- Участник исключён из группы (006) во время конференции → его подключение к конференции прекращается (повторная выдача токена невозможна; активное подключение закрывается).
- Двойное нажатие «видеозвонок»/ретрай создания при уже активной конференции в том же чате → вторая конференция не создаётся: пользователю предоставляется существующая (одна активная конференция на чат; системное сообщение не дублируется).
- Создатель нажал «звонок», но никто (включая его) не вошёл → конференция завершается по таймауту пустой комнаты; системное сообщение остаётся в истории, ссылка после завершения показывает «конференция завершена».
- Участник закрыл pre-join без «Войти» → подключение отменяется без следов: слот не занимался, треки не публиковались, конференция продолжает жить.
- Вход с обоими тумблерами выключенными → подключение в режиме «только слушаю»; включение публикации в звонке подчиняется правам участника (заблокированный источник не включается).
- Кикнутый член чата переподключается по ссылке-приглашению из чата → допустимо (кик разрывает текущее подключение, не banning); повторный проблемный участник исключается из чата механизмами 006.
- Кикнутый гость повторно использует ту же гостевую ссылку → вход возможен, пока ссылка действительна (TTL не истёк, не отозвана) — ссылка многоразовая (решение specify-раунда, Q2=A); радикальная мера — отзыв ссылки модератором.
- Участник с модерационным ограничением (мьют/«право слова») отключается и переподключается к той же конференции → ограничение сохраняется до конца конференции (Q5=A); снимается только модератором или завершением конференции (кик — иная мера: разрыв подключения без персистентного ограничения).
- Все модераторы покинули конференцию → конференция продолжает жить; их роли сохраняются, модерационные действия (мьют/кик/завершение/отзыв ссылок) недоступны до возвращения модератора; автопередача роли не выполняется (Q9=A).
- Гостевая ссылка открыта после завершения конференции → отказ «конференция завершена», без раскрытия деталей чата.
- Подделанный/повреждённый nonce гостевой ссылки → отказ без раскрытия причин подделки; попытки брутфорса ограничиваются rate limiting публичного endpoint.
- Флуд публичного endpoint join-by-invite → rate limiting отвечает контролируемым отказом; остальные API не деградируют (паттерн 002).
- Гостевое имя пустое/пробельное/сверхлимитное → валидация с понятной ошибкой; имя отображается с пометкой «гость». Совпадение имён у двух гостей → допустимо: имя только отображаемое, внутренние идентификаторы подключений уникальны (Q7=A).
- Один участник подключён с нескольких устройств/вкладок → каждое подключение занимает слот квоты participants и отображается отдельно (квота считается по подключениям).
- Участник активной конференции подключается к другой конференции в том же клиенте (вкладке) → текущее подключение корректно закрывается (слот освобождается, остальные видят выход), пользователь попадает во вторую; параллельное участие в одном клиенте не поддерживается (Q10=A).
- Кратковременный обрыв сети участника → реконнект без потери конференции; качество адаптируется вниз и восстанавливается.
- Недоступность медиа-плоскости при создании звонка → понятная ошибка «звонок временно недоступен», чат и остальные API не затронуты.
- Потерян вебхук завершения → компенсация таймаутом пустой комнаты (SC-007): ресурсы всё равно освобождаются.
- E2EE-чаты будущей фичи 010: создание конференции из E2EE-чата в v1 не поддерживается (граница фиксируется, реализация — отдельным решением).

## Requirements *(mandatory)*

### Functional Requirements

Создание и подключение:

- **FR-001**: Система MUST позволять аутентифицированному пользователю создать конференцию из любого своего чата (личного или группового) кнопками «видеозвонок»/«аудиозвонок» в заголовке чата; обе кнопки создают одну и ту же конференцию, различаясь только стартовыми дефолтами pre-join (видеозвонок → камера+микрофон; аудиозвонок → только микрофон). В одном чате одновременно активна не более одной конференции; повторное нажатие при активной конференции MUST предоставлять существующую, а не создавать новую. Клиент поддерживает одну активную конференцию на вкладку: подключение к другой конференции MUST корректно покидать текущую (слот освобождается, участники видят выход); параллельное участие в нескольких конференциях в одном клиенте не поддерживается (решение clarify-раунда от 2026-10-15, Q10=A).
- **FR-002**: При создании конференции система MUST автоматически постить в чат системное сообщение со ссылкой-приглашением и кнопкой «Подключиться» (переход по ссылке); сообщение принадлежит истории чата на общих основаниях системных сообщений.
- **FR-003**: Подключение к конференции MUST быть доступно только членам чата: при каждом запросе доступа бэкенд выполняет проверку членства в чате (механизм 006) и только после успеха выдаёт короткоживущий токен подключения; запрос не-участника MUST отклоняться с 403 без раскрытия деталей конференции. Вышедший/исключённый из чата участник теряет право (пере)подключения; его активное подключение MUST быть прекращено.
- **FR-004**: Конференции MUST поддерживать 1:1 и групповые сценарии: речь, видео и демонстрация экрана участников; качество MUST адаптироваться к условиям сети (понижение/повышение слоёв) без обрыва подключения. Переключение устройств ввода/вывода (микрофон, камера, динамики) MUST быть доступно непосредственно в звонке, а не только на pre-join (решение clarify-раунда от 2026-10-15, Q11=B). Своего медиа-кода не пишется — медиа-плоскость строится на готовом проверенном SFU-решении (выбор фиксируется с обоснованием и альтернативами в plan/research по конституции VII).

Pre-join экран:

- **FR-005**: Перед входом в конференцию система MUST показывать единый pre-join экран для всех точек входа (видеозвонок, аудиозвонок, ссылка-приглашение, гостевая ссылка): локальное превью камеры, тумблеры стартового состояния «микрофон вкл/выкл» и «камера вкл/выкл», выбор устройств ввода/вывода, кнопка «Войти». Дефолты: видеозвонок → камера+микрофон; аудиозвонок и инвайт-ссылка → только микрофон, тумблер камеры присутствует и доступен. Жёсткий запрет публикации видео в аудиозвонке не вводится — действует soft-режим: камера включается в любой момент, в том числе до входа (решение specify-раунда от 2026-10-15, Q3=A).
- **FR-006**: Система MUST допускать вход с обоими тумблерами выключенными: подключение без публикации треков («только слушаю») с возможностью включить публикацию тумблерами в звонке — в рамках прав участника.
- **FR-007**: Pre-join экран MUST отражать ограничения прав участника: недоступные источники публикации (например, при «право слова») скрываются или блокируются с понятным пояснением. Отказ браузера в доступе к камере/микрофону на pre-join MUST не блокировать вход: участник видит понятное предупреждение и может войти без недоступных треков (режим «только слушаю»); повторный запрос доступа выполняется уже в звонке (решение clarify-раунда от 2026-10-15, Q6=A). Pre-join MUST не занимать слот участника и не публиковать треки до нажатия «Войти»; выход из pre-join без входа MUST отменять подключение без последствий для конференции. Доступность pre-join и экрана конференции — по стандартам UI 008.

Модерация:

- **FR-008**: Система MUST обеспечивать роли модератора конференции (создатель — модератор по умолчанию; может назначать других) и серверные модерационные действия: принудительный мьют микрофона, отключение камеры, «право слова» (ограничение всех публикаций участника: аудио, видео и демонстрации экрана — решение clarify-раунда от 2026-10-15, Q4=A), мгновенное исключение (кик) участника или гостя, завершение конференции. Действия применяются серверно и немедленно отображаются у всех участников; ограниченный участник видит отражение ограничения в своих элементах управления. Ограничения (мьют, «право слова») привязаны к участнику и сохраняются до конца конференции, включая переподключение; снимаются модератором или завершением конференции (решение clarify-раунда от 2026-10-15, Q5=A). Роли модератора также персистентны до конца конференции (включая переподключение); автопередача роли не выполняется — конференция без модераторов продолжает жить до их возвращения или завершения (решение clarify-раунда от 2026-10-15, Q9=A).

Гостевой доступ:

- **FR-009**: Владелец инвайт-ссылки MUST иметь возможность пригласить внешнего пользователя без аккаунта: гостевая ссылка несёт подписанный nonce (проверяемая подлинность) с ограниченным TTL и может быть отозвана модератором. Гостевой вход выполняется через единственный публичный endpoint join-by-invite — контролируемое исключение из правила «все API только для аутентифицированных»; после валидации nonce выдаётся токен с ограниченными правами (подключение к комнате; права источников публикации — FR-011, права модерации отсутствуют).
- **FR-010**: Гость MUST получать доступ только к экрану конференции через лёгкую join-страницу (ввод имени → pre-join → «Войти»); доступ к чату, его истории и участникам вне конференции MUST быть исключён. В списке участников гость MUST быть помечен как «гость». Введённое имя — отображаемое и неуникальное (дубли допустимы); внутренний идентификатор подключения гостя генерируется сервером уникально (решение clarify-раунда от 2026-10-15, Q7=A).
- **FR-011**: Стартовое состояние публикации гостя — только аудио (без демонстрации экрана и без камеры); гостю MUST быть разрешено включать публикацию видео и демонстрацию экрана тумблерами в звонке — по источникам наравне с участниками, отличаясь стартовым состоянием и отсутствием прав модерации (решение specify-раунда от 2026-10-15, Q1=C).
- **FR-012**: Публичный endpoint гостевого входа MUST быть защищён rate limiting по существующему паттерну (002); лимит гостей входит в общую квоту участников конференции (maxParticipants); кик гостя модератором MUST применяться мгновенно. Гостевая ссылка многоразовая в пределах TTL: одной ссылкой могут войти несколько гостей, каждый со своим именем; вход возможен, пока не истёк TTL, ссылка не отозвана и не исчерпана квота; радикальная мера при эбьюзе — отзыв ссылки модератором (решение specify-раунда от 2026-10-15, Q2=A).

Жизненный цикл, события, квоты:

- **FR-013**: События начала и завершения конференции MUST доставляться участникам чата в реальном времени через существующий канал чата (SSE/RealtimePubSub) — как события конференции, не как пользовательские сообщения. Оповещение о звонке — только внутри приложения: индикатор «звонок идёт» и voluntary-вход по кнопке; рингтон и accept/decline-поток вызова (включая «пропущенные звонки») в v1 не реализуются (решение clarify-раунда от 2026-10-15, Q12=A).
- **FR-014**: Система MUST корректно завершать конференции и освобождать ресурсы комнаты: при выходе последнего участника (с таймаутом пустой комнаты), по команде модератора; после завершения выданные токены перестают действовать, повторное подключение по старым ссылкам отклоняется («конференция завершена»). Потеря сигнала завершения компенсируется таймаутом пустой комнаты.
- **FR-015**: Лимиты и квоты (maxParticipants и др.) MUST применяться при создании комнаты и при каждой выдаче токена; значения квот — конфигурация per-env (prod и dev-стенды отличаются). Превышение квоты отклоняется с понятной ошибкой.

Контракт и наблюдаемость:

- **FR-016**: Все операции и события конференции MUST быть аддитивно описаны в публичном OpenAPI-контракте (источник истины, конституция IV), включая публичный гостевой endpoint; обратная совместимость MUST сохраняться.
- **FR-017**: Контрольная плоскость конференций MUST быть stateless-модулем существующего монолита по образцу существующих доменов (чаты/группы/присутствие), а не отдельным сервисом; хранение сущностей конференции — в основной реляционной БД проекта, миграции — по существующему процессу. Архитектурный выбор (медиа- и контрольная плоскости) предписан фичей и фиксируется с обоснованием и альтернативами в research/plan (конституция VII).
- **FR-018**: Система MUST предоставлять наблюдаемость конференций: число активных конференций и участников, события жизненного цикла, применение квот, отказы гостевого входа (rate limiting) — в существующей observability-инфраструктуре.

### Key Entities *(include if feature involves data)*

- **Конференция (Conference)**: сущность «звонок», привязанная к чату; атрибуты: состояние (создана/идёт/завершена), лимит участников (maxParticipants), время создания/начала/завершения; не является сообщением, но порождает системное сообщение со ссылкой.
- **Ссылка-приглашение (участнику чата)**: адрес подключения членов чата; право входа определяется членством при каждой выдаче токена, а не фактом обладания ссылкой.
- **Гостевая инвайт-ссылка**: ссылка с подписанным nonce, TTL и признаком отзыва; создаётся владельцем-инвайтёром; открывает внешний вход без аккаунта через публичный endpoint.
- **Гость**: внешний участник без аккаунта; отображается именем, введённым на join-странице (имя неуникально — дубли допустимы), внутренний идентификатор подключения генерируется сервером уникально; помечен «гость»; права модерации отсутствуют, стартовая публикация — только аудио (FR-011); доступ к чату исключён.
- **Роль в конференции**: участник / модератор; определяет права модерации (мьют, право слова, кик, завершение, отзыв гостевых ссылок, назначение модераторов); роль персистентна до конца конференции, включая переподключение (Q9=A).
- **Событие конференции**: realtime-событие жизненного цикла (начало/завершение) в канале чата; адресовано участникам чата.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 95% подключений членов чата: от нажатия «Войти» на pre-join до получения медиа (видят/слышат других) — не более 5 секунд (p95) в нормальных сетевых условиях.
- **SC-002**: 100% попыток подключения не-членов чата по чужой ссылке отклоняются (автотест); токен не выдаётся ни в одном случае.
- **SC-003**: 100% попыток гостевого входа по истёкшим, отозванным или подделанным ссылкам отклоняются; валидный гостевой вход требует не более 3 действий пользователя (открыть ссылку → ввести имя → «Войти»).
- **SC-004**: Публичный гостевой endpoint под целевым профилем нагрузки отвечает стабильно, при превышении лимита — контролируемый отказ; деградация остальных API ≤ 10% к базовому прогону (Δp99).
- **SC-005**: Модерационные действия (мьют микрофона/камеры, кик) применяются к целевому участнику не более чем за 2 секунды в 95% случаев.
- **SC-006**: События начала/завершения конференции доставляются участникам чата не позднее 2 секунд в 95% случаев.
- **SC-007**: 100% завершённых конференций освобождают ресурсы комнаты: медиа-комната закрывается автоматически не позднее фиксированного таймаута после выхода последнего участника (автотест); «зависшие» комнаты отсутствуют.
- **SC-008**: Ёмкость соответствует конституционному бюджету (до 1000 одновременных конференций, принцип II) с горизонтальным масштабированием медиа-плоскости; квоты per-env соблюдаются (dev-стенд: maxParticipants ≤ 16, ёмкость стенда валидируется нагрузочным тестом); расчёт нагрузки приводится в plan.md.
- **SC-009**: Метрики наблюдаемости (FR-018) доступны в эксплуатации — по ним SC-001–SC-008 проверяются на реальных данных.

## Assumptions

- Переиспользуются без изменений: аутентификация и JWT-инфраструктура проекта, чаты и membership-check (006), SSE-канал/RealtimePubSub доставки событий чата, rate limiting (паттерн 002), дизайн-система и стандарты доступности (008).
- Архитектура предписана описанием фичи и конституцией (VII): медиа-плоскость — self-hosted SFU LiveKit (отдельный Deployment, своего медиа-кода нет); контрольная плоскость — stateless-модуль `conferences/` существующего Spring Boot-монолита (сущность в PostgreSQL/Flyway, не микросервис); фронтенд — `@livekit/components-react`, модуль `frontend/src/conferences/`. Обоснование выбора и альтернативы (Jitsi, CPaaS, свой SFU) фиксируются в research.md/plan.md.
- «Зал ожидания» (вход гостей без получения медиа до апрува модератором) — вне объёма v1; кандидат в отдельный инкремент при появлении эбьюза или сценария «открытых встреч».
- Запись конференций, трансляции, E2EE-медиа, «залы ожидания», рингтон/accept-decline-механика вызова и «пропущенные звонки» — вне объёма v1 (YAGNI); ringing — кандидат в отдельный инкремент (Q12=A).
- Одна активная конференция на чат; повторный старт при активной конференции возвращает существующую (разумный дефолт, фиксируется в контракте). Одна активная конференция на клиент/вкладку — вход во вторую покидает первую (Q10=A).
- Квота участников считается по одновременным подключениям (устройство/вкладка = слот); таймаут пустой комнаты, TTL гостевых ссылок и токенов — числовые дефолты, фиксируются в контракте/конфигурации per-env.
- Конференции создаются из обычных чатов; E2EE-чаты фичи 010 в v1 конференций не порождают (граница, реализация — отдельным решением).
- UI конференций в v1 — standalone SPA и публичная лёгкая гостевая join-страница; встраивание conferences-модуля в виджет (фича 015) — на общих модулях `frontend/src/conferences/` без дублирования, отдельная задача не создаётся. Целевые клиентские платформы v1 — настольные браузеры (последние версии Chrome, Firefox, Safari, Edge); мобильный веб вне объёма v1 — кандидат в отдельный инкремент (решение clarify-раунда от 2026-10-15, Q8=A).
- Гостевая ссылка не постится в чат автоматически (внешний получатель — вне чата); передача ссылки — руками владельца.
- Кикнутый член чата может переподключиться по действующей ссылке-приглашению (кик ≠ бан); для гостей радикальная мера — отзыв многоразовой ссылки модератором.
- Решения specify-раунда от 2026-10-15: Q1=C — гостю разрешена публикация видео и экрана (включаются в звонке; старт — только аудио); Q2=A — гостевые ссылки многоразовые в пределах TTL (single-use не вводится); Q3=A — soft-режим аудиозвонка (жёсткий запрет публикации видео через права не вводится).
- Решения clarify-раунда от 2026-10-15: Q4=A — «право слова» ограничивает все публикации участника (аудио, видео, экран); Q5=A — модерационные ограничения персистентны до конца конференции, включая переподключение; Q6=A — отказ браузера в доступе к устройствам не блокирует вход (режим «только слушаю»); Q7=A — имена гостей неуникальны, идентификатор серверный; Q8=A — v1 только для настольных браузеров.
