# Load-test отчёт: медиа-плоскость видеоконференций (SC-008)

Фича: [009-video-conferences](../specs/009-video-conferences/) — задача T068, критерий SC-008
(конституция II «Масштабируемость по построению», VI Test-First). Контрольная плоскость
(создание/join/гость/rate-limit) закрыта k6-смоуком [conferences.smoke.js](./k6/conferences.smoke.js)
(T058, прогнано в T067: checks 5206/5206, Δp99 фона −42.9 %/−4.7 % ≤ 10 %, SC-004); настоящий
отчёт — валидация **медиа-плоскости** (SFU LiveKit): join-латентность, потери, CPU/mem ноды,
подтверждение ёмкости dev-стенда и экстраполяция prod-бюджета по формуле
[research.md §12](../specs/009-video-conferences/research.md#12-нагрузочный-расчёт-принцип-ii-sc-008).
Полноразмерная валидация пика (1000 конференций) — платформенная фича 016 (ROADMAP).

Прогон: **2026-10-18 20:46–21:07 UTC**, раннер `lk load-test` (livekit-cli v2.19.0),
оркестратор [media-loadtest.sh](./lk/media-loadtest.sh), сырые данные — `load/lk/results/20261018T204603Z/`

## 2. Профили и результаты

Счётчик помещений/участников — «модель чата»: 1:1 = комната на 4 симулятора (2 publisher'а
audio+video + 2 subscriber'а, layout `speaker` — каждый получает 1 доминантный видеопоток,
как реальный 1:1); групповая = 4 publisher'а av + 8 subscriber'ов layout `3x3` (12 участников,
каждый подписчик ~4 видео + 4 аудио). Потери/битрейты — клиентские сводки `lk`; латентность/RTT —
серверные гистограммы Prometheus LiveKit.

| Фаза | Комнат | Участников | SFU CPU (steady avg/max, % от 1 core) | SFU mem max | Egress/комнату | Потери | Join-латентность |
|---|---|---|---|---|---|---|---|
| B: 1:1 аудио ×10 | 10 | 40 | 34 / 57 | 101 MiB | 83 kbps | **0 %** | см. §3 |
| C@2: 1:1 видео 720p | 2 | 8 | 26 / 45 | 102 MiB | 4.9 Mbps | 0 % | « |
| C@4 | 4 | 16 | 33 / 50 | 102 MiB | 4.9 Mbps | 0 % | « |
| C@6 | 6 | 24 | 46 / 92 | 133 MiB | 5.0 Mbps | 0 % | « |
| C@8 | 8 | 32 | 58 / 105 | 156 MiB | 5.0 Mbps | 0 % | « |
| C@10 | 10 | 40 | 62 / 109 | 195 MiB | 5.0 Mbps | **0 %** | « |
| D: групповые ×2 (3x3) | 2 | 24 | 88 / 94 | 148 MiB | 22 Mbps | **0 %** | « |

Наблюдения:

- **Ёмкость «~10 одновременных 1:1» подтверждена с запасом**: 10 комнат 720p vp8 simulcast
  стабильно держатся на 1.1 core из выделенных 1.5 (лимит не выбран, throttling отсутствует —
  docker stats не выходил за ~110 % = 1.1 core при cap 150 %). Линейная масштабируемость CPU от
  числа комнат (≈ 0.10–0.11 core/комнату steady): 2→4→6→8→10 без переломов.
- **«~2 групповые» подтверждены как оценочный максимум**: 2 комнаты (12 участников, 64
  видеопересылки каждая) — 0.9 core из 1.5; третья групповая на лимите 1.5 CPU уже невозможна,
  что совпадает с заявленной ёмкостью стенда. Бэкенд-квота maxParticipants ≤ 16 (Q19) отсекает
  более тяжёлые комнаты на уровне API (FR-015), а dynacast/simulcast на реальных клиентах
  снижает число слоёв относительно синтетического worst-case прогона.
- Память всюду ≤ 195 MiB из 1 Gi — не является ограничивающим фактором.
- Потери пакетов 0 % во всех профилях (клиентские сводки; серверные гистограммы
  `livekit_packet_loss_percent`: все наблюдения в бакете `le=0`, 5458 сэмплов входящего VIDEO,
  2896 AUDIO).

линейно и не влияет на ёмкостные выводы.

## 4. Экстраполяция prod-бюджета (research §12)

Расчётный бюджет: 1000 конференций × ~6 участников ≈ 6000 подключений, ~3000 publisher-потоков,
~24 000 подписок, с учётом simulcast ≈ **36–40k поток-эквивалентов**.

Измеренная удельная стоимость пересылки на этом стенде (docker bridge, software VP8 simulcast):

- 1:1 комната (2 pubs av simulcast + 2 subs) ≈ 0.10–0.11 core; с учётом слоёв (~16
  поток-эквивалентов) → **~0.006–0.007 core на поток-эквивалент**;
- групповая комната (64 пересылки) ≈ 0.44 core → ~0.007 core/пересылку — согласуется с 1:1.

Отсюда ёмкость ноды 8 vCPU (≈ 7 эффективных ядер на медиа):

| Модель | Поток-эквивалентов на ядро | На ноду 8 vCPU | Нод на 36k | Комментарий |
|---|---|---|---|---|
| Бенчмарк LiveKit (research §12) | ~400–500 | 3–4k | **10–14** | оптимистичный ориентир вендора |
| **Измерено (T068, loopback)** | **~150** | **~1.0–1.1k** | **~34 (28 с N+1 → ~28–36)** | консервативная база для планирования |

Вывод: измеренная удельная стоимость в 2.5–3 раза выше вендорского бенчмарка (типично для
виртуализации/bridge-сети и синтетического worst-case simulcast без dynacast-переключений).
Prod-планирование фазы 016 следует вести от измеренной базы: **~30 медиа-нод 8 vCPU (± N+1)
на полный бюджет 1000 конференций**, с уточнением полноразмерным прогоном (фича 016) —
реальные клиенты переключают слои dynacast'ом на low/medium, что снижает стоимость против
синтетики. Контрольная плоскость при этом остаётся ничтожной (§12: ~2–3 rps минта токенов,
SSE-фанаут — доли % бюджета Redis-паб-саб; k6 T058/T067 подтвердил контрольную плоскость
эмпирически, SC-004).

Медиа-ноды горизонтально масштабируются (stateless, координация через Redis — конфиг
`deploy/k8s/base/livekit.yaml` уже содержит distributed-mode), соответствие конституции II
подтверждено: единица масштабирования — нода LiveKit, без изменений приложения.

## 5. Метрики приложения (`webchat_conference_*`)

Синтетические комнаты `lt-*` создаются генератором напрямую в LiveKit (минуя backend №44),
поэтому счётчики жизненного цикла конференции от load-прогона не двигаются — это ожидаемо:
медиа-валидация изолирована от контрольной плоскости. Поведение `webchat_conference_*`
(joins/tokens_minted/joins_denied/ended и др.) зафиксировано реальным трафиком в T067
(все семьи двигаются, включая `joins_denied{reason=quota}` на заниженной квоте против реального
WebRTC-подключения Playwright fake-media) — SC-009 закрыт там; совместный прогон
контрольная+медиа для полного бюджета — сфера 016.

## 7. Выводы по SC-008

1. Ёмкость dev-стенда подтверждена практически: **10 одновременных 1:1 (720p vp8 simulcast)
   на 1.1/1.5 core** и **2 групповые комнаты** в пределах лимитов; потери 0 %, join-латентность
   p100 ≤ 10 мс — деградации нет (SC-008: квоты per-env соблюдаются, ёмкость валидирована).
2. Горизонтальное масштабирование медиа-плоскости зафиксировано измеримо: стоимость на
   поток-эквивалент стабильна между профилями (~0.007 core), узкое место — только CPU ноды;
   память и контрольная плоскость не ограничивают.
3. Prod-бюджет: от измеренной базы — **~28–36 медиа-нод 8 vCPU** на 1000 конференций
   (бенчмарк-ориентир 10–14 нод подтверждён как верхняя граница вендорских условий);
   полноразмерный прогон и финальный сайзинг — платформенная фича 016.
