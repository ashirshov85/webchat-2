# WebChat Constitution

## Core Principles

### I. Spec-Driven (NON-NEGOTIABLE)
Никакой код не пишется без утверждённых артефактов SDD: `spec.md`, `plan.md`, `tasks.md`.
Рабочий процесс строго: `/speckit.specify` → `/speckit.clarify` → `/speckit.plan` →
`/speckit.tasks` → `/speckit.implement` → `/speckit.checklist`.
Каждая задача в `tasks.md` атомарна, самодостаточна и проверяема; размер задачи подбирается
так, чтобы AI-агент (OpenCode) выполнял её за одну итерацию без потери контекста.
Код, не покрытый задачей из `tasks.md`, не пишется.

### II. Масштабируемость по построению (NON-NEGOTIABLE)
Все backend-сервисы stateless и масштабируются горизонтально; состояние сессий и сообщений
хранится только во внешних хранилищах (брокер, СУБД, кэш), не в памяти процесса.
Проектные бюджеты, обязательные для всех решений:
- до 1 000 000 одновременных пользователей;
- до 100 000 сообщений в секунду;
- до 1 000 одновременных видеоконференций;
- хранение истории 12 месяцев с архивацией старых сообщений.
Решение, не укладывающееся в эти бюджеты, MUST быть отклонено или явно обосновано
в `plan.md` с расчётом нагрузки.

### III. Гарантированная доставка без дублей (NON-NEGOTIABLE)
Сообщения доставляются exactly-once (эффект для пользователя): не теряются и не дублируются.
- Идемпотентность на всех уровнях: client-generated message ID, дедупликация по ID.
- Кворум подтверждения записи; ретраи безопасны и не порождают дублей.
- Порядок сообщений гарантируется в рамках одного чата.
- Тесты на потерю, дубль и нарушение порядка обязательны для любого пути доставки.

### IV. API-First и встраиваемость
Чат существует в двух формах — standalone SPA и встраиваемый виджет, — и обе формы
являются клиентами одного и того же публичного API.
- Контракты API описываются в OpenAPI и являются источником истины; TypeScript-типы
  фронтенда генерируются/синхронизируются из контракта.
- Обратная совместимость публичного API обязательна; breaking changes — только через
  версионирование и явное решение в `plan.md`.
- Типы контента (текст, изображения, видео с превью, кнопки, таблицы, календари,
  голосования и др.) реализуются как расширяемая система виджетов/плагинов,
  а не хардкодом в ядре.

### V. Безопасность и приватность по умолчанию
- Доступ к чату — только для зарегистрированных/аутентифицированных пользователей.
  Регистрация: username + email → подтверждение по email-ссылке → ввод и подтверждение
  пароля. Обязательная поддержка SSO (OIDC/OAuth2) и интеграций с identity-провайдерами.
- Приватные беседы со сквозным шифрованием (E2EE) доступны только привилегированным
  пользователям; сервер не имеет технической возможности читать содержимое E2EE-чатов
  (ключи не покидают клиентов).
- Авторизация на уровне каждого ресурса (проверка membership чата) на всех endpoints.
- Секреты только в secret manager / переменных окружения; никогда в коде и репозитории.

### VI. Test-First (NON-NEGOTIABLE)
Тесты пишутся до или одновременно с реализацией; задача не считается выполненной без
зелёных тестов и пройденного `/speckit.checklist`.
Интеграционные тесты обязательны для: контрактов API, взаимодействия сервисов,
доставки сообщений (дубли/порядок/потери), шардирования и SSO.
Изменения, влияющие на пропускную способность, MUST сопровождаться нагрузочными тестами.

### VII. Простота (YAGNI)
Минимальная сложность; фичи, не требуемые спецификацией, не реализуются.
Предпочтение проверенным готовым решениям (брокер сообщений, поиск, SFU для WebRTC)
перед самописными. Выбор конкретных middleware фиксируется в `plan.md` с обоснованием.
Начинать с простого вертикального среза, усложнение — только по требованию спецификации.

## Technology Stack Constraints

- Backend: Kotlin 2.x + Spring Boot 3.x; сборка Maven или Gradle (выбор фиксируется
  в `plan.md` первой фичи и далее не меняется).
- Frontend: React + TypeScript (strict mode); standalone SPA и embeddable widget
  строятся из общей библиотеки компонентов.
- AI-инструменты: OpenCode. Сложные и архитектурные задачи — GLM-5.3; простые задачи
  (boilerplate, мелкие правки, фиксы линтера, документация) — GLM-5.3-Flash.
- Инфраструктура: контейнеризация и оркестрация (Kubernetes), CI/CD для сборки, тестов
  и деплоя обязательны с первой фичи.
- Polyglot persistence и middleware (СУБД, брокер, полнотекстовый поиск, SFU,
  object storage) выбираются на этапе `plan.md` с расчётом под бюджеты принципа II.

## Performance & Data Retention Standards

- Пик: 1 000 000 одновременных пользователей; 100 000 сообщений/сек; 1 000
  видеоконференций одновременно.
- История сообщений хранится 12 месяцев; сообщения старше — архивируются (доступны,
  но вынесены из горячего хранилища); полнотекстовый поиск покрывает и активную,
  и архивную историю.
- Observability обязательна: structured logging, распределённый tracing, метрики
  (latency, throughput, delivery errors) для каждого сервиса.
- Деградация под нагрузкой MUST быть контролируемой: backpressure, rate limiting,
  graceful degradation вместо отказа.

## Security & Privacy Requirements

- Идентификация: username + email, подтверждение email-ссылкой, пароль с подтверждением;
  SSO/OIDC-провайдеры как равноправный способ входа.
- JWT/сессионные токены с коротким TTL и refresh; ротация ключей.
- Rate limiting и защита от спама/флуда на публичных endpoints.
- E2EE-беседы: end-to-end шифрование на клиентах, key management без доступа сервера
  к открытому тексту; доступ только привилегированным пользователям (RBAC).

## Development Workflow & Quality Gates

- Единственный путь реализации — SDD-команды Spec Kit (см. принцип I).
- Каждая задача в `tasks.md` MUST содержать: что делается, какие файлы/модули затрагиваются,
  критерии приёмки, ссылки на тесты.
- Definition of Done для задачи: реализация + зелёные тесты + линт/форматирование
  + обновлённый API-контракт (если затронут) + пройденный `/speckit.checklist`.
- Реализация задач ведётся последовательно, с пометкой статуса в `tasks.md`;
  перескоки и параллельная реализация несвязанных задач одним агентом запрещены.

## Governance

- Конституция главенствует над всеми остальными артефактами; при конфликте
  `spec.md`/`plan.md` с конституцией побеждает конституция, а артефакт исправляется.
- Изменения конституции — только через `/speckit.constitution` с semantic versioning:
  MAJOR — удаление/пересмотр принципов, MINOR — новые принципы/разделы, PATCH — уточнения.
- Каждый PR/коммит обязан проходить проверку на соответствие конституции;
  сложность сверх необходимой MUST быть обоснована в `plan.md`.
